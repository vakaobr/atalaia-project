# Phase 2 -- Field Network: Architecture Decisions

Fifteen decisions settle the structure of the field network, the radio
protocol, the field controller, and the GM console before implementation
begins. Each one answers a question the research phase identified and
creates a constraint that the planning phase must respect.

---

### ADR-P2-1: LoRa packet header bit layout and byte order

**Status:** Accepted

**Context:** The Skirmesh-RF header is 9 bytes (defined in
`protocol/schema/messages.yaml`) but the `version_flags` byte has no
bit-level layout, and the multi-byte fields (`game_id`, `source`, `seq`)
have no specified byte order. Both must be frozen before any codec work
begins.

**Decision:** The `version_flags` byte is laid out MSB-first:

```
Bit   7   6   5   4   3   2   1   0
    [  version  ] [prio ] [ack] [enc] [rsv]
```

| Bits | Field | Width | Values |
|------|-------|-------|--------|
| 7-5  | `version` | 3 | Protocol version; v1 = `0b001` (1) |
| 4-3  | `priority` | 2 | 0 = telemetry, 1 = normal, 2 = critical, 3 = reserved |
| 2    | `ack_req` | 1 | 1 = sender requests ACK from the controller |
| 1    | `encrypted` | 1 | 1 = payload is AES-CCM encrypted; always 1 on LoRa |
| 0    | `reserved` | 1 | Must be 0; receivers ignore it |

For v1 on LoRa, a normal-priority message with ACK request produces
`0b001_01_1_1_0` = `0x2E`. A critical message without ACK request
produces `0b001_10_0_1_0` = `0x32`.

All multi-byte header fields are **big-endian** (network byte order).
This matches LoRa's on-air byte order and CBOR's integer encoding,
avoiding byte-swap code on either side.

Complete 9-byte header layout with byte offsets:

```
Offset  Size  Field            Encoding
  0       1   version_flags    bit field (see above)
  1       2   game_id          uint16 big-endian
  3       2   source           uint16 big-endian
  5       2   seq              uint16 big-endian
  7       1   hop_limit        uint8 (default 2)
  8       1   type             uint8 (1-8, see messages.yaml)
```

C struct (packed, for codec use only -- not for direct SPI reads):

```c
typedef struct __attribute__((packed)) {
    uint8_t  version_flags;
    uint16_t game_id;       /* big-endian on wire */
    uint16_t source;        /* big-endian on wire */
    uint16_t seq;           /* big-endian on wire */
    uint8_t  hop_limit;
    uint8_t  type;
} skirmesh_header_t;        /* 9 bytes */
```

Encode/decode helpers convert between host byte order and big-endian
on the wire. On ESP32 (little-endian Xtensa), `game_id`, `source` and
`seq` are byte-swapped during encode/decode.

Macros for `version_flags` construction and extraction:

```c
#define SKMESH_VF_VERSION(vf)   (((vf) >> 5) & 0x07)
#define SKMESH_VF_PRIORITY(vf)  (((vf) >> 3) & 0x03)
#define SKMESH_VF_ACK_REQ(vf)   (((vf) >> 2) & 0x01)
#define SKMESH_VF_ENCRYPTED(vf) (((vf) >> 1) & 0x01)

#define SKMESH_VF_MAKE(ver, prio, ack, enc) \
    ((uint8_t)(((ver) << 5) | ((prio) << 3) | ((ack) << 2) | ((enc) << 1)))
```

**Consequences:**
- 3 version bits support 7 protocol revisions before a layout change.
  Version 0 is reserved (reject as malformed).
- 2 priority bits map directly to the 3 `atalaia_prio_t` values (0-2)
  with one spare (3) for future use.
- The `encrypted` bit is always 1 on LoRa; a receiver seeing 0 on LoRa
  drops the packet silently. On Wi-Fi/BLE transports (JSON framing),
  the header is not used.
- `reserved` must be 0 on send and ignored on receive, following the
  robustness principle.
- All codec test vectors must include big-endian wire bytes to catch
  byte-order bugs.

### ADR-P2-2: AES-CCM authentication and encryption

**Status:** Accepted

**Context:** Spec section 14 requires a per-game 128-bit key with
AES-CCM MIC on every LoRa packet. The nonce construction, AAD scope,
tag length and encryption policy must be defined so that ESP32
(mbedtls hardware-accelerated) and Raspberry Pi (mbedtls or OpenSSL)
produce identical ciphertext.

**Decision:**

**Key**: AES-128 (16 bytes), generated by the controller using a CSPRNG
(`esp_fill_random` on ESP32, `os.urandom` on Pi) when a game is created.
Distributed to nodes during join (NFC, QR, BLE); never sent over LoRa.

**Nonce** (13 bytes, the maximum AES-CCM supports):

```
Offset  Size  Field       Source
  0       2   game_id     from header (big-endian)
  2       2   source      from header (big-endian)
  4       4   nonce_ctr   uint32 big-endian, monotonic per source
  8       5   zeros       0x00 * 5
```

The `nonce_ctr` is a 32-bit value constructed as:

```
nonce_ctr = (epoch << 16) | seq
```

where `epoch` is a uint16 and `seq` is the 16-bit header sequence
number. The epoch is the high half; seq is the low half. Together they
form a monotonic 32-bit counter that never repeats under one game key.

**Epoch lifecycle (the only NVS write):**

The node persists `epoch` (uint16) in NVS. It is written:

1. **At boot**, before the first transmission: read the stored epoch,
   increment it, persist the new value, then begin transmitting.
2. **At seq wrap**, when seq rolls from 65535 to 0: increment epoch,
   persist it, then continue transmitting with seq=0 under the new
   epoch. If the NVS write fails, the node MUST NOT transmit; it emits
   `nonce.nvs_fail` (critical, local-only via serial log) and halts
   the radio until the GM intervenes.

There are no per-packet NVS writes. Epoch is written at most once per
boot plus once per 65536 packets, which means negligible flash wear.

**Epoch exhaustion:**

At epoch 65535 with seq 65535, the node has used all 2^32 nonce values
for this game key. It refuses to start a new epoch and emits
`nonce.exhausted` (critical). The GM must end the game and start a new
one. At one packet per second, exhaustion takes ~136 years, so it is
operationally unreachable.

**How receivers learn the epoch:**

Receivers track the last successfully authenticated epoch per source.
When a packet arrives:

1. Construct nonce_ctr using the sender's last known epoch and the
   packet's seq. Attempt AES-CCM auth_decrypt.
2. If authentication succeeds, the epoch is correct. Accept the packet.
3. If authentication fails, try epoch+1 (the sender may have rebooted
   or wrapped seq). If auth_decrypt succeeds with epoch+1, adopt the
   new epoch for that source. Reset the replay window for that source.
4. If both fail, drop the packet.
5. Never try a lower epoch. A packet claiming a lower epoch is a
   replay attempt.

This trial mechanism means receivers handle seq wraps and reboots
without waiting for HELLO or STATE. HELLO and STATE still announce
the epoch explicitly, allowing receivers to resync after a longer
gap (e.g. when a node was out of range and missed the epoch
transition).

**Controller failover and nonce space:**

- The controller has its own (source, epoch, seq) triple. A new
  controller after failover has a different `source` (node_id), so its
  nonce space is independent. It never reuses a previous controller's
  nonces.
- If the same device becomes controller again after a reboot, its
  epoch increments, preventing nonce reuse.

**Threat model:**

| Threat | Mitigation |
|--------|-----------|
| Reboot reuses nonce | Epoch increments on boot and is persisted before first TX; nonce_ctr = (epoch << 16) | seq |
| seq wraps at 65535 | Epoch increments on wrap, persisted before transmitting with seq=0; new epoch = new nonce range |
| NVS write fails on epoch increment | Node halts radio and emits `nonce.nvs_fail`; never transmits with a stale epoch |
| Attacker dumps flash of stolen box | Gets the epoch but not the game key (encrypted NVS, see ADR-P2-12); cannot forge packets |
| Controller failover reuses nonce | Different source (node_id) per controller; independent nonce space |
| Replay of packets from previous epoch | Receivers never accept a lower epoch; trial with epoch+1 only on auth failure |

**AAD** (Additional Authenticated Data): 8 bytes of the header --
everything except `hop_limit` (byte 7). That is: version_flags (1) +
game_id (2) + source (2) + seq (2) + type (1) = header[0..6] +
header[8]. The header is authenticated but not encrypted, so a
receiver can read it to identify the game, source and type before
decrypting. hop_limit is excluded so relay nodes can decrement it
without invalidating the MIC (see ADR-P2-6). To prevent a forger from
raising hop_limit to amplify flooding, relay nodes clamp the incoming
hop_limit to the game's configured maximum (default 2) before
rebroadcasting.

**Tag length**: 8 bytes (the MIC appended to the packet). AES-CCM
supports 4, 6, 8, 10, 12, 14 or 16. Eight bytes (64-bit MAC) provides
a forgery probability of 2^-64, which far exceeds the game-integrity
threat model. Longer tags waste airtime.

**Encryption**: mandatory on LoRa. The `encrypted` bit in
`version_flags` is always 1. The payload (CBOR, up to 200 bytes) is
encrypted. A debug monitor tool on the controller can decrypt received
packets using the game key for display in the GM console log, but the
controller never sends unencrypted packets.

**Packet structure on the wire:**

```
[ 9-byte header (cleartext, authenticated) ]
[ 0-200 byte ciphertext (encrypted payload) ]
[ 8-byte MIC (authentication tag) ]
```

Total maximum: 9 + 200 + 8 = 217 bytes, within the LoRa maximum
payload of 255 bytes at all spreading factors.

**mbedtls API usage on ESP32:**

```c
mbedtls_ccm_context ctx;
mbedtls_ccm_init(&ctx);
mbedtls_ccm_setkey(&ctx, MBEDTLS_CIPHER_ID_AES, key, 128);

/* Build 8-byte AAD: header[0..6] + header[8] (skip hop_limit) */
uint8_t aad[8];
memcpy(aad, header, 7);          /* bytes 0-6 */
aad[7] = header[8];             /* type byte */

/* Build 13-byte nonce: game_id(2) + source(2) + nonce_ctr(4) + zeros(5) */
uint8_t nonce[13] = {0};
memcpy(nonce, &header[1], 2);    /* game_id */
memcpy(nonce + 2, &header[3], 2);/* source */
/* nonce_ctr = (epoch << 16) | seq, big-endian */
nonce[4] = (nonce_ctr >> 24) & 0xFF;
nonce[5] = (nonce_ctr >> 16) & 0xFF;
nonce[6] = (nonce_ctr >>  8) & 0xFF;
nonce[7] = (nonce_ctr      ) & 0xFF;

/* Encrypt + authenticate */
mbedtls_ccm_encrypt_and_tag(&ctx,
    payload_len,           /* plaintext length */
    nonce, 13,             /* nonce */
    aad, 8,                /* AAD = header minus hop_limit */
    plaintext, ciphertext, /* in/out */
    mic, 8);               /* tag */

/* Decrypt + verify */
int ret = mbedtls_ccm_auth_decrypt(&ctx,
    ciphertext_len,
    nonce, 13,
    aad, 8,
    ciphertext, plaintext,
    mic, 8);
/* ret != 0 means authentication failed; drop the packet */
```

**Key distribution during join:**

The join payload (carried over NFC, QR or BLE) contains:

| Field | Size | Purpose |
|-------|------|---------|
| `game_id` | 2 bytes | Which game to join |
| `game_key` | 16 bytes | AES-128 key |
| `node_id` | 2 bytes | Assigned short id for this node |
| `team_count` | 1 byte | Number of teams |
| `team_names` | variable | NUL-separated team name strings |
| `mode_id` | variable | Mode identifier string |
| `role` | variable | Role within the mode |

The join payload is authenticated with a HMAC-SHA256 tag (32 bytes)
using a controller-specific long-term key. This prevents forged join
cards. The HMAC key is set during controller setup and persisted in
the controller's config. For QR codes, the payload is base64url-encoded.

**HELLO and STATE carry the epoch:**

The HELLO message payload (ADR-P2-3) gains a new field:

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 9 | `epoch` | uint16 | yes | Current epoch; receivers use it to resync after long gaps (the trial mechanism handles normal transitions) |

The STATE message payload gains the same field (key 8, after `flags`):

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 8 | `epoch` | uint16 | yes | Current epoch; confirms the node's nonce range |

Receivers primarily learn epoch transitions via the AES-CCM trial
mechanism (try current epoch, try epoch+1 on auth failure). The epoch
field in HELLO and STATE is a secondary resync path for receivers that
were out of range during the transition.

**Consequences:**
- Nonce uniqueness is guaranteed across reboots and seq wraps. The
  nonce_ctr = (epoch << 16) | seq gives 2^32 unique nonces per game
  key, which is operationally inexhaustible.
- NVS is written only at boot and at seq wrap (~once per 65536
  packets). No per-packet NVS writes. Flash wear is negligible.
- If the NVS write fails at epoch increment, the node halts the radio
  rather than risk nonce reuse. This is a fail-safe: a broken NVS is
  visible as a `nonce.nvs_fail` alert, not silent corruption.
- Receivers handle epoch transitions automatically via the trial
  mechanism (try current epoch, then epoch+1 on auth failure). No
  out-of-band signalling is needed, though HELLO/STATE carry the
  epoch for resync after long gaps.
- The header is readable without decryption, enabling flood routing
  and dedupe.
- The 8-byte MIC adds ~1 ms of airtime at SF7/125 kHz, acceptable.
- ESP32-S3's AES hardware accelerator handles 128-bit CCM natively
  through mbedtls, so encryption adds negligible CPU time.
- A compromised key affects only one game. Per-node session keys
  (HKDF-derived) are a future improvement noted in the spec.
- The join HMAC prevents an attacker from manufacturing join cards
  without the controller's long-term key.
- An attacker who dumps a stolen box's flash gets the epoch but not
  the game key (encrypted NVS, see ADR-P2-12). Without the game key,
  they cannot forge packets or perform keystream recovery.

### ADR-P2-3: Message payload schemas

**Status:** Accepted

**Context:** All 8 message types are listed in `messages.yaml` but only
EVENT has a defined payload (in `events.yaml`). The remaining 7 need
concrete CBOR schemas with integer keys. Each payload must fit in the
200-byte LoRa limit.

**Decision:** Define payload schemas for all 8 message types as CBOR
maps with integer keys. Keys 1-23 encode in 1 byte; higher keys take
2+ bytes. All payloads are added to a new `payload` section in
`messages.yaml` and processed by `protogen.py`.

#### HELLO (type 1) -- Node announcement

Sent after joining a game. The controller builds its node registry from
HELLO messages.

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 1 | `node_name` | text | yes | Human-readable name, max 24 bytes |
| 2 | `platform` | uint8 | yes | 0=esp32, 1=esp32s3, 2=linux, 3=android |
| 3 | `fw_version` | text | yes | Firmware version string |
| 4 | `core_version` | text | yes | Core library version string |
| 5 | `tier` | uint8 | yes | 0=full, 1=reduced, 2=proxy |
| 6 | `capabilities` | array[uint8] | yes | Capability type ids (enum) |
| 7 | `transports` | uint8 | yes | Bitmask: bit 0=lora, 1=wifi, 2=ble |
| 8 | `battery_pct` | uint8 | no | Battery level 0-100, if available |

Typical size: ~40-60 bytes. Well within the 200-byte limit.

Capability type ids (enum, generated by protogen):

| Id | Capability |
|----|-----------|
| 0 | button |
| 1 | keypad |
| 2 | display |
| 3 | led |
| 4 | audio |
| 5 | nfc |
| 6 | qr |
| 7 | gps |
| 8 | imu |
| 9 | hit |
| 10 | output |
| 11 | battery |

#### EVENT (type 2) -- Game or system event

Already defined in `events.yaml`. The payload is the event envelope
(keys 1-8) as specified. No changes.

#### ACK (type 3) -- Sequence acknowledgement

Sent by the controller to confirm receipt. Also sent by a node to
acknowledge a CMD or CONFIG.

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 1 | `ack_node` | uint16 | yes | Source node being acknowledged |
| 2 | `ack_seq` | uint16 | yes | Highest contiguous seq received from that node |
| 3 | `ack_bitmap` | bytes | no | Selective ACK bitmap for gaps (up to 32 bytes = 256 seqs) |

The `ack_seq` field acknowledges all sequences up to and including
that value. The optional `ack_bitmap` covers the 256 sequences after
`ack_seq` (bit n = seq `ack_seq + 1 + n` received). This allows
selective acknowledgement without multiple ACK packets.

Typical size: 6 bytes (without bitmap), up to 38 bytes (with bitmap).

#### STATE (type 4) -- Periodic snapshot

Each node sends STATE every 10-60 seconds (per field profile). The
controller merges these into the game state.

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 1 | `owner_team` | uint8 | yes | Current owner team id (0 = none) |
| 2 | `phase` | uint8 | yes | Mode-specific phase (enum per mode) |
| 3 | `game_time_ms` | uint32 | yes | Node's local game time |
| 4 | `counters` | map[uint8 -> uint32] | yes | Per-team score counters (team_id -> value) |
| 5 | `rssi` | int8 | no | Last received signal strength (dBm) |
| 6 | `battery_pct` | uint8 | no | Battery level 0-100 |
| 7 | `flags` | uint8 | no | Bit 0: game running, bit 1: game paused |

Typical size: 20-40 bytes for a 2-team game.

The `counters` map carries only non-zero entries. On the receiver side,
`atalaia_score_merge` takes the maximum of each counter, which is
already proven correct in `score.h` tests.

Phase enum values are mode-specific and defined in each mode's
manifest. The controller maps them using the mode's phase table. A
universal set covers common states:

| Value | Phase |
|-------|-------|
| 0 | idle |
| 1 | active |
| 2 | armed |
| 3 | defused |
| 4 | exploded |
| 5 | captured |
| 6-15 | mode-defined |

#### CMD (type 5) -- Controller/GM instruction

Sent by the controller to one node (unicast using the `source` header
field as destination) or to all nodes (source = `0xFFFF` broadcast
address).

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 1 | `cmd` | uint8 | yes | Command opcode (enum) |
| 2 | `params` | map | no | Command-specific parameters |

Command opcodes:

| Opcode | Command | Params |
|--------|---------|--------|
| 0 | start | (none) |
| 1 | pause | `{1: reason_text}` |
| 2 | resume | (none) |
| 3 | end | `{1: reason_text}` |
| 4 | set_owner | `{1: team_id}` |
| 5 | message | `{1: text, 2: audience}` |
| 6 | reset | (none) |
| 7 | reboot | (none) |

Typical size: 4-30 bytes.

The broadcast address `0xFFFF` in the packet header's `source` field
is reused: for CMD packets, the `source` field carries the *destination*
(the node that should execute the command), not the sender. The sender
is always the controller. The controller's own node id is known to all
nodes from the join flow. Actually -- correction: to avoid ambiguity,
CMD packets use a different convention. The header `source` remains the
controller's node id. A new payload field carries the destination:

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 1 | `cmd` | uint8 | yes | Command opcode |
| 2 | `params` | map | no | Parameters |
| 3 | `dest` | uint16 | no | Destination node; absent = broadcast to all |

#### TIME (type 6) -- Game clock beacon

The controller sends TIME every 30 seconds (10 seconds with failover
enabled). TIME doubles as the controller heartbeat.

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 1 | `game_time_ms` | uint32 | yes | Controller's game time |
| 2 | `game_state` | uint8 | yes | 0=waiting, 1=running, 2=paused, 3=ended |
| 3 | `duration_ms` | uint32 | yes | Total game duration (0 = unlimited) |
| 4 | `wall_s` | uint32 | yes | Unix epoch seconds (for GPS-less sync) |
| 5 | `term` | uint32 | yes | Current election term (for failover) |
| 6 | `tx_time_us` | uint16 | no | Microseconds since the controller started TX |

The `tx_time_us` field helps nodes estimate one-way delay for clock
correction. The controller records the value of a microsecond counter
just before calling the radio send function, and embeds it in the
payload. The receiver subtracts the known airtime to estimate
processing delay.

Typical size: 18-20 bytes.

#### CONFIG (type 7) -- Preset push

Sent by the controller to assign a mode and role to a node. The actual
script source is NOT sent over LoRa (too large); the node must already
have the mode installed. CONFIG carries only the parameters.

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 1 | `mode_id` | text | yes | Mode identifier (e.g. "org.atalaia.domination") |
| 2 | `role` | text | yes | Role within the mode |
| 3 | `params` | text | yes | Preset parameters as JSON string |
| 4 | `teams` | array[text] | yes | Team names in order |
| 5 | `game_seed` | uint32 | yes | Seed for deterministic rand() |

Typical size: 60-150 bytes (depends on team count and param size).
The 200-byte limit constrains parameter complexity over LoRa; large
parameter sets are pushed via Wi-Fi during join.

#### CLAIM (type 8) -- Controller election

Sent by a candidate during election. All nodes listen; the one with
the highest priority wins.

| Key | Field | Type | Required | Notes |
|-----|-------|------|----------|-------|
| 1 | `term` | uint32 | yes | Monotonically increasing election term |
| 2 | `priority` | uint16 | yes | Candidate priority score (higher = better) |
| 3 | `node_id` | uint16 | yes | Candidate's node short id (tiebreaker: lowest wins) |
| 4 | `last_ack_seq` | map[uint16 -> uint16] | no | Per-node last ACK'd seq the candidate knows |

The `last_ack_seq` map tells other nodes what the candidate already
has, so they know what to replay during recovery.

Typical size: 12-60 bytes.

**Consequences:**
- All payloads fit comfortably in the 200-byte limit for typical games.
  CONFIG is the tightest; the planning phase must enforce a parameter
  size warning in the preset builder.
- Integer keys keep payloads compact (1-byte overhead per field for
  keys 1-23).
- `protogen.py` must be extended to generate payload codec tables for
  C (struct definitions + encode/decode) and Python (dict schemas).
- The selective ACK bitmap in ACK allows efficient gap repair without
  multiple round trips.
- Phase enum values 0-5 are universal; modes that need more use 6-15.
  This is extensible; the controller interprets phase via the mode's
  manifest, so unknown values are safe.

### ADR-P2-4: Radio HAL, SX1262 driver, and USB radio modem

**Status:** Accepted (revised: USB modem replaces SPI HAT for Pi)

**Context:** Phase 1's HAL (ADR-P1-1) uses function-pointer ops structs.
ADR-P1-1 explicitly says "Adding a new peripheral (GPS, IMU, LoRa)
follows the same pattern." Phase 2 needs a radio HAL that wraps the
Semtech SX1262 driver on ESP32.

**Hardware:** Heltec WiFi LoRa 32 V4.3 high-power (863-928 MHz). This
is an ESP32-S3R2 with 2 MB PSRAM, 16 MB flash, an SX1262 radio, and a
front-end module (FEM) that delivers 28 +/- 1 dBm TX and -137 dBm RX
sensitivity at SF12/125 kHz. The V4.3 replaces the V3 from the original
research (V3 has no PSRAM). The controller's USB radio modem is the
same board.

**FEM control GPIOs:**

The FEM is controlled by two GPIOs:
- **GPIO2 (FEM_EN):** FEM power enable. High = FEM on, Low = FEM off.
  Must be HIGH during both TX and RX. Set LOW during radio sleep to
  save power.
- **GPIO7 (VFEM_Control):** TX/RX switch. High = TX path, Low = RX
  path. Must be set before the SX1262 enters TX or RX mode.

The radio HAL wraps FEM control around every TX/RX operation:

```c
/* Before TX: */
gpio_set_level(FEM_EN, 1);       /* power on FEM */
gpio_set_level(VFEM_CONTROL, 1); /* switch to TX path */
sx1262_set_tx(...);
/* ... TX completes (DIO1 interrupt) ... */
gpio_set_level(VFEM_CONTROL, 0); /* switch back to RX path */

/* Before RX: */
gpio_set_level(FEM_EN, 1);
gpio_set_level(VFEM_CONTROL, 0); /* RX path */
sx1262_set_rx_continuous();

/* Sleep: */
gpio_set_level(FEM_EN, 0);       /* power off FEM */
sx1262_set_sleep();
```

The FEM GPIO pins are Kconfig symbols per ADR-P1-1:
`CONFIG_HAL_RADIO_FEM_EN_PIN` and `CONFIG_HAL_RADIO_VFEM_PIN`.

**Transmit power cap (EU868 with FEM):**

The FEM adds gain to the SX1262's output. The firmware MUST set the
SX1262's output power so that the total ERP (SX1262 output + FEM
gain - antenna loss) stays within EU868 limits:

- g/g1/g3 sub-bands: max 14 dBm ERP (25 mW).
- g2 sub-band (869.4-869.65 MHz): max 27 dBm ERP (500 mW).

The FEM gain on the V4.3 is approximately 13-14 dB (board output
28 dBm from SX1262 at ~14 dBm + ~14 dB FEM gain). Therefore:

```c
/* EU868 ERP limits, accounting for FEM gain. */
#define EU868_FEM_GAIN_DB    14  /* V4.3 FEM typical gain */
#define EU868_G_MAX_ERP_DBM  14  /* 25 mW ERP for g, g1, g3 */
#define EU868_G2_MAX_ERP_DBM 27  /* 500 mW ERP for g2 */

/* SX1262 output power = target ERP - FEM gain */
#define EU868_G_SX_POWER   (EU868_G_MAX_ERP_DBM - EU868_FEM_GAIN_DB)  /* 0 dBm */
#define EU868_G2_SX_POWER  (EU868_G2_MAX_ERP_DBM - EU868_FEM_GAIN_DB) /* 13 dBm */
```

A **calibration step** in the field-test plan measures the actual
board output with a spectrum analyser or RF power meter to verify the
FEM gain assumption. The `EU868_FEM_GAIN_DB` constant is adjustable
via Kconfig for different boards or antenna combinations.

**Transmit current budget:**

The V4.3 with FEM active draws ~400-500 mA during TX at 28 dBm. At
EU868 g-band power (SX1262 at 0 dBm), TX current is lower (~80-120 mA
plus FEM quiescent ~50 mA). RX with FEM draws ~30-40 mA. Sleep with
FEM off draws ~10 uA. These numbers must be confirmed during bring-up.

The power budget from ADR-P1-6 is not affected (TX is brief and
duty-cycle limited; average current is dominated by RX and CPU).

**Antenna safety:**

Transmitting without an antenna can damage the FEM's PA stage.
The bring-up checklist MUST include:
- "NEVER power on the radio or enable FEM_EN without an antenna
  connected."
- A visual check step before first power-on.
- If a u.FL connector is used, a lanyard or warning label on the
  connector.

The firmware does NOT attempt to detect a missing antenna
(SWR measurement requires hardware not on this board). The protection
is procedural.

**Controller radio: USB radio modem, not SPI HAT.**

The controller (Raspberry Pi) does NOT use an SPI LoRa HAT. Instead,
a second Heltec V4 board is connected to the Pi over USB and runs a
dedicated **radio modem firmware**. This modem firmware is a stripped
version of the node firmware: it runs the SX1262 driver, AES-CCM,
dedupe, and duty-cycle enforcement, but no Lua sandbox or game logic.
The Python controller communicates with it over USB serial.

Advantages over an SPI HAT:
- Same SX1262 driver and radio code on both nodes and the modem --
  single implementation, tested once.
- AES-CCM, dedupe, and duty-cycle run on the modem's ESP32, not on
  the Pi. The Pi never touches radio timing.
- No spidev/libgpiod/kernel driver on the Pi. Just USB serial.
- The modem can be flashed with the same toolchain as the nodes.
- A spare node board doubles as the controller's radio.

**USB serial framing:**

The modem and the Python controller exchange length-prefixed binary
frames over USB CDC (appears as `/dev/ttyUSBx` or `/dev/ttyACMx` on
Linux). The framing borrows from the spec's capability proxy protocol
(section 7: IDENT/EVT/CMD/ACK):

```
Byte 0:   frame type (1 byte)
Byte 1-2: payload length (uint16 big-endian)
Byte 3+:  payload (up to 256 bytes)
```

Frame types:

| Type | Direction | Payload | Purpose |
|------|-----------|---------|---------|
| 0x01 IDENT | modem -> Pi | JSON: firmware version, radio config, capabilities | Sent on connect and on request |
| 0x02 RX | modem -> Pi | header (9) + plaintext payload + rssi (1) + snr (1) | Received and decrypted packet |
| 0x03 TX | Pi -> modem | header (9) + plaintext payload | Packet to encrypt and send |
| 0x04 TX_ACK | modem -> Pi | seq (2) + status (1: 0=ok, 1=duty_cycle, 2=timeout) | TX result |
| 0x05 CMD | Pi -> modem | opcode (1) + params | Set channel, set game key, set config, status query |
| 0x06 STATUS | modem -> Pi | JSON: duty_cycle_remaining, channel, rssi, uptime | Periodic or on request |
| 0x07 ERROR | modem -> Pi | error code (1) + message | Radio error, key error |

The modem performs AES-CCM encryption on TX and decryption+verification
on RX. Plaintext payloads cross the USB link. This keeps the game key
on the modem (never on the Pi's filesystem) and puts all radio timing
on the ESP32.

**Modem firmware:**

A build variant of the ESP32 firmware (`firmware/esp32/`) selected by
Kconfig: `CONFIG_ATALAIA_MODEM_MODE=y`. In modem mode:
- No Lua sandbox, no game logic, no LVGL, no preset store.
- Radio task + USB CDC serial task + flood/dedupe + AES-CCM + duty-cycle.
- The modem receives the game key via a CMD frame from the Pi at game
  start. The key is stored in RAM only on the modem.

**Modem watchdog and reconnect:**

The Python controller pings the modem every 5 seconds (CMD frame
with opcode `ping`). If 3 pings are missed:
1. Log a warning.
2. Close and reopen the serial port.
3. Re-send the game key and configuration.
4. If reconnect fails after 3 attempts, emit `radio.down` system event
   to the GM console.

The modem has a hardware watchdog timer (ESP-IDF `esp_task_wdt`) that
reboots it if the main loop hangs.

**Decision:** Add `hal_radio_ops_t` to the HAL following the ADR-P1-1
pattern. Use the Semtech SX126x BSD-licensed reference C driver, wrapped
behind the ops struct.

**`hal_radio_ops_t` definition:**

```c
typedef enum {
    HAL_RADIO_MODE_SLEEP = 0,
    HAL_RADIO_MODE_STANDBY,
    HAL_RADIO_MODE_RX,         /* continuous receive */
    HAL_RADIO_MODE_TX,
} hal_radio_mode_t;

typedef struct {
    /* One-time init. Returns 0 on success. */
    int (*init)(const hal_radio_config_t *cfg);

    /* Transmit a packet. Blocks until TX complete or timeout.
     * Returns 0 on success, -1 on duty-cycle exceeded, -2 on timeout. */
    int (*send)(const uint8_t *buf, size_t len);

    /* Receive a packet. Blocks until a packet arrives or timeout_ms
     * elapses. Returns bytes received (0 on timeout), -1 on error.
     * Writes RSSI to *rssi_out if non-NULL. */
    int (*recv)(uint8_t *buf, size_t cap, uint32_t timeout_ms,
                int8_t *rssi_out);

    /* Switch channel. freq_hz is the centre frequency. */
    int (*set_channel)(uint32_t freq_hz);

    /* Power mode. */
    int (*set_mode)(hal_radio_mode_t mode);

    /* Current RSSI in dBm. */
    int8_t (*rssi)(void);

    /* Remaining duty-cycle budget in milliseconds of airtime. */
    uint32_t (*duty_cycle_remaining_ms)(void);

} hal_radio_ops_t;

typedef struct {
    uint32_t freq_hz;      /* centre frequency (e.g. 868100000) */
    int8_t   tx_power_dbm; /* SX1262 output power (after FEM gain subtraction) */
    uint8_t  sf;           /* spreading factor (7-12) */
    uint8_t  bw;           /* bandwidth: 0=125kHz, 1=250kHz, 2=500kHz */
    uint8_t  cr;           /* coding rate: 1=4/5, 2=4/6, 3=4/7, 4=4/8 */
    uint16_t preamble_len; /* preamble symbols (default 8) */
    uint8_t  sync_word;    /* LoRa sync word (0x12 = private, 0x34 = public) */
    int8_t   fem_gain_db;  /* FEM gain in dB (14 for V4.3; 0 if no FEM) */
    uint8_t  fem_en_pin;   /* GPIO for FEM power enable (Kconfig) */
    uint8_t  vfem_pin;     /* GPIO for TX/RX switch (Kconfig) */
} hal_radio_config_t;
```

The `hal_t` struct in `firmware/esp32/main/hal/hal.h` gains one pointer:

```c
typedef struct {
    const hal_button_ops_t  *buttons;
    const hal_keypad_ops_t  *keypad;
    const hal_led_ops_t     *leds;
    const hal_display_ops_t *display;
    const hal_nfc_ops_t     *nfc;
    const hal_audio_ops_t   *audio;
    const hal_battery_ops_t *battery;
    const hal_radio_ops_t   *radio;    /* Phase 2: LoRa radio */
} hal_t;
```

**Semtech SX126x driver integration:**

The Semtech reference driver (`sx126x_driver`, BSD-3-Clause) is a pure C
library that calls platform-provided callbacks for SPI, GPIO and delay.
The ESP-IDF implementation provides these callbacks using:

- `spi_device_transmit` for SPI (HSPI bus, DMA channel 1)
- `gpio_get_level` / `gpio_set_level` for BUSY, DIO1, RESET, NSS
- `vTaskDelay` or `esp_timer` for delays

The same driver runs on both node boards and the USB radio modem (both
are Heltec V4 / ESP32-S3). No Pi-side radio driver is needed.

**FreeRTOS task (ESP32):**

A new `radio_task` runs on core 0 at priority 3 (below game_task, same
as audio_task). It owns the SPI bus to the radio and has a 6 KB stack.

```
Task         Core  Priority  Stack
game_task       1     5       6 KB   (ADR-P1-7, unchanged)
lvgl_task       1     4       6 KB   (ADR-P1-7, unchanged)
radio_task      0     3       6 KB   (Phase 2, new)
audio_task      0     3       4 KB   (ADR-P1-7, unchanged)
wifi_task       0     2       4 KB   (ADR-P1-7, unchanged)
```

Communication:
- `game_task` -> `radio_task`: a FreeRTOS queue of `radio_tx_msg_t`
  (encoded packet bytes to send).
- `radio_task` -> `game_task`: a FreeRTOS queue of `radio_rx_msg_t`
  (received packet bytes + RSSI + timestamp).

The radio task loop:
1. Check TX queue; if a message is waiting and duty-cycle budget allows,
   transmit it.
2. Call `recv()` with a short timeout (50 ms).
3. If a packet was received, push it to the RX queue.
4. Repeat.

**Interrupt handling:**

The SX1262's DIO1 pin triggers an ISR on packet received or TX done.
The ISR gives a binary semaphore that the radio task waits on (instead
of polling with timeout). This reduces latency and power:

```c
void IRAM_ATTR radio_dio1_isr(void *arg) {
    BaseType_t woken = pdFALSE;
    xSemaphoreGiveFromISR(radio_sem, &woken);
    portYIELD_FROM_ISR(woken);
}
```

**Stub implementation:**

`hal_radio_stub.c` records calls and allows test code to inject
received packets and verify transmitted packets. It simulates
duty-cycle tracking with a virtual clock.

**Consequences:**
- The HAL pattern is preserved; no existing code changes except adding
  the `radio` pointer to `hal_t`.
- The same SX1262 driver, AES-CCM code, flood/dedupe, and duty-cycle
  enforcement run identically on nodes and the USB modem. One
  implementation, tested once.
- The radio task on core 0 does not compete with the game loop on
  core 1.
- Pin assignments for the radio (SPI pins, DIO1, BUSY, RESET, NSS) are
  Kconfig symbols per ADR-P1-1.
- The 6 KB radio task stack is sufficient for the SX126x driver (which
  uses ~2 KB of stack) plus the AES-CCM encrypt/decrypt context (~1 KB).
- The USB modem firmware is a build variant, not a separate project.
  One ESP-IDF project produces both the node firmware and the modem
  firmware via Kconfig.
- The Pi needs no SPI/GPIO libraries for radio. Just `pyserial` for
  USB serial.
- TX power is capped in the HAL regardless of board variant. The
  28 dBm high-power Heltec V4 provides no benefit on EU868 g-band
  channels (14 dBm max).
- A spare node board can serve as the controller's radio modem,
  reducing the number of distinct hardware builds.

### ADR-P2-6: TTL-limited flooding and deduplication

**Status:** Accepted

**Context:** The spec says hop_limit default 2, and nodes rebroadcast
once if not seen before. The dedupe table, rebroadcast delay, and
controller flood handling need concrete parameters.

**Decision:**

**Flood algorithm:**

1. A node receives a packet. It checks the (source, seq) pair against
   its dedupe table.
2. If already seen, drop silently.
3. If new, record (source, seq) in the dedupe table.
4. Process the packet (deliver to the game loop).
5. If `hop_limit > 0`, decrement hop_limit and rebroadcast after a
   random jitter delay.
6. Rebroadcast uses the same header (with decremented hop_limit) and
   the same ciphertext+MIC. The packet is rebroadcast verbatim except
   for hop_limit.

**AAD and hop_limit (consistent with ADR-P2-2):**

The AAD is 8 bytes: header[0..6] + header[8] (everything except
hop_limit at byte 7). This is defined in ADR-P2-2 and restated here
for clarity:

```
AAD = version_flags + game_id + source + seq + type
    = header[0..6] + header[8]
    = 8 bytes
```

hop_limit (header[7]) is NOT authenticated. A relay node decrements it
freely and the MIC remains valid. This is safe because:
- hop_limit only controls rebroadcast depth, not content.
- A forger who raises hop_limit to amplify flooding is stopped by the
  relay clamp: every relay node clamps the incoming hop_limit to the
  game's configured maximum (default 2) before decrementing and
  rebroadcasting. The configured maximum is set during join and never
  exceeds 3.
- Setting hop_limit to 0 prevents further rebroadcast (a localised
  DoS, but the direct link still works and the dedupe table prevents
  duplicates from other paths).

**Dedupe table:**

On ESP32: a fixed-size array of 64 entries, each storing:

```c
typedef struct {
    uint16_t source;
    uint16_t seq;
    uint32_t expire_ms;   /* game time when this entry can be evicted */
} dedupe_entry_t;
```

Eviction: entries expire after 30 seconds (longer than any reasonable
rebroadcast chain). When the table is full and a new entry is needed,
the oldest expired entry is overwritten. If no entries are expired, the
oldest entry is evicted (LRU).

On the controller (Pi): a Python dict keyed by `(source, seq)` with
timestamp values. Entries older than 60 seconds are pruned every 10
seconds. No size limit (Pi has ample RAM).

**Rebroadcast jitter:**

A relay node waits a random delay of 10-50 ms before rebroadcasting.
This reduces collision probability when multiple nodes hear the same
packet simultaneously. The jitter is drawn from the node's `rand()`
with the source+seq as additional seed, so it is deterministic in the
simulator.

The controller does NOT rebroadcast by default. It is the hub; packets
reach it directly or through relays. However, the controller DOES
rebroadcast CMD and TIME packets (which originate from itself) -- this
is normal transmission, not relay. Nodes marked as dedicated repeaters
always rebroadcast (hop_limit permitting).

**Consequences:**
- 64 dedupe entries on ESP32 uses 64 * 8 = 512 bytes of DRAM, well
  within the memory budget.
- The 30-second expiry covers the worst case: a packet at hop_limit 2
  with 50 ms jitter at each hop takes at most ~100 ms to traverse the
  entire network.
- The controller's larger table (Python dict) handles the full node
  count without eviction pressure.
- hop_limit exclusion from the AAD is a deliberate trade-off: it
  enables relay without re-encryption. By excluding hop_limit, relay
  is a simple byte decrement + retransmit.
- The relay clamp (incoming hop_limit capped to the game's configured
  maximum) prevents hop_limit inflation attacks. This must be enforced
  in both the ESP32 flood module and the simulator's flood logic.
- The clamp value is part of the join payload and stored alongside
  the game key.

### ADR-P2-7: Time synchronisation

**Status:** Accepted

**Context:** The spec requires +/-250 ms game clock accuracy across all
nodes. The controller sends TIME beacons every 30 seconds (10 seconds
with failover). Nodes must correct their local game clocks without
visible jumps.

**Decision:**

**Algorithm: linear slew with capped rate.**

When a node receives a TIME beacon:

1. Compute the one-way delay estimate:
   `delay_ms = known_airtime_ms + processing_overhead_ms`
   where `known_airtime_ms` is calculated from the packet size, SF and
   BW (deterministic for a given radio configuration), and
   `processing_overhead_ms` is a fixed estimate of 5 ms (radio IRQ to
   application delivery).

2. Compute the controller's game time at the moment of reception:
   `controller_time = beacon.game_time_ms + delay_ms`

3. Compute the offset:
   `offset = controller_time - local_game_time`

4. Apply correction:
   - If `|offset| < 5 ms`: no correction (within noise).
   - If `|offset| < 500 ms`: slew. Adjust the local clock rate by
     `offset / SLEW_PERIOD_MS` per tick, where `SLEW_PERIOD_MS = 10000`
     (spread the correction over 10 seconds, i.e. before the next
     beacon at the fastest rate). Maximum slew rate: 50 ms/s (5%).
   - If `|offset| >= 500 ms`: step. This only happens at game start or
     after a long partition. Apply the full correction immediately and
     log `time.step` as a system event.

5. Track the running average offset over the last 4 beacons (exponential
   moving average, alpha = 0.25). Use this for display and diagnostics.

**TIME message fields** (from ADR-P2-3):

The `tx_time_us` field in the TIME payload records microseconds of
processing time between the controller deciding to send and actually
calling the radio send function. The receiver adds this to the
airtime estimate for a more accurate one-way delay.

**Wall clock sync:**

The `wall_s` field carries Unix epoch seconds. Nodes without GPS use
this to set their RTC (if present) or to timestamp log entries with
wall-clock time. Wall clock sync has no accuracy requirement beyond
~1 second (for log correlation).

**Beacon sub-band:**

TIME beacons use the 869.4-869.65 MHz sub-band, which allows 10% duty
cycle (vs 1% on the main channels). At SF7/125 kHz, a 20-byte TIME
packet takes ~60 ms of airtime. At 10% duty cycle, the controller can
send one TIME beacon every 600 ms. Sending every 10 seconds uses only
~1% of the 10% budget, leaving room for CMD packets on the same
sub-band.

**Implementation on ESP32:**

The game timer (ADR-P1-3) is shell-owned. Phase 2 adds a `time_sync`
module that intercepts TIME beacons from the radio RX queue and adjusts
the shell's game timer:

```c
typedef struct {
    int32_t  offset_ms;        /* current estimated offset */
    int32_t  slew_remaining_ms;/* remaining correction to apply */
    uint32_t last_beacon_ms;   /* local time of last beacon */
    int32_t  avg_offset_ms;    /* EMA of recent offsets */
    uint8_t  beacon_count;     /* beacons received this game */
} time_sync_t;

void time_sync_on_beacon(time_sync_t *ts, const time_payload_t *beacon,
                          game_timer_t *timer, uint32_t local_time_ms);

/* Called every tick to apply slew. Returns the adjusted delta_ms. */
uint32_t time_sync_adjust(time_sync_t *ts, uint32_t raw_delta_ms);
```

The shell's main loop calls `time_sync_adjust` to get a corrected
delta for `atalaia_node_advance`. During a positive slew (local clock
is behind), each 10 ms tick advances by 10.5 ms. During a negative
slew, each tick advances by 9.5 ms. This is invisible to the game
logic.

**Consequences:**
- The 250 ms target is achievable with a simple linear slew. Even at
  SF9 with ~180 ms airtime, the one-way delay estimate is within
  ~20 ms (airtime is deterministic; the uncertainty is processing
  time).
- Steps only happen at game start and after long partitions, so players
  never see a timer jump during normal play.
- The slew rate cap (5%) prevents the game clock from running too fast
  or too slow during correction.
- GPS-equipped nodes bypass LoRa time sync entirely; they use GPS PPS
  to maintain their own accurate clock and ignore TIME beacons.

### ADR-P2-8: Controller failover and CLAIM protocol

**Status:** Accepted

**Context:** Spec section 11 describes election by priority. The CLAIM
protocol must guarantee single-controller operation and handle recovery.
Per the research recommendation, automatic failover is implemented and
tested in the simulator but defaults to manual activation in Phase 2.

**Decision:**

**Priority score calculation** (uint16, higher is better):

```
priority = (power_source * 4096)
         + (battery_pct * 32)
         + (storage_ok * 512)
         + (link_quality * 2)
```

Where:
- `power_source`: 3 = mains/USB, 2 = large battery (>10 Ah),
  1 = small battery, 0 = unknown
- `battery_pct`: 0-100
- `storage_ok`: 1 if the node has SQLite-capable storage (SD card or
  filesystem), 0 otherwise
- `link_quality`: 0-100 based on average RSSI over recent beacons

A mains-powered Pi with full battery backup scores ~15,000+. A
battery-only ESP32 scores ~3,000-4,000. This heavily favours the Pi,
which is the intended controller.

Tiebreaker: if two candidates have equal priority, the one with the
lowest `node_id` wins. Node IDs are assigned during join in the order
nodes join, so the first Pi to join becomes the primary controller.

**Election protocol:**

1. **Detection**: nodes count consecutive missed TIME beacons. After 3
   missed beacons (30 seconds at normal rate, 30 seconds at failover
   rate), the controller is considered down.

2. **Candidacy**: each controller-capable node calculates its priority
   and sends a CLAIM message with a new term number = `last_seen_term +
   1`.

3. **Resolution**: every node compares incoming CLAIM messages. A node
   follows the CLAIM with the highest term. Among CLAIMs with the same
   term, the highest priority wins; equal priorities break by lowest
   node_id.

4. **Acceptance**: a candidate that does not see a higher-priority CLAIM
   within 5 seconds (election timeout) assumes the role and begins
   sending TIME beacons with the new term.

5. **Step-down**: a former controller that receives a TIME or CLAIM with
   a higher term immediately stops sending TIME beacons, merges its log
   into a STATE message, and steps down to regular node operation.

**Recovery:**

When a new controller takes over:

1. It sends a CMD(reset_ack) broadcast, asking every node to report its
   last ACK'd sequence number.
2. Each node responds with a STATE message containing its full score
   counters and its last ACK'd seq.
3. The new controller rebuilds its node registry from HELLO messages
   (nodes re-announce on seeing a new term).
4. Nodes replay events from their last ACK'd seq to their current seq.
5. The new controller processes replayed events through `field.lua`
   (which is replayable by design: state from events + params + seeded
   rand).
6. Scores merge by maximum per counter, so no score is lost or
   double-counted.

**Term number semantics:**

- Terms are monotonically increasing uint32 values.
- Every TIME beacon includes the current term.
- Every node tracks the highest term it has seen.
- A node only accepts CMD and CONFIG from the controller with the
  highest term.
- A CLAIM with a term <= the highest seen term is ignored.

**Phase 2 default: manual failover.**

Automatic failover is fully implemented and tested in the simulator,
but the default field profile sets `failover_mode = manual`. The GM
can promote a backup controller from the GM console. Automatic
failover (`failover_mode = auto`) is enabled per field profile after
field testing confirms reliability. This reduces risk for Phase 2
while delivering the full protocol.

**Consequences:**
- The CLAIM protocol guarantees at most one active controller per
  term. Split-brain is impossible: any node seeing a higher term
  immediately steps down.
- Recovery relies on event replay, which requires nodes to buffer
  events since their last ACK. ADR-P2-9 sizes the event buffer.
- The 5-second election timeout means a game is without a controller
  for ~30 seconds (detection) + ~5 seconds (election) = ~35 seconds.
  During this time, all nodes continue running locally.
- Manual failover as the default reduces the risk of premature
  elections caused by radio dead zones.

### ADR-P2-9: Log merge and partition recovery

**Status:** Accepted

**Context:** Each node keeps events after its last ACK. The controller
merges by `(t, node, seq)`. The buffer size on ESP32 and the replay
protocol need concrete parameters.

**Decision:**

**Event log on ESP32: flash-backed append log.**

The spec (section 8) says "each node keeps an append-only log: a flash
ring buffer on ESP32." The gate is "zero lost captures." A DRAM buffer
loses unacknowledged events on brownout or battery pull and overwrites
them on long partitions. Therefore the event log is flash-backed,
using LittleFS on the storage partition already allocated by ADR-P1-4
(1 MB).

**Storage format:**

Events are appended to `/log/game.bin` on LittleFS. Each entry is a
length-prefixed record:

```c
typedef struct {
    uint16_t len;            /* total record length including this field */
    uint16_t seq;
    uint32_t game_time_ms;
    uint8_t  type_id;        /* standard event id, or 0 for custom */
    uint8_t  team;
    uint8_t  priority;
    uint8_t  acked;          /* 1 if controller has ACK'd this event */
    uint8_t  cbor[];         /* variable-length CBOR payload, up to 200 B */
} event_log_entry_t;
```

Typical entry: 12 + 30 = ~42 bytes. Maximum: 12 + 200 = 212 bytes.

**Capacity:**

The 1 MB LittleFS partition is shared with presets, modes, state and
audio (ADR-P1-4). Reserving 256 KB for the event log gives:

- At ~42 bytes average: ~6,100 events.
- At the busiest rate (4 events/min): ~25 hours of continuous play.
- A weekend milsim (2 days, 16 hours active): ~3,840 events at the
  busy rate, well within 6,100.

The file is truncated (compacted) when the game ends or when it
exceeds 256 KB during a game (oldest ACK'd entries are discarded).

**Flush policy:**

Events of **normal or critical priority** are flushed to LittleFS
immediately on append. This covers every event that changes ownership,
score, or game state: zone.captured, zone.neutralized, bomb.armed,
bomb.defused, bomb.exploded, bomb.reset, score.delta, game.start,
game.pause, game.resume, game.end, code.used, tag.scanned, and all
other normal and critical events. Since zone.captured is normal
priority (not critical) in `protocol/schema/events.yaml`, flushing
only critical events would lose captures in a power cut -- which
violates the gate.

**Telemetry events** (battery.low, node.online, node.offline) are
buffered in a small DRAM write cache (8 entries, ~340 bytes) and
flushed:

1. Every 5 seconds if the cache is non-empty.
2. When the cache is full (8 entries).

**Worst-case power-cut data loss:** at most 7 telemetry events (those
in the write cache). No game events (normal or critical) are ever
lost, because they are flushed immediately. This meets the gate
requirement of "zero lost captures."

**Wear analysis (with immediate normal/critical flush):**

LittleFS uses copy-on-write. A 256 KB region on a flash with 100,000
erase cycles per page (typical NOR flash on ESP32 modules) gives:

- Each page is 4 KB. 256 KB = 64 pages.
- Worst-case event rate for a domination box: one zone.captured every
  15 seconds = 4 events/min = 480 events in a 2-hour game. Plus
  STATE snapshots every 30 seconds = 240. Plus game lifecycle events
  (~10). Total: ~730 writes per 2-hour game.
- A busy bomb box: captures + arms + defuses + score deltas, perhaps
  ~1,500 writes in a 2-hour game.
- With wear levelling across 64 pages, 1,500 writes = ~23 erases per
  page per game.
- At 100,000 cycles: ~4,300 games before wear-out.
- At 2 games per weekend: ~41 years. More than sufficient.

The previous estimate of 7,200 writes/game assumed 1 flush/second.
With immediate flush only on actual events (not a timer), the rate
is much lower because LoRa games produce events at human pace, not
CPU pace. Telemetry events buffered at 5-second intervals add at most
~1,440 writes (2 hours * 60 min * 60 sec / 5 sec). Even in the
extreme: 1,500 + 1,440 = ~2,940 writes, giving ~2,200 games (~21
years).

**Replay after reboot:**

On boot, if `/log/game.bin` exists and the game key is available
(see ADR-P2-12 revision), the node:

1. Reads the last ACK'd seq from the log (scanning for the highest
   seq with `acked == 1`).
2. Replays all entries with `acked == 0` to the controller.
3. Emits `node.rebooted` (critical priority, flushed immediately).

**Overflow:**

If the 256 KB log fills during a game (>6,100 events without ACK --
an extreme multi-hour partition):

1. The oldest ACK'd entries are compacted (file rewritten without
   them) to free space.
2. If no ACK'd entries remain (the entire log is unacknowledged), the
   node emits `event_log.full` as a system event and stops appending.
   Score counters in STATE messages remain accurate regardless.
3. The GM console shows `event_log.full` as a warning.

**Event log on the controller (Pi):**

SQLite table:

```sql
CREATE TABLE events (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    game_id    INTEGER NOT NULL,
    node_id    INTEGER NOT NULL,
    seq        INTEGER NOT NULL,
    game_time  INTEGER NOT NULL,
    type       TEXT NOT NULL,
    team       INTEGER,
    squad      INTEGER,
    priority   INTEGER NOT NULL,
    data_json  TEXT,
    received_at REAL NOT NULL,   -- wall clock (for diagnostics)
    UNIQUE(game_id, node_id, seq)
);
CREATE INDEX idx_events_game_time ON events(game_id, game_time);
```

The UNIQUE constraint on `(game_id, node_id, seq)` enforces dedupe at
the storage layer. `INSERT OR IGNORE` silently drops duplicates.

**Replay protocol after reconnect:**

1. A node that has not received an ACK for > 3 TIME beacon intervals
   considers itself partitioned.
2. On receiving a TIME beacon again (reconnect), the node sends a
   STATE message with its current score counters.
3. The controller compares the node's last ACK'd seq with the node's
   current seq (from the STATE message or by requesting it).
4. The controller sends an ACK with the last seq it has from that
   node.
5. The node replays all buffered events with seq > last ACK'd seq.
6. The controller processes each replayed event through `field.lua`,
   using the event's original game_time for ordering.
7. Once all replayed events are ACK'd, the node resumes normal
   operation.

**Score merge:**

Scores merge by maximum per counter per team, using the existing
`atalaia_score_merge` function. This is already unit-tested. The
controller calls it whenever it receives a STATE with score counters.
Even if event replay is incomplete (buffer overflow), the score totals
are correct because STATE carries the authoritative counters.

**Consequences:**
- All game events (normal and critical priority) survive brownout and
  battery pull. The gate requirement of "zero lost captures" is met:
  zone.captured (normal priority) is flushed immediately.
- Only telemetry events (battery.low, node.online/offline) may be lost
  in a power cut -- at most 7 cached entries. These do not affect
  game scoring.
- 256 KB of flash covers a weekend milsim. The wear budget of ~4,300
  games (41 years at 2/week) exceeds any realistic device lifetime.
- The DRAM write cache for telemetry (8 entries, ~340 bytes) is
  negligible.
- SQLite's UNIQUE constraint makes controller-side dedupe zero-cost.
- Score accuracy survives even total partition (no events reach the
  controller) because STATE carries the totals and scores merge by
  maximum.
- The replay protocol adds no new message types; it uses existing
  STATE, ACK and EVENT messages.
- After a reboot, unacknowledged events are replayed from flash,
  combined with the epoch increment from ADR-P2-2 for nonce safety.

### ADR-P2-10: GM console technology

**Status:** Accepted

**Context:** The GM console is a web app served by the controller as
static files, installable as a PWA. The research evaluated vanilla JS,
Preact+HTM, Alpine.js and Svelte/React.

**Decision:** **Preact + HTM, no build step.**

Preact (3 KB gzipped) + HTM (JSX-like tagged templates, <1 KB) provide
a reactive component model without requiring npm, webpack, or any build
toolchain. The GM console is served as plain HTML, CSS and JS files from
the controller's FastAPI static file mount.

**Architecture:**

```
controller/console/src/
    index.html          # PWA shell, loads app.js
    manifest.json       # PWA manifest (name, icons, display: standalone)
    sw.js               # Service worker for offline caching
    app.js              # Main application: router, state, WebSocket
    components/
        field-view.js   # Node map (Leaflet for GPS, or draggable on image)
        game-control.js # Start/pause/end, broadcast message
        preset-builder.js  # Forms from mode parameter schemas
        live-feed.js    # Filterable event stream
        node-list.js    # Node health table
        score-panel.js  # Live score display
    lib/
        preact.module.js   # Preact ESM bundle (vendored, pinned version)
        htm.module.js      # HTM ESM bundle (vendored)
        leaflet/           # Leaflet for map view (vendored)
    style.css           # Single stylesheet
    icons/              # PWA icons (192x192, 512x512)
```

**Live data transport: WebSocket.**

The controller exposes `WS /api/v1/stream`. The GM console connects on
load and receives JSON messages for:

- Every game event (type, team, node, time, data)
- Score updates (per-team totals)
- Node state changes (owner, phase, battery, RSSI)
- Node health (online/offline, last seen)

SSE was considered but rejected: WebSocket is bidirectional (the console
sends commands through the same connection), has better browser support
for reconnection in PWA/service-worker contexts, and FastAPI has
excellent WebSocket support via Starlette.

**Offline capability:**

The service worker caches all static assets. The console works offline
for viewing cached game data. Live data requires a connection to the
controller. When the connection drops, the console shows a "reconnecting"
banner and automatically reconnects.

**Map view:**

The primary map option is an **uploaded field image or floor plan**
(spec section 10). The GM uploads a photo, satellite image, or floor
plan drawing; nodes are dragged onto it and their positions saved in
the controller's SQLite store. This works fully offline and covers
both indoor CQB sites and outdoor fields.

OpenStreetMap tiles via Leaflet are a **secondary, online-only**
option for outdoor fields with GPS and internet. OSM tiles are NOT
cached for offline use because the OSM tile usage policy prohibits
bulk prefetching and requires attribution. The console displays the
required "© OpenStreetMap contributors" attribution when OSM tiles are
active.

When no field image is uploaded and no internet is available, the map
view falls back to a plain coordinate grid with node markers (GPS
coordinates displayed as text).

Self-hosted tile servers (e.g. OpenMapTiles) or offline tile packs
(e.g. MBTiles) are a future option for fields that want offline
satellite imagery without violating OSM policy. This is out of scope
for Phase 2.

**Consequences:**
- No Node.js, npm or build step on the Pi or in CI. The console is
  plain files served by FastAPI's `StaticFiles` mount.
- Preact + HTM is ~4 KB total; the entire console including Leaflet is
  under 200 KB gzipped.
- Vendored libraries (checked into the repo) ensure offline builds and
  reproducibility. Versions are pinned and updated manually.
- Leaflet is vendored for the tile layer but OSM tiles are online-only.
  The uploaded field image is the primary and offline-capable option.
- The same console works on phones, tablets and laptops -- Preact's
  virtual DOM handles responsive layouts.
- PWA installation means the GM can "install" the console to their
  phone's home screen for quick access.

### ADR-P2-11: Simulator extension architecture

**Status:** Accepted

**Context:** The simulator (`simulator/atalaia_sim/sim.py`) runs virtual
nodes but has no cross-node delivery. Phase 2 needs a simulated lossy
radio for multi-node testing, partition simulation, and duty-cycle
tracking.

**Decision:** Add a `RadioModel` class and extend the `Simulation`
class with a delivery queue and flood logic.

**`RadioModel` class:**

```python
class RadioModel:
    """Simulates a lossy radio channel between virtual nodes."""

    def __init__(self, *,
                 loss_rate: float = 0.0,       # 0.0-1.0
                 latency_ms: int = 5,          # simulated one-way delay
                 duty_cycle: float = 0.01,     # 1% default
                 range_m: float = 1000.0,      # max range
                 sf: int = 7):                 # spreading factor
        ...

    def transmit(self, sender_id: int, packet: bytes,
                 sender_pos: tuple[float, float] | None = None
                 ) -> list[tuple[int, int]]:
        """Returns [(recipient_id, delay_ms), ...] for nodes that
        receive the packet. Distance-based loss if positions are set."""
        ...

    def airtime_ms(self, packet_len: int) -> float:
        """Calculates airtime for a packet at the current SF/BW."""
        ...

    def airtime_ok(self, sender_id: int, packet_len: int) -> bool:
        """Returns True if sender has enough duty-cycle budget."""
        ...

    def budget_remaining_ms(self, sender_id: int) -> float:
        """Remaining airtime budget for sender in the current hour."""
        ...
```

**Integration with `Simulation`:**

The `Simulation` class gains:

```python
class Simulation:
    def __init__(self, ..., radio: RadioModel | None = None):
        self.radio = radio or RadioModel()
        self._pending: list[PendingDelivery] = []
        self._dedupe: dict[int, set[tuple[int, int]]] = {}  # node -> seen (src, seq)
        ...

    def send_packet(self, sender_id: int, msg_type: int,
                    payload: dict, priority: int = 1,
                    ack_req: bool = False):
        """Called by a virtual node to send a LoRa message."""
        ...

    def _deliver_pending(self, now_ms: int):
        """Called during advance_to; delivers packets whose delay
        has elapsed. Implements flood rebroadcast."""
        ...
```

Existing `Simulation.broadcast()` remains for direct event delivery
(legacy tests). New `send_packet` goes through the radio model.

**Virtual field controller:**

A new `FieldController` class wraps a virtual node running `field.lua`:

```python
class FieldController:
    """Virtual field controller for multi-node simulation."""

    def __init__(self, sim: Simulation, node_id: int = 0):
        self.node = sim.create_node(node_id)
        self._score_table: dict[int, dict[int, int]] = {}
        self._event_log: list[dict] = []
        ...

    def on_event(self, event: dict): ...
    def send_time_beacon(self): ...
    def merge_scores(self, node_id: int, counters: dict): ...
```

**Partition simulation:**

```python
sim.partition(node_ids=[3, 4])    # nodes 3,4 cannot reach anyone
sim.heal(node_ids=[3, 4])        # reconnect
sim.link(1, 2, loss=0.5)         # set per-link loss rate
```

**Duty-cycle tracking:**

The `RadioModel` tracks per-node airtime in a sliding 1-hour window. If
a node exceeds its budget, `airtime_ok` returns False and `transmit`
logs a warning. Tests can assert that no node exceeds the budget:

```python
def test_duty_cycle():
    sim = Simulation(radio=RadioModel(duty_cycle=0.01))
    # ... run a 20-minute game with 5 nodes ...
    for node_id in range(5):
        assert sim.radio.budget_remaining_ms(node_id) > 0
```

**Consequences:**
- Existing single-node mode tests are unchanged; `RadioModel` is
  optional (`None` disables it).
- Multi-node tests exercise the full protocol: flood, dedupe, TIME
  sync, partition, score merge.
- Duty-cycle tracking catches protocol designs that violate EU868
  before hardware testing.
- The `FieldController` class exercises the same code path as the
  real controller (via ctypes to the core).

### ADR-P2-12: Join flow

**Status:** Accepted

**Context:** Nodes join by NFC card, QR code, or BLE. The join carries
the game key, game ID, node short ID, and other configuration. Phase 2
must define which transports are in scope and what data each carries.

**Decision:**

**Phase 2 scope: NFC and QR. BLE is deferred to Phase 3** (when the
Android app and BLE provisioning arrive).

Both NFC and QR carry the same join payload (defined in ADR-P2-2):

```
game_id (2) + game_key (16) + node_id (2) + team_count (1) +
team_names (variable) + mode_id (variable) + role (variable) +
hmac (32)
```

**NFC join card (Phase 2 primary method):**

The GM prepares join cards using the controller. Each card is an
NTAG215 or NTAG216 (504 or 888 bytes of user data), written with:

1. An NDEF record containing the join payload as a binary blob.
2. The HMAC-SHA256 tag (32 bytes) authenticating the payload.

Total payload size: ~80-120 bytes (depending on team names and mode
id). Fits in NTAG215 (504 bytes) with room to spare.

The node's NFC reader (PN532) reads the NDEF record, verifies the HMAC,
extracts the game key and configuration, and joins the game. A
successful join triggers:
1. Store the game key in RAM (never persisted to flash).
2. Configure teams and mode parameters.
3. Send a HELLO message over LoRa to announce to the controller.
4. Start the mode's `node.lua`.

**QR code join (Phase 2 secondary method):**

The GM console generates a QR code containing the join payload
base64url-encoded. The QR is displayed on the console screen (phone,
tablet, laptop). Since ESP32 nodes in Phase 2 do not have cameras, QR
join works differently:

1. The GM scans the QR with their phone (or the console displays it).
2. The phone (or console) sends the join payload to the node over Wi-Fi
   (the node is on the controller's Wi-Fi network).
3. The controller pushes the join payload to the node via a REST
   endpoint: `POST /api/v1/nodes/{id}/join`.

This means QR join in Phase 2 requires Wi-Fi connectivity between the
console and the node. Direct QR scanning by nodes arrives in Phase 3
with Android props (which have cameras).

**Post-join: script and asset delivery:**

If the node does not have the required mode installed, the controller
pushes it over Wi-Fi:
- `POST /api/v1/nodes/{id}/mode` with the mode package (node.lua,
  mode.yaml, assets) as a multipart upload.
- The node stores the mode in LittleFS (per ADR-P1-4).

Scripts and assets never travel over LoRa (spec rule).

**Key lifecycle and reboot survival:**

The spec (section 14) says a node whose battery is pulled resumes its
countdown after reboot and emits `node.rebooted`. This requires the
game key to survive reboots. Storing it in plaintext NVS would let an
attacker who dumps a stolen box's flash extract the key for the
current game. Therefore the game key is stored in NVS encryption.

**ESP32-S3 NVS encryption:**

ESP-IDF supports NVS encryption using a key derived from the eFuse
HMAC key (HMAC-based key derivation, available on ESP32-S3 with
`CONFIG_NVS_SEC_KEY_PROTECT_USING_HMAC`). This requires:

1. A one-time eFuse HMAC key burn during device provisioning (field
   owner setup, not per-game). The eFuse key is hardware-locked and
   cannot be read by software.
2. NVS encryption enabled in `sdkconfig.defaults`:
   `CONFIG_NVS_ENCRYPTION=y` and
   `CONFIG_NVS_SEC_KEY_PROTECT_USING_HMAC=y`.
3. The game key is stored in the encrypted NVS partition as
   `game_key` (16 bytes).

**What an attacker gets from dumping flash:**

- The encrypted NVS blob, which cannot be decrypted without the eFuse
  HMAC key (which is not readable from flash or JTAG once the eFuse
  read-protect bit is set).
- The epoch counter (not secret -- it is broadcast in HELLO/STATE).
- The LittleFS event log (CBOR payloads encrypted with AES-CCM; the
  attacker cannot decrypt them without the game key).

**Key lifecycle:**

- On first join (NFC tap or QR push), the game key is written to
  encrypted NVS along with the game_id, node_id, team configuration,
  and mode parameters.
- On reboot, the node reads the encrypted NVS. If a valid game key
  and game_id exist, it resumes: increments epoch, replays
  unacknowledged events from the flash log, sends HELLO with the new
  epoch, and emits `node.rebooted` (critical).
- On `game.end`, the node zeroes and deletes the game key from
  encrypted NVS. The game_id is cleared. The next boot starts in
  idle mode.
- A new game always generates a new key on the controller and
  distributes it during a fresh NFC/QR join.

**Provisioning requirement:**

The eFuse HMAC key must be burned once per device. This is a
setup-time operation documented in the bring-up checklist. Devices
without the eFuse key fall back to unencrypted NVS with a build-time
warning -- acceptable for development but not for field use.

NFC and QR remain the only join methods for the initial join. A
rebooted node does not need a new NFC tap; it rejoins automatically
using the persisted credentials and the new epoch.

**Consequences:**
- A rebooted node resumes its game without GM intervention, matching
  the spec's requirement. The new epoch prevents nonce reuse
  (ADR-P2-2).
- NFC join is the fastest method: tap a card, node joins in <1 second.
  Each node in a 5-box game needs one tap. Reboots do not require
  re-tapping.
- QR join requires Wi-Fi, which limits it to nodes within range of the
  controller's AP. This is acceptable for Phase 2 setup.
- BLE join (Phase 3) will use the same payload format.
- The eFuse HMAC key adds a one-time provisioning step per device.
  The bring-up checklist must include this.
- The join HMAC prevents forged cards but does not prevent cloning.
  Acceptable: join cards are prepared by the GM during setup.

### ADR-P2-13: Airtime budget and duty-cycle enforcement

> **Superseded in part:** The three-channel round-robin hopping in the
> original decision was found to be incompatible with single-radio
> half-duplex operation (nodes listening on different channels after TX).
> Amendment 1 of RFC 0001 (2026-10-18) replaces it with a single shared
> game channel, by default 869.525 MHz (g2 sub-band).

**Status:** Accepted

**Context:** EU868 requires 1% duty cycle on most channels and 10% on
869.4-869.65 MHz. The firmware must track and enforce airtime limits.

**Decision:**

**Duty-cycle tracking in the radio HAL:**

The `hal_radio_ops_t` implementation tracks airtime per sub-band using
a sliding window of 1 hour (3,600,000 ms). For each sub-band, it
maintains:

```c
typedef struct {
    uint32_t window_start_ms;     /* start of current tracking window */
    uint32_t used_ms;             /* airtime used in this window */
    uint32_t limit_ms;            /* max airtime per hour for this band */
    uint32_t freq_min_hz;         /* sub-band lower frequency */
    uint32_t freq_max_hz;         /* sub-band upper frequency */
} duty_cycle_band_t;
```

EU868 bands tracked:

| Sub-band | Frequency range | Duty cycle | Airtime/hour |
|----------|----------------|------------|-------------|
| g (default) | 868.0-868.6 MHz | 1% | 36,000 ms |
| g1 | 868.7-869.2 MHz | 0.1% | 3,600 ms |
| g2 | 869.4-869.65 MHz | 10% | 360,000 ms |
| g3 | 869.7-870.0 MHz | 1% | 36,000 ms |

Before every transmission, the radio HAL:
1. Calculates the airtime for the packet: `airtime_ms = f(payload_len,
   sf, bw, cr, preamble_len)` using the LoRa airtime formula.
2. Checks that `used_ms + airtime_ms <= limit_ms` for the current
   sub-band.
3. If the budget allows, transmits and adds `airtime_ms` to `used_ms`.
4. If the budget is exhausted, returns `-1` (DUTY_CYCLE_EXCEEDED) and
   does NOT transmit.

**Window management:** Every minute, the HAL slides the window forward
by checking if `current_time - window_start_ms > 3600000`. If so, it
resets `used_ms` proportionally (decays the oldest minute's
contribution). A simpler approach: track the last 60 minutes as 60
one-minute buckets, summing them for the current total.

**What happens when the budget is exhausted:**

1. The radio HAL returns `DUTY_CYCLE_EXCEEDED`.
2. The radio task logs the failure and increments a Prometheus-style
   counter.
3. The packet is queued for retry after a backoff period (calculated
   from the remaining budget).
4. If the TX queue is full, the lowest-priority packet is dropped.
5. The node emits `airtime.low` when the remaining budget drops below
   20% of the hourly limit, visible in the GM console.

**Controller TIME beacons on the 10% sub-band:**

The controller sends TIME beacons on 869.525 MHz (centre of the g2
sub-band). At SF7/125 kHz, a 20-byte TIME packet takes ~60 ms. At 10%
duty cycle (360,000 ms/hour), this allows up to 6,000 beacons/hour.
Sending every 10 seconds = 360 beacons/hour = 21,600 ms = 6% of the
budget. This leaves room for CMD packets on the same sub-band.

**Per-channel hopping:**

For the default sub-band (g, 1%), nodes hop across three channels:
868.1 MHz, 868.3 MHz, 868.5 MHz. Each channel has its own independent
1% budget. This effectively triples the available airtime for nodes
(108,000 ms/hour across 3 channels). Channel selection:
- Events and STATE: round-robin across the 3 channels.
- ACKs: sent on the same channel as the message being acknowledged.
- TIME and CMD: always on 869.525 MHz (g2 sub-band).

**Simulator enforcement:**

The `RadioModel` (ADR-P2-11) tracks the same per-band budgets. Tests
that exceed the budget fail with a clear error message showing which
node exceeded which band's limit.

**Consequences:**
- The duty-cycle tracking is in the HAL, so the radio task does not
  need to track it -- it just checks the return code.
- Three-channel hopping triples effective throughput for the 1% band.
- The 10% sub-band is reserved for controller traffic (TIME, CMD),
  ensuring game control messages always have airtime.
- The `airtime.low` system event gives the GM warning before messages
  start being dropped.
- The bucket-based sliding window uses 60 * 4 bytes = 240 bytes per
  sub-band, ~1 KB total for 4 sub-bands. Negligible memory cost.

### ADR-P2-14: `state.field{}` and `field.*` Lua API additions

**Status:** Accepted

**Context:** The core's `script_api.c` lists `state.field{}` and
`field.*` as "not yet." Phase 2 needs these for `field.lua` scripts
running on the controller. The question is whether these are core
changes or controller-only additions.

**Decision:** Both are **core changes** to `script_api.c`, guarded by
a node type flag.

**`state.field{}`**

A replicated state table, similar to `state.node{}` but shared across
nodes via the controller:

```lua
-- In field.lua (controller only):
local fs = state.field { boost_active = false, multiplier = 1 }

-- Reading and writing works like state.node:
fs.boost_active = true
fs.multiplier = 1.5
```

Implementation in `script_api.c`:
- `state.field` creates a Lua table backed by a C-side
  `atalaia_field_state_t` struct (a key-value store of
  string -> Lua value).
- When a field state value changes, the runtime calls the `field_state`
  callback (new callback in `atalaia_node_callbacks_t`).
- The controller serialises the field state as JSON and pushes it to
  nodes via a STATE-like mechanism (piggybacked on TIME beacons or
  sent as a dedicated message if it changes).
- On nodes, `state.field` is **read-only**. The controller is the only
  writer. Nodes receive field state updates and expose them to their
  `node.lua` scripts as a read-only table.

New callback:

```c
typedef struct {
    void (*event)(void *user, const atalaia_event_t *ev, const char *data_json);
    void (*command)(void *user, const char *target, const char *method, const char *args_json);
    void (*log)(void *user, const char *message);
    /* Phase 2: field state changed (controller only) */
    void (*field_state)(void *user, const char *key, const char *value_json);
    void *user;
} atalaia_node_callbacks_t;
```

**`field.*` functions (controller only)**

These functions are registered in `script_api.c` only when the node is
created with a new `ATALAIA_NODE_FIELD` type flag:

| Function | Signature | Returns |
|----------|-----------|---------|
| `field.nodes()` | `field.nodes()` or `field.nodes(role)` | Array of node descriptors |
| `field.owner(node)` | `field.owner(node_id_or_name)` | Team name or nil |
| `field.common_owner(nodes)` | `field.common_owner({n1, n2, ...})` | Team name if all same, else nil |
| `field.send(node, cmd, params)` | `field.send(node_id, "set_owner", {team="red"})` | boolean |
| `field.score()` | `field.score()` | Table of {team -> total} |

Implementation:
- These functions call back into the controller via a new callback:

```c
/* Phase 2: field query callback (controller only) */
typedef struct {
    /* Returns a JSON array of node descriptors, filtered by role.
     * role may be NULL for all nodes. Caller frees the result. */
    char *(*nodes)(void *user, const char *role);
    /* Returns the owner team name for a node, or NULL. */
    const char *(*owner)(void *user, uint16_t node_id);
    /* Sends a command to a node. Returns true on success. */
    bool (*send)(void *user, uint16_t node_id, const char *cmd, const char *params_json);
} atalaia_field_ops_t;
```

- The `atalaia_node_config_t` gains an optional `field_ops` pointer:

```c
typedef struct {
    uint16_t node_id;
    uint32_t game_seed;
    size_t mem_limit;
    uint32_t instr_limit;
    atalaia_node_callbacks_t callbacks;
    atalaia_alloc_fn alloc;
    void *alloc_ud;
    const atalaia_field_ops_t *field_ops;  /* NULL for regular nodes */
} atalaia_node_config_t;
```

When `field_ops` is non-NULL, the node registers the `field.*`
functions and `state.field{}` is read-write. When NULL, `field.*`
functions are not available and `state.field{}` is read-only (set
externally by the host).

**Core version bump:** These additions constitute a minor API change.
The core version bumps from 0.1.x to 0.2.0.

**Consequences:**
- `field.lua` scripts work identically in the simulator and on the
  real controller -- both provide `field_ops` callbacks to the core.
- Regular nodes (ESP32 props) never see `field.*` functions; their
  `field_ops` is NULL.
- `state.field{}` on nodes is read-only, set by the controller. This
  prevents conflicts and keeps the controller authoritative.
- The `field_state` callback lets the controller serialise and
  distribute field state changes efficiently.
- The core remains platform-agnostic; all field logic is in callbacks.

### ADR-P2-15: RFC-0001 for protocol changes

**Status:** Accepted by the maintainer (2026-10-17)

**Context:** Protocol changes need an RFC per project conventions
(spec section 13). The wire format decisions from ADR-P2-1 through
ADR-P2-13 must be formalised in a single document that new
contributors can read.

**Decision:** The normative wire-format specification is
[`docs/rfcs/0001-skirmesh-rf-wire-format.md`](../rfcs/0001-skirmesh-rf-wire-format.md).
This ADR (and the other Phase 2 ADRs) document the rationale; the RFC
is the specification. The two are not maintained in duplicate.

The RFC covers: the 9-byte header bit layout and byte order, AES-CCM
(key, epoch-based nonce, 8-byte AAD, relay clamp), CBOR payloads for
all 8 message types, flood routing, time sync, CLAIM election,
duty-cycle and FEM power rules, join flow, and rejoin after reboot.
It also lists the alternatives considered (with why each was rejected)
and the open questions.

The RFC was accepted by the maintainer on 2026-10-17. No 2-week
review wait applies. Future protocol changes (v2+) follow the normal
RFC process with the review period per spec section 13.

**Test vectors** (at least 3 per message type, plus security vectors)
are defined in the RFC and added to `protocol/vectors/`. They cover:

- Encode/decode round-trips for all 8 message types.
- Nonce construction: (epoch << 16) | seq for several (epoch, seq)
  pairs including reboot (epoch+1/seq=0) and seq wrap
  (epoch=0/seq=65535 then epoch=1/seq=0).
- Seq wrap triggers epoch persist before TX with seq=0.
- NVS write failure halts radio (`nonce.nvs_fail`).
- AAD: hop_limit change does not invalidate MIC; type change does.
- Relay clamp: hop_limit > game_max is clamped.
- Receiver trial: accepts epoch+1 on auth failure; rejects lower
  epoch; adopts new epoch on success.

**Consequences:**
- The RFC is a single self-contained document a new contributor can
  read to understand the wire format.
- The ADRs (this file) explain why each choice was made.
- Test vectors ensure cross-platform codec compatibility.
- Implementation can begin immediately (RFC accepted).
- Future protocol changes follow the normal RFC process.

## Constraints for Planning

The planning phase must respect the following constraints derived from
the decisions above:

1. **AAD is 8 bytes, not 9.** The AES-CCM AAD covers the header minus
   hop_limit (bytes 0-6 + byte 8). hop_limit is excluded so relay
   nodes can decrement it without invalidating the MIC.

2. **Radio HAL before protocol code.** `hal_radio_ops_t` (header, ESP
   impl, stub) must land before the packet codec, flood logic, or
   duty-cycle tracker. This follows ADR-P1-1's "HAL-first" principle.

3. **Packet codec is shared C.** The header encoder/decoder and
   AES-CCM wrapper live in `core/include/atalaia/packet.h` and
   `core/src/packet.c`, shared between ESP32 firmware and the Pi radio
   gateway. CBOR payload codecs also go in the core.

4. **USB radio modem, not a C daemon.** The controller radio is a
   Heltec V4 board running modem firmware, connected to the Pi over
   USB. The Python controller communicates via USB serial (`pyserial`)
   using the binary framing in ADR-P2-4. There is no C process on the
   Pi. All radio/crypto code lives in the modem firmware.

5. **Python controller reuses simulator bindings.** The `core.py`
   ctypes wrapper from `simulator/atalaia_sim/` is the primary FFI to
   `libatalaia_core.so`. Do not create a second set of bindings.

6. **No build step for the GM console.** The console is plain HTML,
   CSS and JS files. Preact and HTM are vendored ESM bundles. Leaflet
   is vendored. No npm, no webpack, no Node.js.

7. **NFC and QR join only in Phase 2.** BLE join is deferred to
   Phase 3. QR join in Phase 2 requires Wi-Fi (the controller pushes
   the payload).

8. **Game key in encrypted NVS.** The AES-128 game key is stored in
   the ESP32-S3's encrypted NVS partition (eFuse HMAC-derived key).
   It survives reboots so the node can rejoin without a new NFC tap.
   It is zeroed and deleted from NVS when the game ends.

9. **Event log: flash-backed on LittleFS.** The event log is an
   append file on LittleFS (`/log/game.bin`), up to 256 KB. Normal
   and critical events are flushed immediately. Only telemetry events
   are buffered (8-entry DRAM cache, flushed every 5 s). All game
   events survive reboot and battery pull.

10. **Dedupe table: 64 entries on ESP32.** Each entry is 8 bytes
    (source + seq + expiry). Entries expire after 30 seconds. The
    controller uses a Python dict with no size limit.

11. **Duty-cycle enforcement in the HAL.** The `send` function returns
    `-1` if the duty-cycle budget is exhausted. Upper layers must
    handle this (queue, retry, or drop).

12. ~~**TIME beacons on 869.525 MHz (g2 sub-band).** CMD packets from
    the controller also use this sub-band. Node-to-controller traffic
    uses the g sub-band (868.1/868.3/868.5 MHz, round-robin).~~
    **Superseded by RFC 0001 Amendment 1 (2026-10-18):** all game
    traffic uses a single shared channel per game, default 869.525 MHz
    (g2 sub-band, 10% duty cycle, 500 mW ERP).

13. **Failover defaults to manual.** `failover_mode = manual` is the
    default field profile setting. The CLAIM protocol is fully
    implemented and tested in the simulator, but automatic election
    requires the GM to enable it.

14. **Core version bump to 0.2.0.** The `state.field{}` and `field.*`
    additions require a minor version bump. `field_ops` is a new
    optional pointer in `atalaia_node_config_t`.

15. **Slew, not step, for time sync.** The default behaviour is to
    slew the game clock at max 5% rate. Steps only happen when the
    offset exceeds 500 ms (game start, long partition). The shell's
    `game_timer_t` is adjusted by `time_sync_adjust()`, not replaced.

16. **protogen.py extension required.** `tools/protogen.py` must
    generate payload codec tables (C structs + encode/decode, Python
    dicts) from the new `payload` section in `messages.yaml`. This
    is a prerequisite for all codec work.

17. **RFC-0001 accepted.** The RFC has been accepted by the maintainer
    (2026-10-17). No review wait; implementation can begin immediately.
    The RFC stays in the repo for new contributors. Future protocol
    changes follow the normal RFC process.

18. **Scoreboard example in `examples/`.** A Python script subscribing
    to MQTT `score` topic, printing to stdout. Not a firmware project.

19. **SQLite for controller storage.** Games, presets, event logs, node
    registry. The events table has a UNIQUE constraint on
    `(game_id, node_id, seq)` for dedupe.

20. **Mosquitto as system service.** The controller connects to
    Mosquitto as a client (`paho-mqtt`). No embedded MQTT broker in
    Phase 2.

21. **SPDX headers on every file.** New files under `controller/`
    use `AGPL-3.0-or-later` per the spec's licence table (section 17).
    New files under `firmware/` and `core/` use `GPL-3.0-or-later`.
    Documentation uses `CC-BY-SA-4.0`.

22. **Rebroadcast jitter: 10-50 ms.** Random, deterministic in the
    simulator (seeded by source + seq).

23. ~~**Three-channel hopping on the g sub-band.** 868.1, 868.3,
    868.5 MHz, round-robin for node transmissions. Per-channel
    independent duty-cycle tracking.~~
    **Superseded by RFC 0001 Amendment 1 (2026-10-18):** one shared
    game channel per game (default 869.525 MHz, g2 sub-band).

24. **Nonce = (epoch << 16) | seq.** The nonce_ctr is derived from the
    persisted epoch and the header seq. Epoch increments at boot and at
    seq wrap. Receivers discover epoch transitions via AES-CCM trial
    (try current epoch, then epoch+1 on auth failure). HELLO and STATE
    carry the epoch for resync after long gaps.

25. **Epoch persisted in NVS at boot and seq wrap only.** No per-packet
    NVS writes. If the NVS write fails, the node halts the radio and
    emits `nonce.nvs_fail` (critical). Never transmits with a stale
    epoch.

26. **eFuse HMAC key required for production.** NVS encryption using
    the eFuse HMAC key is mandatory for field use. The bring-up
    checklist must include the one-time eFuse key burn. Development
    builds may use unencrypted NVS with a build warning.

27. **Relay clamp.** Every relay node clamps the incoming hop_limit to
    the game's configured maximum (default 2) before decrementing and
    rebroadcasting. The configured maximum is part of the join payload.

28. **Uploaded field image is the primary map.** OSM tiles are
    secondary and online-only. No bulk tile prefetching. OSM
    attribution required when tiles are active.

29. **Power-loss tests.** The test plan and field test must include a
    battery-pull scenario and verify that events are replayed from
    flash and the node rejoins with a new epoch without NFC re-tap.
