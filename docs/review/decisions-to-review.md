## Phase 2, plan phase C (firmware radio)

| # | Question | Answer chosen | Why | Status |
| --- | --- | --- | --- | --- |
| C1 | How large should the OTA slots be? | 2 MB each (was 1.5 MB), plus a 4 KB nvs_keys partition; 9.9 MB of the 16 MB flash stays free. | The image was at 87% of 1.5 MB before the radio code. The agent reports that 3 MB slots broke LittleFS in Wokwi; that needs a root cause before going further. | open |
| C2 | Which antenna gain does the EU868 power cap assume? | A conservative Kconfig default for the stock antenna, to be measured at bring-up. Conducted power = the limit minus the FEM gain minus the antenna gain, never above 25 mW ERP on the g bands and 500 mW ERP on 869.4-869.65 MHz. | The first version ignored the antenna gain and could exceed the legal limit. | open |
| C3 | How is the game key protected at rest? | NVS encryption with the ESP32-S3 HMAC (eFuse) scheme in production, and a clearly marked fallback for development boards without a burned eFuse key. The eFuse burn is a one-time provisioning step, documented in BRING_UP.md. | ADR-P2-12. Burning an eFuse cannot be undone, so it must not happen by accident on a dev board. | open |
| C4 | The radio is disabled in the Wokwi build because probing it reportedly corrupted the emulated flash. Is that acceptable? | No (maintainer's answer). It must be fixed: the Wokwi build runs with the radio enabled, the probe finds no chip and carries on, and the root cause is found. A disable is only allowed with proof of an emulator defect and the maintainer's agreement. | The radio code has never run in a runtime test, and a real driver bug could look the same. | confirmed |
| C5 | How do boxes choose radio channels? | **Changed from the accepted design.** ADR-P2-13 and RFC 0001 had boxes rotate their transmissions across three 1% channels (868.1, 868.3 and 868.5 MHz), with time and commands on 869.525 MHz, but never said where a box listens. The SX1262 hears one channel at a time, so most packets would be missed. Chosen: one shared channel per game, by default 869.525 MHz (the 869.4-869.65 MHz sub-band: 10% duty cycle and up to 500 mW ERP), for everything; configurable per game to separate neighbouring games. RFC 0001 gets a dated amendment. | The standard approach for single-radio LoRa meshes (Meshtastic's EU868 default uses the same frequency). It gives more airtime than the three 1% channels together, and every box hears every packet. | open |

## Phase 2, plan phase D (field controller and USB modem)

| # | Question | Answer chosen | Why | Status |
| --- | --- | --- | --- | --- |
| D1 | ADR-P2-4's modem frames are type + length + payload. How does a receiver find frame boundaries after junk? | Each frame starts with a sync byte `0xA5` and ends with a CRC-16/CCITT-FALSE over type, length and payload; the decoder resynchronises byte by byte. Specified in protocol/usb-modem.md. | The serial line carries the ESP32-S3 boot text, and the Pi may open the port in the middle of a frame; with a bare length prefix one lost byte desynchronises the link for good. | open |
| D2 | The RX frame (header + payload + RSSI + SNR) does not say which nonce epoch authenticated the packet. | It carries the epoch too (2 bytes after RSSI and SNR). | A box restarts its seq at 0 after every reboot, so the controller needs the epoch to tell new packets from old ones and to ACK per epoch. | open |
| D3 | ADR-P2-4 lists three TX_ACK statuses and no CMD opcodes. | TX_ACK statuses 3-7 added (not configured, invalid, nonce reuse, queue full, no radio); CMD opcodes PING, CONFIGURE, SET_CHANNEL, STATUS, SET_PEER_EPOCH, CLEAR, IDENT; every command answered by STATUS or ERROR. | The controller must know why a packet was not sent, and every command needs a reply for the watchdog. | open |
| D4 | ADR-P2-2's receiver tries only the last epoch and the next one. A box that reboots twice out of range, or joins with an epoch above 1, is never decrypted again. | The modem tries up to 16 epochs above the last known one (never below), and the controller can set a box's epoch (SET_PEER_EPOCH). The boxes' own receive code (`radio_protocol.c`) still tries one; a window function is ready for them. Recommend an RFC 0001 amendment. | Without it a twice-rebooted box is silently lost: the opposite of "zero lost captures". 16 extra AES-CCM checks per unknown packet are cheap on the ESP32-S3's AES hardware. | open |
| D5 | Who owns the controller's nonce counter, the Pi or the modem? | The Pi: it stores its epoch +1 in SQLite before the first packet of every run and at seq wrap, and sends the epoch with CONFIGURE. The modem refuses any (epoch, seq) not above the last one it sent. | The Pi has the persistent storage and outlives modem reboots; the modem's check stops a Pi bug from reusing a nonce. | open |
| D6 | ADR-P2-9's events table is UNIQUE on (game, node, seq). A box's event seq restarts at 1 after a reboot, so its new events would be dropped as duplicates. | UNIQUE on (game, node, seq, game time, type). Replays still match exactly. | A battery pull would otherwise lose every capture after it: the phase 2 gate. | open |
| D7 | ACK `ack_seq` is "highest contiguous seq", but a box's STATE and telemetry packets share the seq space and are never resent, so one lost STATE leaves a gap for ever. | Implemented as specified, per (box, epoch), with `ack_seq = 0xFFFF` meaning "seq 0 not received" and the bitmap for the next 256 seqs. Boxes must treat bitmap bits as ACKs. Recommend an RFC change (separate seq spaces for reliable traffic, or per-packet ACKs). | Fails safe (events are resent, never lost) but wastes airtime after a lost STATE. A protocol change needs an RFC. | open |
| D8 | The core's C payload codec disagreed with the schema, RFC 0001 and the shared vectors (HELLO capabilities as bytes, STATE counters and CLAIM acks as arrays, CMD params as text, required fields dropped when zero), and its vector tests skipped every vector it could not decode. | **Fixed in the core** to match the schema exactly; required fields and value ranges are now checked; the vector tests in C and Python are strict and also check the invalid vectors. | The controller (Python, schema-exact) could not have read a box's HELLO or STATE. The RFC is the accepted specification, so the C code was the bug. | open |
| D9 | CMD `params` is a "map"; the C struct keeps it as 128 bytes of JSON. | A CBOR map with text keys whose JSON form fits 127 bytes; the controller refuses bigger ones. | Matches the schema and what a box can hold. | open |
| D10 | Where does the controller keep the game key? (ADR-P2-4: never on the Pi's disk.) | In memory only by default; `persist_game_key = true` keeps it in the SQLite file (mode 0600) so a game survives a controller restart. Without it, a game whose controller restarted can only be ended. | Follows the ADR by default; a field owner who prefers continuity over at-rest secrecy can choose it. | open |
| D11 | Which REST endpoints make up "17"? | Spec section 11's 15 plus `GET /api/v1/games` and `GET /api/v1/games/{id}`; also `GET /api/v1/controller`, `POST /api/v1/controller/promote` (manual failover) and `GET /healthz`. Mode upload is JSON `{"files": {...}}` (1 MB cap, P5-6), not a zip. The node command endpoint takes `set_owner`, `message`, `reset` and `reboot`; the lifecycle goes through the game endpoints. | No multipart dependency; scripts are checked in the core before they are stored. | open |
| D12 | How do REST tokens work? | Read token for reading and the WebSocket, GM token for changes, as `Authorization: Bearer` (or `?token=` for the WebSocket). Unset tokens are generated on first start and kept in the store; `python -m atalaia_controller tokens` prints them. | Spec section 11's read and GM tokens; nothing to configure for a first run. | open |
| D13 | How are MQTT commands authorised? | By Mosquitto users and an ACL (`controller/deploy/`), not by a token inside the message. Events published while the broker is down are not queued; retained topics are republished on reconnect. | The broker already does authentication; the SQLite log is the record. | open |
| D14 | How many games can be live at once? | One per controller: the modem holds one game key. Other games can be listed and exported. | One radio channel and one key per game. | open |
| D15 | Plan names: `controller/src/` and pytest. | Package `controller/atalaia_controller/` (like `atalaia_sim`), unittest like the simulator; dependencies from Ubuntu's packages in the dev image and CI (FastAPI 0.101, pydantic 1, paho-mqtt 1.6), with `requirements.txt` for pip. | `src` makes a poor import name; Raspberry Pi OS ships the same generation of packages. | open |
| D16 | Which serial port does the modem use? | The ESP32-S3's built-in USB-Serial-JTAG by default; UART0 as a Kconfig option. To be confirmed at bring-up: BRING_UP.md mentions `/dev/ttyUSB0`, which suggests a USB-UART bridge on the board. | The Kconfig comments list GPIO 19/20 as USB; both paths are compiled in every build. | open |
| D17 | Can a second Pi stand by as a backup controller in phase 2? | Not until the join flow (plan phase E) can give it the game key. The election code is shared and tested in the simulator (two and three controllers, priority, ties, manual promote, step-down); the real controller steps down on a higher term and can be promoted. | A standby needs the key to hear the game. | open |
| D18 | The node firmware starts the radio task but does not yet send its events and STATE or act on TIME, CMD and ACK (found while building the controller; plan phase C left it unwired). | To be wired before plan phase F, as a phase C follow-up; nothing on the controller side depends on it. | The controller and modem are tested against the protocol, but no box talks it yet. | open |

## Phase 2, plan phase E (GM console, join flow, scoreboard, boxes on the radio)

| # | Question | Answer chosen | Why | Status |
| --- | --- | --- | --- | --- |
| E1 | ADR-P2-12's join payload is a list of fields with no encoding, and lacks what a box and a standby controller turned out to need. | A versioned binary payload: version byte, a CBOR map with integer keys, HMAC-SHA256 tag; 448 bytes at most (fits an NTAG215). Beyond ADR-P2-12's list it carries `controller_id`, `channel_hz`, `max_hops` (the ADR-P2-6 clamp the ADR says the join carries), `game_seed`, optional `params`, and `kind` (box or standby controller); keys 13-31 are kept for optional fields. NFC: one NDEF MIME record `application/vnd.atalaia.join`; text and QR: `atalaia:join:` + base64url. Specified in protocol/join.md with shared vectors checked by C and Python; recorded as RFC 0001 Amendment 2. | Every other payload is CBOR with integer keys and shared vectors; the version byte and the reserved keys leave room for phase 3 (Android props) without breaking boxes. | open |
| E2 | ADR-P2-2/P2-12 tag the payload with "the controller's long-term key", which a box cannot check unless it holds that key. | A 32-byte **field join key**, made once per field: generated by the controller on first start (`python -m atalaia_controller join-key` prints it, `[join] key` sets it, so a standby controller can share it), and given to each box once: the setup portal's new optional field, or `@joinkey <hex>` on the serial console (only while no game is joined). Stored in the same NVS namespace as the game key. A development key (`CONFIG_ATALAIA_DEV_JOIN_KEY`) is set only in the Wokwi build. | The tag must be checkable by every reader; a per-field key keeps another field's cards out without a public-key system. | open |
| E3 | ADR-P2-12's QR join has the controller push the payload to the box over Wi-Fi (`POST /api/v1/nodes/{id}/join`). Boxes have no HTTP server on the field network. | `POST /api/v1/nodes/{id}/join` (and `POST /api/v1/join`, which picks the id) return the payload as text, QR-ready, and as the bytes for an NFC card; they push nothing. Boxes join by NFC card (PN532 read path written, not yet run on hardware) or by the text on the serial console (bring-up, Wokwi). QR codes are for phones (phase 3) and for copying the text. | A box-side Wi-Fi endpoint means station mode during games and its own authentication; not needed for the phase 2 gate. | open |
| E4 | How does a second controller stand by (D17)? | It takes a `kind: controller` payload through `POST /api/v1/controller/join`: the game is stored with the payload's node id, channel and relay clamp, the modem gets the key, and it follows the TIME beacons (state, duration, scores, event log) without acknowledging anything until the GM promotes it. When the TIME beacons say the game ended it leaves the game and forgets the key. After its own restart a joined game comes back as standby (only with `persist_game_key`). Tested over the air with two C host modems: standby follows, the primary stops, the standby is promoted and continues the game with term 2. | Closes D17 with the same election code as the simulator. | open |
| E5 | The plan's field view uses Leaflet with OpenStreetMap tiles as a second option. | Not in phase E: the field view shows the uploaded field image (or a plain grid) with draggable node markers; positions are stored per game. No Leaflet is vendored and no tile server is contacted. | ADR-P2-10 makes the uploaded image primary and OSM online-only; leaving Leaflet out keeps the console small and offline. Add it when a field asks. | open |
| E6 | What does a box put in STATE? | `counters` = points **gained** per team (never decreasing, so the controller's merge by maximum works); `owner_team` = the team of the last `zone.captured` (0 after `zone.neutralized`); `phase` = the box's game state (0 waiting, 1 running, 2 paused, 3 ended), although the schema calls it "mode-specific phase"; `flags` bit 0 running, bit 1 paused. Sent every 15 s (Kconfig) and at once after a capture. | Penalties are not in `counters`: a box's `score.delta` events are logged but not subtracted from the totals. A per-team "lost" counter needs an RFC. | open |
| E7 | What do CMD `set_owner` and `message` do on a box? | They reach the mode as input events `cmd.set_owner` and `gm.message` with the CMD's params (`{"team": ...}`, `{"text": ...}`); `message` is also logged. The built-in Domination and Bomb do not handle them yet, so the console's owner override has no effect on those modes. | What an override means is mode-specific; scripts decide. | open |
| E8 | How does a box resend unacknowledged events? | Normal and critical events (and HELLO) ask for an ACK and wait in a 32-entry outbox; each resend (every 3 s) is a **new** packet with a new seq, because the modem and the controller drop an identical packet as a flood copy and would never ACK it. Normal events give up after 10 resends (STATE repairs scores), critical ones never. They are also written to the flash event log first, and resent after a reboot; the log is compacted as ACKs arrive. ACKs are read as D7 says (bitmap bits count). | Zero lost captures across a battery pull, as the phase 2 gate requires. | open |
| E9 | Box receive and relay. | Boxes use the 16-epoch receive window of D4 (not ADR-P2-2's one), drop packets of other games and their own relayed copies before any decryption, dedupe on (source, epoch, seq) for 30 s, and relay every authenticated packet once after the 10-50 ms jitter with hop_limit clamped to the join's `max_hops` and decremented (core flood.c: hop_limit counts the relays left, so 1 is relayed once more with 0). | The same rules as the modem; tested with a box out of the modem's range heard through another box. | open |
| E10 | A lost CMD (CMDs are not acknowledged). | The box also follows the game state in each TIME beacon: if it shows the game running, paused or ended and the box missed the command, the box acts as if it had received it (a late start steps its clock to the controller's). | CMD start, pause and end must not depend on one packet. | open |
| E11 | Where does a box keep the join? | The whole verified payload (game key included) in NVS namespace `radio`, erased when the game ends (the copy in RAM goes once the last events are acknowledged, at most a minute later). NVS is encrypted only on boxes provisioned as BRING_UP.md step 0 says (C3); other builds now log a warning at boot that the key is in plain NVS. | ADR-P2-12's reboot survival, with the at-rest protection decided in C3. | open |
| E12 | GM console libraries. | Preact 10.24.3 (MIT), HTM 3.1.1 (Apache-2.0) and qrcode-generator 2.0.4 (MIT), vendored unmodified from their npm tarballs (checksums checked against the registry and pinned in `lib/README.md`). Class components only: Preact's hooks import a bare `preact` specifier, which needs an inline import map that the CSP forbids. | No build step (ADR-P2-10), a strict CSP, reproducible files. | open |
| E13 | Where do the console's browser tests run? | Headless Chromium through Playwright 1.49.0 in its own Docker image (`tools/dev/console/Dockerfile`, `python tools/docker_console.py`) and a new CI job `console`; not in `tools/check.sh`, so the dev image needs no browser. A missing browser or tool is an error there, never a skip. | The browser is 400 MB; keeping it out of the dev image keeps `check.sh` fast. | open |
| E14 | The console keeps the token in the browser's local storage. | Yes, per device, with a "leave" button that clears it. The read token can go in a scoreboard URL fragment (`#token=`), which is not sent to the server. | A GM's phone is a personal device; typing a 32-character token for every page load is not workable on the field. | open |
| E15 | The game task's stack on the ESP32. | 12 KB (was 8 KB): joins (CBOR, HMAC) and the radio link now run on it, and the Wokwi join scenario overflowed 8 KB before the preset list moved off the stack. | Found by the Wokwi run; 184 KB of DRAM stays free. | open |
| E16 | A game whose parameters do not fit in a join payload (over 200 bytes of JSON, or 448 bytes in all). | The controller refuses to make the payload (HTTP 409) instead of sending the box the mode's defaults. | A box playing different rules from the controller is worse than a clear error. | open |
| E17 | Which Heltec V4 revision does the firmware drive (the boards arriving may be V4.2 or V4.3)? | A Kconfig choice, *Board revision*: **V4.3 (KCT8103L FEM)**, the default, or **V4.2 (GC1109 FEM)**, for the Field Box and the USB modem. Both: GPIO 7 (the FEM's LDO) high, then GPIO 2 (chip enable) high; V4.3: GPIO 5 (CTX) low = receive LNA; V4.2: GPIO 46 (CPS) high = full PA; DIO2 drives the TX/RX switch on both. Driven only after the SX1262 answers its probe (Wokwi stays safe), in an order planned by `hal/board_fem.c` and tested on the host. Before this, GPIO 7 was held **low** ("RX path"), which would have left the FEM unpowered: the radio nearly deaf and weak on real boards. Pin facts from Heltec's public V4 pinout and Meshtastic's public V4 variant description (facts only, no code). | The revision cannot be read by software; BRING_UP.md tells how to read it off the FEM chip. | open |
| E18 | Button 2 was on GPIO 5, which is the V4.3 FEM's CTX pin. | Button 2 moves to **GPIO 39** (on the GNSS header, freed from the keypad matrix by the PCF8574). The radio logs an error at boot if any team button shares a FEM pin. The Wokwi build keeps button 2 on GPIO 5 (its diagram), where no FEM is driven. `hardware/field-box/` needs the same change (left to the build-manual work). | Other free pins are strapping, PSRAM, USB or console pins; 39 keeps the buttons on GPIOs (no I2C latency on the PCF8574). | open |
| E19 | Button 4 is on GPIO 34, the V4's GNSS power control (VGNSS_Ctrl). | Kept, with a caveat in Kconfig and BRING_UP.md: with no GNSS module plugged in, pressing button 4 only switches the empty connector's supply; bring-up checks it reads high at rest. | Moving it would take the last free GPIO; GPS is not used in this pin map (E21). | open |
| E20 | Does the 14 dB FEM-gain assumption keep both FEMs inside the 500 mW ERP cap? | Kept at 14 dB for both, **not verified**: the firmware sets the SX1262 to 13 dBm, which is legal (26.85 dBm ERP with a 2 dBi antenna) only if the real gain is at most ~14 dB. The FEMs saturate at 27-28 dBm, so the worst case is under 1 dB over the cap. BRING_UP.md step 10 now requires measuring the conducted power before any game transmission and setting `ATALAIA_RADIO_FEM_GAIN_DB` to the measured gain (C2). | The gains of the GC1109 and KCT8103L at our drive level are not known from public facts; a measurement settles it, and a too-low setting would cost range for nothing. | open |
| E21 | The V4 ships with a GNSS module for its SH1.25 connector (GPIO 34, 38-42). | **GPS is not supported on the Field Box in this pin map**: the GNSS header pins stay with the display and buttons, and BRING_UP.md says not to plug the module in. Revisit the pin map in phase 4, when GPS-based modes (VIP, Payload) arrive. | The display needs those pins now; no phase 2 or 3 mode needs the box's position. | open |
| E22 | Vext (GPIO 36, active low) was never driven. | The firmware drives it low at boot, before probing peripherals, on the Field Box and the USB modem (`hal_esp_board_power_on`, `CONFIG_ATALAIA_VEXT_CTL_PIN`, -1 to leave it alone). | The OLED and the external peripherals are powered from it on the V4. | open |
| E23 | `python tools/docker_fw.py build` used `firmware/esp32/sdkconfig`, which a local Wokwi or menuconfig session could leave with emulator values (a keypad matrix on GPIO 1/2/7/39), so a "Field Box" image could drive the radio front-end pins as keypad lines. | `build` now keeps its configuration in `build/sdkconfig`, made from `sdkconfig.defaults` alone and remade when the defaults change, like the Wokwi and modem variants; `clean` also deletes a stray `firmware/esp32/sdkconfig`. CI's job is unchanged (a fresh checkout has no `sdkconfig`). | Found by the build-manual work. | open |
| E24 | The Heltec V4's only USB port is the ESP32-S3's own USB-Serial-JTAG, but the shell read console input from UART0 only, so `@join`, `@joinkey` and serial keys could not reach a real box. | The Field Box reads console input from both: USB-Serial-JTAG (the driver installed at boot, `CONFIG_ATALAIA_CONSOLE_USB_INPUT`, default on) and UART0, each with its own line parser. IDF's driver drops console output after 50 ms when no USB host listens, so a box on battery does not block. The Wokwi build keeps UART0 only. Not yet run on a board: the parser is host-tested, the USB path is only compiled. | Bring-up and joining from a laptop need it. | open |
| E25 | The LED ring had no brightness control (WS2812 has none of its own); 24 LEDs at full white draw about 1.4 A. | The driver scales every colour at `show()`: 40% at boot (`CONFIG_ATALAIA_LED_BRIGHTNESS_PCT`), and `ring:set_brightness(percent)` from modes (0-100, clamped). The scaling is host-tested; the LED count fallback is 24, as in Kconfig. | Power budget of a battery box; 40% is still daylight-visible on a WS2812 ring (to confirm at bring-up). | open |

### Phase 3, Android and players (design: docs/phase-3-android-players/)

## Field check-in, registration and scheduling (maintainer request, 2026-10-19)

The maintainer asked for field check-in by a printed QR code, per-game replica declaration so marshals see in advance which replicas still need the chronograph, game scheduling and registration, and publication on the field's page and on shared or third-party platforms such as jogarairsoft.pt. Split agreed with the maintainer, local-first: the game-day part is phase 3 plan phase E (ADR-P3-13 in `docs/phase-3-android-players/ADR.md`), the site-server part is phase 4 (ADR-P4-11 and ADR-P4-12 in `docs/phase-4-site-server/ADR.md`, plan Phase I). Design only; nothing is built.

| # | Question | Answer chosen | Why | Status |
| --- | --- | --- | --- | --- |
| F1 | Is the check-in poster per field or per game, and is it signed? | Per field, printed once (optionally pinned to one game). Not signed and no MAC. It holds no secret: no join key, game key, token key or Wi-Fi password. The app pins the field's CA certificate per `field_id` on the first scan (fetched over Wi-Fi and checked against the poster's fingerprint, P3-8) and refuses a later poster for the same field with another fingerprint. | A player's app holds no key that could check a signature, and the poster must be safe to photograph. The controller answers only on the field network, so reaching it already means being at the field. A forged poster can only fool a phone that never saw the real one, and a check-in asks for no password or payment. | open |
| F2 | The poster's format. | `atalaia:checkin:` + base64url of a version byte (1) and a CBOR map: 1 `field_id`, 2 `field_name`, 3 `urls` (1-3), 4 `ca_sha256`, 5 `wifi_ssid` (optional), 6 `game_id` (optional); at most 192 bytes; keys 7-31 skipped. Specified in `protocol/checkin.md` with shared vectors for Dart and Python. A field whose Wi-Fi has a password can print a standard `WIFI:` QR code beside it; the console draws it and does not store the password. | The same shape as the join text, so the CBOR codecs and the tests are reused. | open |
| F3 | Who a player is without an account. | Per field, the app makes a `player_id` (`p-` and 12 random base32 characters) and a 32-byte secret, kept in its private storage; the controller keeps the id and the secret's SHA-256. | F4 | Which role does a self check-in give? | Only `player`. Marshal, GM and the other roles come from the GM, with a new token. | F9 | What happens to check-ins when a standby controller takes over? | They are not copied to the standby in this version. After a takeover the app checks in again by itself with its field identity and resends its declaration, and the marshals' apps resend their signed readings, which rebuilds the list. | Check-ins never travel on the radio; copying them over the network is extra work for a rare case, and the phones hold copies. To revisit if takeovers turn out to be common. | open |
| F10 | The federation number (many Portuguese games require players federated with the FPA, per the maintainer). | An optional field per check-in and registration, set per field: `off` (default), `optional` or `required`, with a label such as "FPA". | F11 | Check-in personal data and its retention. | Kept: a display name, the optional federation number, a team preference, the declared replicas, the time, the per-field id and its secret's hash; nothing else. | F12 | A player without the app. | A marshal (app) or the GM (console) checks them in by hand with the same fields; the controller makes the id, which the tag writer can put on a player tag (PD14). | F14 | Does online registration need an account? | Yes (ADR-P4-2). A name-only guest registration would need an email to deliver the ticket, which is more data, not less. | open |
| F15 | Pre-declared replicas and the check-in ticket. | Declared at registration (on by default per game), sent in the roster and shown as pending in the controller's list before anyone arrives. | F16 | Who is in charge on game day, and what goes back? | The controller pulls the roster until the game starts (additions and cancellations apply to players not yet checked in); after the start nothing from the site server changes that game; staff changes on the day win. | F17 | A waiting list when a game is full? | Not in this version: registration closes at `max_players`. | Keeps the first version small; easy to add if fields ask. | open |
| F18 | iCalendar feed details. | Public `.ics` per field and per game (when the field page is on); RFC 5545 with UTC times (no `VTIMEZONE`), stable `UID`, `SEQUENCE` raised on changes of time, place or status, cancelled games kept for 30 days as `STATUS:CANCELLED`; drafts never; no personal data. | Every calendar app can subscribe; UTC avoids shipping time-zone definitions. | open |
| F19 | JSON feed format. | The project's own versioned `atalaia.games` version 1 with a JSON Schema, `Access-Control-Allow-Origin: *`; the game page also embeds schema.org `Event` JSON-LD. | No shared format for airsoft game listings is known to the project; a small documented one is easy for clubs' sites and platforms to read. | open |
| F20 | What the registration import reads. | CSV (RFC 4180) or JSON with only `display_name`, `external_ref`, `team_preference`, `federation_number` and `replicas`; any other column (an email, a phone number) is ignored and named in the preview; rows update by `(source, external_ref)`; dry run first. | Minimisation even when another platform's export carries more; re-importing an updated export is safe. | open |
| F21 | Rules for platform adapters. | Only through the platform's documented API or a written agreement. No scraping, no automated form posting, no use of someone's login beyond what the API offers. Off by default, per field, credentials encrypted, every call audited, outbound from the site server only; registrations go through the import rules. | Clean-room policy (spec section 17), the platforms' own terms, and legal safety. | open |
| F22 | jogarairsoft.pt | **Needs the maintainer.** No public information or API about it was found (web search, 2026-10-19), so no adapter is designed and nothing about it is assumed. The maintainer would contact its operators to ask whether they offer an API or a registration export, or would read the iCalendar and JSON feeds. Until then a field can use the feeds and the CSV import (if the platform lets it export a list). No scraping. | Nothing about a third party is invented. | open |
| F23 | Importing a registration list without a site server. | Not now: the import is a site-server feature (phase 4). A GM-console import of the same CSV straight into the controller's check-in list, for fields that take registrations elsewhere and have no site server, is a small follow-up if the maintainer wants it. | The agreed split puts the import in phase 4; the format is shared, so the controller can take it later without a new design. | open |

## Medic Kit (Ligaduras), queued after phase 3 plan phase E

Maintainer request, 2026-10-19: "bandages": a hit player asks for medic assistance, touches and holds the button (as when arming the bomb) for a time the organisation sets per game, to get healed; the kit has a set number of heals, shows how many remain, and updates the GM console and the players' view. Then: "in order to activate the heal, the player must identify himself with his NFC tag (so we know who is the player being healed and can also define a max number of healing per players)".

| # | Question | Answer chosen | Why | Status |
| --- | --- | --- | --- | --- |
| MK1 | Is the player tag required? | **Yes (maintainer).** A heal starts only with the player's signed NFC tag (protocol/nfc-tag.md); forged tags, another game's tags and players of a team the kit does not serve are refused, and the screen says why. | Each heal names the player, and per-player limits need to know who it is. | confirmed |
| MK2 | Flow | Scan the tag, then hold the team button for `heal_hold_s` (per game, default 10 s); letting go early cancels; the screen shows the progress, then "Restam N ligaduras". | The Bomb's hold-to-arm, which players already know. | open |
| MK3 | Limits | `charges` per kit (default 5, refused when empty, the GM can refill from the console), `max_heals_per_player` per game (default 2), optional `cooldown_s` per player; `team` = the team the kit serves or any. | The maintainer's two limits, plus what a field would tune. | open |
| MK4 | Where the per-player limit is counted | Game-wide on the controller: it sees every heal (its field.lua keeps the count and tells every kit); each kit also counts its own heals, so it keeps working out of contact, at the risk of one extra heal before the count arrives. | MK5 | Events | `medic.heal` {team, player, remaining, player_heals_used} and `medic.empty`, ids 50 and 51 (phase 4 already plans 42-49), to the controller, the GM console feed, the players' view and the scoreboard; no personal data beyond the player id. | Next free ids; the check-in reused event 15 (F6), so 50 is free. | open |
| MK6 | Running alongside a main mode | A field game assigns the medic role to its kit nodes, and a node runs only the parts for its role (not, say, Domination's capture rules). This needs a small change to how a game composes scripts per node role. | Medic kits sit next to any game. | open |
| MK7 | Hardware | A Field Box with its PN532 NFC reader, or an Android phone's own NFC. | The tag is required (MK1). | open |
| MK8 | Names | "Medic Kit" in English, "Ligaduras" in Portuguese; "squad" stays "squad". | Players' own words. | open |

In a composed game (`org.atalaia.domination+org.atalaia.medic`) the game's roles are the main mode's and the role packages'; a node with a role package's role runs that package's `node.lua` alone, with its parameters only; the other nodes run the main mode and the modifiers as before; every part's `field.lua` runs on the controller. | MK10 | In which language are the kit's screens? | A string parameter `lang`, `pt` (default) or `en`. | MK11 | How do the GM's refill and the controller's counts reach a kit? | A new CMD opcode **8, `mode`** (RFC 0001 Amendment 5, proposed): params `{"name": ..., ...}`, delivered to the script as `cmd.mode` with the params (name included). The GM's commands are declared in the manifest (`commands: { refill: { roles: [medic], label } }`, labels under `i18n.<lang>.commands`); the console shows a button per command on boxes of those roles and the controller refuses undeclared names or a box of another role. | MK13 | Hold details (MK2). | Any team button heals: the tag says who the player is. | MK15 | The per-player count across kits (MK4) in detail. | The controller's `field.lua` counts each player's heals: on each `medic.heal`, the larger of its count + 1 and the kit's `player_heals_used`; it tells every other kit, and the kit that healed only when that kit was behind (`heals` with `player`, `used` and `at`, the controller's game time in whole seconds, which the cooldown uses too). | MK17 | Parameter edges. | `max_heals_per_player` 0 means no limit (1-100 otherwise); `team` is optional: empty means every team, and then a player tag without a team is healed too; the GM console and the app's prop setup offer "every team" for optional team parameters (they always picked a team before). | A field without limits, and kits shared by both teams, are the common cases. | open |

## Field and team branding (maintainer request, 2026-10-19)

Maintainer request: "another nice addition to the mobile app would be each field (or team) running it at their own server be able to set a logo and/or a wallpaper to identify them". The agreed scope: field branding (name, logo, optional wallpaper, accent colour) on the controller a field or club runs, shown in the app, the GM console, the scoreboard and the check-in poster; team branding per game (a display name and a crest next to the colour) with saved team presets; club profiles with accounts left for phase 4.

| # | Question | Answer chosen | Why | Status |
| --- | --- | --- | --- | --- |
| BR1 | Where does a field's branding live? | On the controller the field or club runs: set in the GM console's *Definições / Settings* with the GM token, kept in its SQLite file (schema 4: an `images` table and a `branding.field` setting), so it survives restarts. A standby controller has its own branding (nothing is synced over the radio or between controllers); a field with two controllers uploads it to both. | The field's own server is what the request names; the radio has no room for images. | open |
| BR2 | Who can read it? | Anyone who can reach the field's API, with no token: `GET /api/v1/field/branding`, its images and the crests (players need it before or right after checking in, a prop has no read token). | S11-1 | Refresh tokens: ADR-P4-2's JWT signed with a `REFRESH_SECRET`, kept in `sessions.refresh_token`? | Opaque 256-bit random values (`secrets.token_urlsafe(32)`), stored only as their SHA-256 in a new `refresh_tokens` table (one row per token issued, `used_at` once rotated, `ON DELETE CASCADE` from `sessions`); `sessions.refresh_token` is dropped in `0002_accounts` (the table was always empty). | S11-2 | Are access tokens stateless, as ADR-P4-2 says ("no database lookup on every API call")? | No: every request re-reads the session (it must exist, be the token's, not revoked, not expired) and the user's roles from `user_field_roles`; the token's `roles` claim is kept for the client's display only.
