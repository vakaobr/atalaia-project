# RFC 0001: Skirmesh-RF v1 wire format

- **Author(s):** The Atalaia contributors
- **Status:** Accepted (by the maintainer, 2026-10-17)
- **Discussion:** None yet (no other contributors at the time of acceptance).
  Future protocol changes follow the normal RFC process with a 2-week
  review period (spec section 13).

## Summary

This RFC defines the complete on-wire format for Skirmesh-RF v1
packets: the 9-byte header bit layout and byte order, the AES-128-CCM
security layer (key, nonce, AAD, MIC), CBOR payload schemas for all 8
message types, flood routing rules, duty-cycle and power limits for
EU868, and the join and rejoin-after-reboot flows.

The detailed rationale behind each decision is recorded in
[`docs/phase-2-field-network/ADR.md`](../phase-2-field-network/ADR.md)
(ADR-P2-1 through ADR-P2-15). This RFC is the normative wire-format
specification; the ADRs document why.

## Motivation

Phase 0 defined the EVENT payload (CBOR map with integer keys) and
left the rest for Phase 2: the header bit layout, the byte order of
multi-byte fields, the AES-CCM parameters, and the payloads of the
other 7 message types. Without a frozen wire format, no codec work can
begin, and no two implementations can interoperate.

On the field, the protocol must:

- fit in LoRa's tight airtime budget (EU868: 1% duty cycle on most
  channels);
- authenticate every packet so a player with an SDR cannot inject fake
  captures;
- survive reboots and radio partitions without losing events;
- keep game clocks synchronised within 250 ms across all nodes.

## Design

### 1. Packet structure

```
[ 9-byte header (cleartext, authenticated) ]
[ 0-200 byte ciphertext (encrypted CBOR payload) ]
[ 8-byte MIC (AES-CCM authentication tag) ]
```

Total maximum: 9 + 200 + 8 = 217 bytes, within LoRa's 255-byte limit
at all spreading factors.

### 2. Header (9 bytes)

```
Offset  Size  Field            Encoding
  0       1   version_flags    bit field (see below)
  1       2   game_id          uint16 big-endian
  3       2   source           uint16 big-endian
  5       2   seq              uint16 big-endian
  7       1   hop_limit        uint8 (default 2)
  8       1   type             uint8 (1-8)
```

All multi-byte fields are big-endian (network byte order).

#### version_flags byte

```
Bit   7   6   5   4   3   2   1   0
    [  version  ] [prio ] [ack] [enc] [rsv]
```

| Bits | Field | Width | Values |
|------|-------|-------|--------|
| 7-5 | `version` | 3 | Protocol version; v1 = 1. Version 0 is rejected as malformed. |
| 4-3 | `priority` | 2 | 0 = telemetry, 1 = normal, 2 = critical, 3 = reserved |
| 2 | `ack_req` | 1 | 1 = sender requests ACK from the controller |
| 1 | `encrypted` | 1 | 1 = AES-CCM encrypted. Always 1 on LoRa. |
| 0 | `reserved` | 1 | Must be 0 on send; ignored on receive. |

Examples: normal + ACK + encrypted = `0x2E`; critical, no ACK,
encrypted = `0x32`.

### 3. AES-CCM security

**Key:** AES-128 (16 bytes), generated by the controller with a CSPRNG
when a game is created. Distributed during join (NFC or QR); never
sent over LoRa.

**Nonce** (13 bytes):

```
Offset  Size  Field       Source
  0       2   game_id     from header (big-endian)
  2       2   source      from header (big-endian)
  4       4   nonce_ctr   (epoch << 16) | seq, big-endian
  8       5   zeros       0x00 * 5
```

`nonce_ctr` is a 32-bit monotonic counter composed of two halves:

- **epoch** (uint16, high half): incremented and persisted to NVS at
  boot (per game key since Amendment 9: a new key starts at 1) and
  whenever `seq` wraps from 65535 to 0. If the NVS write fails, the
  node halts the radio and emits `nonce.nvs_fail` (critical). No per-packet NVS writes.
- **seq** (uint16, low half): the header sequence number, incremented
  per packet.

At epoch 65535 with seq 65535, the node has exhausted 2^32 nonces
under this game key. It refuses to start a new epoch and emits
`nonce.exhausted` (critical). A new game (new key) is required.

**Receiver epoch discovery:** receivers track the last authenticated
epoch per source. On a new packet:

1. Try auth_decrypt with the current epoch for that source.
2. On failure, try epoch + 1.
3. On success with epoch + 1, adopt it. Reset the replay window for
   that source.
4. On both failures, drop the packet.
5. Never accept a lower epoch.

(Amendment 9: receivers search further above for HELLO and TIME, and a
node's epochs are per game key.)

HELLO and STATE messages also announce the epoch explicitly, allowing
receivers to resync after a longer gap.

**AAD** (8 bytes): header bytes 0-6 plus byte 8 (everything except
`hop_limit` at byte 7). `hop_limit` is excluded so relay nodes can
decrement it without invalidating the MIC.

**Relay clamp:** because `hop_limit` is unauthenticated, an attacker
could raise it to amplify flooding. Every relay node therefore clamps
the incoming `hop_limit` to the game's configured maximum (default 2)
before decrementing and rebroadcasting.

**MIC:** 8 bytes (64-bit tag). Forgery probability 2^-64.

**Encryption:** mandatory on LoRa (`encrypted` bit always 1). The
CBOR payload is encrypted. The header is cleartext (but
authenticated), so receivers can route and deduplicate before
decrypting.

### 4. Message payloads

All payloads are CBOR maps with integer keys. Keys 1-23 encode in
1 byte.

#### HELLO (type 1)

Sent after joining a game.

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `node_name` | text | yes | Human-readable, max 24 bytes |
| 2 | `platform` | uint8 | yes | 0=esp32, 1=esp32s3, 2=linux, 3=android |
| 3 | `fw_version` | text | yes | Firmware version string |
| 4 | `core_version` | text | yes | Core library version |
| 5 | `tier` | uint8 | yes | 0=full, 1=reduced, 2=proxy |
| 6 | `capabilities` | array[uint8] | yes | Capability type ids |
| 7 | `transports` | uint8 | yes | Bitmask: bit 0=lora, 1=wifi, 2=ble |
| 8 | `battery_pct` | uint8 | no | 0-100 |
| 9 | `epoch` | uint16 | yes | Current nonce epoch |

Typical size: 40-60 bytes.

#### EVENT (type 2)

Defined in `protocol/schema/events.yaml`. The payload is the event
envelope (keys 1-8) as already specified. No changes from Phase 0.

#### ACK (type 3)

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `ack_node` | uint16 | yes | Source node being acknowledged |
| 2 | `ack_seq` | uint16 | yes | Highest contiguous seq received |
| 3 | `ack_bitmap` | bytes | no | Selective ACK for gaps (up to 32 bytes = 256 seqs) |

Typical size: 6-38 bytes.

#### STATE (type 4)

Sent every 10-60 seconds (per field profile).

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `owner_team` | uint8 | yes | Current owner (0 = none) |
| 2 | `phase` | uint8 | yes | Mode-specific phase |
| 3 | `game_time_ms` | uint32 | yes | Node's local game time |
| 4 | `counters` | map[uint8->uint32] | yes | Per-team score counters |
| 5 | `rssi` | int8 | no | Last received signal strength |
| 6 | `battery_pct` | uint8 | no | 0-100 |
| 7 | `flags` | uint8 | no | Bit 0: running, bit 1: paused |
| 8 | `epoch` | uint16 | yes | Current nonce epoch |
| 9 | `lost` | map[uint8->uint32] | no | Per-team points lost to penalties on this node (Amendment 18); absent = none |

Typical size: 20-40 bytes (2-team game); a team with a penalty adds 2-6 bytes.

#### CMD (type 5)

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `cmd` | uint8 | yes | Opcode (see table) |
| 2 | `params` | map | no | Command-specific |
| 3 | `dest` | uint16 | no | Destination node; absent = broadcast |

Opcodes: 0=start, 1=pause, 2=resume, 3=end, 4=set_owner,
5=message, 6=reset, 7=reboot; 8=mode (Amendment 5); 9=update (Amendment 6).

#### TIME (type 6)

Controller heartbeat, every 30 s (10 s with failover).

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `game_time_ms` | uint32 | yes | Controller's game time |
| 2 | `game_state` | uint8 | yes | 0=waiting, 1=running, 2=paused, 3=ended |
| 3 | `duration_ms` | uint32 | yes | Total duration (0 = unlimited) |
| 4 | `wall_s` | uint32 | yes | Unix epoch seconds |
| 5 | `term` | uint32 | yes | Election term |
| 6 | `tx_time_us` | uint16 | no | Processing time before TX |

Typical size: 18-20 bytes.

#### CONFIG (type 7)

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `mode_id` | text | yes | e.g. "org.atalaia.domination" |
| 2 | `role` | text | yes | Role within the mode |
| 3 | `params` | text | yes | Preset parameters as JSON |
| 4 | `teams` | array[text] | yes | Team names in order |
| 5 | `game_seed` | uint32 | yes | Seed for deterministic rand() |

Typical size: 60-150 bytes.

#### CLAIM (type 8)

Controller election.

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `term` | uint32 | yes | Monotonically increasing |
| 2 | `priority` | uint16 | yes | Higher = better |
| 3 | `node_id` | uint16 | yes | Tiebreaker: lowest wins |
| 4 | `last_ack_seq` | map[uint16->uint16] | no | Per-node last ACK'd seq |

Typical size: 12-60 bytes.

### 5. Flood routing

Topology: star centred on the controller, extended by TTL-limited
flood.

1. On receiving a packet, check (source, seq) against the dedupe
   table. If seen, drop.
2. Record (source, seq) in the dedupe table (64 entries on ESP32,
   30 s expiry, LRU eviction; unlimited on the controller).
3. Process the packet.
4. If `hop_limit > 0`, clamp it to the game's configured maximum
   (default 2), decrement, and rebroadcast after a random jitter
   of 10-50 ms (seeded deterministically by source + seq).
   *Amendment 13 (2026-10-26) replaces this rebroadcast: whether to relay
   and after how long now depend on the kind of frame, on the controller's
   ACK and on how many boxes the relayer hears; the check, clamp and
   decrement of steps 1-4 stay.*

The controller does not rebroadcast received packets. It originates
TIME and CMD on the 10% sub-band.

### 6. Time synchronisation

Target: +/-250 ms across all nodes.

On receiving a TIME beacon, a node:

1. Estimates one-way delay: known airtime (deterministic from packet
   size, SF, BW) + 5 ms processing overhead + `tx_time_us`.
2. Computes offset: `controller_time + delay - local_time`.
3. If |offset| < 5 ms: no correction.
4. If |offset| < 500 ms: linear slew at max 5%/s (spread over 10 s).
5. If |offset| >= 500 ms: step (game start, long partition).

TIME beacons use 869.525 MHz (g2 sub-band, 10% duty cycle).

### 7. Controller failover (CLAIM)

Detection: 3 missed TIME beacons (~30 s). Each controller-capable
node sends CLAIM with `term = last_seen_term + 1` and its priority
score. Highest term wins; highest priority breaks ties; lowest
node_id breaks further ties. 5 s election timeout. The winner sends
TIME with the new term. Any node seeing a higher term steps down.

Recovery: the new controller asks nodes to replay events from their
last ACK'd seq. Scores merge by maximum per counter (conflict-free).

Default: manual failover. Automatic CLAIM is tested and enabled per
field profile after field validation.

### 8. Duty-cycle and power (EU868)

| Sub-band | Frequency | Duty cycle | Airtime/hour |
|----------|-----------|------------|-------------|
| g | 868.0-868.6 MHz | 1% | 36,000 ms |
| g1 | 868.7-869.2 MHz | 0.1% | 3,600 ms |
| g2 | 869.4-869.65 MHz | 10% | 360,000 ms |
| g3 | 869.7-870.0 MHz | 1% | 36,000 ms |

Node TX hops across three g-band channels (868.1, 868.3, 868.5 MHz)
round-robin, with independent per-channel duty-cycle tracking.
Controller TIME and CMD use the g2 sub-band.

The radio HAL tracks airtime per sub-band with a 60-bucket sliding
1-hour window. If the budget is exhausted (or the packet's time on air does not fit in
what is left), `send()` refuses it (`DUTY_CYCLE_EXCEEDED`; the radio task
reports `RADIO_TX_RESULT_DUTY_CYCLE`) and the packet is **dropped, not
queued**: nothing is held for later. What must arrive is sent again by its
sender: an EVENT or HELLO is resent from the box's outbox on the schedule
of Amendment 13, a STATE is replaced by the next one, and a relay is not
repeated. (This sentence said "queued for retry" until Amendment 13; the
radio task never did that, and the relay study measured why it should not:
with the rules of Amendment 13 no box was refused a single frame at 20 or
30 boxes, so a queue would only fill when a field is already saturated,
and would then release stale relays in a burst.)

**Listen before talk (Amendment 14).** The regulations allow listen-before-talk with adaptive
frequency agility *instead of* a duty-cycle limit; Skirmesh-RF does not use it that way. Before
every transmission a box (and the modem and the I/O pod) asks the radio whether the channel is
busy and waits if it is, **only to avoid collisions between boxes that hear each other**; the
duty-cycle limit above is unchanged and is spent by the real send, after the wait.

**Power cap with FEM (Heltec V4.3):** the board's front-end module
adds ~14 dB of gain. The SX1262 output power is set so the total ERP
stays within EU868 limits:

- g/g1/g3: SX1262 at 0 dBm -> ~14 dBm ERP (25 mW limit).
- g2: SX1262 at 13 dBm -> ~27 dBm ERP (500 mW limit).

The FEM gain is a Kconfig constant (`EU868_FEM_GAIN_DB`), verified
during field-test calibration with a power meter.

### 9. Join flow

Nodes join by tapping an NFC card or scanning a QR code (BLE deferred
to Phase 3). The join payload:

| Field | Size | Purpose |
|-------|------|---------|
| `game_id` | 2 | Which game |
| `game_key` | 16 | AES-128 key |
| `node_id` | 2 | Assigned short id |
| `team_count` | 1 | Number of teams |
| `team_names` | variable | NUL-separated |
| `mode_id` | variable | Mode identifier |
| `role` | variable | Role within the mode |
| `hmac` | 32 | HMAC-SHA256 with controller's long-term key |

NFC: written to an NTAG215/216 as an NDEF binary record. QR: the same
payload base64url-encoded, pushed to the node over Wi-Fi by the
controller.

### 10. Rejoin after reboot

The game key is stored in the ESP32-S3's encrypted NVS partition
(eFuse HMAC-derived key). On reboot:

1. Read game key and epoch from encrypted NVS (the epoch of that key:
   Amendment 9).
2. Increment epoch; persist before first TX.
3. Replay unacknowledged events from the flash-backed event log
   (`/log/game.bin` on LittleFS).
4. Send HELLO with the new epoch.
5. Emit `node.rebooted` (critical).

No NFC re-tap is needed. The key is zeroed and deleted from NVS when
the game ends.

## Compatibility

This is the initial v1 definition. There is no previous version. The
3-bit version field allows 6 future revisions (v2-v7) before a layout
change. Older nodes never receive messages with a version they do not
understand (they drop them silently based on the version bits).

## Alternatives

### Nonce construction

**Considered: nonce = game_id + source + seq + 7 zeros.** Rejected
because a 16-bit seq wraps at 65535, and a reboot resets it. Both
cause nonce reuse under the same key, breaking AES-CCM confidentiality
and enabling forgery.

**Considered: per-packet NVS persist of a monotonic counter
(nonce_high_water + SKIP_GAP).** Rejected because per-packet flash
writes cause unnecessary wear, and receivers cannot reconstruct the
counter from the cleartext header without adding bytes to every
packet.

**Chosen: (epoch << 16) | seq.** Epoch is persisted only at boot and
seq wrap (two writes, not per-packet). Receivers reconstruct it via
AES-CCM trial (try current epoch, then epoch+1). No extra header bytes.

### AAD scope

**Considered: full 9-byte header as AAD.** Rejected because relay
nodes must decrement `hop_limit`, which would invalidate the MIC.
Re-encrypting on every relay adds CPU cost and code complexity.

**Chosen: 8-byte AAD (header minus hop_limit).** Relay nodes decrement
`hop_limit` freely; the relay clamp prevents amplification.

### Event log storage

**Considered: 128-entry DRAM ring buffer.** Rejected because events
are lost on brownout or battery pull, violating the "zero lost
captures" gate. `zone.captured` is normal priority, not critical, so
a "flush only critical" policy loses captures.

**Chosen: flash-backed append log on LittleFS.** Normal and critical
events flushed immediately; only telemetry buffered. Survives power
loss.

### Game key storage

**Considered: key in RAM only, zeroed on game end.** Rejected because
the spec requires a rebooted node to resume its game (countdown,
scores) without GM intervention. RAM-only keys require a new NFC tap
after every battery pull.

**Chosen: encrypted NVS (eFuse HMAC).** The key survives reboots.
An attacker who dumps flash cannot read it without the eFuse key.

### Controller radio

**Considered: SPI LoRa HAT on the Raspberry Pi with a C radio gateway
daemon.** Rejected because it requires spidev/libgpiod dependencies,
a separate C codebase for the Pi, and splits the radio code between
two platforms.

**Chosen: USB radio modem (same Heltec V4.3 board).** All radio,
AES-CCM, dedupe, and duty-cycle code runs on the modem's ESP32, shared
with the node firmware. The Pi needs only `pyserial`.

## Amendment 1 (2026-10-18): Single shared game channel

**Supersedes:** section 8 paragraph "Node TX hops across three g-band
channels..." and section 6 sentence "TIME beacons use 869.525 MHz."

**Change:** All game traffic (events, STATE, ACK, TIME, CMD) uses a
single shared channel per game, by default 869.525 MHz in the g2
sub-band (869.4-869.65 MHz, 10% duty cycle, 500 mW ERP).  The
channel is configurable per game via the CONFIG message.

**Reason:** With a single-radio half-duplex transceiver (SX1262), the
round-robin hopping scheme in section 8 left nodes listening on
different frequencies after their last TX, so they missed each other's
packets.  A single shared channel is the standard single-radio mesh
approach (Meshtastic's EU868 default uses the same frequency).

The g2 sub-band was chosen because:
- 10% duty cycle (360,000 ms/h) gives 10x the airtime of the g-band
  (36,000 ms/h), which is important for a 5-node game with TIME
  beacons, events, STATEs and ACKs.
- 500 mW ERP gives better range than the g-band's 25 mW.
- Neighbouring games are separated by choosing different channels
  within the sub-band or in other sub-bands.

**Duty-cycle tracking:** The firmware tracks the g2 10% budget per
device with a 60-bucket sliding one-hour window.

**Power:** The SX1262 conducted power for the g2 sub-band accounts
for the FEM gain (14 dB) and the antenna gain (2 dBi, Kconfig):
27 dBm ERP + 2.15 - 14 - 2 = 13.15 -> 13 dBm conducted.

**Channel validation:** The firmware validates the configured channel
against the EU868 sub-band table and refuses to transmit if the
channel is outside all sub-bands.

## Amendment 2 (2026-10-18): Join payload encoding

**Supersedes:** the field table of section 9 ("Join flow"), which lists
the fields but not how they are encoded or which key the HMAC uses.

**Change:** The join payload is a version byte (1), a CBOR map with
integer keys, and a 32-byte HMAC-SHA256 tag over the version byte and the
map, at most 448 bytes in all. Beyond section 9's fields the map carries
the controller's node id, the game channel, the relay clamp (`max_hops`,
which section 9's companion ADR-P2-6 says the join carries), the scripts'
seed, the preset parameters, and whether the payload is for a box or a
standby controller. Keys 13-31 are reserved for optional fields and
skipped by readers. The tag key is a 32-byte **field join key** shared by
the controllers and boxes of one field, not a key only the controller
holds: every reader must be able to check the tag. On NFC cards the
payload is one NDEF MIME record of type `application/vnd.atalaia.join`;
as text (QR codes, the serial console) it is `atalaia:join:` followed by
base64url without padding.

The full specification, with shared test vectors checked by the C and
Python codecs, is [protocol/join.md](../../protocol/join.md). Decisions E1
and E2 in `docs/review/decisions-to-review.md`.

**Reason:** Section 9 could not be implemented as written: it gives no
encoding, its "team_names NUL-separated" and variable-length text fields
need lengths, a box cannot verify a tag made with a key only the controller
has, and a box or a standby controller also needs the channel, the relay
clamp and the controller's id before it hears its first TIME beacon.

## Amendment 3 (2026-10-18): Choosing the field's channel; the whole channel inside one sub-band

**Supersedes:** in Amendment 1, "The channel is configurable per game via the CONFIG message" (CONFIG has no channel field; the channel reaches boxes in the join payload, Amendment 2) and the "Channel validation" paragraph; the open question on adaptive channel selection, in part. Section 8's sub-band table stands, with the sources and the note on its labels below.

**Change:**

1. **Why 869.525 MHz is the default.** It is the centre of 869.4-869.65 MHz, the only part of the European 863-870 MHz short-range band where a device may transmit up to 10% of the time at up to 500 mW ERP. Everywhere else in 868-870 MHz the limit is 25 mW ERP with 1% of the time (0.1% on 868.7-869.2 MHz): about a tenth of the airtime, and roughly 13 dB less power, so much less range. 868.1, 868.3 and 868.5 MHz are LoRaWAN's three default channels, which every LoRaWAN device in Europe implements and joins on, so they are often busy. The default is shared too: LoRaWAN uses 869.525 MHz for its RX2 receive window and Class B beacons, and Meshtastic's EU_868 default sits on the same 869.525 MHz with a 250 kHz preset, the whole sub-band. Their packets are not mistaken for the game's (the game's are encrypted and authenticated, and use another sync word), but every transmission nearby shares the airtime, which is why the GM can scan for a quieter channel.

2. **The channel is a field setting.** The field controller keeps it in its store (it survives a restart; `[radio] channel_hz` is the default until the GM first chooses). From the GM console (Settings), and only while no game is live, the GM can keep 869.525 MHz, run a noise scan of the candidate channels with the USB modem ("find a quiet channel"), draw a random candidate, or pick one from the list; scan and random choices are suggestions that change nothing until the GM accepts one. The controller sends the channel to the modem (SET_CHANNEL when no game is live, CONFIGURE for a game), stores it with each game, and puts the game's channel in every join payload (key 5, `channel_hz`). A game keeps its channel until it ends. Without a USB modem or without a radio chip the scan is unavailable and the channel stays as it is. The candidate list, the scan's dwell, the quiet threshold and the random rule are decisions CH1-CH8 in `docs/review/decisions-to-review.md`.

3. **The whole channel must fit in one sub-band.** A centre frequency is legal only if centre - BW/2 and centre + BW/2 both lie inside one sub-band of section 8 (edges included), where BW is the game's LoRa bandwidth, 125 kHz. A centre inside a sub-band is not enough: 869.40 MHz at 125 kHz occupies 869.3375-869.4625 MHz and spills below the sub-band. The legal centres are:

   | Sub-band | Edges | Legal centres (125 kHz) |
   |----------|-------|-------------------------|
   | g | 868.0-868.6 MHz | 868.0625-868.5375 MHz |
   | g1 | 868.7-869.2 MHz | 868.7625-869.1375 MHz |
   | g2 | 869.4-869.65 MHz | 869.4625-869.5875 MHz |
   | g3 | 869.7-870.0 MHz | 869.7625-869.9375 MHz |

   The rule is applied in one place per language (`atalaia_band_of_channel()` in `core/src/duty_cycle.c`, `simulator/atalaia_sim/eu868.py`) and used everywhere a channel enters: the controller's configuration and API, the modem's CONFIGURE, SET_CHANNEL and MEASURE, the join payload (both codecs; new invalid vectors in `protocol/vectors/join.json`, and two valid vectors moved from 869.65 and 870.0 MHz to the highest legal centres), the radio HAL's `set_channel()` on boxes and modems, and the simulator's radio model.

4. **The limits follow the channel.** Boxes and the USB modem take the duty-cycle budget and the TX power from the sub-band of the channel in use, not from fixed g2 values: 10% and 500 mW ERP on g2, 1% (0.1% on g1) and 25 mW ERP elsewhere, with the conducted power reduced by the front-end module's gain and the antenna gain (decision C2). Airtime is the LoRa time on air for SF7/125 kHz, tracked per sub-band over a sliding hour, so moving to another channel does not reset what was spent in a sub-band. A packet whose time on air does not fit in what is left is not sent (TX_ACK `duty_cycle`). The simulator's radio model follows the same rules. The regulations also allow listen-before-talk with adaptive frequency agility instead of a duty-cycle limit; Skirmesh-RF does not use it *as that alternative* (Amendment 14 adds listen-before-talk for collision avoidance only: the duty-cycle limit stays).

5. **Measuring does not transmit.** The noise scan uses a new USB modem command, MEASURE, which listens on a channel for a given dwell and reports instantaneous RSSI statistics and LoRa channel-activity detections (`protocol/usb-modem.md`). It never puts anything on air, and the modem refuses it while a game is configured.

6. **Sync word.** The SX1262 is set to the private-network LoRa sync word, register value 0x1424 (0x12 in SX127x terms), as the phase 2 radio settings intended; the first firmware wrote 0x3444, LoRaWAN's public sync word, by mistake. All Skirmesh-RF devices must use the same value.

**Note on the sub-band labels.** The labels g, g1, g2 and g3 in section 8 are this project's own. ERC Recommendation 70-03 now calls these bands h1.5, h1.6, h1.7 and h1.9 (Annex 1); its older editions lettered them g1 to g4, so 869.4-869.65 MHz was "g3" there, and LoRa documents that follow the older lettering call it g3. The code keeps the project's labels; user-facing text gives the frequencies.

**Sources** (all checked on 2026-10-18):

A field next to a LoRaWAN gateway or a Meshtastic mesh had no way to see that, or to move.

## Amendment 5 (2026-10-19, proposed): Mode commands (CMD opcode 8)

**Status:** proposed with the Medic Kit (decision MK11); for review.

CMD opcode **8, `mode`**: a command for the node's mode script. Its `params` (key 2) must hold `name`, 1-24 bytes of `a-z`, `0-9` and `_` starting with a letter, and may hold the command's own parameters; the whole compact JSON form stays within the 127 bytes a box takes, as for every CMD. A node gives its script the input event `cmd.mode` with the params as its data (the name included) and nothing else: the opcode changes no game state on the node. It comes from:

- the GM, through `POST /api/v1/nodes/{id}/cmd` with `{"cmd": "mode", "params": {"name": ...}}`: the controller sends only names that the game's manifests declare under `commands` for the node's role (the Medic Kit's `refill`);
- a mode's `field.lua`, through `field.send(node, "mode", {name = ..., ...})` (the Medic Kit's `heals`, a player's count of heals at every kit).

Over Wi-Fi ([protocol/prop-link.md](../../protocol/prop-link.md)) the command is a `cmd` message with `cmd: "mode"` and `opcode: 8`. A box or prop from before this amendment logs the opcode as unknown and ignores it, so a game whose modes do not use mode commands is unaffected. The CMD payload's encoding is unchanged; `protocol/vectors/cmd.json` gains a vector with opcode 8.

**Reason:** opcodes 0-7 are taken by the lifecycle and the GM's built-in commands, and a mode had no way to hear from the GM or from its controller script beyond `set_owner` and `message`, which mean something else to every box (`message` is also shown as the organisers' word). One generic opcode with a named command keeps new modes from needing new opcodes.

## Amendment 6 (2026-10-21, proposed): Firmware updates (CMD opcode 9)

**Status:** proposed with over-the-air firmware updates for the Field Box (decisions FU3-1 onwards); for review.

CMD opcode **9, `update`**: the controller offers a box a firmware release. Its `params` (key 2) hold `id` (16 lower-case hex digits: the start of the image's SHA-256) and `version` (the release's version), and its `dest` (key 3) is always one box; the compact JSON form stays within the 127 bytes a box takes. Nothing of the image travels over LoRa: the box fetches the signed release text and the image over the field's Wi-Fi, by HTTPS pinned to the field CA of its join payload (Amendment 4's keys 13 and 14), and checks the Ed25519 signature with the release keys built into its firmware before it installs anything ([protocol/firmware-update.md](../../protocol/firmware-update.md)).

- The controller sends it only at a GM's request (`POST /api/v1/firmware/{id}/install`), only while the live game has not started, and only to boxes whose HELLO says the release's platform, a box's tier and a lower version; a mode's `field.lua` cannot send it.
- A box refuses it while a game is played (running or paused), and stops a download when a game starts.
- A box or prop from before this amendment logs the opcode as unknown and ignores it. Android props (tier proxy) are never sent it. The CMD payload's encoding is unchanged; `protocol/vectors/cmd.json` gains a vector with opcode 9.

**Reason:** a box hears the controller over LoRa during and between games, but has no Wi-Fi link to it until it needs one; a short command over the radio wakes the update, and everything that matters for safety (the signature, the version, the image's own descriptors, the hash) is checked by the box over the faster link.

## Amendment 7 (2026-10-21, proposed): Field frames, and invites over LoRa

**Status:** proposed with re-inviting boxes between games and the start guard (decisions RJ-1 to RJ-15); for review. The maintainer decided on 2026-10-21 to invite boxes over the radio with a key derived from the field join key, accepting the trade-off below (RJ-2).

**Supersedes:** in section 9 and Amendment 2, that the join payload is "never sent over LoRa" (join.md); it may now travel inside an INVITE, sealed. Section 4 gains message type 9 and HELLO key 10.

**Change:**

1. **Message type 9, `FIELD`**: a frame outside any game, `game_id` 0 (game ids are 1-65534), `source` 0, `seq` 0, `hop_limit` 0, never relayed. After the 9-byte header comes a 13-byte nonce in the clear, then a CBOR body of at most 187 bytes encrypted with AES-128-CCM (8-byte MIC, AAD the header without `hop_limit` as in section 3), so a frame is at most 217 bytes, as any packet. The key is HKDF-SHA256 (RFC 5869) of the 32-byte field join key with no salt and the info `atalaia field frame v1`, 16 bytes. The nonce never comes from a random number generator: `HMAC-SHA256(K_n, sender id)[0..7] | boot (3 bytes) | ctr (2 bytes)`, with `K_n` = HKDF-SHA256 of the join key with the info `atalaia field nonce v1` (32 bytes), the sender id a box's device id (its boot count persisted in NVS before the first frame of every run, as section 3's epoch, and raised again when the frame count would wrap) or a controller's sender id, fresh from the CSPRNG at every start and never stored, so a restored backup or a copied database cannot roll it back. Section 3's game epochs are untouched.
2. **Three bodies**, kind first: ANNOUNCE (a free box: its device id, a fresh token, its name, tier, last game and role, battery; or the answer to an invite: its id and the result), DISCOVER (a controller asks the free boxes to announce now), INVITE (to one box's device id with its current token: a random invite id and one of 1-3 parts of a join payload, 153 bytes each at most). The field tables, the decoders' rules, the box's and the controller's behaviour, timings and limits are in [protocol/field-frames.md](../../protocol/field-frames.md); shared vectors in `protocol/vectors/field_frame.json` (RFC 5869's own cases among them), checked by C and Python.
3. **HELLO key 10, `device_id`** (bytes, exactly 8, optional): the box's stable device id, random, made once and kept in NVS. A HELLO without it is as before; older decoders skip it (section 4's rule for unknown keys), and the app's codec reads it.
4. **A box accepts an invite** only while it has no game or its game is over, for its own device id and its current or previous token (it changes the token every 10 minutes and at every start, and drops it whenever it answers an invite, joins a game in any way or its game ends, so an invite recorded and played back never works), for a game it has not played to its end; the join payload then goes through every check of a card (its HMAC with the join key included). It answers with an ANNOUNCE carrying the invite's id and the result; its HELLO in the game confirms.
5. **The USB modem** carries field frames as they are, with or without a game configured, and never holds the field key: FIELD_TX (0x09), FIELD_RX (0x0A), FIELD_ACK (0x0B) frames and TX status 8 `busy`, IDENT `"field": true` ([protocol/usb-modem.md](../../protocol/usb-modem.md)).
6. **Duty cycle**: a free box's periodic announcements take at most 2 % of its sub-band's budget, never more than once a minute (about every 72 s on 869.4-869.65 MHz); invites are paced by their time on air and tried three times at most. The numbers are in field-frames.md.

**Security trade-off (accepted by the maintainer):** anyone who holds the field join key and records the radio can open the invites and read the game keys of every game invited that way. A card or a QR code already exposes one game's key to whoever reads it; the invites make the join key a field secret on which every such game's confidentiality rests. It stays only on the controllers and in the boxes' encrypted NVS, and is changed everywhere if a box or a controller is lost (SECURITY.md).

**Compatibility:** the version bits do not change. A box or a modem from before this amendment drops type 9 (another game's id); its HELLO has no key 10, so it is not listed as a previous game's box, and it joins by card as before. A controller from before ignores FIELD_RX frames (an unknown frame type is logged).

**Reason:** on the first field test with real boxes (2026-10-21) every game needed every box joined again by card, QR code or serial line, and a GM could start a game no box had joined. Field frames let the controller find the free boxes and bring them into the next game from the console; the start guard (controller side, no wire change) refuses a start while a role has no joined node unless the GM confirms.

**Addendum (2026-10-22, proposed): GAME_OVER, kind 4** (decisions OT-7, OT-13 to OT-16; the maintainer's decision OT-7). A fourth body, controller to boxes: `{1: 4, 4: game_id (uint, 1-65534), 5: key_tag (bytes, 8)}`, sealed like any field frame. `key_tag` is the game key's tag in the epoch store, the first 8 bytes of `HMAC-SHA256(game_key, "atalaia epoch tag")` (vectors `protocol/vectors/epoch_tag.json`), which a controller keeps beside the game, not secret, so it can still name the game after a restart without its key. A box in a game (joined or playing) whose id and key tag both match ends it exactly as on CMD end; anything else changes nothing. It carries no time or counter: a game's end is a fact that stays true, so a GAME_OVER played back later can only end that same game, which a box no longer joins (played to its end, BN-19), and a later game with the same id has another key, so another tag. A controller sends it three times, 4 s apart (about 0.28 s of air in all), on the game's channel, after every game it ran ends (besides CMD end) and as the only way when it restarted without the key; a standby controller never sends it. Kinds 5-7 stay unused; type 10 (Amendment 8) is unchanged. **Compatibility:** a box from before refuses kind 4 (unknown kind) and stays in its game as before; a modem passes it on its shape alone. Fields in [protocol/field-frames.md](../../protocol/field-frames.md); vectors in `protocol/vectors/field_frame.json` (`game_over`, `game_over_last_game_id`, seven bodies to refuse).

## Amendment 8 (2026-10-21, proposed): Pair frames, adopting a box by its code

**Status:** proposed with the pairing code over the radio, the third way to adopt a box (decisions AD-1, accepted by the maintainer, and AD-15 to AD-27); for review.

**Change:**

1. **Message type 10, `PAIR`**: a frame outside any game, with Amendment 7's header rules (`game_id` 0, `source` 0, `seq` 0, `hop_limit` 0, never relayed) but **not encrypted** (`version_flags` 0x28): the box has no key yet. After the header comes a CBOR body of at most 200 bytes (so 10-209 bytes in all), the kind first: OFFER (an unadopted box showing a code: a random pair id, its name, tier), START (a controller: the pair id, a 16-byte sid, CPace's Ya), REPLY (the box: Yb and its key confirmation), KEY (the controller: its confirmation, a 13-byte nonce and the field join key and name sealed with AES-128-CCM), DONE (the box: its adoption result and the fingerprint of the key it holds, authenticated). Tables and rules in [protocol/adoption.md](../../protocol/adoption.md) section 7; shared vectors in `protocol/vectors/pairing.json`.
2. **The security is CPace** (draft-irtf-cfrg-cpace-14, `CPACE-X25519-SHA512`), run with the 6-digit code the box shows as its password, `CI` = `lv_cat("atalaia pair v1", pair id)`. From its ISK, HKDF-SHA256 (RFC 5869, salt the sid) gives the two confirmation keys, the AES-128-CCM key and the key of KEY's nonce pseudonym; the nonce follows Amendment 7's rule with a sender id the controller draws for every run, boot 1, count 0. Only the controller encrypts. The draft's Appendix B.1 and B.1.10 vectors are checked by both implementations.
3. **The USB modem** carries type 10 as it carries type 9 (FIELD_TX, FIELD_RX), checking only its shape (version 1, not encrypted, game 0, 10-209 bytes), and says so in IDENT (`"pair": true`).
4. **Where**: an unadopted box listens on its default channel (869.525 MHz unless its build says otherwise). A box offers itself only while its code shows (5 minutes), at most every max(15 s, its time on air / 5 % of the sub-band's duty cycle); it answers a START once per sid (twice at most for a repeated one), burns its code after every failed run, waits a minute after three and stops after ten until it restarts.

**Compatibility:** the version bits do not change. A box or a modem from before drops type 10 (game id 0 and not a field frame); a controller from before ignores what it hears in FIELD_RX that does not open as a field frame. Pairing needs both the box's and the modem's new firmware.

**Reason:** the maintainer's decision (2026-10-21) to adopt boxes three ways: a field card, a USB cable and, for a box with a screen and nothing else at hand, its code over the radio, where an eavesdropper without the code learns nothing and an active attacker gets one guess per run.

## Amendment 9 (2026-10-22, proposed): The nonce epoch is per game key

**Status:** proposed after the bench boards (decisions BN-7 to BN-9); for review.

**Supersedes:** in section 3, "**epoch** (uint16, high half): incremented and persisted to NVS at boot" and, in section 10, "Read game key and epoch from encrypted NVS. Increment epoch; persist before first TX", where the one epoch counter served every game the node ever played; and, in section 3's "Receiver epoch discovery", the one-epoch trial for the packets a node sends first after a start.

**Change:**

1. **A node keeps an epoch per game key.** At every start in a game (a join, a rejoin after a reboot, a seq wrap as before) the node takes that key's last epoch + 1; a key it has no epoch for starts at **1**. The epoch is persisted before the first packet that uses it, as before. Nonces stay unique: AES-CCM needs a nonce used once per key, every game has a fresh random 16-byte key (ADR-P2-2), and within one key the epoch still only grows.
2. **The key is named by a tag, never stored for this.** The tag is the first 8 bytes of `HMAC-SHA256(game_key, "atalaia epoch tag")` (vectors: `protocol/vectors/epoch_tag.json`). The same key always gives the same tag; the tag tells nothing about the key (HMAC is a PRF keyed by it, and the label keeps it apart from any other use of the key). Two different keys share a tag with probability 2^-64; if they ever did, the second would go on above the first's epoch: never a reused nonce, at worst a node not heard in that game.
3. **Storage.** The Field Box keeps the epochs of its last 16 game keys and the tags alone of the 48 before them (*retired*) in one NVS blob (`radio/epochs`: version 2, the two counts, a zero byte, 10-byte records of tag and big-endian epoch, the most recent first, then the retired 8-byte tags; version 1, of the first builds, had 8 records and no retired tags and is still read), written whole by one `nvs_set_blob` and commit. After a power cut the blob is the old one or the new one, never a mix, so a key's record never goes back and a new key never takes another key's epoch: a cut before the write leaves the old store and nothing was sent with the new epoch; a cut after it leaves an epoch that was never used. The controller does the same in its SQLite settings (`tx_epochs`, one row). An unreadable or malformed store stops the radio (`tx_blocked`), as an NVS read error did.
4. **Migration.** Firmware from before kept one `u16` `epoch`. It is read only while no per-key store exists, and only for the stored game the box resumes at boot (the key it belonged to): that game goes on above it, so a box updated in the middle of a game keeps working. Any other game starts at 1 and the old value is never read again. The controller's single `tx_epoch` is used the same way, only for the game it restores after a restart.
5. **Receivers search further for what a node sends first.** HELLO (and TIME, a controller's first packets after a restart) is tried up to 256 epochs above the source's last authenticated one (`ATALAIA_RESTART_EPOCH_WINDOW`), every other type up to the receiver's window (16 on the modem and the box; 1 in the original rule), and a lower epoch never. Once the HELLO authenticates, the source's epoch is known and the rest of its packets are heard. Replays stay refused: a recorded packet has an epoch at or below the one already seen. *(Review of 2026-10-22, decision BN-20:)* the normal window is always tried first, and the wide search runs at most once per source every 2 s and 20 times a minute in all (source and type are in the clear, so junk HELLOs could otherwise cost 257 decryptions each); a node's HELLO is resent every 3 s until acknowledged, so a genuine one is searched within a retry or two.
6. **A retired key does not transmit** (review, decision BN-19). Its epochs are no longer known, so starting it again could reuse a nonce: the box refuses the join (card, QR code, text or invite, before anything changes), as it refuses a game it played to its end (it remembers its last four). A floor (the highest epoch of a forgotten key, every new key starting above it) was considered and not chosen: every new key's epochs are above the floor, so each forgotten key raises it, and it becomes a lifetime counter again, out of the receivers' reach after some 240 games.
7. **One device per node id** (review, decision BN-18). Two devices on one (game key, node id) would use the same nonces with certainty. The controller never issues a join for a node id it already issued one for, or heard a box on, in the game (a replacement box gets a new node id), except to the same device invited again; and when two device ids (HELLO key 10) say HELLO on one node id it flags the node in the console ("two boxes share node N") so the GM takes one out and joins it again.
8. **A receiver's first epoch for a source is provisional** (review, decision BN-21). A receiver that has not heard a source (or whose table dropped it) could take a recorded old HELLO at a low epoch and then drop the source's real packets more than 16 above it. Until a packet authenticates in the normal window, the source's packets of any type may get the (budgeted) wide search; a source the controller names (SET_PEER_EPOCH) is trusted.

**Compatibility:** no wire change. A receiver from before meets a node in a new game at epoch 1, inside its window, so new nodes are heard by old receivers; the wider search for HELLO needs the new firmware on the receiver. An old node keeps its single counter and is still unheard after ~16 games until it is updated. The epoch of the first game after an update starts at 1, which is safe because that game's key is new to the node.

**Reason:** found on the bench (2026-10-22): a box that had booted or joined more than ~16 times since it was flashed was never heard in a new game (the modem counted 863 authentication failures for a box at epoch ~127 in a fresh game, while the box believed it had joined), and the controller's own single counter made it unheard by the boxes after ~16 games in the same way. A box in a crash loop (35 reboots in one game) jumped past the window within one game (decision BN-5).

**Left open:** a key older than 64 newer games is new to the box again, so its card tapped once more would start it at 1 (a game whose controller has long moved on). A card of a game played before the update, tapped after it, starts at 1 too: the old single counter cannot say which keys it covered (only the game resumed at the update takes it up). A box reflashed with its NVS erased forgets every key, so the same card tapped again reuses that game's nonces: re-join it with a new join. Two devices on one node id are flagged only when both send their device id (Field Boxes with a field join key do; an Android prop does not yet). The controller keeps its own epochs for its last 8 game keys only (it restores only its live game). A box that reboots more than 256 times in one game is still lost to that game.

## Amendment 12 (2026-10-23, proposed): Radio regions; AS923 as Taiwan uses it

**Status:** proposed with the Traditional Chinese page (decision P5K-12 and the maintainer's RF-AS923-1, 2026-10-23); decisions RF-AS923-2 to RF-AS923-12 in `docs/review/decisions-to-review.md`, several for the maintainer. Not checked on air yet.

**Change:**

1. **A region table.** Everything section 8 and Amendment 3 say about sub-bands, limits and the channel rule now belongs to a *region*, one row of a table kept once per language (`atalaia_region_info()` in `core/src/duty_cycle.c`, `simulator/atalaia_sim/regions.py`, `app/lib/protocol/radio_region.dart`): its LoRa spreading factor and bandwidth (the channel's width), its sub-bands with their power limit (and whether that limit is ERP, EIRP or conducted at the antenna port) and airtime budget, its default channel, the channels a GM can pick, and a dwell limit (none in either region today). Code asks the region; no frequency is special-cased. Two regions:

   | Region | Number | Band | LoRa | Power limit | Airtime | Default |
   |--------|--------|------|------|-------------|---------|---------|
   | `eu868` | 0 | section 8's four sub-bands, 868.0-870.0 MHz | SF7, 125 kHz | 25 mW or 500 mW ERP | 1%, 0.1% or 10% (law) | 869.525 MHz |
   | `as923-tw` | 1 | 920.0-925.0 MHz, one sub-band | SF9, 500 kHz | 0.5 W peak at the antenna port, less antenna gain above 6 dBi | 10% (this project's own) | 921.5 MHz |

2. **Why Taiwan is SF9 at 500 kHz.** Taiwan's NCC LP0002 (edition of 2020-07-01), 5.8, allows "other IoT devices" 920-925 MHz. The 1 W (indoors or a closed, access-controlled site) and 0.5 W (outdoors) limits of 5.8.1.2 apply only to frequency hopping (at least 10 channels, at most 0.4 s on each) or to digital modulation, whose 6 dB bandwidth must be at least 500 kHz with at most 8 dBm in any 3 kHz (5.8.1.5). Anything else falls under 5.8.2: 50 mV/m at 3 m (average), about -1 dBm EIRP, less than the Heltec V4's front-end module puts out at the SX1262's lowest setting. A single shared channel (Amendment 1) does not hop, so the region uses LoRa at 500 kHz; 0.5 W in 500 kHz is about 4.8 dBm per 3 kHz. At SF9 a 500 kHz symbol lasts 1.024 ms, as an SF7 symbol at 125 kHz does, so the preamble, CAD and timing are unchanged, a packet is shorter (a 47-byte packet: 77 ms instead of 92), and the sensitivity is within about 2 dB of SF7 at 125 kHz. LP0002 sets no duty cycle and no listen-before-talk for these devices; the 10% budget is kept so a game behaves as in Europe. The 6 dB bandwidth of LoRa at 500 kHz is to be measured by a certification lab (RF-AS923-3).

3. **The default channel and the candidates.** 921.5 MHz keeps clear of LoRaWAN AS923-1's two default channels, 923.2 and 923.4 MHz, which every AS923 device joins on (RP002-1.0.4 lists Taiwan under AS923-1), of the AS923-925 plan The Things Network uses in Taiwan (923.2-924.6 MHz), and of Meshtastic's TW default (LongFast, 923.875 MHz at 250 kHz). The candidates are 920.5 to 924.5 MHz in 500 kHz steps (nine), each whole channel inside 920-925 MHz with at least 250 kHz to spare; those that overlap the busy channels above are marked. Legal centres: 920.25-924.75 MHz.

4. **The power follows the region's kind of limit.** Conducted power = ERP limit + 2.15 dB - antenna gain - FEM gain (EU868, decision C2), EIRP limit - antenna - FEM, or (AS923-TW) the conducted limit - FEM - the antenna gain above 6 dBi. With the Kconfig defaults (14 dB FEM, 2 dBi) that is 13 dBm in AS923-TW, as on g2. A channel whose limit the SX1262 cannot keep even at -9 dBm is refused (before, the power was clamped to -9 dBm and could exceed the limit).

5. **Join key 18, `region`.** The join payload ([protocol/join.md](../../protocol/join.md)) gains an optional key **18**: the region's number, an unsigned integer from 1 (`as923-tw`); EU868 (0) is the key's absence, so an EU868 join is unchanged byte for byte, and a payload that writes 0, an unknown number or anything else is refused as a body error. The channel (key 5) must fit in that region's sub-bands at its bandwidth. Readers now skip keys 19-31. A reader from before skips key 18 and checks the channel against EU868, so it refuses a Taiwanese join too: no box ever transmits outside its band by misreading a join. Shared vectors: the `region` section of `protocol/vectors/join.json`.

6. **The firmware is built for one region.** Kconfig `ATALAIA_RADIO_REGION` (EU868 by default, or AS923-TW; `tools/docker_fw.py build|bench|modem|pod --region=as923-tw`) sets the region a Field Box, a USB modem or an I/O pod may use, its LoRa settings and its default channel. A box refuses an authentic join of another region before anything changes (its log says "another radio region's game"; a radio invite is answered `refused`); the modem and the pod refuse CONFIGURE, SET_CHANNEL and MEASURE on another region's channel (`bad_params`), and the modem's IDENT gains `"region"` (`protocol/usb-modem.md`; a modem without it is an EU868 build). The board (Heltec V4.3, 863-928 MHz) is the same; its antenna and its labelling are not, which is why the region is a build option and not a field setting a box would take over the air.

7. **The field's region.** The field controller keeps the region like the channel: `[radio] region` is the default until the GM picks one in the console (`PUT /api/v1/radio/region`, only with no live game and no scan); changing it moves the field to the region's default channel, unconfirmed, and forgets the last scan. `GET /api/v1/radio` names the region, the regions and the modem's (`region_mismatch` when they differ). Scans, random picks, the channel check and an unadopted box's pairing channel are the region's; every join of the field carries key 18; a standby controller refuses a game of another region.

**Compatibility:** EU868 fields, boxes, modems, joins and vectors are unchanged (key 18 absent; IDENT gains a key older controllers ignore). An EU868 box refuses a Taiwanese join, old or new firmware alike; a Taiwanese box needs this firmware. Mixing regions in one field is not possible by design.

## Amendment 13 (2026-10-26): Relay, ACK and retry rules for a field of 20-30 boxes

**Status:** built, from decision SL-16 of the maintainer (2026-10-26; decisions SL-7 to SL-24 in `docs/review/decisions-to-review.md`, the study in `docs/review/relay-study-results.md`). The core, the box's field link and both controllers carry it; not yet confirmed on air (SL-18 says what a field test should measure). The draft it came from, `docs/rfcs/0000-relay-ack-and-retry-rules.md`, is marked superseded by this text.

**Supersedes:** in section 5, step 4's rebroadcast (every authenticated frame once, after 10-50 ms seeded by source and sequence number) and the 4 relay slots; in section 8, the sentence "the packet is queued for retry" (corrected in place above: the packet is refused); and the box's resend of an unacknowledged EVENT or HELLO every 3 s (ADR-P2-3's `ACK_RETRY_MS`). Section 4's ACK message, the header, every encoding, the nonce, the dedupe key, `max_hops`, the channel, the regions and the budgets are unchanged.

**Change:**

1. **The controller skips a hole in a box's sequence** (decision SL-8, built the same day in `AckTracker`, Python and Dart): every sequence number more than 128 below the highest one received from a (node, epoch) counts as received, so `ack_seq` is never more than 129 behind the box's newest packet and its bitmap always reaches it. Before this, one packet lost for good (a STATE; an EVENT's resend takes a new number) left a hole that closed the box's ACKs for good 256 packets later (about an hour). The bound must stay above `FIELD_LINK_OUTBOX` plus the packets a box sends in one ACK round trip. No change on the box or the wire.
2. **Relaying** (every box; `atalaia_relay_*` in `core/src/flood.c`, called by `field_link.c`). After the checks and the clamp of section 5, a frame that has `hop_limit` left is one of three kinds:
   - **A frame that asks for an ACK** (header `ack_req`: an EVENT or HELLO). The relay waits a random **350-700 ms**. If the controller's ACK for that (source, seq) is heard first (`ack_node` is the source and `ack_seq` or the bitmap covers the seq), the relay is cancelled. Otherwise it goes out, and the source is *on this box's path* for 30 s.
   - **The controller's ACK** (type 3) is relayed only for an `ack_node` that is on the box's path (a box none of whose frames this box relayed has nothing to be delivered here), and then like the next kind.
   - **Everything else** (STATE, TIME, CMD, CLAIM, an EVENT that asks for no ACK, and an ACK on the path) is relayed with probability **min(1, 3 / n)** after a uniform random **20-600 ms**; `n` is the number of different boxes (sources other than the controller) heard in the last 600 s, at least 1, counted from the frames the box accepts anyway. Up to three neighbours it always relays; `n` is local, so a box at the end of a field relays everything.
   - The relay table has **8 slots** (was 4); a frame that finds none is dropped. The dedupe table stays at 64 entries and 30 s. `hop_limit`, the clamp, "never relay your own frame" and "FIELD and PAIR frames are not relayed" are unchanged. A box also keeps the controller's ACK for *itself* out of the relay (it is never on its own path).
   - **The random numbers come from the box's own entropy** (the shell's `random` source, the one for the device id and timing spread; never a nonce): a delay is `min + r mod (max - min + 1)`, the probability a draw `r mod n < 3`. They are no longer a function of the frame (`atalaia_flood_jitter_ms`, kept for its tests, is not called): a function of the frame cannot give two boxes different delays, which was the point.
3. **Resends back off.** An unacknowledged EVENT or HELLO is sent again after **3, 6, 12, 24 s and then every 30 s**, each gap times a random 0.75-1.25 (`atalaia_retry_gap_ms`). Normal priority still gives up after 10 resends and critical resends until acknowledged; a resend is a new packet (new `seq`) as before.
4. **Not built: a STATE period that grows with the field** (the draft's optional join key 19 `boxes`). The maintainer's answer to SL-5 (15 s) stands; the model says rules 1-3 hold 20-30 boxes at about 2.6-2.9 % airtime without it (SL-15), and key 19 is not defined here.

**Compatibility:** no change to the packet or to any message. A box from before relays more than a box with these rules (as today) and resends every 3 s; a mixed field is safe and gains in proportion to the boxes that have the rules. The controller's rule (1) works with every box. A box with these rules adds up to 0.7 s per hop to an EVENT or HELLO that the controller did not hear directly. The reach is unchanged: `hop_limit` 2 reaches three hops, so a field longer than about nineteen boxes in a line is not served by any relay rule (`max_hops` 3 in the join, or a second controller; SL-9).

**Reason:** the relay study (`simulator/atalaia_sim/relay_study.py`, decisions SL-7 to SL-20): with the flood of section 5, 20-30 boxes spent 8-12 % of every box's airtime (the budget is 10 %), lost most of the controller's ACKs to their own relays and stopped acknowledging after an hour; with these rules every box stays at about 2.6-2.9 % airtime, no frame is refused, and 94-100 % of captures are acknowledged in a mesh and in CQB (a long field of 30 boxes: 56 %, which no relay rule can fix). The model's numbers and the numbers of the same harness run on the code that was built are in the study's results, and agree within a point or two.

## Amendment 14 (2026-10-26): Listen before talk, to avoid collisions

**Status:** built, from decision SL-25 of the maintainer (2026-10-26; decisions SL-25 to SL-37 in `docs/review/decisions-to-review.md`, the numbers in section 13 of `docs/review/relay-study-results.md`). The core, the radio task of the Field Box, the USB modem and the I/O pod carry it; the bench gate for its busy test passed on EU868 (section 12 of the results); not yet confirmed in a field (`docs/runbooks/radio-field-test.md` says how to compare a field with it on and off).

**Supersedes:** the sentence of Amendment 3, item 4, and the note in section 8 that Skirmesh-RF does not use listen-before-talk. Section 8's duty-cycle limits, the relay and retry rules of Amendment 13, every message, the header, the nonce, the dedupe key and the channels are unchanged.

**Change:**

1. **Before a frame goes on air the box asks whether the channel is busy.** The radio's busy test is the receiver's first: while the radio is in receive, a *preamble detected* or *header valid* flag means a frame is being received (the whole frame, not only its preamble: a CAD alone is blind to about 85 % of a frame's life) and the answer is "busy" with no CAD, because a CAD would take the radio out of receive and lose the frame it is receiving; a frame that has just ended is not busy. Only if nothing is flagged does the radio run **one CAD** (channel activity detection) and go back to receive. A radio with no such test, or whose test fails, is taken to be free.
2. **A busy channel holds the frame.** The frame stays the next to go (the queue behind it keeps its order), the box goes on receiving, and the radio is asked again after a random **20-200 ms** (uniform, from the box's own entropy as Amendment 13's delays are: `atalaia_lbt_*`, `core/src/lbt.c`). After **8 busy answers in a row** the frame is **sent anyway**, without another look at the channel (the model of the study did the same; a dropped frame is worse than a collision, and an EVENT or HELLO has its own resends). The count starts again for the next frame.
3. **The CAD's settings are the region's** (the core's region table, `atalaia_region_info()->cad`): 2 symbols, detection minimum 10, detection peak **22 at SF7/125 kHz (EU868)** and **29 at SF9/500 kHz (AS923-TW)**. Semtech's application note AN1200.48 gives the peaks for 125 kHz; the EU868 value passed the bench gate (2026-10-26). For AS923-TW, Semtech's 23 gave 17.8 % false busy with the same modulation on 868.3 MHz, and 29 gave 0.5 % with frames still detected (2026-10-26, decision SL-38); it stays **unproven** until the gate has run on an AS923-TW image.
4. **The duty-cycle budget is unchanged.** A CAD is not time on air and records nothing; the limit of section 8 is checked and spent at the real send, after the wait, as before (a frame the budget refuses after waiting is refused with the same result; a box whose budget is already empty does not listen, wait or CAD for a frame it cannot send). This is listen-before-talk **for collision avoidance only**, not the regulation's alternative to the duty-cycle limit: the 10 % budget of the game's sub-band stays.
5. **A build setting, on by default** (`CONFIG_ATALAIA_LBT`; every image that transmits). With it off a frame goes at the first turn of the radio task, as before. There is no field-level switch: a controller cannot turn it on or off without a new join key, which this amendment does not define (decision SL-33).
6. **The radio task's turn is shortened with it**: with listen before talk on, the task waits at most 10 ms for a frame and then one tick (it was 50 ms and then 10 ms), so a wait of 20-200 ms is honoured to about 10 ms rather than 60.
7. **Counters** (decision SL-35): the CADs run, the frames that waited for a busy channel, and the frames sent after the eighth busy answer, in `field_link_stats_t` and the `radio_stats` line (`lbt_cads`, `lbt_deferrals`, `lbt_gave_up`).

**Compatibility:** nothing on the wire changes. A box with listen before talk yields to a box without it and not the other way round, so a mixed field is safe and gains in proportion to the boxes that listen. A frame may leave up to 8 x (200 ms + a CAD), about 1.7 s, after the radio task took it from the queue: an EVENT's or HELLO's resend schedule (Amendment 13: 3 s first) and the box's STATE period (15 s) are well above that, and a STATE or a relay is already not time-critical to that degree; the controller's ACK, which a box waits for 3 s, is the one frame whose delay adds to a round trip and it too waits at most that long.

**Reason:** the relay study (section 11 of the results, decision SL-25): with Amendment 13's rules the flood is controlled and what is left is collisions between boxes that hear each other; a CAD before the frame removes most of them. In a mesh of 20 boxes on EU868 the controller hears 89 % of the boxes' STATEs instead of 65 %, a capture's latency has a p95 of 1.4 s instead of 3.4 s, and the cost is about 0.3 point of airtime per box (2.9 % against 2.6 %) and about 1 050 CADs an hour. On a field that cannot hear itself (hidden nodes) it helps little. The numbers on the hardware's own timing (an 8 ms CAD, the receiver's flags costing none) are section 13 of the results.

## Amendment 15 (2026-10-26): The controller leaves a gap between its own frames

**Status:** built and **off by default** (`controller_pace_ms` 0), from decision SL-13 of the maintainer (accepted 2026-10-26; the pacing half of its follow-up; decision SL-39 records the build; the maintainer decides the default after the 20-box field test, `docs/runbooks/radio-field-test.md`; the numbers are table 7 of `docs/review/relay-study-results.md`). The Pi's controller (`controller/atalaia_controller/engine.py`, `ModemTransport`) and the phone's (`app/lib/controller/controller_radio.dart`, `RadioTransport`) carry it; the shared cases are "TX pacing" in `protocol/vectors/controller_api.json`.

**Supersedes:** nothing on the wire. It adds to section 5's transmit rules a rule for the controller alone; the boxes' rules (Amendments 13 and 14) are unchanged.

**Change:**

1. **One queue for every frame the controller puts on the radio in a game**: ACKs, TIME beacons and CMDs (setup bursts, a mode's `field.send`, the GM's commands, START/PAUSE/RESUME/END), first in first out, with no priorities (the relay study's `H_paced`). With pacing on, a frame leaves when the one before it has been **on the air for 800 ms** (`[radio] controller_pace_ms`, **0 by default: no queue, as before**; 800 is the study's value and the one to try in the field test; the phone's `ControllerConfig.controllerPaceMs`): the modem's TX_ACK says when a frame's air time ended, and a controller that has not heard it counts 800 ms from the hand-over to the modem. An idle queue sends the next frame at once.
2. **The queue holds 8 frames**, the length of the modem's own (`RADIO_TX_QUEUE_LEN`). A frame sent to a full queue is dropped and counted (`tx_queue.dropped` in `GET /api/v1/controller`); nothing in the study's runs came near it (no frame was dropped in the 45 `H_paced` runs of table 7, 90 minutes each).
3. **A frame's seq is taken when it is queued**, in queue order, so the order on the air is the order of the seqs and the modem's rule (never an (epoch, seq) at or below the last sent) holds; a dropped frame takes none. A seq wrap flushes the queue under the old epoch before the new one is announced to the modem.
4. **When the game ends the stale frames are dropped and the end goes at once**: the waiting CMDs and TIMEs are dropped (the game is over; they are counted with the dropped ones) but **the waiting ACKs stay** (a box leaves a finished game once its last events are acknowledged, and waits 60 s otherwise); then the end's CMD and TIME are queued and everything is handed to the modem together, in order, before the modem is told to forget the key. This is what the controller did before for the end's two frames.
5. **Below the queue nothing changes**: the modem's listen-before-talk (Amendment 14) and its duty-cycle guard (a refusal comes back as `duty_cycle` in a TX_ACK and is counted in `tx_status`) work on each frame as it arrives; the frames outside a game (invites, GAME_OVER, pairing) and the Wi-Fi props' copies of TIME and CMDs do not go through the queue.

**Compatibility:** nothing on the wire changes and no box needs updating; a controller with the rule works with every box, and with the default of 0 behaves as before. A CMD that used to go with the START's TIME within a few milliseconds now follows it, or is followed, by up to 0.8 s per frame ahead of it (a scenario's four setup CMDs: about 2.4 s after the first); an ACK that waits behind them is later by the same, well inside the 3 s a box waits for it before its first resend. A frame queued when the controller crashes or restarts is lost (the box's resend, 3 s later, heals an ACK; a CMD stays one shot).

**Reason:** the controller's frames were the one flood nobody spaced: a burst of four setup CMDs lands its own relays on the next, and the study measured (table 7, five seeds) that a 0.8 s gap adds 0 to 22 points to the CMDs that reach their box, on top of Amendment 13's rules. It does not make the CMD reliable (**still one shot, no ACK, no resend on the air**: 0-78 % reach their box; that needs a box ACK, a wire change, or the scenario's own re-send, and stays open).

## Amendment 16 (2026-10-28): A box says it took a scenario's setup command

**Status:** built (decision PKB-3 of the maintainer's 2026-10-28 choice to build the box ACK that Amendment 15 and decisions SL-13 and SL-39 left open). The objectives package (`modes/objectives/node.lua`, built into the Field Box and the app) says it; the scenario runtime (`core/scenario/runtime.lua`, and the hand-written example's `field.lua`) hears it; the shared case is the event vector "A box confirms a capture setup" in `protocol/vectors/events.yaml`.

**Supersedes:** nothing. It adds one standard event and a rule to the scenario's script; the radio, the CMD (opcode 8) and the box's ACK and retry rules are unchanged.

**Change:**

1. **A new standard event, `node.setup_applied`** (id 56, normal priority, data `kind`, key 11 as for the other events that carry it: the setup's `kind`). A box running the objectives package sends it each time it takes the mode command `setup`, once the setup is in force. As a normal-priority event it is what the link already does with one: an ACK is asked for and the packet is repeated until the controller's ACK arrives (up to ten tries). No new frame, opcode or ACK: the CMD stays one shot on the air, and its acknowledgement is an event going the other way.

**Compatibility:** an older box ignores nothing and breaks nothing (it never sends the event); an older controller logs an event of an id it does not know as any other. A new box with an older scenario or controller sends one extra normal event per setup. The event shows in the GM's feed and the staff's event pages (it names a kind, never a code).

**Reason:** the model measured (decision SL-13, table 7) that 0-78 % of a scenario's setup CMDs reach their box and, with the scenario's repeats and the box's confirmation in the same model (`python -m atalaia_sim.relay_report --setup-study`; `docs/phase-2-field-network/STATUS.md`), every setup reaches its box in the meshes and the CQB layout up to 20 boxes (89-100 % at 30), in the long field at 10 boxes, and 56 % and 11 % in the long field of 20 and 30 (one shot: 0-78 %), at 1.4-2.8 CMD frames per setup in the cases that work; the repeats without the confirmation reach about the same fraction and always cost six.

## Amendment 18 (2026-10-28): A box reports the points its teams lost to penalties

**Status:** built (decision BSC-1 of the maintainer's 2026-10-28 choice to close decision E6: a penalty was logged but never subtracted from a total). Core codec (`atalaia_state_msg_t.lost`), the Field Box's STATE (`firmware/esp32/main/box_game.c`), both controllers (`simulator/atalaia_sim/field_controller.py` for the Pi, `app/lib/controller/field_controller.dart` for the phone), the Dart codec (`app/lib/radio/rf_codec.dart`); the shared cases are `protocol/vectors/state.json` (`state_with_lost`, `state_full_with_lost`, `state_lost_not_a_map`) and the controller contract case "box penalties" in `protocol/vectors/controller_api.json`.

**Supersedes:** the sentence of decision E6 that said a box's STATE carries gains only and that a per-team "lost" counter "needs an RFC". Nothing else: `counters` (key 4) is still the points **gained**, never decreasing.

**Change:**

1. **STATE gets one optional key, 9 `lost`**: a CBOR map from team id (uint8) to the points that team lost to penalties on this node (uint32), the node's `atalaia_score_t.lost[team]`, the sum of its `score.add(team, -n)` calls. It is the mirror of `counters`: it only ever grows, so a controller merges it by the **maximum** per (node, team), a late or repeated STATE changes nothing and a lost STATE is repaired by the next. The score's own saturating add (`UINT32_MAX`) holds for both.
2. **Sent only when a team lost something**, and then only for the teams that did. A game with no penalty sends byte for byte the STATE of before this amendment (no airtime change); a penalty adds 2 bytes of key and map header plus 2-6 per team (a Kill Confirmed box that has penalised one team: 6 bytes, under 1 % of a 52-byte frame's time on air).
3. **A controller's total per team** is `sum over nodes of gained (key 4) - sum over nodes of lost (key 9) + the GM's adjustments (score.delta events the controller itself logged) + the field script's own points`. Boxes' own `score.delta` events (the penalty's explicit event for the GM's feed) are **not** added again by the controller: the lost counter is the number, the event is the news. (The site server already adds every `score.delta` event of a game to its counters' sum, protocol/sync.md; it therefore already subtracted a box's penalty, and after this amendment the controller's live total and the server's agree.)
4. **The controller keeps it with the node** (`lost` next to `score` in the node's stored info, in `GET /api/v1/nodes`, the `node` stream message and after a restart); the totals, the `score` stream message, MQTT's `.../score`, the console, the scoreboards and the app show the net figure. A box's own screen was never wrong: `score.get(team)` in a mode's script is gained minus lost on that node, so Kill Confirmed's station already showed a team's points net of its penalty; what was missing was the controller (and everything fed by it) learning the penalty.

**Compatibility:** the key is additive and optional. A box without it (an older firmware) is read as having lost nothing: its penalties stay as before (logged as `score.delta`, not subtracted live). An older controller built on the C codec or the Python decoder skips key 9 (unknown keys are skipped) and shows the totals it always showed. **An older phone controller (the Android app before this change) refuses a STATE with an unknown key** (`RfState.decode` rejects any key above 8), so with such an app as the controller a box that has penalised a team looks silent until the app is updated: update the app first on a field that plays Kill Confirmed or any mode that penalises. Relays and modems forward the ciphertext whole and need no change. The Android prop link (`protocol/prop-link.md`) does not carry the key yet: a phone playing a box that penalises is not subtracted live, as before.

**Reason:** decision E6 (2026-10-21) shipped gains only so the controller's merge by maximum works, and recorded the price: Kill Confirmed's penalty (the only built-in mode that uses one) lowered the station's own number and never the team's total. A second grow-only counter keeps the merge rule, costs nothing when unused, and needs no new frame, event or acknowledgement.

## Open questions

- Per-node session keys (HKDF-derived from the game key) would limit
  the blast radius of a compromised node. Deferred: the current
  per-game key is adequate for the "hard to cheat casually" threat
  model.
- The `tx_time_us` field in TIME beacons measures processing delay.
  Its usefulness for time-sync accuracy depends on how stable the
  delay is in practice; field testing will determine whether it
  improves the slew algorithm or just adds noise.
- Channel hopping currently uses a fixed round-robin. Adaptive channel
  selection based on RSSI or error rates is a future improvement.
  (Amendment 1 replaced hopping with one shared channel per game, and
  Amendment 3 adds a noise scan when the field's channel is chosen; moving
  a game to another channel while it runs is still open.)
- Amendment 13's values (350-700 ms, `c` = 3, 600 s, 128, 30 s) come from a model whose link
  budget and capture effect are assumptions; a field test with the counters the box already keeps
  (`field_link_stats_t`, now with `relay_skipped`, `relay_cancelled` and `relay_no_slot`)
  should confirm them (decision SL-18). Whether a box's last STATE (the one that ends the game)
  should ask for an ACK and be resent, and whether `max_hops` 3 should be the default above ten
  boxes, are open (SL-20, SL-9).
