# RFC 0001: Skirmesh-RF v1 wire format

- **Author(s):** The Atalaia contributors
- **Status:** Accepted (by the maintainer, 2026-10-17)
- **Discussion:** None yet (no other contributors at the time of acceptance).
  Future protocol changes follow the normal RFC process with a 2-week
  review period (spec section 13).

## Summary

This RFC defines the complete on-wire format for Skirmesh-RF v1
packets: the 9-byte header bit layout and byte order, the AES-128-CCM
security layer (key, nonce, AAD, MIC), CBOR payload schemas for all 8
message types, flood routing rules, duty-cycle and power limits for
EU868, and the join and rejoin-after-reboot flows.

The detailed rationale behind each decision is recorded in
[`docs/phase-2-field-network/ADR.md`](../phase-2-field-network/ADR.md)
(ADR-P2-1 through ADR-P2-15). This RFC is the normative wire-format
specification; the ADRs document why.

## Motivation

Phase 0 defined the EVENT payload (CBOR map with integer keys) and
left the rest for Phase 2: the header bit layout, the byte order of
multi-byte fields, the AES-CCM parameters, and the payloads of the
other 7 message types. Without a frozen wire format, no codec work can
begin, and no two implementations can interoperate.

On the field, the protocol must:

- fit in LoRa's tight airtime budget (EU868: 1% duty cycle on most
  channels);
- authenticate every packet so a player with an SDR cannot inject fake
  captures;
- survive reboots and radio partitions without losing events;
- keep game clocks synchronised within 250 ms across all nodes.

## Design

### 1. Packet structure

```
[ 9-byte header (cleartext, authenticated) ]
[ 0-200 byte ciphertext (encrypted CBOR payload) ]
[ 8-byte MIC (AES-CCM authentication tag) ]
```

Total maximum: 9 + 200 + 8 = 217 bytes, within LoRa's 255-byte limit
at all spreading factors.

### 2. Header (9 bytes)

```
Offset  Size  Field            Encoding
  0       1   version_flags    bit field (see below)
  1       2   game_id          uint16 big-endian
  3       2   source           uint16 big-endian
  5       2   seq              uint16 big-endian
  7       1   hop_limit        uint8 (default 2)
  8       1   type             uint8 (1-8)
```

All multi-byte fields are big-endian (network byte order).

#### version_flags byte

```
Bit   7   6   5   4   3   2   1   0
    [  version  ] [prio ] [ack] [enc] [rsv]
```

| Bits | Field | Width | Values |
|------|-------|-------|--------|
| 7-5 | `version` | 3 | Protocol version; v1 = 1. Version 0 is rejected as malformed. |
| 4-3 | `priority` | 2 | 0 = telemetry, 1 = normal, 2 = critical, 3 = reserved |
| 2 | `ack_req` | 1 | 1 = sender requests ACK from the controller |
| 1 | `encrypted` | 1 | 1 = AES-CCM encrypted. Always 1 on LoRa. |
| 0 | `reserved` | 1 | Must be 0 on send; ignored on receive. |

Examples: normal + ACK + encrypted = `0x2E`; critical, no ACK,
encrypted = `0x32`.

### 3. AES-CCM security

**Key:** AES-128 (16 bytes), generated by the controller with a CSPRNG
when a game is created. Distributed during join (NFC or QR); never
sent over LoRa.

**Nonce** (13 bytes):

```
Offset  Size  Field       Source
  0       2   game_id     from header (big-endian)
  2       2   source      from header (big-endian)
  4       4   nonce_ctr   (epoch << 16) | seq, big-endian
  8       5   zeros       0x00 * 5
```

`nonce_ctr` is a 32-bit monotonic counter composed of two halves:

- **epoch** (uint16, high half): incremented and persisted to NVS at
  boot and whenever `seq` wraps from 65535 to 0. If the NVS write
  fails, the node halts the radio and emits `nonce.nvs_fail`
  (critical). No per-packet NVS writes.
- **seq** (uint16, low half): the header sequence number, incremented
  per packet.

At epoch 65535 with seq 65535, the node has exhausted 2^32 nonces
under this game key. It refuses to start a new epoch and emits
`nonce.exhausted` (critical). A new game (new key) is required.

**Receiver epoch discovery:** receivers track the last authenticated
epoch per source. On a new packet:

1. Try auth_decrypt with the current epoch for that source.
2. On failure, try epoch + 1.
3. On success with epoch + 1, adopt it. Reset the replay window for
   that source.
4. On both failures, drop the packet.
5. Never accept a lower epoch.

HELLO and STATE messages also announce the epoch explicitly, allowing
receivers to resync after a longer gap.

**AAD** (8 bytes): header bytes 0-6 plus byte 8 (everything except
`hop_limit` at byte 7). `hop_limit` is excluded so relay nodes can
decrement it without invalidating the MIC.

**Relay clamp:** because `hop_limit` is unauthenticated, an attacker
could raise it to amplify flooding. Every relay node therefore clamps
the incoming `hop_limit` to the game's configured maximum (default 2)
before decrementing and rebroadcasting.

**MIC:** 8 bytes (64-bit tag). Forgery probability 2^-64.

**Encryption:** mandatory on LoRa (`encrypted` bit always 1). The
CBOR payload is encrypted. The header is cleartext (but
authenticated), so receivers can route and deduplicate before
decrypting.

### 4. Message payloads

All payloads are CBOR maps with integer keys. Keys 1-23 encode in
1 byte.

#### HELLO (type 1)

Sent after joining a game.

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `node_name` | text | yes | Human-readable, max 24 bytes |
| 2 | `platform` | uint8 | yes | 0=esp32, 1=esp32s3, 2=linux, 3=android |
| 3 | `fw_version` | text | yes | Firmware version string |
| 4 | `core_version` | text | yes | Core library version |
| 5 | `tier` | uint8 | yes | 0=full, 1=reduced, 2=proxy |
| 6 | `capabilities` | array[uint8] | yes | Capability type ids |
| 7 | `transports` | uint8 | yes | Bitmask: bit 0=lora, 1=wifi, 2=ble |
| 8 | `battery_pct` | uint8 | no | 0-100 |
| 9 | `epoch` | uint16 | yes | Current nonce epoch |

Typical size: 40-60 bytes.

#### EVENT (type 2)

Defined in `protocol/schema/events.yaml`. The payload is the event
envelope (keys 1-8) as already specified. No changes from Phase 0.

#### ACK (type 3)

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `ack_node` | uint16 | yes | Source node being acknowledged |
| 2 | `ack_seq` | uint16 | yes | Highest contiguous seq received |
| 3 | `ack_bitmap` | bytes | no | Selective ACK for gaps (up to 32 bytes = 256 seqs) |

Typical size: 6-38 bytes.

#### STATE (type 4)

Sent every 10-60 seconds (per field profile).

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `owner_team` | uint8 | yes | Current owner (0 = none) |
| 2 | `phase` | uint8 | yes | Mode-specific phase |
| 3 | `game_time_ms` | uint32 | yes | Node's local game time |
| 4 | `counters` | map[uint8->uint32] | yes | Per-team score counters |
| 5 | `rssi` | int8 | no | Last received signal strength |
| 6 | `battery_pct` | uint8 | no | 0-100 |
| 7 | `flags` | uint8 | no | Bit 0: running, bit 1: paused |
| 8 | `epoch` | uint16 | yes | Current nonce epoch |

Typical size: 20-40 bytes (2-team game).

#### CMD (type 5)

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `cmd` | uint8 | yes | Opcode (see table) |
| 2 | `params` | map | no | Command-specific |
| 3 | `dest` | uint16 | no | Destination node; absent = broadcast |

Opcodes: 0=start, 1=pause, 2=resume, 3=end, 4=set_owner,
5=message, 6=reset, 7=reboot.

#### TIME (type 6)

Controller heartbeat, every 30 s (10 s with failover).

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `game_time_ms` | uint32 | yes | Controller's game time |
| 2 | `game_state` | uint8 | yes | 0=waiting, 1=running, 2=paused, 3=ended |
| 3 | `duration_ms` | uint32 | yes | Total duration (0 = unlimited) |
| 4 | `wall_s` | uint32 | yes | Unix epoch seconds |
| 5 | `term` | uint32 | yes | Election term |
| 6 | `tx_time_us` | uint16 | no | Processing time before TX |

Typical size: 18-20 bytes.

#### CONFIG (type 7)

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `mode_id` | text | yes | e.g. "org.atalaia.domination" |
| 2 | `role` | text | yes | Role within the mode |
| 3 | `params` | text | yes | Preset parameters as JSON |
| 4 | `teams` | array[text] | yes | Team names in order |
| 5 | `game_seed` | uint32 | yes | Seed for deterministic rand() |

Typical size: 60-150 bytes.

#### CLAIM (type 8)

Controller election.

| Key | Field | Type | Req | Notes |
|-----|-------|------|-----|-------|
| 1 | `term` | uint32 | yes | Monotonically increasing |
| 2 | `priority` | uint16 | yes | Higher = better |
| 3 | `node_id` | uint16 | yes | Tiebreaker: lowest wins |
| 4 | `last_ack_seq` | map[uint16->uint16] | no | Per-node last ACK'd seq |

Typical size: 12-60 bytes.

### 5. Flood routing

Topology: star centred on the controller, extended by TTL-limited
flood.

1. On receiving a packet, check (source, seq) against the dedupe
   table. If seen, drop.
2. Record (source, seq) in the dedupe table (64 entries on ESP32,
   30 s expiry, LRU eviction; unlimited on the controller).
3. Process the packet.
4. If `hop_limit > 0`, clamp it to the game's configured maximum
   (default 2), decrement, and rebroadcast after a random jitter
   of 10-50 ms (seeded deterministically by source + seq).

The controller does not rebroadcast received packets. It originates
TIME and CMD on the 10% sub-band.

### 6. Time synchronisation

Target: +/-250 ms across all nodes.

On receiving a TIME beacon, a node:

1. Estimates one-way delay: known airtime (deterministic from packet
   size, SF, BW) + 5 ms processing overhead + `tx_time_us`.
2. Computes offset: `controller_time + delay - local_time`.
3. If |offset| < 5 ms: no correction.
4. If |offset| < 500 ms: linear slew at max 5%/s (spread over 10 s).
5. If |offset| >= 500 ms: step (game start, long partition).

TIME beacons use 869.525 MHz (g2 sub-band, 10% duty cycle).

### 7. Controller failover (CLAIM)

Detection: 3 missed TIME beacons (~30 s). Each controller-capable
node sends CLAIM with `term = last_seen_term + 1` and its priority
score. Highest term wins; highest priority breaks ties; lowest
node_id breaks further ties. 5 s election timeout. The winner sends
TIME with the new term. Any node seeing a higher term steps down.

Recovery: the new controller asks nodes to replay events from their
last ACK'd seq. Scores merge by maximum per counter (conflict-free).

Default: manual failover. Automatic CLAIM is tested and enabled per
field profile after field validation.

### 8. Duty-cycle and power (EU868)

| Sub-band | Frequency | Duty cycle | Airtime/hour |
|----------|-----------|------------|-------------|
| g | 868.0-868.6 MHz | 1% | 36,000 ms |
| g1 | 868.7-869.2 MHz | 0.1% | 3,600 ms |
| g2 | 869.4-869.65 MHz | 10% | 360,000 ms |
| g3 | 869.7-870.0 MHz | 1% | 36,000 ms |

Node TX hops across three g-band channels (868.1, 868.3, 868.5 MHz)
round-robin, with independent per-channel duty-cycle tracking.
Controller TIME and CMD use the g2 sub-band.

The radio HAL tracks airtime per sub-band with a 60-bucket sliding
1-hour window. If the budget is exhausted, `send()` returns
`DUTY_CYCLE_EXCEEDED` and the packet is queued for retry.

**Power cap with FEM (Heltec V4.3):** the board's front-end module
adds ~14 dB of gain. The SX1262 output power is set so the total ERP
stays within EU868 limits:

- g/g1/g3: SX1262 at 0 dBm -> ~14 dBm ERP (25 mW limit).
- g2: SX1262 at 13 dBm -> ~27 dBm ERP (500 mW limit).

The FEM gain is a Kconfig constant (`EU868_FEM_GAIN_DB`), verified
during field-test calibration with a power meter.

### 9. Join flow

Nodes join by tapping an NFC card or scanning a QR code (BLE deferred
to Phase 3). The join payload:

| Field | Size | Purpose |
|-------|------|---------|
| `game_id` | 2 | Which game |
| `game_key` | 16 | AES-128 key |
| `node_id` | 2 | Assigned short id |
| `team_count` | 1 | Number of teams |
| `team_names` | variable | NUL-separated |
| `mode_id` | variable | Mode identifier |
| `role` | variable | Role within the mode |
| `hmac` | 32 | HMAC-SHA256 with controller's long-term key |

NFC: written to an NTAG215/216 as an NDEF binary record. QR: the same
payload base64url-encoded, pushed to the node over Wi-Fi by the
controller.

### 10. Rejoin after reboot

The game key is stored in the ESP32-S3's encrypted NVS partition
(eFuse HMAC-derived key). On reboot:

1. Read game key and epoch from encrypted NVS.
2. Increment epoch; persist before first TX.
3. Replay unacknowledged events from the flash-backed event log
   (`/log/game.bin` on LittleFS).
4. Send HELLO with the new epoch.
5. Emit `node.rebooted` (critical).

No NFC re-tap is needed. The key is zeroed and deleted from NVS when
the game ends.

## Compatibility

This is the initial v1 definition. There is no previous version. The
3-bit version field allows 6 future revisions (v2-v7) before a layout
change. Older nodes never receive messages with a version they do not
understand (they drop them silently based on the version bits).

## Alternatives

### Nonce construction

**Considered: nonce = game_id + source + seq + 7 zeros.** Rejected
because a 16-bit seq wraps at 65535, and a reboot resets it. Both
cause nonce reuse under the same key, breaking AES-CCM confidentiality
and enabling forgery.

**Considered: per-packet NVS persist of a monotonic counter
(nonce_high_water + SKIP_GAP).** Rejected because per-packet flash
writes cause unnecessary wear, and receivers cannot reconstruct the
counter from the cleartext header without adding bytes to every
packet.

**Chosen: (epoch << 16) | seq.** Epoch is persisted only at boot and
seq wrap (two writes, not per-packet). Receivers reconstruct it via
AES-CCM trial (try current epoch, then epoch+1). No extra header bytes.

### AAD scope

**Considered: full 9-byte header as AAD.** Rejected because relay
nodes must decrement `hop_limit`, which would invalidate the MIC.
Re-encrypting on every relay adds CPU cost and code complexity.

**Chosen: 8-byte AAD (header minus hop_limit).** Relay nodes decrement
`hop_limit` freely; the relay clamp prevents amplification.

### Event log storage

**Considered: 128-entry DRAM ring buffer.** Rejected because events
are lost on brownout or battery pull, violating the "zero lost
captures" gate. `zone.captured` is normal priority, not critical, so
a "flush only critical" policy loses captures.

**Chosen: flash-backed append log on LittleFS.** Normal and critical
events flushed immediately; only telemetry buffered. Survives power
loss.

### Game key storage

**Considered: key in RAM only, zeroed on game end.** Rejected because
the spec requires a rebooted node to resume its game (countdown,
scores) without GM intervention. RAM-only keys require a new NFC tap
after every battery pull.

**Chosen: encrypted NVS (eFuse HMAC).** The key survives reboots.
An attacker who dumps flash cannot read it without the eFuse key.

### Controller radio

**Considered: SPI LoRa HAT on the Raspberry Pi with a C radio gateway
daemon.** Rejected because it requires spidev/libgpiod dependencies,
a separate C codebase for the Pi, and splits the radio code between
two platforms.

**Chosen: USB radio modem (same Heltec V4.3 board).** All radio,
AES-CCM, dedupe, and duty-cycle code runs on the modem's ESP32, shared
with the node firmware. The Pi needs only `pyserial`.

## Amendment 1 (2026-10-18): Single shared game channel

**Supersedes:** section 8 paragraph "Node TX hops across three g-band
channels..." and section 6 sentence "TIME beacons use 869.525 MHz."

**Change:** All game traffic (events, STATE, ACK, TIME, CMD) uses a
single shared channel per game, by default 869.525 MHz in the g2
sub-band (869.4-869.65 MHz, 10% duty cycle, 500 mW ERP).  The
channel is configurable per game via the CONFIG message.

**Reason:** With a single-radio half-duplex transceiver (SX1262), the
round-robin hopping scheme in section 8 left nodes listening on
different frequencies after their last TX, so they missed each other's
packets.  A single shared channel is the standard single-radio mesh
approach (Meshtastic's EU868 default uses the same frequency).

The g2 sub-band was chosen because:
- 10% duty cycle (360,000 ms/h) gives 10x the airtime of the g-band
  (36,000 ms/h), which is important for a 5-node game with TIME
  beacons, events, STATEs and ACKs.
- 500 mW ERP gives better range than the g-band's 25 mW.
- Neighbouring games are separated by choosing different channels
  within the sub-band or in other sub-bands.

**Duty-cycle tracking:** The firmware tracks the g2 10% budget per
device with a 60-bucket sliding one-hour window.

**Power:** The SX1262 conducted power for the g2 sub-band accounts
for the FEM gain (14 dB) and the antenna gain (2 dBi, Kconfig):
27 dBm ERP + 2.15 - 14 - 2 = 13.15 -> 13 dBm conducted.

**Channel validation:** The firmware validates the configured channel
against the EU868 sub-band table and refuses to transmit if the
channel is outside all sub-bands.

## Amendment 2 (2026-10-18): Join payload encoding

**Supersedes:** the field table of section 9 ("Join flow"), which lists
the fields but not how they are encoded or which key the HMAC uses.

**Change:** The join payload is a version byte (1), a CBOR map with
integer keys, and a 32-byte HMAC-SHA256 tag over the version byte and the
map, at most 448 bytes in all. Beyond section 9's fields the map carries
the controller's node id, the game channel, the relay clamp (`max_hops`,
which section 9's companion ADR-P2-6 says the join carries), the scripts'
seed, the preset parameters, and whether the payload is for a box or a
standby controller. Keys 13-31 are reserved for optional fields and
skipped by readers. The tag key is a 32-byte **field join key** shared by
the controllers and boxes of one field, not a key only the controller
holds: every reader must be able to check the tag. On NFC cards the
payload is one NDEF MIME record of type `application/vnd.atalaia.join`;
as text (QR codes, the serial console) it is `atalaia:join:` followed by
base64url without padding.

The full specification, with shared test vectors checked by the C and
Python codecs, is [protocol/join.md](../../protocol/join.md). Decisions E1
and E2 in `docs/review/decisions-to-review.md`.

**Reason:** Section 9 could not be implemented as written: it gives no
encoding, its "team_names NUL-separated" and variable-length text fields
need lengths, a box cannot verify a tag made with a key only the controller
has, and a box or a standby controller also needs the channel, the relay
clamp and the controller's id before it hears its first TIME beacon.

## Amendment 3 (2026-10-18): Choosing the field's channel; the whole channel inside one sub-band

**Supersedes:** in Amendment 1, "The channel is configurable per game via the CONFIG message" (CONFIG has no channel field; the channel reaches boxes in the join payload, Amendment 2) and the "Channel validation" paragraph; the open question on adaptive channel selection, in part. Section 8's sub-band table stands, with the sources and the note on its labels below.

**Change:**

1. **Why 869.525 MHz is the default.** It is the centre of 869.4-869.65 MHz, the only part of the European 863-870 MHz short-range band where a device may transmit up to 10% of the time at up to 500 mW ERP. Everywhere else in 868-870 MHz the limit is 25 mW ERP with 1% of the time (0.1% on 868.7-869.2 MHz): about a tenth of the airtime, and roughly 13 dB less power, so much less range. 868.1, 868.3 and 868.5 MHz are LoRaWAN's three default channels, which every LoRaWAN device in Europe implements and joins on, so they are often busy. The default is shared too: LoRaWAN uses 869.525 MHz for its RX2 receive window and Class B beacons, and Meshtastic's EU_868 default sits on the same 869.525 MHz with a 250 kHz preset, the whole sub-band. Their packets are not mistaken for the game's (the game's are encrypted and authenticated, and use another sync word), but every transmission nearby shares the airtime, which is why the GM can scan for a quieter channel.

2. **The channel is a field setting.** The field controller keeps it in its store (it survives a restart; `[radio] channel_hz` is the default until the GM first chooses). From the GM console (Settings), and only while no game is live, the GM can keep 869.525 MHz, run a noise scan of the candidate channels with the USB modem ("find a quiet channel"), draw a random candidate, or pick one from the list; scan and random choices are suggestions that change nothing until the GM accepts one. The controller sends the channel to the modem (SET_CHANNEL when no game is live, CONFIGURE for a game), stores it with each game, and puts the game's channel in every join payload (key 5, `channel_hz`). A game keeps its channel until it ends. Without a USB modem or without a radio chip the scan is unavailable and the channel stays as it is. The candidate list, the scan's dwell, the quiet threshold and the random rule are decisions CH1-CH8 in `docs/review/decisions-to-review.md`.

3. **The whole channel must fit in one sub-band.** A centre frequency is legal only if centre - BW/2 and centre + BW/2 both lie inside one sub-band of section 8 (edges included), where BW is the game's LoRa bandwidth, 125 kHz. A centre inside a sub-band is not enough: 869.40 MHz at 125 kHz occupies 869.3375-869.4625 MHz and spills below the sub-band. The legal centres are:

   | Sub-band | Edges | Legal centres (125 kHz) |
   |----------|-------|-------------------------|
   | g | 868.0-868.6 MHz | 868.0625-868.5375 MHz |
   | g1 | 868.7-869.2 MHz | 868.7625-869.1375 MHz |
   | g2 | 869.4-869.65 MHz | 869.4625-869.5875 MHz |
   | g3 | 869.7-870.0 MHz | 869.7625-869.9375 MHz |

   The rule is applied in one place per language (`atalaia_band_of_channel()` in `core/src/duty_cycle.c`, `simulator/atalaia_sim/eu868.py`) and used everywhere a channel enters: the controller's configuration and API, the modem's CONFIGURE, SET_CHANNEL and MEASURE, the join payload (both codecs; new invalid vectors in `protocol/vectors/join.json`, and two valid vectors moved from 869.65 and 870.0 MHz to the highest legal centres), the radio HAL's `set_channel()` on boxes and modems, and the simulator's radio model.

4. **The limits follow the channel.** Boxes and the USB modem take the duty-cycle budget and the TX power from the sub-band of the channel in use, not from fixed g2 values: 10% and 500 mW ERP on g2, 1% (0.1% on g1) and 25 mW ERP elsewhere, with the conducted power reduced by the front-end module's gain and the antenna gain (decision C2). Airtime is the LoRa time on air for SF7/125 kHz, tracked per sub-band over a sliding hour, so moving to another channel does not reset what was spent in a sub-band. A packet whose time on air does not fit in what is left is not sent (TX_ACK `duty_cycle`). The simulator's radio model follows the same rules. The regulations also allow listen-before-talk with adaptive frequency agility instead of a duty-cycle limit; Skirmesh-RF does not use it.

5. **Measuring does not transmit.** The noise scan uses a new USB modem command, MEASURE, which listens on a channel for a given dwell and reports instantaneous RSSI statistics and LoRa channel-activity detections (`protocol/usb-modem.md`). It never puts anything on air, and the modem refuses it while a game is configured.

6. **Sync word.** The SX1262 is set to the private-network LoRa sync word, register value 0x1424 (0x12 in SX127x terms), as the phase 2 radio settings intended; the first firmware wrote 0x3444, LoRaWAN's public sync word, by mistake. All Skirmesh-RF devices must use the same value.

**Note on the sub-band labels.** The labels g, g1, g2 and g3 in section 8 are this project's own. ERC Recommendation 70-03 now calls these bands h1.5, h1.6, h1.7 and h1.9 (Annex 1); its older editions lettered them g1 to g4, so 869.4-869.65 MHz was "g3" there, and LoRa documents that follow the older lettering call it g3. The code keeps the project's labels; user-facing text gives the frequencies.

- SX1261/2 LoRa sync word values (public 0x3444, private 0x1424, register 0x0740): Semtech's SX126x driver headers; checked against a secondary copy, not the datasheet itself.

**Reason:** the first firmware had one fixed channel and hard-coded the g2 duty cycle and power, so a field that chose another channel (Amendment 1 allowed it) would have kept g2's 10% budget and 500 mW power on a 1%, 25 mW channel, and the channel check accepted centres whose channel spilled out of the sub-band. A field next to a LoRaWAN gateway or a Meshtastic mesh had no way to see that, or to move.

## Amendment 4 (2026-10-19, proposed): The field CA and the controller's addresses in the join payload

**Status:** proposed with phase 3 plan phase E (decision PE4); for review.

Two optional keys of the join payload's body ([protocol/join.md](../../protocol/join.md)), from the range kept for optional fields:

| Key | Field | Type | Values |
| --- | --- | --- | --- |
| 13 | `ca_sha256` | bytes | 32: SHA-256 of the field CA's DER certificate (decision P3-8) |
| 14 | `urls` | array of text | 1-3 different `https://host[:port]` base addresses of the controller, at most 64 bytes each |

An Android prop, which has no LoRa radio of its own, uses them to link to the controller over the field's Wi-Fi ([protocol/prop-link.md](../../protocol/prop-link.md)): it fetches the CA from one of the addresses, checks it against key 13 and trusts it for that game only. The controller adds them to payloads for boxes (kind 0) when it serves HTTPS, and leaves them out when the payload would not fit. Boxes skip keys 13-31 as before, so their firmware is unchanged; the Python and Dart codecs read 13 and 14 and skip 15-31. The vector that tested a skipped optional key used key 13 and now uses key 20.

Nothing on the radio changes: the keys are inside the join payload's tag, which still authenticates the whole payload with the field join key.

## Open questions

- Per-node session keys (HKDF-derived from the game key) would limit
  the blast radius of a compromised node. Deferred: the current
  per-game key is adequate for the "hard to cheat casually" threat
  model.
- The `tx_time_us` field in TIME beacons measures processing delay.
  Its usefulness for time-sync accuracy depends on how stable the
  delay is in practice; field testing will determine whether it
  improves the slew algorithm or just adds noise.
- Channel hopping currently uses a fixed round-robin. Adaptive channel
  selection based on RSSI or error rates is a future improvement.
  (Amendment 1 replaced hopping with one shared channel per game, and
  Amendment 3 adds a noise scan when the field's channel is chosen; moving
  a game to another channel while it runs is still open.)
