## [Unreleased]

### Added
- The keypad's expander is found at any PCF8574 (0x20-0x27) or PCF8574A (0x38-0x3F) address, as listings sell both under one name; the configured address is tried first, and the bus's other parts (NFC 0x24, battery gauge 0x36, OLED 0x3C) are never probed (decision HB-11)
- Scenarios in the controller, console and app (phase-4-site-server plan phase 8, ADR-P4-6 as amended, decisions P4R8, P4R24, M8-1 to M8-9; in software, tested with C host boxes and in Chromium, not yet on radio hardware or a real phone in the field): the controller's `POST /api/v1/scenarios/check` (every problem of a manifest with its place, then the compiled `field.lua`'s load in the core), `POST /api/v1/scenarios` (GM: compile and install, the manifest kept next to the package), `GET /api/v1/scenarios` and `GET /api/v1/scenarios/{id}` (GM: the manifest and the generated files); the GM console's *Cenários* / *Scenarios* tab, a YAML editor checked as it is typed with an example, the boxes to name and the installed scenarios; in the *Join* tab the GM gives each box one of the scenario's names, which the scenario's `field.nodes()` returns (`controller/atalaia_controller/scenario_service.py`)
- Scenario objectives reach the players they are for (P4R24): staff see every objective event; players see an objective by its visibility (`public`, the assignee team's or squad's, a hidden one only once revealed) on the stream, the log and the game, which carries the scenario's names and the objectives each viewer may know; MQTT and other teams learn only that a team completed, failed or was shown an objective
- The app's player view shows the scenario's objectives with their names in the app's language, where each stands (waiting, in progress, completed by a team, failed and why), its team and squad and its points, and names them in the list of what happened
- A game whose id does not fit a join (63 bytes) is refused when it is created; a standby controller that lacks a game's scenario says which part to install (decision M6-1)
- A game picked on the Field Box survives a power loss with its mode's state (decision HB-7): the box saves the script's `state.node` (as JSON, up to 1 KB), the scores and the game's seed with its time every second, and gives them back on resume without replaying the time between, so nothing is counted twice; an armed Bomb comes back armed with the fuse it had left (a new `node.rebooted` handler). Core: `atalaia_node_state_save`, `atalaia_node_state_restore`, `atalaia_node_resume_at`, `atalaia_node_score_restore`. The state file (`/state/current.bin`, version 2) is written to a temporary file and renamed, so a power loss mid-write keeps the last good state. A field game resumes as before (its controller sets the mode up again)
- ATAK / Cursor on Target feed on the field controller (phase-4-site-server plan phase 9, ADR-P4-7 as amended, decision P4R18; in software, tested with loopback receivers, not yet with a real ATAK device: HW3): `controller/atalaia_controller/atak.py` sends every box placed on the field image as a coloured spot marker (`b-m-p-s-m`: name, owner, the owner's colour as `<color>` and, for a team named after an ATAK team colour, `<__group>`, battery) and a VIP / Payload extraction zone, every `interval_s` (30 s) and at once on a capture, neutralisation, move or game change, with `stale` at twice the interval and every marker dropped when the game ends; over UDP to `[atak] multicast` (`239.2.3.1:6969`, TTL 1), one event per datagram (TAK Protocol version 0). **Player positions are never multicast**: only with `players = true`, and only to the staff ATAK devices of `staff_endpoints` (TCP, 4242 by default), by pseudonymous player id, never by name. XML built with ElementTree (escaped, characters XML forbids dropped, texts capped). Off by default (`[atak] enabled = false`, `ATALAIA_ATAK_*`), only on the controller in charge; `GET /api/v1/atak` for its counters. The field image's georeference (`controller/atalaia_controller/georef.py`, `GET`/`PUT`/`DELETE /api/v1/field/georef`): two opposite corners of a north-up image, or 3-8 control points for a rotated one (least-squares affine fit in a local plane), with degenerate, mirrored and inconsistent points refused; kept in the store's settings, cleared by a new image. The GM console's *Campo / Field* tab gets *Posição no mapa (ATAK)*: the two corners pasted as `latitude, longitude`, the four corners shown back and a pin per point on the image (`console/src/components/georef-panel.js`). `[atak]` in `controller.example.toml`. - After a reboot a game picked on the box lost its scores (they were saved but never given back) and its mode's state: a Domination owner or an armed Bomb was forgotten
- A game picked on the box got stuck when its timer ran out: the buttons and keys did nothing, the screen stayed on the last phase, no way back to the picker, and the ended game was resumed after every reboot. The box now stops the game, forgets its saved state, shows the final screen when the mode drew none, and the next key brings the picker back (found on the first V4.3 board)
- The firmware build guide said typed console input does not reach a Heltec V4 over USB; it does (`CONFIG_ATALAIA_CONSOLE_USB_INPUT`)
- The site server's public pages and feeds answer `HEAD` like `GET` without the body (they answered 405), with the same `ETag`, `Last-Modified` and `Content-Length`, and `304` on a matching conditional request: calendar clients use it
- `protocol/chrono-record.md` said a marshal's private key was also kept encrypted on the site server for recovery; it never is: it stays on the marshal's phone and only public keys travel (decisions P4R14, S14-12)
- Security (decision M4-7, M5-1): the code a Hacking Terminal reveals (`hacking.solved`'s `code`) and the secrets in a game's parameters (Bomb's `team_codes`, Codes' `codes`, the terminal's `reveal_code`) reached every player connection on the controller's stream, the read token's REST views and MQTT, where the app only hid them; the controller now strips them for everyone but staff (`controller/atalaia_controller/visibility.py`), and the stream always uses the role-aware route, with or without check-in
- Project page claims that were out of date or overstated: "Try it today" said there was no firmware to flash; phase 2 was still shown as the current phase and phases 4 and 5 had no status; the I/O pod and the Android device were drawn as planned (dashed) in the Skirmesh-RF diagram, and its Wi-Fi phones had the player app "in phase 3"; the glossary said the Android prop and the pod "arrive in phase 3", the chrono registry "will" keep readings, and only the Skirmesh-RF codec existed (the whole protocol is built in software); "Modes are scripts" and the firmware entry said new modes reach a box without flashing and firmware updates come from the controller (a new mode needs one flash for now; updates over the air are still to come); "Any hardware" said Arduino-class boards already play (thin nodes are not built); "Built for fields" called built work "part of the design"; LoRa's 0.5-2 km and the ESP32's one to three days on a battery are now marked as estimates; the field controller entry says the Android controller is still to come; the Portuguese phase 3 text used the English mode names
- The app: closing a pod client from a listener of its own (synchronous) events threw "Cannot fire new event" (found by the new tests against the host pod; decision PF13) (phase-3-android-players, plan phase F)
- The app: a prop's manual-clock tick that was still waiting on the core when the screen closed the session threw; `PropSession.advance` now ends quietly once the session is closed (with the coordinator's fix of notifications after dispose, and a test that fails without it) (phase-3-android-players, plan phase E)
- The controller's SQLite file is created with mode 0600 before SQLite opens it, so its WAL and shared-memory files (which hold the tokens too) are private as well (phase-3-android-players, plan phase E)
- App on-device tests: `pageBack()` looked for the English "Back" tooltip and never found the Portuguese app's back button; role cards below the fold on a small screen (CI's emulator) were tapped where they were not; a new `app/tool/emulator_tests.ps1` grants the notification permission Android 13+ asks for, which needed a person to tap it (phase-3-android-players)
- Core: `{x|clock}` on a value beyond a 64-bit integer converted it anyway (undefined behaviour in C: x86 and ARM showed different texts); the seconds are now clamped at 1e15. Found by the app's template tests against the core (phase-3-android-players, plan phase D)
- Core: `field.common_owner()` kept the team name from one `owner()` call and compared it after the next call, reading memory the host may already have freed (the simulator's and the app's bindings keep only the latest answer), so Hold-All's scoring could go wrong; the core now copies it first, `field_ops.h` states how long an answer must stay valid, and a core test catches the old behaviour. Found by the app's mode tests (phase-3-android-players, plan phase C)
- `tools/docker_app.py` crashed on Windows when its output was redirected to a file or a pipe and Flutter printed a character the console's code page lacks (phase-3-android-players, plan phase C)
- Core: a penalty with a reason and no squad (`score.add(team, -n, reason)`) put the `score.delta` data inside itself, so the event could not be encoded and the handler failed with `script.error`; found by Kill Confirmed (phase-3-android-players, plan phase A)
- A channel centre inside an EU868 sub-band was accepted even when its 125 kHz channel spilled over the sub-band's edge (869.40 MHz occupies 869.3375-869.4625 MHz). Now the whole channel must fit in one sub-band, in the controller's config and API, the USB modem (CONFIGURE, SET_CHANNEL, MEASURE), the join payload codecs (C and Python; two valid vectors moved to legal centres, four invalid vectors added) and the radio HAL (phase-2-field-network)
- The Field Box and USB modem firmware used the 869.4-869.65 MHz sub-band's 10% duty cycle and 500 mW power on every channel; the budget and the TX power now follow the channel's sub-band (1% or 0.1% and 25 mW elsewhere), per sub-band over a sliding hour, with the LoRa time on air instead of a rough estimate, and a packet that does not fit in the budget left is not sent. The simulator's radio model follows the same rules and now refuses to transmit over budget (phase-2-field-network)
- The SX1262 was given LoRaWAN's public sync word (0x3444) although the code said "private"; it now uses the private-network value 0x1424 (phase-2-field-network)
- Project page: the English LoRa glossary entry wrote `class=”nowrap”` with curly quotes, so its range figure was not kept on one line (no other curly quotes inside HTML tags in either language)
- `hardware/field-box/README.md`: the BoM had a 2S pack on the board's single-cell battery socket (it would destroy the board); Vext and the board's ADC were described as used by the firmware; button 2 was on GPIO 5, the V4.3 front-end module's line (phase-1-single-box)
- Heltec V4 radio front end: the FEM's power (GPIO 7, VFEM_Ctrl) was held low, which would have left the front-end module unpowered and the radio nearly deaf on real boards; it is now powered (LDO, then the revision's mode pin, then the chip enable) once the SX1262 answers, for the V4.3 (KCT8103L, GPIO 5 low = LNA) or the V4.2 (GC1109, GPIO 46 high = PA) chosen in Kconfig. Button 2 moved from GPIO 5 (the V4.3's FEM control) to GPIO 39; Vext (GPIO 36, active low) is switched on at boot; GPS is not supported in the Field Box pin map (phase-2-field-network, Phase E)
- Field Box: console input (`@join`, `@joinkey`, serial keys) is read from the board's USB-C port (USB-Serial-JTAG) as well as UART0, since the Heltec V4 has no USB-UART bridge; the LED ring's brightness is applied (40% at boot, `ring:set_brightness(percent)`); `python tools/docker_fw.py build` no longer takes a stray `firmware/esp32/sdkconfig` (it could hold Wokwi pin settings) and `clean` removes it (phase-2-field-network, Phase E)
- ESP32 shell: the serial console code used `CONFIG_ATALAIA_SERIAL_KEYS` in a C expression, which does not compile when the option is off (the Field Box default); found by a clean build (phase-2-field-network, Phase E)
- The core's payload codec (`msg_codec.c`) did not follow the schema and RFC 0001: HELLO capabilities, STATE counters, CMD params and CLAIM acks had other CBOR types, required fields were dropped when zero, and nothing was checked on decode; its vector tests skipped every vector it could not read, as did the Python ones. Both codecs now agree on every shared vector, byte for byte, and reject the invalid ones (phase-2-field-network, Phase D)
- The simulator's ctypes structs lacked `field_state` and `field_ops`, so the core read past the end of the Python config; the simulator's CBOR codec could not encode the ACK bitmap (phase-2-field-network, Phase D)
- Radio HAL: a BUSY timeout or SPI error is now returned to the caller instead of ignored, so a missing SX1262 is reported as "not detected" and released; the debug-step logs are debug level (phase-2-field-network, Phase D)
- Firmware: the memory monitor task overflowed its stack and crash-looped the box; the HAL drivers were never initialised; LittleFS was never mounted; the battery gauge and NFC reader claimed two I2C drivers on the same pins; the display flush queued an SPI transaction from the stack; the Wi-Fi setup never initialised Wi-Fi. Missing parts are now logged and skipped at boot (phase-1-single-box)
- `hardware/field-box/README.md` pin table now matches the Kconfig defaults (PCF8574 keypad, I2S on GPIO 6/15/16, backlight on GPIO 47, display RST on GPIO 38) (phase-1-single-box)
