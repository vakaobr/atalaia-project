# Site server (optional)

A self-hosted server for fields with internet: accounts, field setup, remote management, the player app backend, game history and the chrono registry. It never runs game logic; games keep working without it.

Clubs without IT support will be able to use hosted site servers run by the community hub: one server, one PostgreSQL database, each field in a schema of its own with row-level security under it (hosted mode, below). Hosted mode is off by default, and does not go live before the legal review of the templates (decision P4-6).

Licence: AGPL-3.0-or-later.

## Status

Phase 4 plan phases 10 to 22 are built, and tested on a computer only. Plan phase 10 is the skeleton every later plan phase builds on: the application factory, its settings, the async database layer on PostgreSQL 16, the first migration (the base tables), `GET /api/v1/health` and `GET /api/v1/metrics`, security headers on every response, the server's own image, and the tests with their tooling. Plan phase 11 adds accounts, sessions and roles: registration, login with a TOTP step, rotating refresh tokens, lockouts and rate limits, per-field roles, the audit log and `python -m atalaia_server create-admin`. Plan phase 12 adds the personal data rights: access, export, rectification and erasure of one's own account, consent records, the daily retention purge, and privacy notice and DPA templates. Plan phase 13 adds the controller sync: field controllers push their games, event logs, score counters and nodes with a field API key, offline first and replay-safe, and the site server keeps them with per-game roles and a small games API; it has run against the real controller in tests, not yet over a real 4G link (HW1). Plan phase 14 adds the chrono registry: the controller pushes the marshals' public keys with their periods, the replica registry and the signed chrono readings; the site server verifies every reading with the controller's own verifier, keeps it exactly as signed (or apart, with the reason, when it does not verify), and gives the field's staff, the players themselves and, with consent, other fields their views; tested against the controller's client and the shared vectors, not yet with a real chronograph (HW4). Plan phase 15 adds scheduling and the field's public face: the field's admin and GMs schedule games (drafts, then published by the admin, edited, cancelled with a reason), and a field that turns its page on gets a public page with its upcoming games in Portuguese and English, rendered on the server with no JavaScript, and open iCalendar (RFC 5545) and JSON feeds that calendars and other sites can read ([docs/feeds.md](docs/feeds.md)); no personal data on any of them. Plan phase 22 adds the deployment ([docs/DEPLOY.md](docs/DEPLOY.md)): Caddy in front with an automatic certificate and the security headers the server does not send, the only container with published ports (the database and the server on internal networks); `setup.sh` makes `.env` (mode 0600) with new random secrets, never printed, and starts everything; `backup.sh` makes encrypted backups (AES-256-GCM, the dump never on disk in clear), kept 30 days; `restore.sh` restores one into a fresh database; tested in Docker on one computer, behind Caddy with its own certificate authority (HTTPS, the WebSocket through Caddy, a backup restored into a fresh database with every table compared), not yet on a real server with a real domain and certificate. See [docs/phase-4-site-server/PLAN.md](../docs/phase-4-site-server/PLAN.md). Plan phase 16 adds registration and game-day sync: players register for a published game with an account, with pre-declared replicas and a check-in ticket (only its hash kept); an account can adopt the player id its phone already has at the field, once the field's controller confirms it; the controller pulls the schedule, makes its game from a scheduled game, pulls the roster as expected check-ins until the game starts, and pushes each registration's outcome back after it; tested against the real controller in Docker, not yet on a real game day; the app's screens for it (account login, the field's games, registering, the ticket) are built and tested against a stand-in server, not yet against a real deployment or on a phone. Plan phase 17 adds the registration import and platform adapters ([docs/integrations.md](docs/integrations.md)): a field's staff import a registration list exported from elsewhere (CSV or JSON, only the columns the check-in needs, a dry-run preview first, row-level errors, re-importing the same export changes the same registrations) and export the game's list as formula-safe CSV; the adapter interface for external platforms (only through a platform's documented API or a written agreement, off by default, configuration encrypted, every call audited) ships with an in-memory test adapter only, and there is no adapter for any named platform. Plan phase 18 adds club profiles and branding sync: clubs (name, short name, colour, logo, crest, members invited by their admins) with a public page off by default, a report button and a server administrator who can hide one; a field's branding (name, accent, logo, wallpaper) and saved teams (a club's team carries the club's crest) edited here, with every image checked by the controller's own `images.py`; and controllers set to `[sync] branding = "site"` pull them, so a club's crest uploaded once reaches every field that saved its team; tested against the real controller in Docker, not yet on a real deployment. Plan phase 19 adds device health, a firmware catalogue and the remote GM: the field's staff see each box's battery, link, firmware (against the catalogue) and health flags from what the controllers sync; server administrators keep a catalogue of firmware releases that only takes entries signed with a configured Ed25519 release key and stores no image (OTA is not built); and a user with the `gm` role on the field sees the live game of a controller that turned `[sync] remote_gm` on and starts, pauses, resumes or ends it, sends a GM message or one of the game's declared mode commands, over the WebSocket the controller opened, each command logged on both sides; tested against the real controller and PostgreSQL in Docker, not yet on a real deployment or over 4G (HW1). Plan phase 20 adds game history and the scenario library: the field's synced games with filters, each game's score timeline derived from the per-node counters and its event log by type and time (staff see everything; other roles see a live game a minute behind, without secrets or player ids), a public scoreboard per field (off by default), and the field's scenario library (manifests checked with the controller's own compiler and the core, kept as revisions) with its game presets, which every controller of the field installs from the site with `[sync] library = true`, a standby included; tested against the real controller in Docker, not yet on a real deployment. A Phase 4 follow-up adds the field staff's web pages for these APIs, which had none (decisions FU2-1 to FU2-12): a login (password, then the TOTP code), the field's game history with each game's score timeline and event log and the history settings, the scenario library (a manifest checked with every problem shown, saved as revisions, archived) and the game presets, device health with its flags, and the remote GM (each controller's live view, the commands and the log), in pt-PT and English, on a phone too; the pages hold no data and call the API, so each has exactly its API's role rules; tested in headless Chromium against the real API in Docker, not yet on a real deployment. Another Phase 4 follow-up adds hosted mode's deployment (decisions FU4-1 to FU4-10): `setup.sh DOMAIN --hosted` makes the two database roles and the hub's registry and starts `docker-compose.hosted.yml` on top of the deployment, where Caddy serves `*.DOMAIN` with on-demand certificates that only an active field's name gets (an `ask` endpoint, rate limited), the server runs as the role that owns nothing and the operator's commands run as the owner (`docker compose run --rm hub hosted ...`); `backup.sh` covers every field, the registry and the hub's audit log, and `restore.sh` restores a hub with its owners and grants and refuses a backup of the other mode; tested in Docker on one computer with Caddy's own certificate authority (two fields at their own names, an unknown name refused a certificate, the isolation checked as the server's role before a backup and after its restore into a fresh hub), not yet on a real hosted server with a real domain, and hosted mode still waits for the legal review (P4-6). A Phase 4 follow-up adds the remote ATAK relay (decisions FU5-1 to FU5-20; "Remote ATAK" below): a field controller with `[atak] remote = true` pushes its CoT events on the stream it opens, and the site server relays them over TLS on port 8089 to the field's ATAK devices, each with a client certificate its admin or gm issued from the field's own CA as a TAK data package; boxes and zones to every enrolled device, player positions only to a gm's or a marshal's certificate issued with that option; a revoked certificate is cut off at once; off by default; tested in Docker (TLS clients made from the packages, the real controller through the real site server, the deployments through their published port), not yet with a real ATAK device (HW3) or on a real server.

The site server imports the Python it shares with the field controller (the chrono verifier, the player-token codec, the image checks, the mode loader and its bindings to the C core) from `controller/atalaia_controller/` and `simulator/atalaia_sim/`. That code stays free of FastAPI, pydantic and SQLAlchemy (decision P4R16), because the controller runs on Raspberry Pi OS's own packages; `tests/test_shared_imports.py` checks it.

## Settings

| Variable | Default | Meaning |
| --- | --- | --- |
| `ATALAIA_DATABASE_URL` | (required) | `postgresql+asyncpg://user:password@host:5432/database`; no other database is supported |
| `ATALAIA_SECRET_KEY` | (required) | At least 32 characters (`python3 -c "import secrets; print(secrets.token_urlsafe(32))"`). The keys of the access tokens, the TOTP login step and the encrypted TOTP seeds are derived from it; changing it logs everyone out and makes every TOTP enrolment unreadable. Migrations do not need it |
| `ATALAIA_DB_POOL_SIZE` | 5 | Connections kept open (1-100) |
| `ATALAIA_DB_MAX_OVERFLOW` | 5 | Extra connections under load (0-100) |
| `ATALAIA_DB_TIMEOUT_S` | 5 | Connect and health-check timeout, seconds |
| `ATALAIA_METRICS_TOKEN` | (empty) | Optional bearer token for `/api/v1/metrics`, at least 32 characters, for a monitoring system; server administrators can always read the metrics |
| `ATALAIA_LOG_LEVEL` | `info` | `debug`, `info`, `warning` or `error` |
| `ATALAIA_PURGE_HOUR` | 3 | The hour (UTC, 0-23) at which the server runs the retention purge every day; `off` when something else runs `python -m atalaia_server purge` |
| `ATALAIA_AUDIT_IP_DAYS` | 180 | Days an audit entry keeps the client's network address (90-365); then the address goes and the entry stays (PRIV-6) |
| `ATALAIA_INACTIVE_ACCOUNT_MONTHS` | 24 | Months without any activity after which an account is warned, then anonymised after `ATALAIA_INACTIVE_GRACE_DAYS` (30, 7-180); 12-120 or `off`. Server administrators, accounts with a field role and registrations for a game to come are left out; the warning shows on the account page (`GET /api/v1/me` `inactivity`) (PRIV-7) |
| `ATALAIA_ERASURE_LEDGER` | (unset; the Docker deployment sets `/ledger/erasures.jsonl`) | The file the erasure ledger is appended to, outside the database: hashes of the accounts and players erased, applied again after a restore by `python -m atalaia_server erasure-ledger apply` (PRIV-4) |
| `ATALAIA_ALLOW_SIGNUP_WITHOUT_NOTICE` | `off` | `on`: new accounts may be made while no privacy notice is published (development and tests only); `off`: they are refused with `privacy_notice_unpublished` (LIVE-2) |
| `ATALAIA_PUBLIC_URL` | (empty) | The site's public address, an origin such as `https://campo.example.pt` (no path): the links in the field pages and feeds and the host name in iCalendar UIDs. Set it on a real deployment; unset, they follow the address of each request (a local trial). `http://` only for `localhost` |
| `ATALAIA_TEST_ADAPTER` | `off` | `on` offers the platform adapters' test adapter, an in-memory stand-in for a platform, for trials and tests; leave it off on a real deployment |
| `ATALAIA_FIRMWARE_KEYS` | (empty) | The Ed25519 public keys (32 bytes in standard base64, separated by commas, at most 8) whose signatures the firmware catalogue accepts; empty, it takes no entry. Removing a key withdraws every entry it signed |

## Accounts, sessions and roles

ADR-P4-2, with decisions S11-1 to S11-15:

- **Passwords:** Argon2id with 3 passes over 64 MiB, 4 lanes, a 16-byte salt and a 32-byte tag; an older hash is replaced at the next login. The policy is NIST SP 800-63B's: 10 to 1024 characters (after Unicode NFKC normalisation), no character-class rules, not the username, and not one of the 100,000 passwords seen most often in breaches (the UK NCSC's list: SecLists' `Passwords/Common-Credentials/100k-most-used-passwords-NCSC.txt` at commit `1a7bb9127eca9e6ff2fc0301c597fe6e16a0cb56`, SHA-256 `c2e5696882c603b76bb67a47ee970897e5a76fc4c3f5547abe3d0ca340c576e0`, MIT as part of SecLists), compared whatever the case. The repository keeps it as hashes only (decision S11-4): [`data/breached-passwords.sha256`](atalaia_server/data/breached-passwords.sha256) holds the 9,126 entries of 10 characters or more (shorter ones fail the length rule anyway), each NFKC, lower-cased and hashed with a fixed prefix (SHA-256, 16 bytes), made by [`tools/breached_hashes.py`](../tools/breached_hashes.py) from the pinned list; the hashes keep the passwords out of sight, they do not make them secret. An unknown username takes as long to refuse as a wrong password.
- **TOTP** (RFC 6238): 6 digits every 30 seconds, as authenticator apps do by default; one step of clock drift either side; each code is accepted once. Seeds are stored encrypted (Fernet). Accounts with `admin`, `gm` or `marshal` on any field, and server administrators, must have it, and those roles count only in a session that passed it.
- **Login methods** (decisions LG-1 to LG-12): besides the password, an account can log in with a **social login** (Google, Microsoft, Apple through OpenID Connect) and with **passkeys** (WebAuthn), and **passwords are optional**.
  - *Social login* (`oidc.py`, `api/login_methods.py`): the authorization code flow with PKCE (S256), a `state` and a `nonce`; only the scope `openid` is asked (none for Apple; the one exception is the person's own "use my name" button, below), so the provider tells the server one thing, an opaque subject, and that, the provider and the issuer (and Microsoft's tenant `tid`; migration `0027_identity_issuer`: a subject is only unique within its issuer, so two issuers or tenants cannot collide, SRV-8; a Microsoft row made before takes its issuer at its next login) are all that is stored (`user_identities`): never an email, a name or a picture. The ID token is validated in full: its signature against the provider's JWKS (RS256 only, cached for an hour, refetched at most once a minute for an unknown `kid`), the issuer (for Microsoft, `https://login.microsoftonline.com/<tid>/v2.0` with the token's own `tid`, checked against the configured tenant), the audience, the expiry and issue time, and the nonce. The state, nonce and verifier of an attempt are one row in `oidc_logins` (ten minutes, deleted by the callback, so one use) and the browser carries a random value in the cookie `__Secure-atalaia_oidc` (HttpOnly, Secure, **SameSite=Lax**, only on `/api/v1/auth/oidc`) whose hash the row holds: Lax because the provider's redirect back is a cross-site navigation that a Strict cookie would not go with, and the binding is what stops a login-CSRF (an attacker's callback URL is useless in a browser that did not begin the attempt). The callback sends the browser back to the staff login with a one-minute, single-use signed ticket in the URL fragment, which `POST /api/v1/auth/oidc/complete` turns into a session: the session and its refresh cookie are made by a same-site call, and no token is ever in a URL the server sees. **A first login with an unknown subject makes an account** (username `user-` and random hex, no email, no password), under the registration rules: the consent given in the start request (`consent: true`, recorded with the notice version) and the per-address registration limit. **Nothing is ever linked by email**: a logged-in user links a provider on purpose (`purpose: link`, with the password or, with no password, a login from the last ten minutes) and unlinks it; a provider account belongs to one account, one provider links once.
  - *The username of a social account and the "use my name" round* (LG-10, migration `0024_oidc_name_purpose`): an account a social login makes is called `user-` and 12 hex digits. Right after a **new** account the staff pages send the browser to the Account page with `?welcome=1` (the `complete` answer says `new_account` and `provider`), whose first section is "Choose your username": an empty field with the usual rules, a save, and a skip (the account keeps working with the temporary name until renamed). For the provider the account **signed up with** (read from its `register` audit entry; Google or Microsoft, never Apple, whose name comes once in a form post this flow does not use) the step has a button "Use my Google name" / "Use my Microsoft name": it starts a round with `purpose: name`, which adds the scope `profile` (`openid profile`) **only then**; every normal login, link and reauth keeps asking `openid` only. The callback checks that the subject is the account's own (as a reauth does), reads `name` (Google also `given_name`) from the validated ID token, turns it into a username (accents dropped, lower case, other runs of characters one dot, 3 to 64 characters; nothing usable gives `name_unusable`) and sends it back **in the address fragment** (`#username=...`, never seen by a server). The name is **never stored**: not in `users`, not in the audit entry (`oidc_name_read` has the provider and whether it was usable), nowhere; only the username the person confirms is saved, through `PATCH /api/v1/me`.
  - *Renaming* (`/staff/account`, first section): any account renames itself with `PATCH /api/v1/me`, confirmed with its own login method: an account with a password sends it; an account with none confirms with a login from the last ten minutes, which a passkey, a linked provider (`purpose: reauth`) or a TOTP code gives (the confirmation box of the same page). The rules are the existing ones: unique (409 `username_or_email_taken`), the allowed characters (400 `username_invalid`), the reserved `deleted-` prefix, an audit entry (`profile_update` with the fields, never the values).
  - *Merging two accounts of one person* (LG-11, `api/account_merge.py`): when account A, signed in, links a provider login that belongs to account B (a second social login that made its own account), the provider round that just proved control of B's login ends with a five-minute, single-use signed **merge ticket** in the address fragment (`#merge=...`) instead of only `identity_taken`; the Account page asks "This login belongs to another account (B's username). Merge it into this one?" (`POST /api/v1/me/merge/preview`) and, on A's confirmation as for any sensitive change (`POST /api/v1/me/merge`: the password, or a recent login), moves into A every row that points at B (the model's foreign keys to `users.id` are read, so a table added later is included): linked logins, passkeys, roles and game roles, registrations, consents, club memberships, player ids and claims, the chrono sharing link, ATAK certificates and the "who did it" columns. Where both hold the same thing (a role, a game role, a club, a consent, a registration for the same game) A's stays and B's is dropped (B's registration is cancelled and unlinked). A's username, password and TOTP stay; **B's password is never carried over** (an account with none stays without, and the answer says so). B is kept as an anonymised row (`deleted-...`, no password, no logins, sessions revoked; the audit log points at it), its old username is free, and both accounts get an audit entry (`account_merge`, `account_merged_into`, counts and ids, no names). **Refused (409)**: a B with a staff role (server administrator, or `admin`, `gm` or `marshal` on a field or a game: `merge_staff_account`), a provider both accounts already have a login for (`merge_provider_conflict`), more passkeys together than the limit (`merge_too_many_passkeys`), and a B with passkeys into an A with a staff role (`merge_passkeys_into_staff`, SR-3: nothing is dropped silently, B's person removes the passkeys or keeps the accounts apart). A sign-in with B's login while A's tab is open is just a sign-in to B; a merge is only ever started from A's Account page. The app's `/app/oidc` return never gets a ticket (it still says `identity_taken`). In hosted mode an account is per field and the merge runs inside one request, so in one field's schema as that field's role.
  - *Passkeys* (`passkeys.py`, the `webauthn` library by Duo Labs): the RP ID is the host name of the address the pages are served from (`ATALAIA_PUBLIC_URL`'s host, a hosted field's own `<slug>.<domain>`, else the request's), the origin that address; user verification is required at registration and at every use, the credential is discoverable (a login needs no username), no attestation is asked for. The challenge is a signed five-minute token, accepted once. The signature counter is checked (a clone shows as one that did not advance). A passkey made for another host name does not log in and does not count as a way to log in. At most 20 per account. Failed assertions count against the per-address login lockout like failed passwords.
  - *Passwords optional*: `users.password_hash` may be null. A server administrator sets `ATALAIA_PASSWORD_LOGIN=off` to turn password login and registration off. **An account always keeps at least one way to log in** (the password only when password login is on, each linked provider the server has configured, each passkey of this host name): removing the last is refused with 409 `last_login_method`. An account with no password confirms sensitive changes (profile, linking, passkeys, erasure) with a proof from the last ten minutes: a login of any kind, a step-up, or a social re-login (`purpose: reauth`).
  - *Staff second factor*: the roles that needed TOTP (`admin`, `gm`, `marshal`, server administrators) now need **TOTP or a passkey**, and count in a session with `mfa`: a TOTP step, a passkey login (a passkey is both factors) or a step-up. **A social login alone never sets `mfa`**: such a session must still pass `POST /api/v1/auth/stepup/totp` or the passkey step-up before those roles count; the staff pages offer it (below). Granting one of those roles to an account needs a second factor on it (TOTP on, or a passkey), and an account cannot remove its last one while a role needs it. The TOTP code and rules are unchanged.
  - *Changing how an account logs in needs the second factor* (SRV-1, decisions SR-1 to SR-9, `api/auth.step_up_needed`): when the account has a TOTP or a passkey, or has a staff role and no password, adding, renaming or removing a passkey, starting or turning off TOTP, setting, changing or removing the password, linking or unlinking a social login (and so starting a link round) and confirming a merge are refused with 403 `mfa_required` unless the session has `mfa` (a TOTP step, a passkey login or a step-up; a Google, Microsoft or Apple login never does, and a social re-login confirms without counting). `GET /api/v1/me/login-methods` carries `step_up_needed` (true for this session, now) and the staff page and the app show the TOTP / passkey step-up first, with no provider button. Not covered: an account with no staff role and no TOTP or passkey keeps the old confirmation (password, or a login in the last ten minutes), so a player can add a first passkey after a social login; a staff account that has a password and no second factor yet gets its first with that password (it is how it becomes able to hold the role). Each refusal is in the audit log (`step_up_refused`).
  - Every method, link, unlink, step-up and passkey change is in the audit log (`login` with `method` password, passkey or oidc and the provider; `register` with `method: oidc`; `identity_link`, `identity_unlink`, `passkey_add`, `passkey_rename`, `passkey_remove`, `password_remove`, `stepup`, `oidc_failed`).
- **Sessions:** a 15-minute access token (`Authorization: Bearer`; the server re-reads the session and the roles on every request, so a logout or a removed role counts at once) and a refresh token in the cookie `__Secure-atalaia_refresh` (HttpOnly, Secure, SameSite=Strict, sent only to `/api/v1/auth/refresh`). Each refresh spends the token and issues a new one; a spent token presented again ends the whole session. A session ends after 7 days without a refresh, and after 30 days in any case. The database keeps only SHA-256 hashes of refresh tokens.
- **Limits:** 5 failed logins for one username from one address lock that username at that address for 15 minutes, and 50 failed logins from one address, whatever the usernames, lock the address for 15 minutes (so one player's typos do not lock out a whole field behind one 4G address; decision S12-1); 5 wrong codes lock an account's TOTP for 15 minutes; 10 registrations an hour and 100 API requests a minute per address. The state is in memory, for the one worker process the image runs.
- **Roles** are per field: `player`, `squad_leader`, `vip`, `marshal`, `gm`, `spectator`, `admin`. A field's `admin` grants and revokes any of them; its `gm` the four player roles. The same roles can be granted on one synced game (plan phase 13), by the same people, with the same TOTP rule.
- **The audit log** records registrations, logins, failures and lockouts, refresh replays, logouts, TOTP changes, new fields and every role change, with the address; never a password, a code, a token or a username typed for an account that does not exist.

## Controller sync

ADR-P4-3 as amended, decisions P4R10-P4R13 and S13-1 to S13-12; the wire format is [protocol/sync.md](../protocol/sync.md), with shared vectors in [protocol/vectors/sync.json](../protocol/vectors/sync.json).

- **The controller opens every connection** (it sits behind a phone's 4G link): HTTPS requests and, optionally, one WebSocket. The site server never connects to a controller and holds none of its tokens.
- **API keys:** a field's admin makes one (`POST /api/v1/fields/{field}/sync-keys`, shown once) and sets it on the controller (`python3 -m atalaia_controller sync-key`, or `[sync] api_key`). Only its SHA-256 is stored; a field has at most two live keys, so a new key can be installed before the old one is revoked. Both sides show the first 8 hex digits of the key's SHA-256 as its fingerprint.
- **Games** are `(field, game_id, game_seed)`: the radio's 16-bit id comes round again, the seed does not, and a standby controller has the same seed, so its pushes land in the same game. The state only moves forward; a standby's "ended" does not end the game, a `game.end` event does.
- **Events** are unique on the controller's own key `(game, node, seq, game time, type)`: a replayed, duplicated or out-of-order batch is counted as duplicates and changes nothing. The answer's `acked_id` is the controller's cursor.
- **Scores** are counters per source (`node-3`, or `field-1@0` for a run of a controller's field script) and team, merged by `GREATEST`; totals are derived as the controller derives them: the counters' sum plus every `score.delta` amount, so a GM's negative adjustment lowers the total (P4R10).
- **Never received:** positions (an event whose data has a coordinate is refused), tokens and keys (marshals' private keys included), check-in names.

## Chrono registry

ADR-P4-5 as amended, decisions P4R14, P4R15 and S14-1 to S14-12; the wire format is in [protocol/sync.md](../protocol/sync.md), the records in [protocol/chrono-record.md](../protocol/chrono-record.md).

- **Public keys only.** A marshal's phone makes its Ed25519 key and keeps the private half; the site server gets public keys, from the controller with the period each was the marshal's key (the controller keeps earlier keys after a rotation) or from the marshal's own account. A lost phone means a new key; the old one keeps its period, so what it signed still verifies. A field's admin can revoke a key as compromised.
- **Verified, verbatim.** Each synced reading is verified with `atalaia_controller.chrono` (the controller's own code and the shared vectors) against the keys of its marshal that were valid when the controller received it, and stored exactly as the controller sent it. One that fails (`format`, `unsigned`, `marshal`: no key valid then, `signature`, `conflict`: another record under a stored id) is kept apart with its reason for the field's staff and named in the answer, never silently dropped; one kept apart for want of its marshal's key is checked again when the key arrives. A reading sent twice is a duplicate.
- **Violations:** a spot check the controller judged `fail` or `warn` becomes one violation per series, at its highest-energy reading; staff record what was done. Since PKD-3 (migration `0018_chrono_violation_delta`) the controller sends the class limit with each reading (`limit_j`, additive), and a violation has `limit_j`, `delta_j` (the deciding reading's energy minus the limit; null when the controller sent none) and `repeat_offender` (the player has an earlier violation at the field, by the deciding readings' times, worked out again whenever one arrives), in the staff's list, the player's own history (`GET /api/v1/me/chrono`) and the field export (`chrono_violations`).
- **Sharing between fields** (ADR-P4-5): both fields switch it on, and the person consents for each of the two fields; the other field's staff then see the person's readings, each with the marshal's public key, so they can check them without trusting this server. Per-field player ids are never matched with each other: only an account that holds both links them.
- **Player ids and accounts:** `field_player_ids` says which of a field's pseudonymous player ids are an account's: made on the account's first registration at the field, or adopted from the phone (plan phase 16, below). The person's own history (`GET /api/v1/me/chrono`) follows it.

## Scheduling and the field page

ADR-P4-11 and ADR-P4-12, decisions F13, F18, F19 and S15-1 to S15-12; for readers of the pages and feeds, [docs/feeds.md](docs/feeds.md).

- **Who:** the field's `admin` and `gm` (in a TOTP session) make and edit scheduled games; only the `admin` publishes and cancels (F13). A draft is seen by staff only and can be deleted; a published game can be edited or cancelled with a reason, never deleted or made a draft again, since it may already be in someone's calendar.
- **Times** are sent as RFC 3339 with an offset, kept in UTC and shown in the field's time zone (`fields.timezone`); a game lasts at most 14 days; a registration window must close before the start.
- **Calendars:** a published game's start, end or place changing, its cancellation, or the field's address changing for a game that shows it raise its iCalendar `SEQUENCE`, so subscribed calendars update the event.
- **The public page** is off until the field's `admin` turns it on (`public_page`). It is HTML made on the server from `web/templates/` with every value escaped, no JavaScript and nothing loaded from another site, so it works under the security headers' content security policy as it is; the game pages carry schema.org `Event` JSON-LD as data. Portuguese (pt-PT) and English.
- **Registration** (plan phase 16, below): the game page shows a *Register* button and the JSON feed `"open": true` only while the window is open and places are left; the places left count the live registrations.
- **No personal data** on the pages or in the feeds: never who registered or how many, only the places left.
- **HEAD** is answered like `GET` without the body, for calendar clients (decision S16-10).

## Registration and game day

ADR-P4-11 as amended, decisions F14-F17 and S16-1 to S16-12; the sync's part is in [protocol/sync.md](../protocol/sync.md), the ticket in [protocol/checkin.md](../protocol/checkin.md).

- **Registering** needs an account (F14) and a published game whose window is open (a game with no window takes no online registration) and has places left (no waiting list, F17). The player gives a display name for the game (the username by default), a team preference, the federation number when the game asks for one, and, when the game wants them, up to the field's `max_replicas` pre-declared replicas: one of theirs in the field's registry, or a type and a class of the field's `limit_template` (the controller's own templates, `app/lib/chrono/limit_templates/`). The player changes or cancels until the window closes; the field's `admin` and `gm` until the game starts, and they also restore a withdrawn registration, move one to another game of the field (the ticket stays valid: it holds the registration, not the game), note who paid (no payment is processed) and, after the game, mark a registered player who did not come (Phase 4 follow-up FU7, decisions FU7-1 to FU7-5; the audit log has `registration_restore`, `_move`, `_paid` and `_no_show`, never a name).
- **The player's id at the field** is made on the first registration there (`p-` and 12 base32 characters). A player whose phone already checked in there without an account claims that id instead (`POST /api/v1/me/player-ids` with the phone's id and secret): the site server keeps the secret's SHA-256 in a claim, and the field's controller, which holds the hash from the phone's first check-in, confirms or refuses it at its next sync. The site server never had the controller's hashes, and still has none.
- **The ticket:** 32 random bytes per registration, shown once (`ticket`, the app's, and `ticket_text`, an `atalaia:ticket:` code to print); only its SHA-256 is kept and sent in the roster. It matches an arrival to a registration; it is no game credential.
- **Game day:** the controller pulls the schedule of the next 14 days; the GM makes the game from a scheduled game (the console's *Create from the schedule*), which links the two (`scheduled_games.controller_game`) and moves the scheduled game to `in_progress` and `completed` with the game. The controller pulls the roster until the game starts: registrations become expected check-ins with their replicas already in the "replicas to chrono" list. After the game it pushes each registration's outcome (`checked_in`, `no_show`), its declarations' final states and the walk-ins as a count; a registration it had only from the app is matched by its ticket's hash. The controller is the authority: nothing from the site server changes a game that has started.
- **Chrono sharing across a hosted hub's fields** (decision SVX-2, ADR-P4-4's amendment of 2026-10-28; `hub_share.py`, `api/hub_share.py`, migration 0021): in hosted mode each field is a schema with its own accounts (S21-2), and the server's role may read nothing outside it, so two fields share through three tables in `public` that the hub owns (`atalaia_share_members`, `atalaia_share_records`, `atalaia_share_codes`) and one function, never a query across schemas. The person links their accounts with a code (made at one field, given at the other; nothing is matched by e-mail or user name). A field publishes the signed records of a linked person's player ids, exactly as stored with the marshal's public key, only while the person has a live `chrono_sharing` consent for that field and the field has `chrono_sharing_enabled`; it publishes when the consent, the switch, the link or an adopted id changes, as each reading arrives, and again at the retention purge, and withdraws at once on a withdrawal, an unlink, an erasure of the account or of the player's records. The server's role has one row-level policy on each table (its own tenant's rows only); it reads another field's records only through `public.atalaia_share_read`, a `SECURITY DEFINER` function that takes the tenant from `atalaia.tenant` and returns them only when both fields are active for that person and the other field is not suspended. `hosted check` verifies the tables (row-level security enabled and not forced, the one policy, the server role's exact privileges) and the function; `hosted delete` removes the field's rows (the counts are in the hub's audit log). The results join the other-field records in `shared_history`, so the staff's lookup and the roster pull below work as before. A single-field server, or a self-hosted database with several fields, has no hub: the account's own links do it, as below.
- **Other fields' chrono records for the roster** (decision S14-5): `GET /api/v1/sync/chrono?scheduled_game_id=` answers, for the players of that game's roster only (live registrations that hold an account), what the staff's lookup would (`chrono_registry.shared_for_players` over `shared_history`): both fields with `chrono_sharing_enabled`, the account that holds the id at both, and that person's live `chrono_sharing` consent for each field; each record as signed, with its field's name and the marshal's public key, the newest 100 per player. The audit log has `chrono_shared_pull` with the counts, never the players. The controllers verify each signature and keep the records apart from their own readings ([protocol/sync.md](../protocol/sync.md)).
- **In the app** (decisions S16-13, S17-10 to S17-16): *Participante › Inscrições online* logs in to the site (password, then the TOTP step; the refresh token rotated as the server asks), lists the field's games (`GET /api/v1/fields-by-slug/{slug}`), registers with replicas, keeps the ticket on the phone and can send it at check-in, changes and cancels, and claims the phone's player id. The public register page opens it with an `atalaia://register?site=&field=&game=` link, or the page's address pasted into the app. The app does not make accounts (no privacy notice to show yet, S17-16).

## Registration import and platform adapters

ADR-P4-12, decisions F20-F23 and S17-1 to S17-9 (S17-10 to S17-17 are the app's); the details are in [docs/integrations.md](docs/integrations.md).

- **The membership number does not outlive the card check** (decision LEG-5, `services/registration.py` `erase_numbers`, `sync.py`): the server erases its copy of a registration's number when the controller's outcome arrives (`POST /api/v1/sync/checkins`) or when the game it was made into ends; the APD and the expiry stay to the 30 days of the retention ([protocol/apd.md](../protocol/apd.md#the-card-check)).
- **Association membership, historically "APD"** (migrations `0016_apd_membership` and `0019_field_country`, `protocol/apd.md`; the names stay as they were): the field's `country` (`fields.country`, PT for the existing fields in Portugal's time zones) picks the wording (the staff pages and the public game page say "APD" for PT and "association membership" otherwise: `<key>_m` twins at the end of `staff_i18n.py`, swapped in by `static/staff/staff.js`) and the entries of the shipped list a field offers (`field.apds` in `fields-by-slug` and the registration list: the country's; the rule's `custom` come on top); it travels as `settings.country` in `GET /api/v1/sync/field?settings=1`. The rule: the field's rule (`fields.apd_rule`: accepted APDs or any, needed to register, checked at check-in, expiry checked, the field's own APDs) is set by its admin with `PATCH /api/v1/fields/{field_id}` and travels in `GET /api/v1/fields-by-slug/{slug}`, the staff's registration list, the public game page, `GET /api/v1/sync/roster` (`apd`, only when the rule asks) and `GET /api/v1/sync/field?settings=1` (`settings.apd`, with a `field.changed` note on the stream when the rule changes). A registration body takes `apd_id`, `membership_number` (or the old `federation_number`: the same column, an old number is "membership number, APD unknown"; both given must agree) and `membership_expires` (`YYYY-MM-DD`); a rule with `register` refuses a missing number, an APD it does not accept and an expiry before the game's day (400 `membership_missing`, `apd_not_accepted`, `membership_expired`), staff are never refused. The verdict (`apd_status`: valid, expired, not accepted, missing; null when no rule asks) is worked out when shown, never stored. The number, the APD and the expiry are erased together 30 days after the game, with the account's erasure and in the export, like the federation number.
- **Only what the check-in needs:** `display_name`, `external_ref`, `team_preference`, `federation_number`, `apd_id`, `membership_expires`, `replicas` (the two membership columns are optional; an older file without them imports as before). Any other column is named in the answer as not imported and its values are never stored or logged.
- **Preview, then import:** `dry_run=true` writes nothing; a real import needs `basis_confirmed=true` (the field is the data controller of the list it brings and must have its own basis for it). A refused row does not stop the others.
- **Idempotent:** rows upsert by `(source, external_ref)`; the same export imported again leaves everything `unchanged`, and registrations of that source missing from the file are listed, never cancelled. Imported registrations have no account and no ticket (the marshal ticks them by name), count toward `max_players` and go in the roster.
- **Guests:** imported registrations are deleted 30 days after their game (ADR-P4-8).
- **Adapters** only through a platform's documented API or a written agreement; off by default per field; configuration encrypted; every call audited; a failing or slow platform (20 s) fails only that call. Only the test adapter ships (`ATALAIA_TEST_ADAPTER=on`); no adapter for jogarairsoft.pt or any other named platform (F22).

## Club profiles and branding sync

P4R19, decisions S18-1 to S18-12; the sync's part is in [protocol/sync.md](../protocol/sync.md).

- **Clubs** are organisations' profiles: a name, a short name (the name its teams carry on controllers, 32 characters at most), a slug, a description, a colour, a logo and a crest. Any account can make one and becomes its `admin`; admins invite accounts by username and the person accepts; a club keeps at least one admin. Club roles need no TOTP.
- **Images** (club logos and crests, a field's logo and wallpaper, a saved team's crest) are checked with the controller's own `images.py`, the same limits (logo 1 MiB and 16-2048 px, wallpaper 4 MiB and 320-4096 px, crest 512 KiB and 16-1024 px; PNG, JPEG or WebP; SVG refused; metadata stripped) and stored once by the SHA-256 of the checked bytes. Every upload must say `rights_confirmed=true` and is answered with the rights reminder: upload only images you have the right to use. An image nothing uses is purged a day after its upload.
- **Public club pages** (`/c/<slug>/`) are off by default; a club's admin turns one on. Each has a report button (a plain form; a reason and a text; no address kept; 5 reports an hour per address); a server administrator sees the reports and can hide a page, which is then a 404 like a page that never existed, though fields that saved the club's team keep it. The staff club page (`/staff/clubs/<club>`) lists the fields where the club plays, from `GET /api/v1/clubs/{id}`'s `fields` (a member sees every field that saved a team of the club, a field with a public page as a link to its page; SV8-1).
- **A field's branding and saved teams** are edited by its staff; a club's team uses the club's short name and crest unless it sets its own; names are unique per field. Controllers with `[sync] branding = "site"` pull them (`GET /api/v1/sync/field`, with `?settings=1` for the field's check-in settings too; every change to them sends the field's connected controllers a `field.changed` note on the stream, `RemoteHub.announce_field`, so they pull at once; since PKD-1 so does a change to the scenario library (a scenario saved with a changed manifest or archived, a preset made, replaced or deleted: `what: ["library"]`) and to the schedule (a scheduled game created, changed, published, cancelled or deleted: `what: ["schedule"]`), which the controllers pull at once too; a standby controller does it by its own sync, BR24) and fetch the images they lack by SHA-256 (`GET /api/v1/sync/images/{sha256}`, only the field's own), check each again and apply them; with the default `"local"` nothing is pulled.

## Device health, firmware catalogue and remote GM

ADR-P4-3's amendment, P4R12, RESEARCH section 8; decisions S19-1 to S19-11; the stream's messages are in [protocol/sync.md](../protocol/sync.md).

- **Device health** needs nothing new from the controllers: it reads the nodes they sync (battery, RSSI, SNR, platform, firmware, core version, tier, last seen) and the `node.online`, `node.offline`, `battery.low` and `node.tamper` events. The controller logs `node.online` and `node.offline` about each box (`[health] node_offline_s`, 120 s of silence by default) and `battery.low` from a box's reported level when the box does not send its own; a Field Box with a battery gauge sends its own (decisions FU1-1 to FU1-6; `tests/test_device_health_e2e.py` runs the real controller into this API). Across games a device is its name (node ids are per game). Battery is low under 20 %; a node of a live game is silent after 3 minutes unheard; outdated means the catalogue has a newer verified stable release for its platform.
- **The firmware catalogue** is a list only: no image is stored, served or sent anywhere (the field controller holds the images it offers its boxes, uploaded by the GM; decision FU3-3), and a box verifies an image itself before installing it ([protocol/firmware-update.md](../protocol/firmware-update.md)). The manifest and signature code is the controller's shared `firmware_release.py`; the same fields make the `.release.json` of `tools/firmware_release.py`. An entry must be signed with Ed25519 by a key in `ATALAIA_FIRMWARE_KEYS`, over the text `atalaia-firmware-release-v1` followed by `platform=`, `version=`, `size=` and `sha256=` lines (each ending in a line feed); entries are checked again whenever they are listed. Pre-releases are never the latest.
- **The remote GM** works only with a controller that sets `[sync] remote_gm = true`: that controller opens `WS /api/v1/sync/stream` with the field's API key and keeps it open; the site server never connects to it and holds none of its tokens. Only a user with the `gm` role on the field, in a TOTP session, may read its live view or send it a command, and only from the list (no score adjustments, ownership, reboot or setup); the controller checks every command again and refuses all of them while its setting is off. Every attempt is in the audit log (`remote_gm_command`, with `params.force` for a forced start, and `remote_gm_denied`), and the controller logs each command it gets (`GET /api/v1/remote-gm` there). The links live in the server's one worker process. **Positions** (PKD-5, the maintainer's decision of 2026-10-28: a remote GM sees them whenever players share them with the field controller): the controller sends them in a `positions` message (the live game's players as a GM of the game sees them), the site server keeps the last one of each link **in memory only** (replaced whole, dropped with the live game or after 90 s) and shows it as each controller's `positions` in the view and the server-sent stream, to the field's `gm` in a TOTP session and nobody else; they are never stored and never logged, and those of a link that did not say `remote_gm: true` are dropped. The remote GM page lists them (it has no field plan).

## Remote ATAK

Phase 4 follow-up, decisions FU5-1 to FU5-20 (ADR-P4-7's amendment; M9-10 and S19-10, which deferred it). Off by default. A field's staff away from the field (or a TAK client in a command post) see the field's boxes and zones on ATAK, through this server; player positions only where P4R18 allows.

- **In.** A field controller with `[atak] remote = true` pushes its CoT events on the sync's WebSocket it opened itself (`cot` messages, [protocol/sync.md](../protocol/sync.md)); this server never connects to a controller (P4R12). Each event is checked with the shared `sync_format.cot_event` (only Atalaia's own uids, spot markers and players, the detail elements the emitter writes with only its attributes in its forms, so no `contact endpoint`, free icon path or long remark; no DOCTYPE, entity, comment or CDATA) and serialised again; a field's current picture is kept in memory until its events go stale (1,024 uids a field at most, each 2 hours at most), never stored. At most 120 `cot` messages a minute per field.
- **Out.** With `ATALAIA_ATAK_RELAY=on`, a small asyncio TLS server in this process (`atak_relay.py`) on port 8089, published straight from the server's container (Caddy's image has no layer-4 proxy; server/docs/DEPLOY.md). TLS 1.2 or 1.3 only (ECDHE with AES-GCM or ChaCha20 on 1.2), no compression or renegotiation, a **client certificate required**: signed by a field's CA (checked by OpenSSL in the handshake, with its dates and `clientAuth`), then found in `atak_certs` by its SHA-256, of that CA's field, not revoked, not expired, and its holder still holding a role on the field. The certificate's field picks the field, and in hosted mode the tenant (a suspended field is refused); a device only ever gets its own field's events. Player positions go only to a certificate issued with `positions` whose holder has the field's `gm` or `marshal` role, checked at every connection and again every 30 s. What a device sends is thrown away (TAK's ping is answered). Connections: 16 open and 30 new a minute per address, 64 per field, 256 enrolled devices in all, 10 s for the handshake; connections still in their handshake have their own room (64 in all, 4 per address), so they never take the enrolled devices'; an IPv6 address counts by its /64.
- **Enrolment.** The field's `admin` or `gm`, in a TOTP session, issues a certificate for a named device (for themselves or another member with a role on the field; one that sees positions only if the issuer, too, has `gm` or `marshal` there, since the issuer receives its key), at `/staff/fields/<field>/atak` or through the API above: an RSA 2048 client certificate from the field's CA (RSA 3072, made on the field's first certificate; its private key kept only sealed with a key derived from `ATALAIA_SECRET_KEY`, never exported), valid 90 days by default (`ATALAIA_ATAK_CERT_DAYS`; 365 at most; decision SVX-1), handed out once as a TAK data package (`MANIFEST/manifest.xml`, `certs/atalaia.pref` with one `host:8089:ssl` connection, `certs/truststore.p12` with the relay's CA, `certs/client.p12` with the device's key and certificate, AES-256 PKCS#12) and its password, shown once and not in the package. The server keeps neither the device's key nor the password. The staff page shows each certificate's expiry and says, above the table, when one expires within 14 days (the API's `expiring` flag and `warn_days`): the way to renew is to issue a new package for the device and revoke the old certificate. The relay's own certificate comes from a CA whose key is derived from `ATALAIA_SECRET_KEY` (the same certificate after every restart): changing the secret key means every device's package must be made again. A revoked certificate is refused at once and its connections closed (by the API, an erasure or a CA's rotation; the operator's command within 30 s); an expired one is refused in the handshake. The operator can also issue a package with no holder (boxes and zones only), list and revoke: `python -m atalaia_server atak issue --field SLUG --device NAME --out FILE.zip`, `atak list`, `atak revoke`.
- **Logged.** `atak_cert_issued`, `atak_cert_revoked`, `atak_connect` (with the device's address and who issued the certificate) and `atak_refused` (why, at most once a minute per certificate) in the audit log. A holder's certificates are their personal data (access, export; erasure revokes them and replaces their devices' names in the audit details too, and takes the account's id out of them; a row goes 30 days after it expired).
- **Not yet.** Tested in software in Docker (a TLS client from the package, the real controller through the real site server, the deployment through its published port), **not with a real ATAK device** (HW3) or a real deployment. No CRL or OCSP (the relay's own list is the authority), no TAK Server federation, no data from a device to anyone.

## Game history and the scenario library

Plan phase 20, decisions S20-1 to S20-8; the sync's part is in [protocol/sync.md](../protocol/sync.md).

- **History.** The field's list and each game's views derive everything from what the controllers synced: the totals from the per-node counters plus the GM's adjustments (P4R10), the timeline from every rise of a counter as it arrived (the sync interval, 30 s during a game, is its resolution), the log as the controller logged it.

The field's game presets sit beside it. Every controller of the field with `[sync] library = true` (the default) installs what changed, checking it again; a standby gets the same scenarios (M8-3).

- **The pages FU9 added** (decisions FU9-1 to FU9-7): **roles** (and a game's roles), **sync keys** (labelled, at most two live, the key shown once, then its fingerprint), **branding** and **clubs**, **platform links**, the **firmware** catalogue and **server administration**. Each only makes the calls its API has, with the roles the API requires (shown in words when refused); no endpoint beyond the remote GM's stream was added.
- **Settings** (FS-*; `/staff/fields/<field>/settings`, the field's `admin`, linked from the field's section list and from `/staff/`): what was only reachable through `PATCH /api/v1/fields/{field_id}`, in five sections each saved on its own with only its own members: the public page (`public_page`, `description`, `address_text`, `federation_label`), the check-in rules (`limit_template`, `max_replicas`), the membership rule `apd` (accepted list or any, register, check-in, expiry and the field's own entries, offered from `GET /api/v1/apds?country=`), chrono sharing and `country`, and (RET-1, RET-2) a sixth section, **Data retention** (`chrono_retention_days`, `game_retention_days`). The membership words follow the country by the `_m` twins (`staff_i18n_settings.py`, swapped by `membershipWording` in `staff.js`, which now also puts the APD words back); saving a new country changes the words and the offered list on the page at once. Every refusal of the PATCH has its own text (`e_<code>`; a test lists the codes from the API's source), the page says that the controllers get the change at once (the API's `field.changed`), and it knows no rule: no endpoint, no new refusal code.
- **Data and limits** (PKC-1; `/staff/fields/<field>/data`, the field's `admin`): the field's data export (the API's rules; the ZIP is read with the bearer token and offered from a `blob:` address, its SHA-256 shown) and what the field uses of each hosted limit (`GET /api/v1/fields/{id}/quotas`; a single-field server says it has none). The game page shows nothing of a game under another field's address (PKC-4). The score timeline's `t` is game time, pauses not counted (PKC-2); a club's page and `GET /api/v1/clubs/{id}` list the fields where it plays (PKC-3).
- **No data in the page.** Each page is rendered here, every text escaped, and holds nothing of the field: its script (`static/staff/`, ES modules from this server only, which the content security policy already allows; no inline script, no inline handler, nothing from elsewhere) asks the API for the data with the access token in `Authorization: Bearer`, exactly as the app does. So each page has its API's role rules and no others: the field's `admin` or `gm` for the schedule (and the registrations and the roster, which are personal data; publishing and cancelling a game are the `admin`'s), the library, presets and devices, any role for the history, `gm` (in a TOTP session) for the remote GM's view and commands, `admin` or `gm` for its log and for remote ATAK; a refusal is shown in words, with a note when the session did not pass TOTP.
- **The session.** The access token is kept in the tab's `sessionStorage` until it expires (15 minutes); a new one comes from `POST /api/v1/auth/refresh` with the HttpOnly, `SameSite=Strict` refresh cookie (path `/api/v1/auth/refresh`) and the header `X-Atalaia-Refresh: 1`. Refreshes run one at a time across the site's tabs (Web Locks), since a reused refresh token ends the session. Logging out ends the session for every tab.
- **CSRF.** No request is authorised by a cookie alone: every state-changing call carries the bearer token, which another site cannot read or send, and the refresh needs a header a cross-site form cannot send. The pages' forms are disabled until their script runs, so nothing is ever submitted without it.
- **Escaping.** The scripts write every value with `textContent` or as an attribute through one helper; links are paths on this site only. A test reads the scripts for `innerHTML`, `eval` and anything loaded from elsewhere.
- **Accessibility.** Every control has a label, refusals and results are announced (`role="status"`), the chart has a table beside it, flags are words as well as colours, and the pages work at a phone's width (tables scroll inside their own box). The validator's problem messages are in English (their codes and paths are shown as well).

## Hosted mode

Plan phase 21, ADR-P4-4 as built, decisions S21-1 to S21-13; its deployment (a Phase 4 follow-up, decisions FU4-1 to FU4-10) is in [docs/DEPLOY.md](docs/DEPLOY.md#hosted-mode). Off by default; it does not go live before the legal review (P4-6).

- **One schema per field.** Each hosted field (a tenant) is a PostgreSQL schema `field_<slug>` holding every table a single-field server has, at the same Alembic revision; `public` holds only the hub's registry (`atalaia_tenants`, which the server may read and not change) and the hub's audit log (`atalaia_hub_audit`, which the server cannot read). Accounts, clubs and everything else are per field: a player at two hosted fields has two accounts. One field per tenant: `POST /api/v1/fields` answers `403 hosted_one_field`.
- **Routing by host name.** `https://<slug>.<ATALAIA_HOSTED_DOMAIN>` picks the field (`tenancy.TenantMiddleware`), and so does the field's one **custom host name** once it is verified (below); any other name gets `404 unknown_field` (a WebSocket is closed with 4404), a suspended field `403 field_suspended`; only `GET /api/v1/health` answers without a field. A controller's API key is checked inside the field its host name chose, so a key never selects a field by itself. Access tokens carry their field and are refused at another; login and TOTP lockouts and the remote GM's links are kept per field; the field pages and feeds link to the field's own address.
- **Scoped sessions.** Every database transaction of a request starts with `set_config('search_path', <schema>, true)`, `set_config('atalaia.tenant', <schema>, true)` and `set_config('role', <the field's database role>, true)` (`SET LOCAL ROLE`), all transaction-local, so a pooled connection never carries a field into the next request. A session with no field, and every connection outside a transaction, has only `pg_catalog` on its path: nothing resolves.
- **A database role per field (S21-13, decisions S2113-1 to S2113-8; `tenant_roles.py`, migration `0023_tenant_roles`).** The policy below keys on a setting that any statement able to call `set_config` can rewrite, so the grants, not the setting, now keep the fields apart. Each field has a database role `atalaia_t_<the field's id, 32 hex digits>` (made from the registry's `field_id`, never from text a user typed; `NOLOGIN`, no superuser, no `BYPASSRLS`, owns nothing) that alone holds the grants on the field's schema, tables and sequences and on its rows of the hub's sharing tables. The server's login role (`atalaia_app`) holds **no** grant on any field's table or schema: it reads the registry, adds to the quota inbox, and may `SET ROLE` to a field's role (`GRANT <role> TO atalaia_app WITH INHERIT FALSE, SET TRUE`), which every request's transaction does first. A request for field A that runs `set_config('atalaia.tenant', <B>, ...)` is refused B's schema outright (`permission denied`), reading or writing. Because PostgreSQL authorises `SET ROLE` by the *session* user, a field's role must also not be able to call `set_config` from inside a statement (it could `set_config('role', <B's role>, true)`): `server/hosted-roles.sh` revokes `EXECUTE` on `pg_catalog.set_config` from `PUBLIC` in the hub's database and grants it to the owner and the server's login role only, the server refuses to start while any role can call it, and `asyncpg`'s own type introspection (which calls `set_config('jit', ...)`) is told not to (`tenancy.keep_set_config_to_the_server`). **What is left, stated plainly:** `SET ROLE` as a *command* still works for the session user, so a second statement that is one would switch fields; the server's driver sends one statement per call (extended protocol, bound parameters, tested), so an injection cannot add it, and closing it for good needs a login role and a connection pool per field (an open decision, S2113-8). What runs as which role: **a field's role** runs everything a request of that field does (its schema, and its own rows of the sharing tables and `atalaia_share_read` / `atalaia_share_redeem`, whose policy and functions read the caller's field from the role in use, `atalaia_caller_tenant()`, not from the setting); **the server's login role** runs the host-name lookup, the registry watcher, the TLS `ask` endpoint and the quota notes (registry `SELECT`, quota inbox `INSERT`), and does the `SET ROLE`; **the owner role** (needs `CREATEROLE`) runs the migrations and every `hosted` command, makes a field's role when the field is created or migrated and drops it when the field is deleted; **PostgreSQL's superuser**, inside the database container, runs the backups and `hosted-roles.sh`. The daily purge and the chrono sharing's sync run once per field, as that field's role; nothing the server does reads two fields in one statement, except the sharing's `SECURITY DEFINER` functions, which read only the hub's tables.
- **Row-level security underneath.** Every table of a field's schema has `ENABLE` and `FORCE ROW LEVEL SECURITY` and one policy, `atalaia.tenant` = that schema's name, for reading and writing: a missing setting reads nothing, and the operator's own commands (the owner role, which `FORCE` also binds) set it for themselves. The server connects as its own role (no superuser, no `BYPASSRLS`, owner of nothing, no `TRUNCATE`); it refuses to start otherwise. The schemas, their tables and the migrations belong to a separate owner role, which only the operator's commands use.
- **The operator's commands** (`hosted.py`, with the owner role's `ATALAIA_DATABASE_URL`; deployed: `docker compose run --rm hub hosted ...`): `python -m atalaia_server hosted init`, `create SLUG --name NAME`, `list`, `migrate` (every field to the newest revision, grants and policies again), `check` (every schema and table owned by the owner, row-level security forced and the one policy on every table, each field's database role and its exact grants, the server role's none; exit 1 on any problem), `suspend`/`resume SLUG --reason`, `export SLUG --out FILE --reason`, `delete SLUG --confirm SLUG --reason`, and, from PKC-5 and PKC-6, `quota SLUG NAME VALUE --reason` (a field's own limit over the hub's), `usage [SLUG]`, `quota-hits` (the notes of fields refused for a quota, into the audit log) and `domain set|verify|remove SLUG ...` (a custom host name, below); each is written to the hub's audit log. `create-admin --field SLUG` makes a field's administrator; `purge` and the daily purge run once per field.
- **Export and deletion of a field.** The export is one ZIP (mode 0600, never overwriting a file): `manifest.json` (revision, tables in load order, columns, row counts, SHA-256 of each file), `README.txt` and every table of the field as CSV, read in one repeatable-read, read-only transaction: the field's whole dataset, personal data and credential hashes included, for the data controller on their instruction. `python -m atalaia_server import-field FILE` loads it into an empty single-field server at the same revision (everyone logs in and enrols TOTP again; platform links are set up again, since their secrets were sealed under the hub's key). Deletion drops the field's schema with every row in it and the registry row in one transaction, and the hub's audit log keeps who, when, why and the row counts per table (never a row). Backups still hold a deleted field until they expire (`ATALAIA_BACKUP_DAYS`, 30).
- **A field's own data export** (S21-12; `GET /api/v1/fields/{field_id}/export`, `field_export.py`, `api/export.py`). The field's `admin` (in a TOTP session; a server administrator of that field's schema counts as one) downloads a ZIP, format `atalaia-field-data` 1: `manifest.json` (time, field, server version and migration revision, mode, and for each dataset its file, rows, columns, omitted columns and SHA-256, and the tables left out with the reason), `README.txt` (English and Portuguese) and `data/<table>.jsonl`, one JSON object per line, built in one repeatable-read, read-only transaction. It is the field's own data, **not** the operator's whole-schema export: never in it are password hashes, TOTP secrets, sessions and refresh tokens, API keys' hashes, tickets' and claims' secrets, platform credentials, the ATAK CA's private key, e-mail addresses or IP addresses; the personal-data rules apply as the server holds the data now (what the retention purge or an erasure removed or anonymised is not there). In hosted mode every row of the field's schema (accounts with or without a role, clubs); on a single-field server the rows of that field only. Every export is audit-logged (`field_export`: who, the file's SHA-256, its size and the rows per dataset; the answer carries the same hash in `X-Content-SHA256`). Limits: one at a time per field (`409 export_running`), one per `ATALAIA_EXPORT_MIN_INTERVAL_S` (`429`, `Retry-After`), at most `ATALAIA_EXPORT_MAX_MB` (`413 export_too_large`; use `hosted export` or the backup). `tests/test_field_export.py` fails when a table is neither exported nor listed as skipped, or an exported column looks like a secret: a new table or column needs the decision in `field_export.py`, as `personal_data.py` asks for personal data.
- **Quotas per field** (S21-12; `quotas.py`). One field cannot fill the database for the others: past a limit the request is refused `409` with `{"detail": "quota_exceeded", "quota": NAME, "limit": N}` (the sync answers the same body, a refused game is not stored; a controller's stream past its quota is closed with 4429 before it is accepted; an import refuses the rows past the registrations' quota with the row code `quota_exceeded`). Nothing is ever deleted to make room; the retention purge does. The limits and their defaults are in the settings table (`ATALAIA_QUOTA_*`); they are per field, the same for every field, and only hosted mode has them. Counts are taken just before the insert, so two requests racing at the limit may both pass: it guards against runaway growth, it is not a billing meter. Scenarios and presets keep their own fixed caps. **PKC-5 added**: the operator's per-field limits (`hosted quota`, kept in the registry's `quotas` column and applied on the next request, over `ATALAIA_QUOTA_*`); `stored_mb`, what the field's schema takes (`pg_total_relation_size`, cached 30 s; checked on the sync, an image, a scenario and a registration import, so a burst can pass it a little); and a note for the hub operator when a field is refused (`public.atalaia_quota_hits`: the server's role may only insert; at most one per field and quota every 10 minutes; `hosted quota-hits` moves them to the hub audit log, and `hosted list` and `hosted check` count them; no e-mail). The field's own administrator sees the use read-only on `/staff/fields/<field>/data`.
- **One social login callback for the whole hub** (LG-14 to LG-19, ADR-P4-13; `api/oidc_relay.py`, `oidc.py`, `relay-on.caddy`). Opt-in with `ATALAIA_OIDC_RELAY=on`. Every field sends the provider the hub's own address; the `state` it sends is `r1.<random>.<slug>.<provider>.<s|c>.<expiry>.<HMAC>` (a key of its own, derived from `ATALAIA_SECRET_KEY`). The hub's callback (outside any tenant) checks the signature and expiry, reads the field's row in the registry (unknown or suspended: one plain 400 page, nothing forwarded) and answers a body-less `303` to the field's own callback on the host the *registry* gives (`<slug>.<hub domain>`, or the active custom host name when the login began there), carrying only the state and the `code` (or `error=denied`). The field re-reads the state (its own slug, the provider in the path, not expired), then does what it always did: the binding cookie, one-use login row, code exchange, ID token and nonce. So a result for another field is refused, nothing in the request chooses the target, and the field's database role is never touched by the hub. The app's return to `/app/oidc` is unchanged.
- **A custom host name per field** (PKC-6; `tenancy.py`, `hosted.py`, `dnsquery.py`, `tls_ask.py`, `Caddyfile.hosted`). One name besides `<slug>.<domain>` (two or more labels; not under the hub's domain; one field per name) in the registry, set by `hosted domain set` as *pending* with a DNS TXT challenge (`_atalaia-challenge.<name>` holding `atalaia-verify=<token>`), turned on by `hosted domain verify` only when that record is there (read through the machine's resolver by a few lines of standard-library DNS), routed like the field's own name, and given a certificate by Caddy through the `ask` endpoint only while it is an active field's verified name. Pages' links, feeds and a passkey's origin follow the name the request came by, so passkeys are per name; controllers and the ATAK relay keep the addresses they have, and social login needs the name's redirect address registered at each provider unless the hub-level callback relay is on (`ATALAIA_OIDC_RELAY`, below). `hosted migrate` upgrades an older hub's registry; a server that finds the older one refuses to start. See [docs/DEPLOY.md](docs/DEPLOY.md#custom-domains-per-field).
- **A deleted or suspended field's open sockets close at once** (S21-12; `tenant_watch.py`). The operator's commands run in another process, so while any controller socket, remote-GM link or ATAK relay connection is open the server reads the registry every `ATALAIA_HOSTED_WATCH_S` seconds (2) and closes what belongs to a field that is gone (4404; also a slug made again under another field id) or suspended (4403): the stream's handler ends, the remote-GM link is dropped (a command waiting on it fails `controller_offline` instead of timing out) and the relay's connections close. With nothing open the registry is not read.
- **The deployment** (`setup.sh DOMAIN --hosted`, `docker-compose.hosted.yml`): every field at `https://<slug>.DOMAIN` behind a wildcard DNS record; Caddy gets each field's own certificate the first time it is asked for, after the `ask` endpoint (`tls_ask.py`, its own container on the internal networks, never proxied to) says the name is an active field's: an unknown or suspended field, the hub's own name and any other name get no certificate, and past 5 checks a second (bursts of 20) it answers 429 without touching the database. The server connects as `atalaia_app`, the operator's commands as `atalaia_owner`; PostgreSQL's own superuser is used only by the scripts, inside its container. `backup.sh` dumps every field, the registry and the hub's audit log with their owners, grants and policies; `restore.sh` makes the roles again from `.env`, restores without `--no-owner`, runs `hosted check` before and after the migrations and leaves the server stopped if it fails.

## Personal data

ADR-P4-8, with decisions S12-1 to S12-8. The field operator is the data controller; `personal_data.py` lists every table that holds personal data, and each later plan phase adds its tables there (access, export, erasure, purge) in the same change.

- **Access and export:** `GET /api/v1/me/data` answers `{format, generated_at, user, field_roles, sessions, audit_log, audit_log_about_you, consents, games, player_ids, chrono_records, marshal_keys, scheduled_games, registrations, player_id_claims, clubs, club_reports, game_history}`: the account (never the password hash or the TOTP secret), roles per field, sessions with their addresses and user agents, the person's own audit entries with addresses, entries others made about the account (a role granted: what and when, not who) the consent records, the games the person holds a role on, and the chrono registry's: the person's player id at each field, per field their readings (each as signed, with the marshal's public key), replicas, violations and refused readings, and the keys they registered as a marshal; the games they scheduled as a field's staff; their registrations with the pre-declared replicas and outcomes (never the ticket) and their claims of a phone's player id; and their game history (the games their player ids appear in, with those events and the game's totals, and the games they were checked in to). Login methods add `identities` (each social login linked: provider, the subject it gave, when) and `passkeys` (name, host name, dates; never a key or a credential id). `GET /api/v1/me/export` puts the same data in a ZIP: `export/profile.json`, `identities.json`, `passkeys.json`, `field_roles.json`, `sessions.json`, `audit_log.json`, `audit_log_about_you.json`, `consents.json`, `games.json`, `player_ids.json`, `chrono_records.json`, `marshal_keys.json`, `scheduled_games.json`, `registrations.json`, `player_id_claims.json`, `clubs.json`, `club_reports.json`, `game_history.json` and a `README.txt` in English and Portuguese.
- **Rectification:** the username and email (`PATCH /api/v1/me`) and the password (`POST /api/v1/me/password`), each with the current password, under the same lockouts as a login. The audit log names the fields changed, never their values.
- **Erasure** (`DELETE /api/v1/me`, with the password and, for an account with TOTP, a code) anonymises: the account becomes `deleted-` and 16 random hex characters with no email, no password, no TOTP and no consent; its roles, sessions, consents, social logins and passkeys are deleted; its links to per-field player ids go, while the signed chrono records stay exactly as signed (their replicas without make, model and tag, the person's marshal keys unlinked); the games it scheduled stay the field's, without the link to the account; its registrations for games still to come are cancelled, and every registration loses the account, the name, the team preference, the federation number and the ticket (the outcome and the declarations' states stay, the field's history); its claims are deleted; its club memberships and invitations are deleted, and the clubs it made and the reports it made or decided stay without it; the firmware releases it added stay without it; its audit entries stay without their addresses; the erasure is logged with no account and no address. Names starting with `deleted-` are reserved. The last server administrator cannot be erased.
- **Consents:** each one recorded in `consents` with its purpose (`account`, or `chrono_sharing` for one field) and `ATALAIA_PRIVACY_NOTICE_VERSION`; registration and `create-admin` record the account consent.
- **The privacy notice and consenting again** (decisions CONS-1 to CONS-6; the notice's text is the operator's, the server is only the mechanism): the files of `ATALAIA_PRIVACY_NOTICE_DIR` for the current version are the public page `/privacy` (`?lang=`, else the browser's language) and `GET /api/v1/privacy-notice?lang=` (`{version, lang, requested_lang, available, markdown, html, url}`; a language the version lacks falls back to the default language, then to any; 404 `privacy_notice_not_published` when no file exists). `GET /api/v1/me` carries `consent: {status, version, current_version, given_at, notice_published}`: `current`, `outdated` (given for another version) or `missing`. `POST /api/v1/me/consents/account` with `{"notice_version": "<the version shown>"}` consents again: the live consent for the older version ends (`withdrawn_at`: replaced, not taken back), a new one is recorded, `users.gdpr_consent_at` moves and `consent_renewed` is written to the audit log; a version that is not the current one is refused with 409 `notice_version_changed` and `current_version`, which an app answers by fetching the notice again. `POST /api/v1/auth/register` takes an optional `notice_version` with the same 409. **A social sign-up records the version the person saw** (CONS-7, migration `0025_oidc_notice_version`): `POST /api/v1/auth/oidc/{provider}/start` takes an optional `notice_version` (up to 64 characters); with a ticked `consent` and a version that is not the current one it answers 409 `notice_version_changed` with `current_version` (no round is begun). The version is kept on the `oidc_logins` row (empty when none was named or the box was not ticked), and the callback checks it again when it is about to make an account: if the notice changed during the round trip the browser comes back with `oidc_error=notice_version_changed` and no account is made; otherwise the consent is recorded **for that version**. A client that names none (older apps and pages) gets the server's current version at callback time, as before; a known subject (a login, not a sign-up) is not affected. The staff login page reads `GET /api/v1/privacy-notice` when it opens (404: nothing published, so it names no version), sends the version with the ticked box, and on the 409 or the error unticks the box and says the notice changed (four languages). The staff pages show the prompt at the top after login, in the four languages; nothing is blocked while consent is outdated (the account's export and erasure must always work). The access answer's `user` no longer has `data_retention_days` (the column was dropped by migration 0020: retention is per kind of data, applied by the purge).
- **Retention:** every day at `ATALAIA_PURGE_HOUR` (03:00 UTC) the server deletes sessions 30 days after they expired or ended (with their refresh tokens) and audit entries older than 36 months, games 90 days after they ended (the field's `retention_days`, plan phase 20: 30-730; the default was 24 months until the maintainer's decision of 2026-10-30), scheduled games (with their registrations) 90 days after they ended, a registration's federation number 30 days after its game, claims of player ids 30 days after they were made, imported registrations (guests) 30 days after their game, and social logins never finished after ten minutes, and the chrono registry after the field's `default_retention_days` (365 by default, the admin's to set, 30-3653: readings by their time, readings kept apart by their arrival, then replicas and keys no reading needs), club invitations not accepted after 30 days, decided club page reports after 12 months, branding images nothing uses a day after their upload, and anonymised accounts (the `deleted-...` rows an erasure leaves, and an account merged into another once that lands) as soon as nothing refers to them: no audit entry (so, at the latest, when the last entry naming them has gone by its 36 months) and no row of any table with a foreign key to `users.id` (read from the models, so a table added later is covered), the same pass that purges the audit entries freeing them; in hosted mode this runs per field under the field's database role. It logs what it deleted. `python -m atalaia_server purge [--dry-run]` runs it once (`docker compose exec server python -m atalaia_server purge`).
- **Templates** for the operator to fill in, to be reviewed by a lawyer before use: [`docs/templates/privacy-notice-pt.md`](../docs/templates/privacy-notice-pt.md), [`privacy-notice-en.md`](../docs/templates/privacy-notice-en.md) and the hosted service's data processing agreement [`dpa-template.md`](../docs/templates/dpa-template.md).

The synced games (plan phase 13) name players only by the field's pseudonymous player ids, which an account holds from plan phase 16 (its first registration at the field, or a phone's id the controller confirmed); a person's games in the access answer are still the ones they hold a per-game role on (`games` in the access answer, `games.json` in the export; erasure deletes the roles). Since plan phase 20 the games the person's player ids appear in are their game history too (`game_history`); erasure deletes the player ids, the only link. A game, with its events, counters, samples, nodes and roles, is deleted 24 months after it ended, or after the field's shorter `retention_days`.

Positions never reach the site server (decision P4R25).

## The first administrator

The first administrator is made from the command line, in the server's container: `docker compose exec server python -m atalaia_server create-admin --username NAME [--email ADDRESS]` asks for the password twice, shows a TOTP secret and its `otpauth://` URI for an authenticator app, and creates the account once a code from the app is typed back (`--password-stdin` reads the password, then the code, from standard input).

### An administrator who lost their authenticator

`docker compose exec server python -m atalaia_server reset-totp --username NAME --reason "lost phone, identity checked by ..." [--yes] [--field SLUG]` (decision S11-7; run as the operator, in the server's container; `--field` in hosted mode only). It clears the account's TOTP secret and enrolment, revokes every session of the account (access tokens stop working at once and a login half-way through the TOTP step is refused), and writes a `totp_reset` row to the audit log (the account, the operator's system user, the reason, how many sessions were revoked, `via: cli`). The password is not changed. Unless `--yes` is given it asks for the username to be typed again; an unknown account, or one with no TOTP enrolment, is refused with a message and nothing changes. The server keeps no recovery codes and no remembered devices, so there is nothing else to clear. At the next login the account gets a session that has not passed TOTP (for an administrator or a privileged role that means no administrator powers) and enrols a new secret with `POST /api/v1/auth/totp/enrol` (password) and `/auth/totp/confirm` (a code); the roles work again from the confirmed session. Check who the person is before running it: the command is the only protection that TOTP gives against someone who knows the password.

## Preview deployment

Decisions PV-1 to PV-12 ([docs/review/decisions-to-review.md](../docs/review/decisions-to-review.md)); the day-to-day commands are in [docs/runbooks/preview-server.md](../docs/runbooks/preview-server.md). A preview is a server whose address is given to teams and fields so they can look at the application with invented data and say what looks good, what is hard to use and what should change. It is **not** a way to run real games.

- **`ATALAIA_PREVIEW=on`** turns a server into a preview: a banner on every HTML page ("Preview, not for real games ... Feedback welcome"), `X-Robots-Tag: noindex` on every answer and `/robots.txt` with `Disallow: /`, a landing page at `/`, and the feedback form. Off (the default), none of it exists. Refused in hosted mode.
- **Demo data:** `python -m atalaia_server demo load` makes one invented field (`campo-demo`, public page and scoreboard on), two invented clubs, scheduled games, finished games with scores, events and boxes, a scenario and two presets. It is idempotent (fixed ids) and keeps the demo alive: the newest finished game stays "25 minutes ago" and past scheduled games move to the coming Saturdays; the preview's Compose file runs it every hour. `demo reset` deletes the demo field and clubs and loads them again (accounts and feedback are kept). `demo reviewer --username NAME --out FILE` makes a test account with the GM role on the demo field (a generated password and TOTP secret, written to FILE with mode 0600, never printed). `create-admin --generate FILE` does the same for the administrator.
- **Feedback:** `/feedback` (pt-PT, English, German, Traditional Chinese): a kind, an optional role, a message of at most 2000 characters and an optional contact; no account, no cookie, no address stored. Guarded by a signed timed token, a same-origin check, a honeypot field, a 16 KB body limit and 5 messages an hour per address (300 a day in all). The server administrators read it at `/staff/feedback`, with `GET`, `PATCH` and `DELETE /api/v1/admin/feedback`, and `python -m atalaia_server feedback list`; the contact is erased after 90 days and the row after 12 months by the daily purge.
- **Language:** `ATALAIA_LANG_FROM_BROWSER=off` makes only an explicit choice (`?lang=` or the language switcher, remembered in a `lang` cookie) change the language, and `ATALAIA_DEFAULT_LANG` (`pt` or `en`) is what nobody chose. The preview opens in Portuguese whatever the browser says.
- **Deployment:** [`docker-compose.preview.yml`](docker-compose.preview.yml) on top of `docker-compose.yml`, run by [`preview/preview.sh`](preview/preview.sh) with its settings and secrets outside the repository (`~/atalaia-preview`): no Caddy; the server published on `127.0.0.1:8000` only; a Cloudflare Tunnel that runs outside Docker (cloudflared on the host) forwards the public name to `http://localhost:8000`. The server trusts `X-Forwarded-For` only from the one Docker subnet the tunnel's connection arrives from, so a client's own header is ignored. `python3 tools/docker_server.py preview-check` checks the Compose files' promises (only 127.0.0.1:8000 published, Caddy off, restart unless stopped, pinned images, no way out for the server).
- **The live demo** (decisions DEMO-*; [docs/runbooks/preview-server.md](../docs/runbooks/preview-server.md), "The live demo"): a read-only demo game, so people get an idea of how the application works end to end. The `demo-field` service ([`preview/demo/`](preview/demo/)) runs the field controller with three simulated Field Boxes (the firmware's own game and radio code built for Linux, on a simulated radio) and a director that plays Domination games forever (players with made-up callsigns check in and walk the plan, a marshal's signed chrono readings arrive, boxes are captured, scores rise); a read-only proxy in front of it, published on `127.0.0.1:8001` only for a second Cloudflare Tunnel hostname, shows it through the GM console's read token, the scoreboard, a player's view (`/player/`) and a "Try the demo" home page (`/`, four languages): GET only, a list of read endpoints, one public read token, a one-way stream, no personal data. The controller syncs its games to a field of its own on this server (`demo-ao-vivo`, made by `python -m atalaia_server demo live`, which also makes its API key and deletes old games), so the public pages show them too; `ATALAIA_PREVIEW_DEMO_URL` puts the demo on the landing page. `python3 tools/docker_server.py preview-demo-unit` and `preview-demo` test it (a scratch Compose project).
- **Not in the preview:** the simulator and the mode editor (PV-2), the GM console except in the live demo (read-only), and any link from the project page until the maintainer asks (PV-11).

## Trying it locally

```sh
python3 tools/docker_server.py up      # builds the image, starts PostgreSQL, the server and Caddy on https://localhost:8443
curl -fsSk https://localhost:8443/api/v1/health
docker compose -p atalaia-server-trial exec server python -m atalaia_server create-admin --username admin
python3 tools/docker_server.py down    # stops it and deletes its database
```

The trial runs the deployment's own Compose file, with a certificate from Caddy's own authority (hence `-k`; browsers warn) on 127.0.0.1 only; `ATALAIA_HTTPS_PORT` and `ATALAIA_HTTP_PORT` (8443, 8080) pick other ports. `up` makes a random database password and secret key each time, which is why `down` deletes the data: this is a trial, not a deployment ([docs/DEPLOY.md](docs/DEPLOY.md) is). The image runs `alembic upgrade head`, then `uvicorn --factory atalaia_server.app:create_app` on port 8000 with one worker, as an unprivileged user; it has no compiler.

`python3 tools/docker_server.py deploy` is the deployment test (CI's `server-deploy` job): `setup.sh`, the stack behind Caddy with its own authority under the name `atalaia.test`, HTTPS, the headers, the closed ports and the sync over the WebSocket through Caddy (`tests/deploy_probe.py`, from a container on the public network only), then `backup.sh`, a damaged backup refused by `restore.sh`, and the backup restored into a fresh database with every table compared (`tools/server_deploy.py`). The stack runs with the remote ATAK relay on: the operator's `atak issue` makes a data package in the server's container, the published port answers TLS with the relay's certificate from this machine, and `tests/deploy_probe_atak.py`, on the public network and the relay's own, checks that a device without a certificate is refused and the field's device gets a box its controller pushes over the WebSocket through Caddy, before the backup and after the restore with the same package.

`python3 tools/docker_server.py deploy-hosted` is the hosted hub's (CI's `server-deploy-hosted` job, `tools/server_deploy_hosted.py`): `setup.sh hub.test --hosted` (its env file, its refusals of the other mode, the roles, the registry; no secret in any output or container log), three fields made and one suspended with `docker compose run --rm hub hosted ...`, the `ask` endpoint asked from Caddy's container, then `tests/deploy_probe_hosted.py` from the public network: each field's name gets a certificate for that name only and serves its own page, key and WebSocket sync and nothing of the other field, an unknown field, the suspended one and the hub's own name get no certificate, an unknown field's `Host` gets 404, the database, the server and the `ask` endpoint cannot be reached; the isolation as `atalaia_app` (`hosted check`; with each field's setting only that field's rows in every one of the 114 tables, with none nothing; `TRUNCATE`, the hub's audit log, the registry, dropping `FORCE`, `alembic_version` and a new table refused); `backup.sh`; `restore.sh` refusing a damaged backup, a single-field server's backup and, from a single-field env file, the hub's; then `down --volumes`, a fresh hub and the restore, with every table, the registry and the hub's audit log compared by digest, ownership, grants, policies and the roles compared line by line, the isolation checked again and the probe run again through Caddy with a new CA. With the remote ATAK relay on, before the backup and after the restore: one data package per field from `atak issue --field SLUG`, the published port answering with the hub's `*.hub.test` relay certificate, and each field's device getting its own field's box and never the other's (`tests/deploy_probe_atak.py`).

## Dependencies

The login methods (decisions LG-*) added webauthn 3.0.1 (Duo Labs' WebAuthn library, MIT; with cbor2 6.1.5, pyOpenSSL 26.4.0, pyasn1 0.6.4 and pyasn1-modules 0.4.2; cryptography was already there), pinned the same way (`--exclude-newer 2026-10-05`, every hash in `requirements.txt`); the OpenID Connect client uses PyJWT and the standard library's `urllib` only. Plan phase 19 added wsproto 1.3.2 (pure Python, on h11), so that uvicorn serves the sync's WebSocket in the image (decision S19-1). Plan phase 12 added none (the export's ZIP is the standard library's `zipfile`). Plan phase 11 added argon2-cffi 25.1.0 (with argon2-cffi-bindings 26.1.0), PyJWT 2.15.1 and pyotp 2.10.0, pinned the same way (`--exclude-newer 2026-10-05`, every hash checked against PyPI). Only `requirements.txt` goes into the image, installed with `pip --require-hashes --no-deps --only-binary=:all:` and checked with `pip check`. Every version is a release at least two weeks old when it was pinned; `requirements.in` has the command that refreshes the pins (uv's `pip compile --generate-hashes --exclude-newer`). The base images are pinned by digest: `python:3.12.14-slim` and `postgres:16.15-alpine`.
