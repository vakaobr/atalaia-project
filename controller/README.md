# Field controller

Runs on a Raspberry Pi (or any Linux machine) next to the field. It:

- keeps the official game: creates games from mode packages and presets, starts, pauses, resumes and ends them, merges every box's scores and keeps the event log,
- talks to the boxes over LoRa through a **USB radio modem** (a second Heltec V4.3 running the modem firmware),
- sends the TIME beacons that keep every box's clock in step and double as its heartbeat,
- takes part in **controller failover** (the CLAIM election, ADR-P2-8),
- runs a mode's `field.lua`, the script for logic that spans several boxes,
- serves the REST and WebSocket API, the GM console and a scoreboard page, and publishes to MQTT,
- optionally pushes its games to a **site server** (phase 4), offline first: games never wait for the network.

Licence: AGPL-3.0-or-later. Running a modified controller for other people means sharing your changes.

Status: phase 2, plan phases D and E; phase 3, plan phase E (field check-in, player tokens, chrono readings, player positions, Android props on Wi-Fi, HTTPS with the field's own CA); phase 4, plan phases 13 and 14 (the site server sync, with the field's chrono registry, in software: tested against the real site server and PostgreSQL in Docker, not yet over a real 4G link) and 19 (the remote GM through the site server, off by default, in software: tested against the real site server in Docker). Built and tested in Docker against the modem's real C code, the Field Box's real game and radio code (the host box), a real Mosquitto broker and, for the GM console, headless Chromium; not yet run on a Raspberry Pi with a real modem board and real boxes (that is plan phase F, when the boards arrive).

## Running it

On a Raspberry Pi OS or Ubuntu machine:

```sh
sudo apt install python3-fastapi python3-uvicorn python3-websockets python3-paho-mqtt \
     python3-serial python3-yaml python3-cryptography libmbedtls-dev mosquitto cmake build-essential
cmake -S core -B build -DATALAIA_SHARED=ON && cmake --build build   # the core, for field.lua
cp controller/controller.example.toml controller.toml                 # then edit it
cd controller
ATALAIA_CORE_LIB=../build/libatalaia_core.so python3 -m atalaia_controller run --config ../controller.toml
python3 -m atalaia_controller tokens --config ../controller.toml     # the GM and read tokens
python3 -m atalaia_controller join-key --config ../controller.toml   # the field join key
python3 -m atalaia_controller join-key --fingerprint                # its fingerprint (boxes show it)
python3 -m atalaia_controller join-key --rotate                     # a new key, after a field card is lost
```

Flash the modem board with the modem firmware first (`python tools/docker_fw.py modem`, then the `esptool` command it prints, or `idf.py -B build-modem flash`). Its own OLED then shows whether the controller is talking to it (`LINK OK`, `DOWN`, `waiting`), the game it is configured for, the channel, the TX and RX counts with their failures, the duty-cycle budget left and any radio fault, so a GM can tell a working modem from a stuck one without a laptop ([firmware/esp32/README.md](../firmware/esp32/README.md#the-modems-oled)). [`deploy/`](deploy/) has a systemd unit and a Mosquitto configuration with users and topic permissions.

Without a modem (`[modem] port = ""`) the controller still runs: games can be created and the API works, but nothing reaches the boxes.

Settings come from a TOML file and `ATALAIA_<SECTION>_<KEY>` environment variables; see [controller.example.toml](controller.example.toml).

## Site server sync

Off by default. With `[sync] enabled = true`, a `url` and the field's API key (made by the field's admin on the site server, `POST /api/v1/fields/{field}/sync-keys`, shown once), the controller pushes every game to the site server: its metadata, its event log in id order, its score counters per source and its nodes ([protocol/sync.md](../protocol/sync.md), ADR-P4-3 as amended); and then the field's chrono registry: the marshals' public keys with the period each was the marshal's key, the replica registry and every signed reading with its series and outcome, the record as the text the controller stored (ADR-P4-5 as amended; the site server verifies each one again). It opens every connection (a field behind a phone's 4G link cannot be reached); the site server holds none of its tokens.

```sh
python3 -m atalaia_controller sync-key --config ../controller.toml           # paste the key (stored in the store, mode 0600)
python3 -m atalaia_controller sync-key --status --config ../controller.toml  # where the key comes from, its fingerprint
python3 -m atalaia_controller sync-key --resend --config ../controller.toml  # a new site server: send everything again
```

`[sync] api_key` or `ATALAIA_SYNC_API_KEY` win over the stored key. The site server's certificate is checked against the system's CAs, or `[sync] ca_file`; `http://` only to this machine. **Offline first:** the client is a thread that reads the store; the game runs the same with or without the network. It syncs every 30 s while a game runs and every 5 min between games, doubling the wait after a failure (up to 5 min) and following `Retry-After`; a game's start, pause or end wakes it. Each game's cursor (the last event id the site server acknowledged) is kept in `sync_state` (store schema 5), so a restart resumes where it was, and a batch sent twice is harmless (the site server drops duplicates by the events' own key). What was sent of the chrono registry is in `sync_items` (store schema 6), so each key, replica and reading goes once, and again only when it changed. A marshal's earlier keys are kept in `marshal_key_history` with the time each was replaced (schema 6; purged with the readings after 365 days), so readings signed before a lost phone's key was replaced still verify on the site server. Never sent: positions, check-in names and federation numbers, tokens and keys, marshals' private keys (they never leave the phones). `GET /api/v1/controller` shows `sync`: the last success, the last error, failures, the events and chrono readings still to send, the readings the site server kept apart (it could not verify them) and the last refusal of a chrono registry body.

**Game day** (phase 4 plan phase 16, ADR-P4-11): each cycle also pulls the field's published games of the next 14 days from the site server, which the console's *Check-in* tab lists under *From the schedule*. A game made from one (`POST /api/v1/schedule/{id}/game`) takes its title, mode, teams and length unless the GM gives others, and is linked to it (`schedule_links`, store schema 7); its metadata then names the scheduled game, so the site server shows it in progress and completed. Until that game starts, every cycle pulls its roster: each registration becomes an **expected** check-in with its pre-declared replicas already pending in the "replicas to chrono" list; a cancelled one that has not arrived goes; anyone already at the field stays as the controller has them. After the start nothing from the site server changes the game. A registered player arrives with the app (its check-in carries the registration id and the ticket), with a printed ticket a marshal scans or pastes, or is ticked by name. After the game, each registration's outcome (came or not) and its declarations' final states go back once, with the walk-ins as a count; no names. Accounts on the site server that claim a player id this controller made for a phone get its verdict (confirmed only when the secret's hash is the one it kept; the hashes never leave the controller). `sync` in `GET /api/v1/controller` has `game_day`: whether the site server has these endpoints, when the schedule was last pulled, the linked games and the claims answered.

**Branding from the site server** (phase 4 plan phase 18, P4R19): with `[sync] branding = "site"` (default `"local"`), each cycle also pulls the field's branding and saved teams that its staff edit on the site server (`GET /api/v1/sync/field`), fetches each image it does not have yet by its SHA-256, checks it again with `images.py` (the same limits as an upload here; an image that does not hash to its name, or that the checks would change, is refused and tried again next cycle) and applies them: the field's name, accent, logo and wallpaper, and one team preset per saved team (a club's team with the club's crest, so a club's crest uploaded once reaches every field that saved its team). The console then cannot change the field's branding nor those presets (409, "change it there"); its own presets stay the GM's. `sync` in `GET /api/v1/controller` has `branding`: the source, whether the site server has these endpoints, the last pull, images fetched and images still missing.

**Remote GM** (phase 4 plan phase 19, P4R12): off by default. With `[sync] remote_gm = true` (it needs the sync on), the controller also opens a WebSocket to the site server (`/api/v1/sync/stream`, the same API key and TLS rules; it reconnects by itself) and keeps it open, so that a user with the `gm` role on this field there, logged in with TOTP, sees the live game (its state, score, the boxes' health and latest events; never positions, tokens or check-ins) and can start, pause, resume or end it, send a GM message to every box or one of the game's declared mode commands. Nothing else: no score adjustments, ownership, reboot, joins or setup. The controller opens the connection; the site server cannot reach it and never holds its tokens. Each command is checked again here with the shared `sync_format.check_command`: refused while `remote_gm` is off, for another game than the live one, when sent more than 60 s ago by the site server's clock (the controller's clock must be set), or when its id was already seen; the rest goes through the engine as the console's GM token would (a standby refuses). Every command, done or refused, is logged in `remote_commands` (store schema 8, 365 days) with the site server's account that sent it; `GET /api/v1/remote-gm` (GM token) shows the log and the stream's state, and `sync.remote_gm` in `GET /api/v1/controller` whether it is connected. The same stream carries the remote ATAK relay's events with `[atak] remote = true` (see "ATAK / Cursor on Target"); it is then opened even with `remote_gm` off, and sends no live view and refuses every command.

**The scenario library from the site server** (phase 4 plan phase 20, decisions S20-1 to S20-8): with `[sync] library = true` (the default, once sync is on), each cycle also pulls the field's scenario library and game presets that its staff keep on the site server (`GET /api/v1/sync/presets`: each scenario by id, revision and the SHA-256 of its manifest). A manifest this controller has not installed from the site yet is fetched (`GET /api/v1/sync/scenarios/{id}`, its SHA-256 checked) and installed exactly as the console installs one (compiled, its `field.lua` loaded in the core: the controller checks again and stays the authority), so the primary and every standby have the same scenarios and a standby's join for a scenario game just works. A manifest the controller refuses is not fetched again until the site changes it; one the live game runs waits for the game to end; a scenario installed here by the GM under the same id stays until the site's version changes. A preset is saved by its name once its mode is installed and its parameters fit. What the site no longer lists stays here. `sync` in `GET /api/v1/controller` has `library`: whether it is on and supported, the last pull, what came from the site and the last problems.

## Node health events

The controller in charge logs three events about the boxes (decisions FU1-1 to FU1-6), which go to the log, the console, MQTT and, with the sync on, to the site server's device health; their node is the box's id, they have no epoch (they never go on air) and their seq is the controller's own count, carried over a restart:

- `node.online` (`fw`, `tier` from the box's HELLO) when it first hears a box in a game, or hears it again after `node.offline`;
- `node.offline` (`last_seen`: the game time of the box's last packet) when a box it heard has been silent for `[health] node_offline_s` (120 s by default; a box sends STATE every 15 s, so that is eight missed in a row). At most one of the two per box a minute (less with a threshold under a minute): a flapping link reports where it ended up;
- `battery.low` (`percent`) when a box's STATE or HELLO reports a level below `[health] battery_low_pct` (20 %, the site server's own threshold) for 30 s and the box has not sent its own `battery.low` (a Field Box with a battery gauge does, `CONFIG_ATALAIA_BATTERY_LOW_PCT`); once per crossing, again only after the level has come 5 points back above it.

A standby controller logs none, nor does a game that has ended; a game's `field.lua` gets a box's own `battery.low`, not these. `GET /api/v1/nodes` and the stream's node messages carry `link` (`online`, `offline` or null) and `battery_low`; the console's *Boxes* list marks a box offline and its battery low. `0` turns either setting off. In software and against the host box only, not yet with real boxes (the bench board has no battery gauge).

## The field's radio channel

All of a game's traffic uses one shared LoRa channel (RFC 0001 Amendments 1 and 3). The default, and the recommendation, is **869.525 MHz**: the centre of 869.4-869.65 MHz, the only part of the European 868 MHz band where a device may transmit up to 10% of the time at up to 500 mW ERP. Elsewhere in 868-870 MHz the rules allow 1% of the time (0.1% on 868.7-869.2 MHz) at 25 mW: about a tenth of the airtime and much less range. 868.1, 868.3 and 868.5 MHz are LoRaWAN's default channels, which every LoRaWAN device in Europe uses, so they are often busy. The recommended channel is shared too: LoRaWAN gateways use 869.525 MHz for some downlinks, and Meshtastic's European default is the same frequency. The game's packets are encrypted and use their own sync word, so nobody's traffic is mistaken for anyone else's, but everyone nearby shares the airtime. (Figures and sources: ERC Recommendation 70-03 Annex 1, ETSI EN 300 220-2, LoRaWAN Regional Parameters RP002-1.0.4; RFC 0001 Amendment 3.)

The channel is a **field setting**, chosen in the GM console under *Definições / Settings* (or the API below) while no game is live:

- **keep 869.525 MHz** (recommended);
- **find a quiet channel**: the controller asks the USB modem to listen to each candidate channel for an equal share of `[radio] scan_dwell_s` (60 s by default, at most 10 s per channel), without transmitting (the modem's MEASURE command, [protocol/usb-modem.md](../protocol/usb-modem.md)), and lists them quietest first with each one's power and duty-cycle limits. It suggests the quietest 500 mW channel if its 90th-percentile noise is at or below `[radio] quiet_threshold_dbm` (-105 dBm by default) and little LoRa activity was detected on it, otherwise the quietest channel of all;
- **random channel**: one of the candidates drawn at random; it is usually a 1%, 25 mW channel (8 of the 11), since only 869.475, 869.525 and 869.575 MHz give 10% and 500 mW;
- **pick one from the list** (the 0.1% channels are listed with a warning, but never scanned, drawn or suggested).

A scan or a random draw only suggests: nothing changes until the GM accepts one. The controller keeps the choice in its store (it survives a restart; `[radio] channel_hz` is only the default until the first choice), tunes the modem to it (SET_CHANNEL), and every new game takes it: the modem gets it with the game (CONFIGURE) and the boxes in their join payloads. A game keeps its channel until it ends, so the channel and the scan are locked while a game exists. Until the channel has been chosen once, the console's game tab shows a reminder. Without a modem, or with a modem that has no radio chip, the scan is unavailable (the console says why) and the channel stays as it is.

Every channel must fit inside one EU868 sub-band as a whole: centre ± 62.5 kHz (the game's 125 kHz LoRa channel). 869.40 MHz, at the sub-band's lower edge, is refused because its channel starts at 869.3375 MHz; the legal centres in 869.4-869.65 MHz are 869.4625-869.5875 MHz. The config, the API, the modem and the boxes all apply this rule, and the boxes and the modem take their duty-cycle budget and TX power from the chosen channel's sub-band. The candidates, the thresholds and the other choices are decisions CH1-CH13 in `docs/review/decisions-to-review.md`. The noise readings have not been compared with a real SX1262 yet (plan phase F); calibrate the quiet threshold at bring-up.

## Joining boxes and a standby controller

A box joins a game with a **join payload** ([protocol/join.md](../protocol/join.md)): the game's id and key, the box's node id and role, the teams, the channel and the relay clamp, signed with the **field join key**. Every box of the field gets that key once, when the field adopts it (next section). `join-key` above prints it; `[join] key` in the TOML sets it, so two controllers can share one field.

In the GM console's *Join* tab (or `POST /api/v1/join`), pick the role: the controller gives the box the next free node id, records its role, and shows the payload as a QR code, as text (`atalaia:join:...`) and as the bytes to write on an NTAG215/216 card. A box reads the card with its NFC reader, or takes the text on its serial console (`@join atalaia:join:...`). The payload holds the game key: show it only to the people setting up the field.

### Inviting boxes into the next game, and the start guard

A box whose game is over announces itself over the radio in **field frames** ([protocol/field-frames.md](../protocol/field-frames.md), RFC 0001 Amendment 7, proposed): its device id, a fresh token, its name, its last game and role. The modem passes them up as they are (FIELD_RX); the controller (`reinvite.py`, over the simulator's `atalaia_sim/lobby.py`) keeps the free boxes it hears for two hours. When the GM creates a game, the console's *Boxes for this game* dialog lists them (after a DISCOVER, which makes the free boxes answer within 3 s), with the previous game's boxes ticked and each box's previous role; *Invite* sends each ticked box its join payload, made exactly as for a card, in one to three INVITE parts sealed with a key derived from the field join key (HKDF-SHA256), for the box's device id and token. The box joins only if it is free, takes the payload through every check of a card, answers, and its HELLO (which now carries its device id, key 10) closes the invite. Unanswered invites are sent again after 6 s, three times in all; the console shows each box's progress (`GET/POST /api/v1/games/{id}/invites`). Join cards, QR codes and the serial console work as before. The field join key is a field secret: whoever holds it and records the radio can read the keys of the games joined by invite (decision RJ-2; [SECURITY.md](../SECURITY.md)). Its field frames' nonces are the pseudonym of a sender id drawn fresh from the CSPRNG at every start (never stored, so a restored backup or a standby made from a copy of the database cannot repeat one) and a count within the run (decisions RJ-7, RJ-15). It refuses an announcement that is not newer than the last one heard from that box, and forgets a game's invites when the game ends.

A game **starts only once every role it needs has a joined node** (a box or a linked Android prop): every role of its mode and role packages unless a manifest says `needed: false`, or for a scenario the roles of the boxes it names (decisions RJ-1, RJ-3). `POST /api/v1/games/{id}/start` answers 409 with `start_check` (`needed`, `joined`, `missing`, `warnings`) otherwise; `{"force": true}`, the console's *Start anyway* after a confirmation, starts it, logs it and tells every console (`system` `start.forced`). A mode's minimums (`min_zones`, `min_satellites`, Last Stand's `last_zones`) only warn. The remote GM's start is refused while a role is missing (RJ-4).

The *Boxes for this game* dialog follows the same check live (the game the controller pushes on every HELLO carries it; decisions GM-1 to GM-4): it says *Ready to start: every role has a box* with the joined count per role once every needed role has a box, or which roles it still waits for, and lists each unmet minimum as a warning. Its *Start game* button (*Start anyway* while a role has no box) asks *Review the game's other settings first?*: *Review settings* closes the dialog and opens the game card's *Game settings* (the parameters it was created with, read-only); *Start now* starts it through the same `POST .../start`, with `force` only when a role is missing (logged and told, as above).

A second controller (another Pi with its own modem) stands by for the game: ask the primary for a payload of kind *standby controller*, and paste its text into the standby's console (*Join* tab) or `POST /api/v1/controller/join`. The standby then hears the game, logs its events and follows its clock and scores without acknowledging anything; if the primary fails, *Promote* on the standby makes it take over (manual failover, ADR-P2-8). It leaves the game when the TIME beacons say it ended.

A mode's `field.lua` (Hold-All Domination, Last Stand) runs in the core on the controller from the game's start. Its `score.add()` points are the controller's own counters: they are merged into the totals (by maximum, like a box's) under one key per run of the script, and kept with the game, so they survive a controller restart, after which the script runs again and its new points add to the earlier ones. A standby controller that is promoted starts its own run; the points of the old controller's runs are not known to it (they never travel on the radio; decision K5 in `docs/review/decisions-to-review.md`). A `game.win()` or `game.finish()` from the script ends the game with that winner on the next tick.

A live game survives a controller restart (decision OT-7, the maintainer's, 2026-10-22): with `persist_game_key = true`, the default since then, the game key is kept in the SQLite file (mode 0600) until the game ends, and after a restart the game goes on from its last saved game time, scores and adjustments, its boxes still heard. Keeping it adds little at rest: the field join key, the field's master secret that already opens every game key sent in a radio invite (decision RJ-2), is on the same disk, and a game key is short-lived (erased when its game ends). With `persist_game_key = false` (ADR-P2-4's rule, the default before) a restarted controller can only end the game, but its boxes still hear it: *End* sends **GAME_OVER** over the field radio (the game id and its key's tag, sealed with the field key, three times, on the game's channel), and they leave the game and announce themselves free ([protocol/field-frames.md](../protocol/field-frames.md), decisions OT-13 to OT-16); the answer says whether it went (`game_over_frame`). The controller sends GAME_OVER after every game it ends, too, for a box that missed the end.

## Adopting boxes

A new Field Box is **adopted** once by the field: it gets the field join key, which is also the field's master secret once the radio invites seal games under keys derived from it ([protocol/adoption.md](../protocol/adoption.md), decisions AD-1 to AD-27; `adoption.py`, `pairing.py`). The console's *Adotar / Adopt* tab (GM token) has three ways. In software, against the C host box (and, for the code, the C host modem); not yet with real boards on the Pi's USB, a PN532 or the air.

- **The USB cable.** Plug the box into the controller and press *Look for boxes*: the controller opens every Espressif USB-Serial-JTAG port (303a:1001) but the modem's (`[modem] port`), and the ports of `[adopt] usb_ports` (for a controller in Docker: a COM-to-TCP bridge's `socket://host.docker.internal:7001`, or the board attached with `usbipd` and passed as a device), asks each `@adopt-info`, and lists the boxes with their name, MAC and state. The GM confirms one; the controller checks it is still that MAC on that port and sends `@adopt <key> <PIN|-> <field name>`. An unadopted box takes it; a box of another field, or one still on this field's old key, only with its admin PIN (the console asks; five wrong PINs lock it until it restarts). `[adopt] usb = false` turns this off.
- **The NFC field card.** *Make the field card* gives the bytes of an NTAG215/216 (type `application/vnd.atalaia.field`: the join key and the field's name) to write like a join card and tap once on each new box; a box of another field then asks for its admin PIN on its keypad. **The card is the field's master secret**: keep it locked away. If one is lost or copied, `join-key --rotate` (it keeps the old key's fingerprint, so the console tells boxes on the old key apart), restart, adopt every box again, write new cards; join cards made before stop working.

- **The pairing code over the radio.** An unadopted box shows a 6-digit code when it starts and offers itself in pair frames (message type 10, in the clear, RFC 0001 Amendment 8) on 869.525 MHz, its default channel. *Pair by code (radio)* → *Look for boxes on the radio* (`POST /api/v1/adopt/pair/listen`: with the field's channel elsewhere and no game live, the modem listens on 869.525 MHz for five minutes, then goes back) lists the boxes offering; the GM types a box's code and the controller runs CPace with it (`POST /api/v1/adopt/pair`, `pairing.py`): the join key is sent, sealed under the run's key, only once the box's answer proves it has the same code. A wrong code ends the run and the box shows a new one (three wrong runs: it waits a minute; ten: until it restarts). The modem's firmware must say `"pair": true` in IDENT.

Every field card made, every USB adoption and every pairing run is logged (`atalaia.adoption`) and the last 100 are kept (`GET /api/v1/adopt`: method, box, MAC, port, result; never the key or a PIN). `@joinkey <64 hex>` on a box's console and the setup portal's field still work, under the same rules.

## HTTPS and the field CA

On first start the controller makes the field's own certificate authority and a server certificate for its names and addresses in `tls/` next to the database (`[api] tls_dir`), keys with mode 0600, and serves the same API with HTTPS on `[api] tls_port` (8443) next to plain HTTP on `[api] port` (8080). `python3 -m atalaia_controller ca` prints the CA's fingerprint, which the check-in poster and the join payloads for Android props carry; phones fetch the certificate from `GET /api/v1/controller/ca` (no token, both ports), check it and trust only it for this field. Put the names and addresses phones use in `[api] tls_names` (the controller adds `localhost`, its host name, `name.local` and the addresses it finds; the server certificate is made again when the list changes or it has under 30 days left). The CA itself is never replaced on its own: deleting the folder makes a new one, and every player then has to remove the field in the app. The CA is ECDSA P-256 so that browsers accept it too (decision PE2). The GM console and the scoreboard still work on plain HTTP.

## Firmware updates for the boxes

The GM updates the Field Boxes' firmware from the console's *Boxes* tab, over the field's Wi-Fi ([protocol/firmware-update.md](../protocol/firmware-update.md), decisions FU3-*; `firmware_updates.py`). In software and against the host box; not yet with a real board.

- **Releases.** A release is the image (`atalaia_esp32.bin`) and its `.release.json` (`tools/firmware_release.py sign`, [firmware/esp32/docs/RELEASE_SIGNING.md](../firmware/esp32/docs/RELEASE_SIGNING.md)). The controller keeps one only if a key of `[firmware] release_keys` (Ed25519 public keys, standard base64; none: nothing is accepted) signed exactly its platform, version, size and SHA-256, the image fits a box's 2 MiB slot and its own descriptors say `atalaia_esp32`, that version and an accepted variant (`[firmware] variants`, `["box"]`). At most four, in `[firmware] dir` (`firmware/` next to the database). A key removed from the setting withdraws its releases at once. The site server's catalogue lists releases but holds no image (decision FU3-3).
- **Updates.** Only while the live game is `ready`, never while it runs or is paused; only with HTTPS on (the boxes pin the field CA of their join). For one box or all, the controller checks each box's HELLO (an `esp32s3` box, full or reduced tier, a lower version) and sends it CMD update (opcode 9, `{"id", "version"}`). The box fetches `GET /api/v1/firmware/{id}/release` and `.../image` (no token: a release is public and every box verifies it), checks it all again with the keys in its own firmware, installs it, reports (`POST /api/v1/firmware/report`, an HMAC with the game key) and reboots; its next HELLO shows the version it runs (`done`, or `rolled_back` when the new image did not confirm itself). With no news for `[firmware] update_timeout_s` (600 s) an update counts as `timeout`. The game does not start while an update is on its way, unless the GM stops waiting for it. A mode's `field.lua` can never send `update`.

## Field check-in

Players check in at the field with the app ([protocol/checkin.md](../protocol/checkin.md), ADR-P3-13). In the GM console's *Check-in* tab, *Print the poster* opens an A4 page with the field's QR code: print it once and put it up in the check-in area. The poster carries no secret: the field's id and name, the controller's https addresses (`[checkin] urls`, else `tls_names` first and then the host's own names and addresses, which are left out in a container, where they resolve only inside it: there set `tls_names`), the CA's fingerprint and optionally the Wi-Fi network's name (`[checkin] wifi_ssid`; the poster page can draw a Wi-Fi code from a password typed there, which is never stored).

A player who scans it checks in with a display name (and the federation number if `[checkin] federation` asks for it; never verified automatically: staff tick "card seen"), and gets a **player token** keyed with the game's own token key, made by this controller and kept only in its SQLite file. The token's role, team and squad are checked against the player's check-in on every request, so the GM's changes and removals take effect at once. Check-in is open from a game's creation until it ends (*Close check-in* stops it); with `[checkin] confirm = "staff"` check-ins wait for a marshal or the GM to confirm them. The controller logs `player.checkin` with the player's id, never the name. A team always exists; squads, sub-groups inside a team, only in a game created with `squads` (decision PE25): there the GM gives a squad (team › squad) and the squad-leader role, elsewhere both are refused.

Players declare the replicas they will use; marshals see the **replicas to chrono** list in their app and in the console, and their phones send each signed series of readings (`POST /api/v1/chrono/readings`): the controller verifies them with the marshal's registered Ed25519 key, judges the series against the class limit of `[checkin] limit_template` (one of `app/lib/chrono/limit_templates/`, unverified research figures: decision P3-5) and marks the replica passed or refused. A pass counts for the rest of the field's day (`chrono_valid_for`). A marshal is a checked-in person to whom the GM gave the marshal role; the marshal's app then registers its key itself, or the GM registers one with `POST /api/v1/marshals`.

Personal data stays on the controller: names and federation numbers are shown to staff (the GM token, marshals) only, never in events, MQTT, logs or the read token's views, and are erased `[checkin] retention_days` (30) days after the game; a field identity unused for a year is deleted. The default privacy notice is `templates/checkin-notice-pt.md` and `-en.md` (`[checkin] notice_pt`, `notice_en`; raise `notice_version` when it changes). Everything works without internet.

## Field and team branding

A field or club running its own controller can show who it is (decisions BR1-BR24 in `docs/review/decisions-to-review.md`). In the GM console's *Definições / Settings* (GM token): the field's name (the same name the check-in poster prints), a logo, an optional wallpaper and an accent colour. The controller keeps them in its SQLite file, so they survive restarts. Anyone who can reach the field's API reads them without a token, since players need them before or right after checking in and none of it is personal data: the app shows the logo in its header, the wallpaper (dimmed) behind the player's view and an Android prop's idle screen, and the accent on its primary buttons; the GM console shows the logo and name in its header, the scoreboard above the game, and the check-in poster above the field's name, outside the QR code. Without branding everything keeps the default Atalaia look.

Teams get a display name and a crest per game next to their colour: `team_info` when the game is created, or `PUT /api/v1/games/{id}/teams/{team}` until it ends. The colour stays the team's name (red, blue...), which is what the boxes, their LEDs and buttons, the radio, events and MQTT use. *Saved teams* (team presets) keep a club's name, crest and usual colour for the next game.

Uploads are PNG, JPEG or WebP only (SVG is refused: it can carry scripts), with the type read from the file itself:

| Image | Bytes | Pixels a side | Shape |
| --- | --- | --- | --- |
| Logo | up to 1 MiB (1,048,576) | 16 to 2048 | at most 8:1 |
| Wallpaper | up to 4 MiB (4,194,304) | 320 to 4096 | at most 8:1 |
| Crest | up to 512 KiB (524,288) | 16 to 1024 | at most 4:1 |

The controller has no image library: `images.py` checks each file's structure with the standard library (PNG chunks and checksums with the pixel data inflated to exactly the size its header says, JPEG segments with one frame, WebP's RIFF and image headers), refuses animated images, and rewrites the file without its metadata (text and EXIF chunks, JPEG APP1/APP13 and comments, WebP EXIF and XMP), keeping colour profiles. Images are stored once by the SHA-256 of the result, which is also their ETag; a replaced logo or wallpaper is deleted at once, a crest no game or team preset uses a day after its upload (at most 500 are kept). Whoever uploads an image is responsible for having the rights to it; the console says so next to every upload.

## Player positions

A checked-in player may share their position during a running game (`POST /api/v1/positions`, up to 5 reports). The controller keeps the latest per player for that game only and deletes them when it ends; it sends a position only to those who may see it (ADR-P3-6): a player sees their own (and their squad's with the game parameter `squad_visible`), a squad leader their squad, a VIP their team, marshals and the GM everyone, the read token nobody. A mode's `visibility.granted` event (team, `see_team`, `duration_s`) lets a team see another for a while; the controller logs `visibility.expired` when the time is up. Positions never go on the radio or MQTT. A VIP's GPS reports are also handed, oldest first, to the running game's `field.lua` as the input `position.fix` (`player`, `team`, `role`, `lat`, `lon`, `acc`, `src`; decision P4R6): VIP / Payload extracts the VIP with them. Nothing else gets them: no event, no log, no `state.field`, no standby controller.

## What only staff may read

Some of a game's data is a secret until a team earns it: the code a Hacking Terminal reveals, a Bomb's team codes, the Codes modifier's codes. The schema marks it (`gm_only` on an event's data fields in `protocol/schema/events.yaml`, `gm_only: true` on a mode's parameters in its `mode.yaml`), and the controller (`visibility.py`, decision M5-1) gives it to staff only: the GM token and the marshal and gm player tokens of the game. Players' connections, the read token (scoreboards, a read-only console) and MQTT get the events and the game without those fields, on the stream, `GET /games`, `/games/{id}`, `/games/{id}/log` and the read token's `/presets`. The radio, the controller's own log and the sync to the site server (where events and parameters are staff-only too) keep them whole.

## Android props on Wi-Fi

An Android phone running a prop that joined with a join payload links to the controller over the field's Wi-Fi ([protocol/prop-link.md](../protocol/prop-link.md)): `WS /api/v1/prop`, an HMAC proof of the game key, then its HELLO, STATE and events as JSON, which the controller encodes with the radio's codecs and hands to the same FieldController as a box's packets. TIME beacons and commands reach the linked props too; without a modem, commands reach the Wi-Fi props and are reported as sent. The join payload for a box carries the CA's fingerprint and the https addresses (keys 13 and 14) when HTTPS is on; boxes skip them.

## ATAK / Cursor on Target

Off by default. With `[atak] enabled = true` the controller in charge of the live game puts the field on ATAK maps as Cursor on Target events (`atak.py`; ADR-P4-7 as amended, decisions P4R18 and M9-1 to M9-10). What is sent:

- **every box placed on the field image** (the console's *Campo / Field* tab) as a coloured spot marker (`b-m-p-s-m`, as in the TAK examples): the box's name, its owner in the remarks, the owner team's colour (`<color>`) and, for a team named after one of ATAK's team colours, that team (`<__group>`), and its battery; a VIP / Payload game's extraction zone, with its radius as the circular error. Every `interval_s` (30 s) and **at once** when a box is captured or neutralised, moves on the image, or the game or the georeference changes; `stale` is twice the interval. When the game ends (or the georeference is removed) every marker is dropped (stale before start, CoT's "drop track");
- **over UDP** to `multicast` (`239.2.3.1:6969`, ATAK's mesh default; TTL 1, so it stays on the field's network; a unicast `host:port` works too), one event per datagram (TAK Protocol version 0);
- **player positions are never multicast**: anyone on the field Wi-Fi can read a multicast group, and positions are filtered per role (phase 3 constraint 9). Only with `players = true` do they go, and only to the staff ATAK devices in `staff_endpoints` (TCP, `"host:port"`, 4242 when no port is given; at most 8), which see every player as the GM and marshals do: the latest GPS fix of each player (`a-f-G-U-C`, `m-g`), by pseudonymous player id and never by name, with the team as `<__group>`. Staff endpoints also get the boxes and the zone.

**ATAK away from the field (the remote relay; Phase 4 follow-up, decisions FU5-1 to FU5-20).** Off by default. With `[atak] remote = true` (it needs `[atak] enabled` and the sync on, and a site server whose relay is on), the controller also opens the sync's WebSocket to the site server (`/api/v1/sync/stream`, as the remote GM does: the controller opens the connection, the site server never connects to it) and says so in its `hello`; once the site server answers that its relay takes them, the emitter pushes the same boxes and zone there (`cot` messages, each event in the shared form `sync_format.cot_event` checks on both sides: the emitter's elements with only its attributes, in its forms, decision FU5-17), and everything again whenever the socket is new. The site server relays them over TLS to the field's enrolled ATAK devices, each with a client certificate its admin or gm issued (server/README.md, "Remote ATAK"). **Player positions** go there only with `remote_players = true` as well (default `false`), and the site server sends them only to a certificate whose holder has the field's `gm` or `marshal` role and that was issued with positions (P4R18); never to any other. Remote ATAK alone sends no live view and takes no remote GM command (`[sync] remote_gm` stays off). `GET /api/v1/atak` shows `remote`, `remote_players`, `remote_relay` (whether the site server takes them now) and `remote_events`; `sync.remote_gm.stream.atak` in `GET /api/v1/controller` the stream's side.

**Georeference.** Field Boxes have no GPS, so their places are fractions of the field image. In the *Campo / Field* tab, under the image, the GM gives two opposite corners of the image (top left and bottom right; the image must have north at the top) their latitude and longitude, pasted from a map app as `latitude, longitude` (`PUT /api/v1/field/georef`). The console shows the four corners back and a pin on the image per point. Through the API, 3-8 control points give a rotated or skewed image (a least-squares affine fit); points on one line, too close, mirrored or not fitting one flat image are refused. The points are kept in the store's settings (no schema change) and a new image clears them.

```toml
[atak]
enabled = false
multicast = "239.2.3.1:6969"   # "" for no UDP
interval_s = 30.0
staff_endpoints = []           # ["10.42.0.5:4242"]; ATALAIA_ATAK_STAFF_ENDPOINTS separates them with commas
players = false
remote = false                 # the site server's relay for staff away from the field (needs [sync])
remote_players = false         # positions there too, for certificates allowed them only
```

The XML is built with ElementTree, so names from users are escaped; characters XML does not allow are dropped and texts are capped. The CoT rules the tests check (`protocol/vectors/cot.json`) are copied from the CoT base-event schema, MITRE's CoT types, the TAK detail schemas and examples and the TAK protocol description, each cited, and two TAK examples are rebuilt by the emitter as known answers. Tested in software (a loopback receiver for UDP, multicast and TCP; the remote relay through the real site server to a TLS client with a certificate from the site server's enrolment, `server/tests/test_atak_e2e.py`); **not yet with a real ATAK device** (HW3) or a real deployment.

## Scenarios

A GM writes a custom scenario as a YAML manifest (ADR-P4-6 as amended, decisions P4R7, P4R8 and M7-1 to M7-9); the compiler (`atalaia_controller/scenarios/`) turns it into a scenario package, `mode.yaml` and `field.lua` (`kind: scenario`), that runs on the controller over the built-in objectives package (`org.club.foxhound+org.atalaia.objectives`, [modes/README.md](../modes/README.md#custom-scenarios-and-the-objectives-package-phase-4)). Nothing changes on the boxes.

On the field, the GM console's *Scenarios* tab is the editor (plan phase 8, decisions M8-1 to M8-9): the controller checks the manifest as it is typed (`POST /api/v1/scenarios/check`: every problem with its place, then the compiled `field.lua`'s load in the core) and installs it (`POST /api/v1/scenarios`), keeping the manifest next to the package so the GM can open it again (`GET /api/v1/scenarios/{id}`). A game of it is the scenario with the objectives package (*Game* tab: pick the scenario, tick *Objectives*). In the *Join* tab the GM gives each box one of the manifest's `nodes` names; the box's role is that node's, and the scenario's `field.nodes()` finds the box by that name (a box's own name otherwise). A standby controller needs the scenario too: with the site server's sync on, every controller of the field installs the field's scenario library from it (below, decision S20-1); without it, install the same manifest there before its join (it says which part it lacks; decision M8-3). A package compiled elsewhere can still be uploaded as files (`POST /api/v1/modes`).

Who sees which objective (P4R24, M8-4): staff see everything; players see an objective by its `visibility` (`public`: everyone; `team`, `squad`: the assignee's; `hidden`: the assignee's, once revealed), on the stream, the log and the game, which carries the scenario's names and the objectives each player may know (M8-5); everyone else, MQTT and the read token's scoreboard included for a team's objective, learns that a team completed, failed or was shown an objective, not which one.

```sh
cd controller
python3 -m atalaia_controller.scenarios validate tests/scenarios/multi_objective.yaml  # the manifest's problems
python3 -m atalaia_controller.scenarios check tests/scenarios/multi_objective.yaml     # + compile, load the Lua in the core
python3 -m atalaia_controller.scenarios compile tests/scenarios/foxhound.yaml -o /tmp/foxhound  # write the package
python3 -m atalaia_controller scenario check tests/scenarios/foxhound.yaml             # the same, from the main entry point
```

Each problem says where and why (`objectives[2].depends_on[0]: error: 'nowhere' is not an objective id (unknown_reference)`); `--json` prints them for programs. `check` and `compile` need the core library (`ATALAIA_CORE_LIB`), as an upload does; `--no-core` skips that check. Exit status 0 (warnings are fine), 1 (errors), 2 (not a manifest, or no core). From Python: `load(text)`, `validate(manifest)`, `compile_scenario(manifest)` and `check_package(core, package)`.

The manifest ([tests/scenarios/foxhound.yaml](tests/scenarios/foxhound.yaml) and [multi_objective.yaml](tests/scenarios/multi_objective.yaml) are examples):

| Key | What it is |
| --- | --- |
| `id`, `version`, `name`, `description`, `author` | The package's id (`org.club.name`, at most 40 bytes so the game's id fits a join; not `org.atalaia.`), its version, its texts in English |
| `i18n.pt` | `name`, `description` and `params` labels in Portuguese |
| `lang` | The boxes' screens: `pt` (the default) or `en`; each box shows the objective's name in that language |
| `teams`, `squads` | The game's team names the scenario uses (default `[red, blue]`) and its squads per team (numbers 1 to `squads`, 0: none) |
| `params` | Whole-number parameters for the GM (`{ type: int, min, max, default, label }`), for points: `effect.points: { param: name }` |
| `nodes` | The names the GM gives the boxes (`box-a: { role: objective }`, `{ role: bomb_site }`) and the players an objective is about (`vip: { player: true, role: vip }`, `role` being the player's check-in role) |
| `objectives` | A list; each has `id` (`[a-z][a-z0-9_]`, at most 24), `type`, `name` (one line; `description`, `i18n.pt`), `target`, `assignee` (`team`, `squad`), `params`, `visibility` (`public`, `team`, `squad`, `hidden`), `depends_on`, `time_window` (`start_min`, `end_min`), `effect` (`points`, `win`, `reveal`) |

| Type | Target | Params | Completed | Failed |
| --- | --- | --- | --- | --- |
| `capture_and_hold` | an `objective` box | `hold_ms` (to take it), `duration_s` (to keep it; 0, the default: at the capture) | the team (only the assignee's, if one) has held it for `duration_s` | -- |
| `defend` | an `objective` box | `duration_s` (required), `hold_ms`; an assignee team is required | the defenders still hold it `duration_s` after it opens (they start holding it) | another team captures it (`captured`) |
| `enter_code` | an `objective` box with a keypad | `code` (1-8 digits, in quotes) | the code is typed (credited to the assignee, else the last team to press) | -- |
| `scan_tags` | an `objective` box with NFC | `tag_count` (required), `any` (any cards, not only players' tags) | a team (the assignee, if one) scanned `tag_count` different tags | -- |
| `destroy` | a `bomb_site` box | `hold_ms`, `defuse_ms`, `fuse_s` | the bomb explodes | it is defused (`defused`) |
| `escort` | a player node (`player: true`) | `destination` (`{ lat, lon, radius_m }` or `{ points: [[lat, lon], ...] }`, 3-32 corners), `max_acc_m` | a GPS fix of a player with that role (of the assignee team) inside, no less precise than `max_acc_m` (default: the radius; 25 m for a polygon) | -- |
| `survive` | none | `minimum_lives` (required); an assignee team and `time_window.end_min` are required | the team still has `minimum_lives` of Respawn's lives at the window's end (compose the game with `org.atalaia.respawn`, per-team lives) | fewer lives left, or the team eliminated (`lives`) |

An objective opens when it is revealed (at the start, unless `hidden`; a hidden one when it could open, or when another's `effect.reveal` names it), its time window has started and everything in `depends_on` is completed; a box shows it inactive until then. One still open at `end_min` fails (`time`); a failed one fails what depends on it (`blocked`); an objective never revealed sends no event. Completing one scores its points for the team, reveals what `effect.reveal` lists and, with `effect.win`, ends the game won by that team. An objective of a team the game does not have is off. The validator checks unique ids, references and the dependency graph (a topological sort; every objective on a cycle is named), each type's target and parameters, teams and squads, time windows, destinations (a radius under 10 m is a warning; a polygon whose edges cross is an error), and sizes: every setup command fits a box's 127-byte command and every scenario event a LoRa packet. The rules are written as shared vectors, [`protocol/vectors/scenario.json`](../protocol/vectors/scenario.json).

The generated `field.lua` is a data table (`SCENARIO`) followed by the scenario runtime, [`scenarios/runtime.lua`](atalaia_controller/scenarios/runtime.lua), the same code for every scenario (GPL-3.0-or-later, like the modes, since it is copied into every package; decision M7-2). No text from the manifest is ever Lua code: every value is written as a Lua literal, a quoted string with its quotes, backslashes and control characters escaped, so a name such as `"]] os.exit() --[[` is only ever a name. `mode.yaml` carries the names, teams, squads, nodes and each objective's id, type, names, assignee, visibility, dependencies and points (for the routing and the player view); a code and a destination are only in `field.lua`.

## REST API v1

Reading needs the read or GM token, changing anything the GM token: `Authorization: Bearer <token>` (the WebSocket also takes `?token=`). A player token (field check-in) reads what the read token reads about games, its own check-in and what its role allows; it cannot read modes, presets, the controller's or the radio's state.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/v1/nodes` | Nodes of the live game (or `?game=`): owner, battery, RSSI, epoch, firmware, capabilities, link and battery low (node health events) |
| GET / POST | `/api/v1/modes` | Installed modes, modifiers, role packages and scenarios (`kind`), their parameters and translations (`i18n`) / upload `{"files": {"mode.yaml": ..., "node.lua": ..., "field.lua": ...}}`; a scenario has `mode.yaml` and `field.lua` only, and a game of it is `{"mode_id": "org.club.foxhound", "modifiers": ["org.atalaia.objectives"]}` (each box's join then names `org.atalaia.objectives`; [modes/README.md](../modes/README.md#custom-scenarios-and-the-objectives-package-phase-4)) |
| GET / POST | `/api/v1/presets` | List / save `{"name", "mode_id", "params"}` |
| GET / POST | `/api/v1/games` | List / create `{"name", "mode_id" or "preset_id", "modifiers": [...], "teams", "squads", "params", "duration_ms", "assignments": {"7": "zone"}, "team_info": {"red": {"display_name", "crest_id" or "team_preset_id"}}}`; a game with modifiers gets the mode id `main+modifier`; `squads` (0-16 per team, 0 by default) only for games whose teams split into squads (milsims, big games) |

| GET | `/api/v1/scenarios/{id}` | GM: the manifest (`manifest_text`) and the generated `mode.yaml` and `field.lua` (`no-store`: the Lua holds the codes) |

## GM console and scoreboard

The controller serves the GM console at `http://<controller>:8080/console/` (`/` redirects there) and a read-only scoreboard page at `/scoreboard#token=<read token>`: plain files from [`console/src/`](console/src/), no build step, with a strict Content-Security-Policy. The console asks for the GM or the read token; European Portuguese by default, English too. See [console/README.md](console/README.md). An example scoreboard that follows the game over MQTT is in [`examples/scoreboard/`](../examples/scoreboard/).

## MQTT

```
field/v1/{game}/events/{type}          every game event, JSON
field/v1/{game}/score                  totals per team (retained)
field/v1/{game}/nodes/{node}/state     owner, phase, game time, counters (retained)
field/v1/{game}/nodes/{node}/health    battery, RSSI, SNR, link, battery low, last seen (retained)
field/v1/{game}/cmd/{node}             {"cmd": "message", "params": {"text": "..."}} (GM only)
field/v1/{game}/cmd/all                the same, to every node
```

Who may publish commands is Mosquitto's job: [`deploy/mosquitto.conf`](deploy/mosquitto.conf) and [`deploy/atalaia.acl`](deploy/atalaia.acl) give the controller, a GM user and a read-only user. Retained topics are published again after the broker restarts; events published while the broker is down are not queued (they are in the log).

## Tests

`sh tools/check.sh` in the dev container runs everything, the controller included. From `cmd`, in the repository: `docker run --rm -v "%cd%:/src" atalaia-dev sh tools/check.sh` (the first `python tools/docker_sim.py test` builds the `atalaia-dev` image). The controller's tests (`controller/tests/`, unittest) need the core library (`ATALAIA_CORE_LIB`), the host modem (`ATALAIA_MODEM_HOST`, built from `firmware/esp32/test/modem_host/`) and `mosquitto`; with `ATALAIA_REQUIRE_ALL=1`, as in `check.sh` and CI, a missing one is an error, not a skip. They cover the framing against the C modem, AES-CCM in both directions, the watchdog and reconnect, the engine and restart recovery, every API endpoint, MQTT against a real broker, a `field.lua`, and the app served by uvicorn on a real port. They also check the GM console's files as served (`test_console.py`), run the example MQTT scoreboard against a private broker (`test_scoreboard_example.py`), choose the field's channel, scan for a quiet one over a recording modem and over the C host modem (simulated noise levels per channel, `test_channels.py`, `test_modem_host.py`), issue and refuse join payloads, make a second controller stand by, follow and take over a game over the air with two host modems (`test_join.py`), and play whole games with the host box (`ATALAIA_BOX_HOST`, built from `firmware/esp32/test/box_host/`): a join from the controller's payload, captures and scores over the radio, a battery pull, the end of the game, a box heard only through another box's relay, and the node health events (the box's own `battery.low` from its gauge, `node.offline` and `node.online` around a battery pull; `test_box_e2e.py`, with the engine's side in `test_node_health.py`), a box that played a game announcing itself afterwards and invited into the next game over the radio, which then starts without force (`test_box_e2e.py`; the start guard, the free boxes, invites, retries and refusals against the simulator's box model in `test_reinvite.py`), Hold-All Domination scored by the controller from two boxes' captures, and the Codes modifier composed with Domination on a box, with a keypad code reaching the log.
