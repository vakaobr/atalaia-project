# Field controller

Runs on a Raspberry Pi (or any Linux machine) next to the field. It:

- keeps the official game: creates games from mode packages and presets, starts, pauses, resumes and ends them, merges every box's scores and keeps the event log,
- talks to the boxes over LoRa through a **USB radio modem** (a second Heltec V4.3 running the modem firmware),
- sends the TIME beacons that keep every box's clock in step and double as its heartbeat,
- takes part in **controller failover** (the CLAIM election, ADR-P2-8),
- runs a mode's `field.lua`, the script for logic that spans several boxes,
- serves the REST and WebSocket API, the GM console and a scoreboard page, and publishes to MQTT,
- optionally pushes its games to a **site server** (phase 4), offline first: games never wait for the network.

Licence: AGPL-3.0-or-later. Running a modified controller for other people means sharing your changes.

Status: phase 2, plan phases D and E; phase 3, plan phase E (field check-in, player tokens, chrono readings, player positions, Android props on Wi-Fi, HTTPS with the field's own CA); phase 4, plan phases 13 and 14 (the site server sync, with the field's chrono registry, in software: tested against the real site server and PostgreSQL in Docker, not yet over a real 4G link) and 19 (the remote GM through the site server, off by default, in software: tested against the real site server in Docker). Built and tested in Docker against the modem's real C code, the Field Box's real game and radio code (the host box), a real Mosquitto broker and, for the GM console, headless Chromium; not yet run on a Raspberry Pi with a real modem board and real boxes (that is plan phase F, when the boards arrive).

## Running it

On a Raspberry Pi OS or Ubuntu machine:

```sh
sudo apt install python3-fastapi python3-uvicorn python3-websockets python3-paho-mqtt \
     python3-serial python3-yaml python3-cryptography libmbedtls-dev mosquitto cmake build-essential
cmake -S core -B build -DATALAIA_SHARED=ON && cmake --build build   # the core, for field.lua
cp controller/controller.example.toml controller.toml                 # then edit it
cd controller
ATALAIA_CORE_LIB=../build/libatalaia_core.so python3 -m atalaia_controller run --config ../controller.toml
python3 -m atalaia_controller tokens --config ../controller.toml     # the GM and read tokens
python3 -m atalaia_controller join-key --config ../controller.toml   # the field join key
python3 -m atalaia_controller join-key --fingerprint                # its fingerprint (boxes show it)
python3 -m atalaia_controller join-key --rotate                     # a new key, after a field card is lost
```

Without the distribution packages (another Linux, a development machine), install the pinned set in a virtual environment instead. `requirements.txt` pins every package with its PyPI hashes (made from `requirements.in`, which says how to refresh it; the cryptography floor is 44.0.1) and works on Python 3.11 and later, x86-64 and aarch64 (a Raspberry Pi 4 or 5 on a 64-bit OS; wheels exist for both, so nothing is compiled; a 32-bit OS has no wheels for some packages: use the apt route):

```sh
python3 -m venv .venv && . .venv/bin/activate
pip install --require-hashes --no-deps --only-binary=:all: -r controller/requirements.txt
```

Flash the modem board with the modem firmware first (`python tools/docker_fw.py modem`, then the `esptool` command it prints, or `idf.py -B build-modem flash`). Its own OLED then shows whether the controller is talking to it (`LINK OK`, `DOWN`, `waiting`), the game it is configured for, the channel, the TX and RX counts with their failures, the duty-cycle budget left and any radio fault, so a GM can tell a working modem from a stuck one without a laptop, in the boxes' language (the controller sends it over the serial link with `SET_LANG`, [protocol/usb-modem.md](../protocol/usb-modem.md); [firmware/esp32/README.md](../firmware/esp32/README.md#the-modems-oled)). [`deploy/`](deploy/) has a systemd unit and a Mosquitto configuration with users and topic permissions.

Without a modem (`[modem] port = ""`) the controller still runs: games can be created and the API works, but nothing reaches the boxes.

Settings come from a TOML file and `ATALAIA_<SECTION>_<KEY>` environment variables; see [controller.example.toml](controller.example.toml).

## Site server sync

Off by default. With `[sync] enabled = true`, a `url` and the field's API key (made by the field's admin on the site server, `POST /api/v1/fields/{field}/sync-keys`, shown once), the controller pushes every game to the site server: its metadata, its event log in id order, its score counters per source and its nodes ([protocol/sync.md](../protocol/sync.md), ADR-P4-3 as amended); and then the field's chrono registry: the marshals' public keys with the period each was the marshal's key, the replica registry and every signed reading with its series and outcome, the record as the text the controller stored (ADR-P4-5 as amended; the site server verifies each one again). It opens every connection (a field behind a phone's 4G link cannot be reached); the site server holds none of its tokens.

```sh
python3 -m atalaia_controller sync-key --config ../controller.toml           # paste the key (stored in the store, mode 0600)
python3 -m atalaia_controller sync-key --status --config ../controller.toml  # where the key comes from, its fingerprint
python3 -m atalaia_controller sync-key --resend --config ../controller.toml  # a new site server: send everything again
```

`[sync] api_key` or `ATALAIA_SYNC_API_KEY` win over the stored key. The site server's certificate is checked against the system's CAs, or `[sync] ca_file`; `http://` only to this machine. **Offline first:** the client is a thread that reads the store; the game runs the same with or without the network. It syncs every 30 s while a game runs and every 5 min between games, doubling the wait after a failure (up to 5 min) and following `Retry-After`; a game's start, pause or end wakes it. Each game's cursor (the last event id the site server acknowledged) is kept in `sync_state` (store schema 5), so a restart resumes where it was, and a batch sent twice is harmless (the site server drops duplicates by the events' own key). What was sent of the chrono registry is in `sync_items` (store schema 6), so each key, replica and reading goes once, and again only when it changed. A marshal's earlier keys are kept in `marshal_key_history` with the time each was replaced (schema 6; purged with the readings after 365 days), so readings signed before a lost phone's key was replaced still verify on the site server. Never sent: positions, check-in names and federation numbers, tokens and keys, marshals' private keys (they never leave the phones). `GET /api/v1/controller` shows `sync`: the last success, the last error, failures, the events and chrono readings still to send, the readings the site server kept apart (it could not verify them) and the last refusal of a chrono registry body.

**Game day** (phase 4 plan phase 16, ADR-P4-11): each cycle also pulls the field's published games of the next 14 days from the site server, which the console's *Check-in* tab lists under *From the schedule*. A game made from one (`POST /api/v1/schedule/{id}/game`) takes its title, mode, teams and length unless the GM gives others, and is linked to it (`schedule_links`, store schema 7); its metadata then names the scheduled game, so the site server shows it in progress and completed. Until that game starts, every cycle pulls its roster: each registration becomes an **expected** check-in with its pre-declared replicas already pending in the "replicas to chrono" list; a cancelled one that has not arrived goes; anyone already at the field stays as the controller has them. After the start nothing from the site server changes the game. A registered player arrives with the app (its check-in carries the registration id and the ticket), with a printed ticket a marshal scans or pastes, or is ticked by name. After the game, each registration's outcome (came or not) and its declarations' final states go back once, with the walk-ins as a count; no names. Accounts on the site server that claim a player id this controller made for a phone get its verdict (confirmed only when the secret's hash is the one it kept; the hashes never leave the controller). `sync` in `GET /api/v1/controller` has `game_day`: whether the site server has these endpoints, when the schedule was last pulled, the linked games and the claims answered.

**The class limit with each chrono reading** (PKD-3, closing S14-7's gap; store schema 16: `chrono_readings.limit_j`): the check-in keeps with each reading the class limit its series was judged against (`checkin._judge`), and the sync sends it as `limit_j` in the chrono push when it was known, so the site server can work out how far a violation went (`delta_j`) and flag a player's later violations as repeats. A site server from before PKD-3 refuses the key; the client then sends the batch and every later one without it (`SyncClient.limit_j_supported`), so no reading is lost. The phone controller does the same (`controller_checkin.dart`, `controller_sync.dart`).

**Other fields' chrono records** (decision S14-5): with the roster, each cycle also asks `GET /api/v1/sync/chrono?scheduled_game_id=` for what the roster's players let other fields share: the site server answers only for players who consented to share their chrono records between this field and another that shares too (the same rules as its staff lookup), and this controller keeps a record only when the marshal's key given with it verifies its signature, it is younger than the field's chrono retention (`chrono_retention_days`, 365 by default) and it is not already one of its own readings (`shared_readings`, store schema 13). They show under *From other fields* in the Check-in tab's chrono list and in the check-in row (`shared_readings`, marked `from_other_field` with that field's name), so a marshal sees a replica's history and still chronos it here: they are never judged, never change a declaration's state, never go back to the site server, and are deleted with the readings' retention, the player's erasure and `DELETE /api/v1/players/{player}/chrono`. A consent withdrawn removes them at the next cycle. `game_day.shared_chrono` in `GET /api/v1/controller` says whether the site server has the endpoint and how many records the last pull kept.

**Branding from the site server** (phase 4 plan phase 18, P4R19): with `[sync] branding = "site"` (default `"local"`), each cycle also pulls the field's branding and saved teams that its staff edit on the site server (`GET /api/v1/sync/field`), fetches each image it does not have yet by its SHA-256, checks it again with `images.py` (the same limits as an upload here; an image that does not hash to its name, or that the checks would change, is refused and tried again next cycle) and applies them: the field's name, accent, logo and wallpaper, and one team preset per saved team (a club's team with the club's crest, so a club's crest uploaded once reaches every field that saved its team). The console then cannot change the field's branding nor those presets (409, "change it there"); its own presets stay the GM's. `sync` in `GET /api/v1/controller` has `branding`: the source, whether the site server has these endpoints, the last pull, images fetched and images still missing, whether the last answer carried the field's check-in settings, how many they changed and how many `field.changed` notes came.

**The field's check-in settings and the stream note** (BR24, decision S18-11's two items): the same pull asks for `GET /api/v1/sync/field?settings=1` and, when the site server has them, takes over the field's `max_replicas`, its federation label (if it has one) and its limit template, so a registration the site accepted is one this check-in accepts (decision S16-6). The template arrives whole and is kept in the store (`checkin.site_limits`), so a restart offline keeps the field's rules; with `"local"` nothing is asked and the configured `[checkin] limit_template` stays. The console's check-in settings are not locked: a change there lasts until the next pull. With `branding = "site"` **or `[sync] library` on (the default; PKD-1)** the controller also opens the stream (`remote_gm.py`) even with `remote_gm` and `[atak] remote` off, saying only `hello` (`remote_gm: false`): the site server sends `field.changed` when the field's branding, saved teams or settings change (no `what`), or when its scenario library (`what: ["library"]`: a scenario saved or archived, a preset made, replaced or deleted) or its schedule (`["schedule"]`) do, and the sync cycle runs at once (`SyncClient.field_changed`) instead of at its next interval, pulling the library with `[sync] library` on and the schedule always (`sync.library.changes` and `sync.game_day.changes` count the notes). With `library = false` and `branding = "local"` the stream stays closed unless the remote GM or the ATAK relay is on, and the schedule is pulled at the cycle. An older site server never sends a note with `what`, and an older controller ignores one (`protocol/sync.md`). A **standby controller** has its own `[sync]` and does all of this by itself (it needs `[sync]` with the same field key and `branding = "site"`; nothing is copied from the primary). An older site server answers without `settings` and never sends the note; an older controller never asks and ignores the note (`protocol/sync.md`).

**Remote GM** (phase 4 plan phase 19, P4R12): off by default. With `[sync] remote_gm = true` (it needs the sync on), the controller also opens a WebSocket to the site server (`/api/v1/sync/stream`, the same API key and TLS rules; it reconnects by itself) and keeps it open, so that a user with the `gm` role on this field there, logged in with TOTP, sees the live game (its state, score, the boxes' health and latest events; never tokens or check-ins) and, **whenever players share their position with this controller (the maintainer's decision of 2026-10-28, PKD-5), their positions**, as a GM of the game sees them: a separate `positions` message (the live game's players, each with its pseudonymous `player_id`, team, role, the place and its age; at most every 5 s when changed and every 30 s while there are any), which the site server relays in memory to the remote GM page and neither stores nor logs, and which this controller never logs either (the app's position-sharing notice says so to the players) and can start, pause, resume or end it, send a GM message to every box or one of the game's declared mode commands. Nothing else: no score adjustments, ownership, reboot, joins or setup. The controller opens the connection; the site server cannot reach it and never holds its tokens. Each command is checked again here with the shared `sync_format.check_command`: refused while `remote_gm` is off, for another game than the live one, when sent more than 60 s ago by the site server's clock (the controller's clock must be set), or when its id was already seen; the rest goes through the engine as the console's GM token would (a standby refuses). Every command, done or refused, is logged in `remote_commands` (store schema 8, 365 days) with the site server's account that sent it; `GET /api/v1/remote-gm` (GM token) shows the log and the stream's state, and `sync.remote_gm` in `GET /api/v1/controller` whether it is connected. The same stream carries the remote ATAK relay's events with `[atak] remote = true` (see "ATAK / Cursor on Target"); it is then opened even with `remote_gm` off, and sends no live view and refuses every command.

**The scenario library from the site server** (phase 4 plan phase 20, decisions S20-1 to S20-8): with `[sync] library = true` (the default, once sync is on), each cycle also pulls the field's scenario library and game presets that its staff keep on the site server (`GET /api/v1/sync/presets`: each scenario by id, revision and the SHA-256 of its manifest). A manifest this controller has not installed from the site yet is fetched (`GET /api/v1/sync/scenarios/{id}`, its SHA-256 checked) and installed exactly as the console installs one (compiled, its `field.lua` loaded in the core: the controller checks again and stays the authority), so the primary and every standby have the same scenarios and a standby's join for a scenario game just works. A manifest the controller refuses is not fetched again until the site changes it; one the live game runs waits for the game to end; a scenario installed here by the GM under the same id stays until the site's version changes. A preset is saved by its name once its mode is installed and its parameters fit. What the site archives (a scenario) or deletes (a preset) is removed on the next pull, only if it came from the site (decision S20-9, `protocol/sync.md`): a scenario a game that is not ended runs or a scheduled game names stays until that is over, and one the GM replaced is the GM's. `sync` in `GET /api/v1/controller` has `library`: whether it is on and supported, the last pull, what came from the site, how many scenarios and presets were removed and the last problems.

## Node health events

Scores from boxes arrive with each box's STATE (every 15 s, and at once after a capture, a pause, a resume and the end), so a box's points on the stream trail its own screen by up to about 15 s plus the relay; a `field.lua`'s points are the controller's own (decisions SL-1 to SL-5).

The controller in charge logs three events about the boxes (decisions FU1-1 to FU1-6), which go to the log, the console, MQTT and, with the sync on, to the site server's device health; their node is the box's id, they have no epoch (they never go on air) and their seq is the controller's own count, carried over a restart:

- `node.online` (`fw`, `tier` from the box's HELLO) when it first hears a box in a game, or hears it again after `node.offline`;
- `node.offline` (`last_seen`: the game time of the box's last packet) when a box it heard has been silent for `[health] node_offline_s` (120 s by default; a box sends STATE every 15 s, so that is eight missed in a row). At most one of the two per box a minute (less with a threshold under a minute): a flapping link reports where it ended up;
- `battery.low` (`percent`) when a box's STATE or HELLO reports a level below `[health] battery_low_pct` (20 %, the site server's own threshold) for 30 s and the box has not sent its own `battery.low` (a Field Box with a battery gauge does, `CONFIG_ATALAIA_BATTERY_LOW_PCT`); once per crossing, again only after the level has come 5 points back above it.

A standby controller logs none, nor does a game that has ended; a game's `field.lua` gets a box's own `battery.low`, not these. `GET /api/v1/nodes` and the stream's node messages carry `link` (`online`, `offline` or null) and `battery_low`; the console's *Boxes* list marks a box offline and its battery low. `0` turns either setting off. In software and against the host box only, not yet with real boxes (the bench board has no battery gauge).

## The field's radio channel

All of a game's traffic uses one shared LoRa channel (RFC 0001 Amendments 1 and 3). The default, and the recommendation, is **869.525 MHz**: the centre of 869.4-869.65 MHz, the only part of the European 868 MHz band where a device may transmit up to 10% of the time at up to 500 mW ERP. Elsewhere in 868-870 MHz the rules allow 1% of the time (0.1% on 868.7-869.2 MHz) at 25 mW: about a tenth of the airtime and much less range. 868.1, 868.3 and 868.5 MHz are LoRaWAN's default channels, which every LoRaWAN device in Europe uses, so they are often busy. The recommended channel is shared too: LoRaWAN gateways use 869.525 MHz for some downlinks, and Meshtastic's European default is the same frequency. The game's packets are encrypted and use their own sync word, so nobody's traffic is mistaken for anyone else's, but everyone nearby shares the airtime. (Figures and sources: ERC Recommendation 70-03 Annex 1, ETSI EN 300 220-2, LoRaWAN Regional Parameters RP002-1.0.4; RFC 0001 Amendment 3.)

**The region** (RFC 0001 Amendment 12, decisions RF-AS923-*): a field is in one radio region, `[radio] region` (`eu868`, the default, or `as923-tw`: Taiwan, 920-925 MHz, LoRa SF9 at 500 kHz, at most 0.5 W at the antenna port, default channel 921.5 MHz) until the GM picks one in the console's radio settings (`PUT /api/v1/radio/region`, only with no game and no scan; the field then goes to the region's default channel, to be confirmed). The channels offered, scanned and drawn, the channel check, an unadopted box's pairing channel and join key 18 are the region's. The USB modem and every box must be built for the same region (Kconfig `ATALAIA_RADIO_REGION`): a box built for another refuses the joins, and the modem refuses the channels; the console warns when the modem's IDENT names another region. Leave `channel_hz` out of the config for the region's default.

The channel is a **field setting**, chosen in the GM console under *Definições / Settings* (or the API below) while no game is live:

- **keep 869.525 MHz** (recommended);
- **find a quiet channel**: the controller asks the USB modem to listen to each candidate channel for an equal share of `[radio] scan_dwell_s` (60 s by default, at most 10 s per channel), without transmitting (the modem's MEASURE command, [protocol/usb-modem.md](../protocol/usb-modem.md)), and lists them quietest first with each one's power and duty-cycle limits. It suggests the quietest 500 mW channel if its 90th-percentile noise is at or below `[radio] quiet_threshold_dbm` (-105 dBm by default) and little LoRa activity was detected on it, otherwise the quietest channel of all;
- **random channel**: one of the candidates drawn at random; it is usually a 1%, 25 mW channel (8 of the 11), since only 869.475, 869.525 and 869.575 MHz give 10% and 500 mW;
- **pick one from the list** (the 0.1% channels are listed with a warning, but never scanned, drawn or suggested).

A scan or a random draw only suggests: nothing changes until the GM accepts one. The controller keeps the choice in its store (it survives a restart; `[radio] channel_hz` is only the default until the first choice), tunes the modem to it (SET_CHANNEL), and every new game takes it: the modem gets it with the game (CONFIGURE) and the boxes in their join payloads. A game keeps its channel until it ends, so the channel and the scan are locked while a game exists. Until the channel has been chosen once, the console's game tab shows a reminder.

**A change of channel does not lose the field's free boxes** (RFC 0001 Amendment 19, found on the bench on 2026-10-29: a scan moved the channel and the idle boxes, listening on their last game's, heard neither DISCOVER nor invites). When the GM sets a new channel, the controller keeps the modem on the old one, says where the field went in a **MOVE** field frame (the new channel and a revision that only rises, sealed with the field key, three times 2.5 s apart, about 0.27 s of air in all), then tunes the modem to the new channel and sends a DISCOVER there; the free boxes follow, keep the new channel over a reboot and announce themselves. A box that was off or out of range still listens on an older channel: the field's last four channels are remembered (`radio.channel_history`, `previous_channels_hz` in `GET /api/v1/radio`), and *Find boxes* (`POST /api/v1/boxes/discover`, between games, at most one sweep a minute) also says the MOVE on each of them, then asks again on the field's channel (`{"sent": true, "sweep": [869525000], "sweep_refused": null}`); on a sub-band under 10 % the sweeps also have an hourly cap on air time (decision RL-9, below). With a modem that cannot carry field frames the channel changes at once and a box needs a card once; a box from before the amendment needs a card too. `tests/test_reinvite.py` (`MoveTests`) runs it on a fake modem and clock, `tests/test_channels.py` the setting, the shared cases are `protocol/vectors/field_frame.json`. The change's progress is in the radio settings and on the stream (decision RB-13): `move` in `GET /api/v1/radio` and in every `radio` message is null until a change with MOVEs this run, then `{"state": "telling", "from_hz", "to_hz", "rev", "sent": 1, "repeats": 3}` while the MOVEs are said (the stream sends a `radio` message at each one) and `"state": "moved"` once the modem is on the new channel (the Android controller says the same, the shared case is `S7c MOVE progress` in `protocol/vectors/controller_api.json`); the console shows it in the channel panel, and *Look for boxes* (Settings, between games, and the invite dialog) names the swept channels and how many boxes answered. **The hourly cap on sweeps** (decision RL-9, `docs/review/state-load-results.md` section 6): a sweep's MOVEs (185 ms a remembered channel) are charged to the sub-band of each channel; over a rolling hour a sub-band under 10 % duty gives them at most 5 % of its budget (1.8 s on a 1 % sub-band: two sweeps of four channels, or nine of one; none on 0.1 %), the 10 % sub-band keeps only the once-a-minute limit. A sweep over the cap is refused whole, with the reason and the seconds to the next one in `sweep_refused` (the DISCOVER is not affected), and the console says so; the Android controller does the same (shared case *S7c Find boxes: the hourly cap ...*). The record is in memory: a restart forgets it, the modem's own duty-cycle guard stays. Bench checklist: `docs/runbooks/channel-move-and-start-latency-bench.md`. Without a modem, or with a modem that has no radio chip, the scan is unavailable (the console says why) and the channel stays as it is.

Every channel must fit inside one EU868 sub-band as a whole: centre ± 62.5 kHz (the game's 125 kHz LoRa channel). 869.40 MHz, at the sub-band's lower edge, is refused because its channel starts at 869.3375 MHz; the legal centres in 869.4-869.65 MHz are 869.4625-869.5875 MHz. The config, the API, the modem and the boxes all apply this rule, and the boxes and the modem take their duty-cycle budget and TX power from the chosen channel's sub-band. The candidates, the thresholds and the other choices are decisions CH1-CH13 in `docs/review/decisions-to-review.md`. The noise readings have not been compared with a real SX1262 yet (plan phase F); calibrate the quiet threshold at bring-up.

## A game's state changes reach the boxes in about a second

Start, pause and resume go out as a CMD and a TIME at once, and then as a **TIME alone again 1.0, 2.5, 5.0 and 10.0 s later** (RFC 0001 Amendment 19, part 2; `STATE_REPEAT_GAPS_MS` in `simulator/atalaia_sim/field_controller.py`, the same in the phone's `field_controller.dart`). A TIME carries the game state and a box acts on it as on the CMD, so a box that lost the first frames (on the 2026-10-29 bench the start took 21 s to show on a joined box: CMD and TIME each went once and the next beacon is 30 s away in manual failover) starts within about a second of the press on a quiet channel. The repeats are TIME only, never CMD (a late PAUSE must not undo a RESUME); a new state change replaces the repeats still due; an end is not repeated (GAME_OVER does that); about 0.36 s of air in all. `tests/test_engine.py` (`test_a_state_change_is_repeated_as_time_for_ten_seconds`) and the shared "the radio" case in `protocol/vectors/controller_api.json` pin the times; `tests/test_box_e2e.py` drops the first CMD and TIME through the real box firmware and checks the box starts, pauses and resumes in under two seconds.

## The controller's own frames: TX pacing

The controller spaces its own frames (decision SL-13's pacing half, SL-39, RFC 0001 Amendment 15; the phone's controller does the same, `RadioTransport` in `app/lib/controller/controller_radio.dart`). Every frame it puts on the radio in a game (ACKs, TIME beacons, CMDs: START and END, the GM's commands, a scenario's setup `field.send`) waits in one first-in first-out queue of 8 frames, with no priorities, and is handed to the modem one at a time, **`[radio] controller_pace_ms`** after the previous one was on the air (the modem's TX_ACK says when it was; without one, 800 ms from the hand-over). An idle queue sends at once. **It is off by default (0): no queue, as before.** 800 ms is the relay study's `H_paced` and the value to try in the 20-box field test (`docs/runbooks/radio-field-test.md`), because the model says it also costs some of the controller's ACKs; the maintainer decides from that test. The relay study measured that this gap adds 0-22 points to the setup CMDs that reach their box (`docs/review/relay-study-results.md`, table 7); the CMD is still one shot, with no ACK and no resend.

A frame sent to a full queue is dropped and counted: `GET /api/v1/controller` shows `tx_queue` (`queued`, `dropped`, `pace_ms`) beside `tx_status`. When the game ends the waiting CMDs and TIMEs are dropped (stale; counted in `dropped`), the waiting ACKs stay (a box leaves a finished game once its last events are acknowledged), and everything goes at once with the end's CMD and TIME, because the modem forgets the key next. A frame still queued when the controller crashes is lost; a box's resend heals a lost ACK. Below the queue the modem's listen-before-talk and its duty-cycle guard are unchanged: a refusal for the duty cycle is still a `duty_cycle` in `tx_status`. Frames outside a game (invites, GAME_OVER, pairing) are not queued. `tests/test_tx_pacing.py` runs the rules on a fake modem and clock; the shared cases are "TX pacing" in `protocol/vectors/controller_api.json`.

## Joining boxes and a standby controller

A box joins a game with a **join payload** ([protocol/join.md](../protocol/join.md)): the game's id and key, the box's node id and role, the teams, the channel and the relay clamp, signed with the **field join key**. Every box of the field gets that key once, when the field adopts it (next section). `join-key` above prints it; `[join] key` in the TOML sets it, so two controllers can share one field.

In the GM console's *Join* tab (or `POST /api/v1/join`), pick the role: the controller gives the box the next free node id, records its role, and shows the payload as a QR code, as text (`atalaia:join:...`) and as the bytes to write on an NTAG215/216 card. A box reads the card with its NFC reader, or takes the text on its serial console (`@join atalaia:join:...`). The payload holds the game key: show it only to the people setting up the field.

### Inviting boxes into the next game, and the start guard

A box whose game is over announces itself over the radio in **field frames** ([protocol/field-frames.md](../protocol/field-frames.md), RFC 0001 Amendment 7, proposed): its device id, a fresh token, its name, its last game and role. The modem passes them up as they are (FIELD_RX); the controller (`reinvite.py`, over the simulator's `atalaia_sim/lobby.py`) keeps the free boxes it hears for two hours. When the GM creates a game, the console's *Boxes for this game* dialog lists them (after a DISCOVER, which makes the free boxes answer within 3 s), with the previous game's boxes ticked and each box's previous role; *Invite* sends each ticked box its join payload, made exactly as for a card, in one to three INVITE parts sealed with a key derived from the field join key (HKDF-SHA256), for the box's device id and token. The box joins only if it is free, takes the payload through every check of a card, answers, and its HELLO (which now carries its device id, key 10) closes the invite. Unanswered invites are sent again after 6 s, three times in all; the console shows each box's progress (`GET/POST /api/v1/games/{id}/invites`). Join cards, QR codes and the serial console work as before. The field join key is a field secret: whoever holds it and records the radio can read the keys of the games joined by invite (decision RJ-2; [SECURITY.md](../SECURITY.md)). Its field frames' nonces are the pseudonym of a sender id drawn fresh from the CSPRNG at every start (never stored, so a restored backup or a standby made from a copy of the database cannot repeat one) and a count within the run (decisions RJ-7, RJ-15). It refuses an announcement that is not newer than the last one heard from that box, and forgets a game's invites when the game ends.

A game **starts only once every role it needs has a joined node** (a box or a linked Android prop): every role of its mode and role packages unless a manifest says `needed: false`, or for a scenario the roles of the boxes it names (decisions RJ-1, RJ-3). `POST /api/v1/games/{id}/start` answers 409 with `start_check` (`needed`, `joined`, `missing`, `warnings`) otherwise; `{"force": true}`, the console's *Start anyway* after a confirmation, starts it, logs it and tells every console (`system` `start.forced`). A mode's minimums (`min_zones`, `min_satellites`, Last Stand's `last_zones`) only warn. The remote GM's `start` is refused the same way (`conflict`, with the roles in the result's `missing`) and takes the same `force` after its page's *Start anyway?* (decision RG-1, which reverses RJ-4).

The *Boxes for this game* dialog follows the same check live (the game the controller pushes on every HELLO carries it; decisions GM-1 to GM-4): it says *Ready to start: every role has a box* with the joined count per role once every needed role has a box, or which roles it still waits for, and lists each unmet minimum as a warning. Its *Start game* button (*Start anyway* while a role has no box) asks *Review the game's other settings first?*: *Review settings* closes the dialog and opens the game card's *Game settings* (the parameters it was created with, read-only); *Start now* starts it through the same `POST .../start`, with `force` only when a role is missing (logged and told, as above).

A second controller (another Pi with its own modem) stands by for the game: ask the primary for a payload of kind *standby controller*, and paste its text into the standby's console (*Join* tab) or `POST /api/v1/controller/join`. The standby then hears the game, logs its events and follows its clock and scores without acknowledging anything; if the primary fails, *Promote* on the standby makes it take over (manual failover, ADR-P2-8). It leaves the game when the TIME beacons say it ended.

A mode's `field.lua` (Hold-All Domination, Last Stand) runs in the core on the controller from the game's start. Its `score.add()` points are the controller's own counters: they are merged into the totals (by maximum, like a box's) under one key per run of the script, and kept with the game, so they survive a controller restart, after which the script runs again and its new points add to the earlier ones. A standby controller that is promoted starts its own run; the points of the old controller's runs are not known to it (they never travel on the radio; decision K5 in `docs/review/decisions-to-review.md`). A `game.win()` or `game.finish()` from the script ends the game with that winner on the next tick. In a mode **without** a `field.lua`, a box's own `game.end` (its `node.lua` calling `game.win` / `game.finish`: Sabotage's time limit) ends the game the same way (decision GE-1): the first one from a box assigned in the live game, while it is running and this controller leads it, with the event's winner when it is one of the game's teams, else as a draw (never the points' leader); later ones are only logged, and one that arrives while the game is paused or from an unassigned box is logged and ignored. The controller's `game.end` carries `by_node` and `by_name` (the box), which the console's log shows as *ended by box ...*. With a `field.lua` a box's `game.end` stays an event the script receives (`FieldScript` / `_note_box_end` in `engine.py`; shared cases "a box's game.end ..." in `protocol/vectors/controller_api.json`).

A live game survives a controller restart (decision OT-7, the maintainer's, 2026-10-22): with `persist_game_key = true`, the default since then, the game key is kept in the SQLite file (mode 0600) until the game ends, and after a restart the game goes on from its last saved game time, scores and adjustments (the controller's own events numbered on from the stored ones, decision PE24-42), its boxes still heard; the shared contract cases check the same restart against the app's controller (`protocol/vectors/controller_api.json`). Keeping it adds little at rest: the field join key, the field's master secret that already opens every game key sent in a radio invite (decision RJ-2), is on the same disk, and a game key is short-lived (erased when its game ends). With `persist_game_key = false` (ADR-P2-4's rule, the default before) a restarted controller can only end the game, but its boxes still hear it: *End* sends **GAME_OVER** over the field radio (the game id and its key's tag, sealed with the field key, three times, on the game's channel), and they leave the game and announce themselves free ([protocol/field-frames.md](../protocol/field-frames.md), decisions OT-13 to OT-16); the answer says whether it went (`game_over_frame`). The controller sends GAME_OVER after every game it ends, too, for a box that missed the end.

## Adopting boxes

A new Field Box is **adopted** once by the field: it gets the field join key, which is also the field's master secret once the radio invites seal games under keys derived from it ([protocol/adoption.md](../protocol/adoption.md), decisions AD-1 to AD-27; `adoption.py`, `pairing.py`). The console's *Adotar / Adopt* tab (GM token) has three ways. In software, against the C host box (and, for the code, the C host modem); not yet with real boards on the Pi's USB, a PN532 or the air.

- **The USB cable.** Plug the box into the controller and press *Look for boxes*: the controller opens every Espressif USB-Serial-JTAG port (303a:1001) but the modem's (`[modem] port`), and the ports of `[adopt] usb_ports` (for a controller in Docker: a COM-to-TCP bridge's `socket://host.docker.internal:7001`, or the board attached with `usbipd` and passed as a device), asks each `@adopt-info`, and lists the boxes with their name, MAC and state. The GM confirms one; the controller checks it is still that MAC on that port and sends `@adopt <key> <PIN|-> <field name>`. An unadopted box takes it; a box of another field, or one still on this field's old key, only with its admin PIN (the console asks; five wrong PINs lock it until it restarts). `[adopt] usb = false` turns this off.
- **The NFC field card.** *Make the field card* gives the bytes of an NTAG215/216 (type `application/vnd.atalaia.field`: the join key and the field's name) to write like a join card and tap once on each new box; a box of another field then asks for its admin PIN on its keypad. **The card is the field's master secret**: keep it locked away. If one is lost or copied, `join-key --rotate` (it keeps the old key's fingerprint, so the console tells boxes on the old key apart), restart, adopt every box again, write new cards; join cards made before stop working.

- **The pairing code over the radio.** An unadopted box shows a 6-digit code when it starts and offers itself in pair frames (message type 10, in the clear, RFC 0001 Amendment 8) on 869.525 MHz, its default channel. *Pair by code (radio)* → *Look for boxes on the radio* (`POST /api/v1/adopt/pair/listen`: with the field's channel elsewhere and no game live, the modem listens on 869.525 MHz for five minutes, then goes back) lists the boxes offering; the GM types a box's code and the controller runs CPace with it (`POST /api/v1/adopt/pair`, `pairing.py`): the join key is sent, sealed under the run's key, only once the box's answer proves it has the same code. A wrong code ends the run and the box shows a new one (three wrong runs: it waits a minute; ten: until it restarts). The modem's firmware must say `"pair": true` in IDENT.

Every field card made, every USB adoption and every pairing run is logged (`atalaia.adoption`) and the last 100 are kept (`GET /api/v1/adopt`: method, box, MAC, port, result; never the key or a PIN). `@joinkey <64 hex>` on a box's console and the setup portal's field still work, under the same rules.

## HTTPS and the field CA

On first start the controller makes the field's own certificate authority and a server certificate for its names and addresses in `tls/` next to the database (`[api] tls_dir`), keys with mode 0600, and serves the same API with HTTPS on `[api] tls_port` (8443) next to plain HTTP on `[api] port` (8080). `python3 -m atalaia_controller ca` prints the CA's fingerprint, which the check-in poster and the join payloads for Android props carry; phones fetch the certificate from `GET /api/v1/controller/ca` (no token, both ports), check it and trust only it for this field. Put the names and addresses phones use in `[api] tls_names` (the controller adds `localhost`, its host name, `name.local` and the addresses it finds; the server certificate is made again when the list changes or it has under 30 days left). The CA itself is never replaced on its own: deleting the folder makes a new one, and every player then has to remove the field in the app. The CA is ECDSA P-256 so that browsers accept it too (decision PE2). The GM console and the scoreboard still work on plain HTTP.

## Firmware updates for the boxes

The GM updates the Field Boxes' firmware from the console's *Boxes* tab, over the field's Wi-Fi ([protocol/firmware-update.md](../protocol/firmware-update.md), decisions FU3-*; `firmware_updates.py`). In software and against the host box; not yet with a real board.

- **Releases.** A release is the image (`atalaia_esp32.bin`) and its `.release.json` (`tools/firmware_release.py sign`, [firmware/esp32/docs/RELEASE_SIGNING.md](../firmware/esp32/docs/RELEASE_SIGNING.md)). The controller keeps one only if a key of `[firmware] release_keys` (Ed25519 public keys, standard base64; none: nothing is accepted) signed exactly its platform, version, size and SHA-256, the image fits a box's 2 MiB slot and its own descriptors say `atalaia_esp32`, that version and an accepted variant (`[firmware] variants`, `["box"]`). At most four, in `[firmware] dir` (`firmware/` next to the database). A key removed from the setting withdraws its releases at once. The site server's catalogue lists releases but holds no image (decision FU3-3).
- **Updates.** Only while the live game is `ready`, never while it runs or is paused; only with HTTPS on (the boxes pin the field CA of their join). For one box or all, the controller checks each box's HELLO (an `esp32s3` box, full or reduced tier, a lower version) and sends it CMD update (opcode 9, `{"id", "version"}`). The box fetches `GET /api/v1/firmware/{id}/release` and `.../image` (no token: a release is public and every box verifies it), checks it all again with the keys in its own firmware, installs it, reports (`POST /api/v1/firmware/report`, an HMAC with the game key) and reboots; its next HELLO shows the version it runs (`done`, or `rolled_back` when the new image did not confirm itself). If the radio refuses the offer after taking it (its TX_ACK: `duty_cycle`, `queue_full`, anything else), the update becomes `failed` at once with the reason `radio_duty_cycle`, `radio_queue_full` or `radio_failed` (only for a refusal within 30 s of the offer; nothing is resent: the GM offers again). With no news for `[firmware] update_timeout_s` (600 s) an update counts as `timeout`. The game does not start while an update is on its way, unless the GM stops waiting for it. A mode's `field.lua` can never send `update`.

## Signed mode packages

The GM installs signed community modes from the console's *Presets* tab ([protocol/mode-packages.md](../protocol/mode-packages.md), phase 5 plan phase 6, decisions P5C-17 to P5C-21; `signed_modes.py`). In software.

- **Trust.** Only packages signed by a key of `[modes] keys` (Ed25519 public keys, standard base64, at most 8; none: nothing signed is installed) and not revoked (`[modes] revoked`, key ids, plus the index's `revoked.json`). Everything is checked before anything is kept, and the first problem refuses the package with its reason (`bad_hash`, `bad_signature`, `no_key`, `revoked`, `bad_archive`, `mismatch`, `licence`, ...); then the upload's own checks (the manifest, the scripts loading in the core, never a built-in id).
- **Upload.** `POST /api/v1/mode-packages` with the archive as the body and the `.release.json`'s `id`, `version`, `kind`, `min_tier`, `signature` (and `key_id`) as query parameters, at most 1 000 000 bytes. An upload is *not reviewed by the project*, whoever signed it.
- **The index.** `[modes] index`: an `https://` URL (the system's trust store; never `http://`), or the path of an `index.json` with its packages next to it for a field without internet. `GET /api/v1/mode-packages` lists its entries and what this controller would do with each (`available`, `installed`, `no_key`, `revoked`, `builtin`), read again after 5 minutes or with `?refresh=1`; an index or a `revoked.json` that does not read whole offers nothing. `POST /api/v1/mode-packages/install {"id", "version"}` fetches, checks and installs one; the index's `verified` is the project's review (the verified badge).
- **What is kept.** The files as any upload, plus the release and the archive exactly as signed (store schema 10), for the boxes later (plan phase 13). `GET /api/v1/modes` shows each package's `signed` (key id, `verified`, SHA-256, `source`, licence and `trust` today: `trusted`, `revoked`, or `untrusted` once its key leaves `[modes] keys`); unsigned uploads (`POST /api/v1/modes`) have `signed: null` and replace a signed package of the same id, signature and all. Installing a package tells every console (`{"type": "modes"}` on the stream).
- **Missing modes sent to boxes** (plan phase 13a, `mode_fetch.py`, decisions P5D-1 to P5D-12; the box's side is 13b). In the invite dialog, under a box that answered *no mode*, the parts it would run and *Send missing modes*: an invite with join key 16, after which the box fetches each part it lacks over HTTPS pinned to the field CA, checks it with the keys in its own firmware, reports and says HELLO. A HELLO joins it only when its reports say it keeps every part it was offered: a box that could not report over HTTPS says HELLO to send `node.modes_failed` over the radio and then leaves, so a HELLO without the reports waits for that event, the report, or the timeout (`report_lost`), and the box is never shown as joined meanwhile (decisions P5D-14 to P5D-18). Only parts signed by one of `[modes] box_keys` (the mode and release keys built into the boxes' firmware, at most 8), trusted here now, at most 256 KiB, are offered; only while the live game is ready; the game waits for a fetch at most `[modes] fetch_timeout_s` (300 s) or until the GM stops waiting. The Boxes tab lists what each box keeps and marks a box to forget it at its next invite (join key 17). The contract: [protocol/mode-packages.md](../protocol/mode-packages.md), "Fetching missing modes".

## The I/O pods' settings over the radio

The GM sets the buttons' colours, the ring's brightness, the volume and the enclosure switch of the I/O pod a phone is linked to, from the console's *Boxes* tab (*I/O pods' settings*, `components/pod-config-panel.js`), before a game starts or after it ended ([protocol/pod-config.md](../protocol/pod-config.md), decision PODC; `pod_config.py`). The controller seals CMD pod (opcode 10, `{"v": 1, "rev", "btn", "bright", "vol", "tamper", "reset"}`, `dest` the phone's node id) with the game key; the pod's radio takes it, keeps it in its flash and says so through its phone (`node.setup_applied`, `kind` `pod_config`, `rev`: the boxes' setup acknowledgement). Until it hears that, the controller sends the command again after 8, 16, 32, 64 and 128 s, then shows *no answer*. The candidates are the phones of the live game (HELLO platform 3: a phone's HELLO does not say whether it has a pod, the answer does). `rev` is the clock's seconds, or one above the last sent to that node (a pod keeps the last it took), unless the GM gives one. A mode's `field.lua` can never send `pod`.

## Field check-in

Players check in at the field with the app ([protocol/checkin.md](../protocol/checkin.md), ADR-P3-13). In the GM console's *Check-in* tab, *Print the poster* opens an A4 page with the field's QR code: print it once and put it up in the check-in area. When the poster's addresses (hence its QR code) differ from the poster last printed (a lease moved, the certificate changed), the console says so at login and in the Check-in tab and suggests printing it again (check-R8). After a GM creates a game in the console, a small dialog suggests exactly that (the same page; it closes itself after 10 s, or with Esc, and can be paused with a button, by the pointer or by keyboard focus, WCAG 2.2.1; and *Don't show this again* is kept in the browser; decisions check-R14 to check-R19). The poster carries no secret: the field's id and name, the controller's https addresses (`[checkin] urls`, else `tls_names` first and then the host's own names and addresses, which are left out in a container, where they resolve only inside it: there set `tls_names`; **an address that is on no interface of the host now is left out and warned about in the log, at every start**: a stale `tls_names` or `[checkin] urls` entry, or one in a saved poster, never reaches the poster, while a host name is kept, since a name cannot be checked, and a container keeps what is configured, since its interfaces are not the field's; a list the GM typed that keeps at least one address is the poster as it is, not padded; the server certificate covers every address the poster lists, and an address left out of one is left out of the other; decisions check-R8 to check-R13, `addresses.py`, shared cases `poster_addresses` in `protocol/vectors/checkin.json`), the CA's fingerprint and optionally the Wi-Fi network's name (`[checkin] wifi_ssid`; the poster page can draw a Wi-Fi code from a password typed there, which is never stored).

A player who scans it checks in with a display name (and the federation number if `[checkin] federation` asks for it; never verified automatically: staff tick "card seen"; with the membership rule `apd.checkin` the check-in stays `pending` until a marshal or the GM ticks "card seen, matches", which records who and when, stores the verdict and erases the number: [protocol/apd.md](../protocol/apd.md#the-card-check); the player's own, separate, unticked `share_position` choice is recorded with its time and the notice version and gates `POST /api/v1/positions`: [protocol/checkin.md](../protocol/checkin.md#sharing-the-position)), and gets a **player token** keyed with the game's own token key, made by this controller and kept only in its SQLite file. The token's role, team and squad are checked against the player's check-in on every request, so the GM's changes and removals take effect at once. Check-in is open from a game's creation until it ends (*Close check-in* stops it); with `[checkin] confirm = "staff"` check-ins wait for a marshal or the GM to confirm them. The controller logs `player.checkin` with the player's id, never the name. A team always exists; squads, sub-groups inside a team, only in a game created with `squads` (decision PE25): there the GM gives a squad (team › squad) and the squad-leader role, elsewhere both are refused.

**Players' NFC tags** are signed by this controller, which holds the game's key: `POST /api/v1/games/{id}/tags` (the GM token, or a marshal's for that game) answers the bytes of one tag for a player and a team, and the key never leaves (decision TW-1; [protocol/nfc-tag.md](../protocol/nfc-tag.md)). The console's *Check-in* tab writes it with Web NFC or shows the bytes, a phone controller's own screen writes it with its NFC, and the app's marshal role asks for it over the field's network, so a marshal's phone no longer needs the field join key for tags. The code is `player_tags.py`; the shared contract cases ("player tags") check the Android controller too.

Players declare the replicas they will use; marshals see the **replicas to chrono** list in their app and in the console, and their phones send each signed series of readings (`POST /api/v1/chrono/readings`): the controller verifies them with the marshal's registered Ed25519 key, judges the series against the class limit of `[checkin] limit_template` (one of `app/lib/chrono/limit_templates/`, unverified research figures: decision P3-5) and marks the replica passed or refused. A pass counts for the rest of the field's day (`chrono_valid_for`). **A marshal is someone on the GM's marshal list** (the maintainer's request of 2026-10-26, decisions MR-1 to MR-14): in the console's *Check-in* tab, *Marshals*, the GM adds a player who has checked in (the controller gives the id, `M-01`, `M-02`..., and the marshal role; `POST /api/v1/marshals`), sees whether the player's app has registered its key, renames, rebinds or removes. The app does not take an id from its user: `GET /api/v1/checkin/me` tells a marshal's phone its id and name (`marshal`, or `null` when the player is not on the list: the app then refuses with "ask the GM to add you as a marshal"), and `PUT /api/v1/checkin/me/marshal-key` takes a key for that id and no other. Removing a marshal revokes it at once: the key stops verifying, the player is a player again, and the readings the phone had not sent are refused (they stay on the phone and go if the GM adds the marshal again). A phone that cannot reach the controller may go on as a marshal for two hours (`valid_for_s`, 2 h) after the controller's last yes, never longer and never without one yet. Store schema 12 (`marshal_roster`; the marshals of an older database are on the list). The Android controller keeps the same list and answers the same (decisions MR-12).

Personal data stays on the controller: names and federation numbers are shown to staff (the GM token, marshals) only, never in events, MQTT, logs or the read token's views, and are erased `[checkin] retention_days` (30) days after the game; a field identity unused for a year is deleted. The default privacy notice is `templates/checkin-notice-pt.md` and `-en.md` (`[checkin] notice_pt`, `notice_en`; raise `notice_version` when it changes). Everything works without internet.

**How long the rest is kept, and erasure** (decisions RET-1 to RET-8; `Checkin.purge`, store schema 17): two field settings, set like the others (`[checkin] chrono_retention_days` and `game_retention_days`, default 365, 30-3653; the console's check-in settings, `PUT /api/v1/checkin/settings`; or the site server's, `settings.chrono_retention_days` and `settings.game_retention_days` of `GET /api/v1/sync/field?settings=1` with `[sync] branding = "site"`, after which the console's PUT of them is 409). `chrono_retention_days` is for the chrono readings, other fields' readings pulled for a roster and a marshal's earlier keys (and the erasure records below); `game_retention_days` is for **an ended game**: the purge (at most every ten minutes) deletes games that ended that many days ago with their events, scores, nodes, positions, check-in rows, token key, schedule link, sync bookkeeping and per-game settings. **With `[sync] enabled` a game is deleted only once the site server has all of it** (`sync_state.final`: ended and every event acknowledged), whatever its age, because the controller's copy would be the only one (decision RET-3); the purge's answer counts those kept (`games_unsynced_kept`). Without a sync, age alone decides. When the GM erases a player (`DELETE /api/v1/players/{player}`, with or without `?chrono=true`) or a player erases their readings (`DELETE /api/v1/players/{player}/chrono`) and a sync is set up, the controller keeps an **erasure record** (`erasures`: the player id, whether readings and/or the identity were erased, when; never a name) and sends it with the next sync (`POST /api/v1/sync/erasures`, [protocol/sync.md](../protocol/sync.md)); the site server erases its copies (the player's chrono records, and the link of the id to an account) and the controller forgets the record once acknowledged. An older site server (404) is not asked again until a restart; the record then goes with the chrono retention. `GET /api/v1/controller`'s `sync.erasures` has `supported`, `sent` and `pending`.

**APD / association membership** ([protocol/apd.md](../protocol/apd.md), decisions APD-1 to APD-14, MEM-1 to MEM-6; `apd.py`, vectors in `protocol/vectors/apd.json`; the names are historical): a Portuguese airsoft player belongs to an APD and holds a number with an expiry, and players elsewhere may need a membership of a club, federation or insurance body. The field's **country** (`[checkin] country = "PT"`, the console's field, `PUT /api/v1/checkin/settings` with `country`, or the site server's with `[sync] branding = "site"`: `settings.country`; empty means PT where the controller's time zone is Europe/Lisbon, Atlantic/Azores or Atlantic/Madeira, otherwise unset) picks the words (PT keeps "APD"; any other country or none says "association membership") and which entries of the shipped list `apds` offers (the country's, then the field's own `custom` ones). The controller never verifies any of it. `[checkin] apd_checkin = true` (and `apd_expiry`, `apd_accepted = [ids]`, empty for any) makes the check-in ask for the APD (`apd_id`), the number (`membership_number`; the old `federation_number` is the same value, a legacy number is "APD unknown") and the expiry (`membership_expires`), and work out a verdict for staff: `valid`, `expired`, `not_accepted` or `missing`. A self check-in whose verdict is not `valid` stays `pending` even with `confirm = "auto"`; a marshal or the GM can always confirm it or check a player in by hand, which is logged (`apd override`, the player id and the verdict, never the number) and kept as `apd_override` on the row. The rule is the GM's in the console (`PUT /api/v1/checkin/settings` with `apd`, a whole rule; the field's own APDs are its `custom` entries, ids `x-...`) or, with `[sync] branding = "site"`, the field's from the site server (`settings.apd` of `GET /api/v1/sync/field?settings=1`, with the other check-in settings of BR24; the console's PUT is then 409 once the site has sent one). The project's list (`atalaia_controller/data/apds.json`, a copy of `registry/apds/apds.json`, started from the partners jogarairsoft.pt shows, each cited from its own site) and the rule's own entries are `apds` in `GET /api/v1/checkin`. The roster may carry `apd` (the rule) and per registration `apd_id` and `membership_expires`. The APD, the number and the expiry are personal data like the federation number: staff only, erased by the retention, by leaving and by the player's erasure (store schema 15), in the CSV export as `apd_id`, `membership_expires` and `apd_status`, never sent to the site server.

## Field and team branding

A field or club running its own controller can show who it is (decisions BR1-BR24 in `docs/review/decisions-to-review.md`). In the GM console's *Definições / Settings* (GM token): the field's name (the same name the check-in poster prints), a logo, an optional wallpaper and an accent colour. The controller keeps them in its SQLite file, so they survive restarts. Anyone who can reach the field's API reads them without a token, since players need them before or right after checking in and none of it is personal data: the app shows the logo in its header, the wallpaper (dimmed) behind the player's view and an Android prop's idle screen, and the accent on its primary buttons; the GM console shows the logo and name in its header, the scoreboard above the game, and the check-in poster above the field's name, outside the QR code. Without branding everything keeps the default Atalaia look.

Teams get a display name and a crest per game next to their colour: `team_info` when the game is created, or `PUT /api/v1/games/{id}/teams/{team}` until it ends. The colour stays the team's name (red, blue...), which is what the boxes, their LEDs and buttons, the radio, events and MQTT use. *Saved teams* (team presets) keep a club's name, crest and usual colour for the next game.

Uploads are PNG, JPEG or WebP only (SVG is refused: it can carry scripts), with the type read from the file itself:

| Image | Bytes | Pixels a side | Shape |
| --- | --- | --- | --- |
| Logo | up to 1 MiB (1,048,576) | 16 to 2048 | at most 8:1 |
| Wallpaper | up to 4 MiB (4,194,304) | 320 to 4096 | at most 8:1 |
| Crest | up to 512 KiB (524,288) | 16 to 1024 | at most 4:1 |

The controller has no image library: `images.py` checks each file's structure with the standard library (PNG chunks and checksums with the pixel data inflated to exactly the size its header says, JPEG segments with one frame, WebP's RIFF and image headers), refuses animated images, and rewrites the file without its metadata (text and EXIF chunks, JPEG APP1/APP13 and comments, WebP EXIF and XMP), keeping colour profiles. Images are stored once by the SHA-256 of the result, which is also their ETag; a replaced logo or wallpaper is deleted at once, a crest no game or team preset uses a day after its upload (at most 500 are kept). Whoever uploads an image is responsible for having the rights to it; the console says so next to every upload.

## The field view and multi-story fields

The console's *Campo / Field* tab shows the field's own image (a photo, an aerial view or a floor plan the GM uploads, PNG, JPEG or WebP up to 4 MB) with a marker per box, dragged into place by the GM (`PUT /api/v1/games/{id}/positions/{node}`, fractions of the image). **A multi-story building** (the maintainer's request of 2026-10-22, decisions ML-0 to ML-12): the GM ticks *Edifício com vários pisos / Multi-story building*, chooses the number of levels (2 to 10) and names them (the console fills in "R/C", "1.º andar", "2.º andar", ... or "Ground floor", "Floor 1", ...; a basement is a level the GM names so), and uploads a floor plan on each level's tab. Each tab shows its plan and the boxes on that level; *Each box's level* under the plan moves a box to another level (a box not placed yet is on level 0), and a box dragged on a level's plan stays on that level. Level 0 is the field image of before: the old endpoints still read and write it, and a store from an earlier version keeps its image as level 0 (store schema 9). Turning levels off asks first and keeps everything (the other plans, the names, each box's level) for when they are turned on again; only level 0's plan is used meanwhile and every box shows on it. Fewer levels delete the plans of the levels that go (the console asks first) and move their boxes to level 0. A player's position report may carry `level` (below). The levels stay on this controller: field images are not synced to a site server (ML-10).

**Map features** (the maintainer's request of 2026-10-22, decisions MF-0 to MF-16). Below the plan, *Marcações no mapa / Map features* marks what else is on the field: a safe zone, a team's respawn or HQ (*Base*), the car park, a first aid station, an objective, or anything else with a name. Each is a pin, a circle (a pin and a radius in metres) or an area of 3 to 12 corners, on one level's plan, in the plan's coordinates as the boxes are. The GM adds one by type, clicks the plan for a pin, presses at a circle's centre and drags to its edge (to scale only when the plan has its map position; without it the radius is typed and the circle is drawn dashed at a set size), or clicks each corner of an area; the same is done with the keyboard by typing a place across and down the plan. Each says **who may see it**: everyone, one team (by the team's name, as games name teams: `red`, `blue`...) or only the organisers; a respawn or HQ is its team's by default, anything else everyone's. The controller enforces it on every path: `GET /api/v1/field/features` and the stream's `map_features` message give each token only what it may see (staff, the GM token and marshal and gm player tokens, everything; a player their team's and everyone's; the read token everyone's), and the ATAK feed sends only the features for everyone to the field's Wi-Fi (below). Features belong to the field and stay from game to game (store schema 11); a level that goes takes its features with it, and with levels off the other levels' features are kept but shown nowhere. They stay on this controller: not synced to a site server, and not on the Android controller yet (MF-14).

**The field boundary and loading the field from a map** (the maintainer's idea MF-18, built as decisions MF-19 to MF-30). A map feature of type `boundary` (*Limite do campo / Field boundary*) is the field's real outline: an area only, at most one per level, of no team, for everyone unless the GM says otherwise; the console dims the plan outside it, and ATAK gets it as a closed shape without a fill. The GM draws it by hand with the feature editor, or loads it with the plan: the Field tab's *Carregar o campo de um mapa / Load the field from a map* opens a page (`console/src/field-map.html`) where, with internet while setting the game up, the GM finds the field on an OpenStreetMap map (it opens on the level's map position, else on the GM's own location when the browser already allows it; *Use my location* asks for one fix, which only moves the map and is sent nowhere; a place's name is searched with OpenStreetMap's Nominatim (the requests name the project's contact address, MF-44) only when the GM presses *Search*, at most once a second; a typed `latitude, longitude` goes straight there: decisions MF-41 to MF-49), marks the corners of its outline (3 to 12: a press on the map, a cross moved with the arrow keys, or a typed `latitude, longitude`), and the **browser** draws the field image: OpenStreetMap's data for the area from the Overpass API (one query; when it is busy or does not answer, retried with exponential backoff and asked of one other public instance (`overpass.private.coffee`), within about a minute, each request ending after 35 s, cancellable: decisions MF-50 to MF-53, MF-62) over the open orthophoto of the country (or region, or German Land) the outline is in, when there is one (its open WMS: the DGT's OrtoSat 2023 in mainland Portugal, IGN España's PNOA, IGN France's orthophotos (also overseas) and PDOK's aerial photographs in the Netherlands, decisions MF-65 to MF-72; Belgium's regions', Luxembourg's, swisstopo's in Switzerland and Liechtenstein, eleven German Länder's, Poland's and Czechia's, decisions MF-73 to MF-80), with its credit (e.g. "Ortofotomapas © DGT (CC BY 4.0)") and "© OpenStreetMap contributors" in the image's corner; the image covers the outline's box with a margin, at about half a metre per pixel (at most 4096 pixels on a side and 4 km across). *Use as the field* then sends one request, `POST /api/v1/field/levels/{n}/from-map`, which sets the level's plan, its map position from the image's edges (exact: the image is drawn north-up with latitude and longitude linear in it, which is what the two-corner map position is) and its boundary in one transaction. While finding the field, a *Mapa / Ortofoto* switch shows the orthophoto of the map's centre as the map, naming it (*Ortofoto (IGN España)*; WMTS tiles, or the WMS per tile where there is no WMTS in Web Mercator; MF-54 to MF-57, MF-67); on a wide window the outline sits beside the map (MF-58); the drawn image comes into view with the focus on it, leaving without using it asks first, the outline survives a reload, and after saving the page goes back to the Field tab on that level (MF-59 to MF-63). The controller never needs internet for this; only that page may reach those services (its own Content-Security-Policy) and ask for the GM's location (`Permissions-Policy: geolocation=(self)`; every other console page gets `geolocation=()`), and the rest of the console stays same-origin. Players' phones warn when they leave the boundary (decisions MF-31 to MF-40, app/README.md): the app reads the boundary and the level's map position with the player's token, tests its own fixes, and sends nothing about it, so the controller has no part in it.

**The field grid** (the maintainer's request of 2026-10-23, decisions MF-81 to MF-93). A milsim map grid over a level's plan, for calling positions on the radio: lettered rows (A, B, ... Z, then AA ... AZ, 1-52) and numbered columns (1-52), off by default, one per level (`field_grid.py`, settings `field.grid` / `field.grid.<n>`, no schema change). The GM sets it under the plan (*Quadrícula no mapa / Grid on the map*: on or off, rows, columns, *Fit square cells*; with a map position the console says each cell's size on the ground) or over the preview when loading the field from a map (sent in the same request). It divides the image's rectangle into equal cells (image-aligned, not a UTM/MGRS grid) and is drawn over the plan, never into it: thin white lines and labels on a dark halo, the labels thinned out when cells are too small; every viewer may hide it in their own browser (*Mostrar a quadrícula*). The boxes' labels and the map features' list say their cell ("quadrícula C4", an area "B2–D5"). **On ATAK** (PKE-2) a box, a map feature (at its pin: a circle's centre, an area's vertex average) and an indoor player on a level that has a grid say their cell in the remarks after the level's name, `grid C4` (`Atalaia: red, 1.º andar, grid C4`; a GPS player has no place on the plan, so none), and a changed grid sends everything again; the phone controller does the same, held to `protocol/vectors/atak_xml.json`. **Printing** (PKE-2): *Imprimir o mapa com a quadrícula / Print the grid map* under the plan opens the browser's print dialog with a sheet of the field's name, the plan under its grid and a list of what is in which cell (a poster or a PDF; the sheet is drawn only while printing, `html.print-grid-map` hides the console for print; not in the Android app's web view). Not on the scoreboard or the poster (MF-92).

## Player positions

A checked-in player may share their position during a running game (`POST /api/v1/positions`, up to 5 reports). The controller keeps the latest per player for that game only and deletes them when it ends; it sends a position only to those who may see it (ADR-P3-6): a player sees their own (and their squad's with the game parameter `squad_visible`), a squad leader their squad, a VIP their team, marshals and the GM everyone, the read token nobody. A mode's `visibility.granted` event (team, `see_team`, `duration_s`) lets a team see another for a while; the controller logs `visibility.expired` when the time is up. Positions never go on the radio or MQTT. A VIP's GPS reports are also handed, oldest first, to the running game's `field.lua` as the input `position.fix` (`player`, `team`, `role`, `lat`, `lon`, `acc`, `src`; decision P4R6): VIP / Payload extracts the VIP with them. Nothing else gets them: no event, no log, no `state.field`, no standby controller. On a multi-story field a report may say the player's level (`level`, 0-9, or `null` when the phone does not know it); a report without it keeps the level the player last gave in that game, and a player who never gave one has none (decision ML-5). The staff's ATAK devices see it in the remarks.

**Indoors, BLE beacons** (ADR-P3-6, decisions BLE-1 to BLE-9). The GM registers the iBeacons put up in a building (`GET|POST /api/v1/beacons`, `PUT|DELETE /api/v1/beacons/{major:minor}`, the console's *Indoor beacons* panel under the field plan): UUID, major and minor, the room, an optional zone, the level and, to show it on the map, where it is on that level's plan. A phone that shares its position reports the strongest registered beacon it hears as `{"source": "ble", "beacon_id": "major:minor"}` (every 3 to 30 s, 5 by default, `ble_interval_s` in each answer); the controller accepts only a beacon of the registry (400 otherwise) and stores the beacon's `room`, `zone`, `level` and place with the position, so the room is what `GET /api/v1/positions`, the stream and ATAK show: ATAK puts an indoor player at the beacon's place on its level's plan (`h-e`) with the room in the remarks. The registry is the GM's: staff read all of it, every other token only each beacon's `id` and `uuid`. Room-level, never metre-level.

**The Field Boxes are beacons too** (decisions BBC-1 to BBC-12, [protocol/box-beacon.md](../protocol/box-beacon.md), RFC 0001 Amendment 20). A box joined to a game advertises an iBeacon (the field's UUID derived from the join key, major 45253, minor its node id), and the controller registers each box the GM has placed on the field view **by itself** (`box_beacons.py`): room = the box's name or the room the GM gives (`PUT /api/v1/box-beacons/{node_id}`, with `enabled` to disable one), level, x and y = the box's place, so moving a box or changing its level moves its beacon. `GET /api/v1/beacons` lists the tags and the boxes together (staff: each box with `kind: "box"`, its node, name, room and `enabled`, and the field's switch as `box_beacons`; every other token: the `id` and `uuid` of each tag and each enabled box, so the phone's UUID filter list gains the box UUID and nothing else changes). A phone that hears a box reports `45253:<node>` like a tag and is located the same way (BLE-3, BLE-4, BLE-8). `PUT /api/v1/box-beacons` `{"enabled": false}` is the field's switch: the registry stops listing the boxes at once and the join of each new game carries key 19 = false, so its boxes do not advertise. **A standby serves the same registry** (decision BBC-20, RFC 0001 Amendment 21): the GM's choices live in the primary's store, and the only thing that travels from a primary to its standby is the standby's join, so the join carries them: key 19 (the field's switch, which the standby now reads) and key 21, `box_beacons`, the boxes the GM disabled and the rooms the GM gave in this game (`{"off": [node ids], "rooms": {node id: text}}`, at most 200 bytes). The standby stores them as its own settings when it joins (`box_beacons.apply_mirror`), so after a failover `GET /api/v1/beacons` and the join of the next box say what the primary's did. A choice made after the standby joined reaches it when the primary makes the standby's join again and the GM pastes it again (*Join* tab, or `POST /api/v1/controller/join`): a join of the game and key the standby already follows is a **refresh** (the box language and the beacon choices; nothing is reconfigured), no longer a conflict. **The boxes' places travel too** (decision BBC-25, RFC 0001 Amendment 22): key 22, `box_places`, is where the GM placed each box (node id, level, x, y; 7 bytes a box, at most 28, 20 boxes take 142 bytes), so a promoted standby lists every box at once, in place, without the GM placing them again (`box_beacons.mirror_places` / `apply_places`; a box moved on the primary reaches the standby with the join made again, and applying the places sends the stream's `position` message of every box whose place or level changed, at the first join and at every refresh, so a console open on the standby's plan moves the marker at once (BBC-30); more than fits is refused, not dropped). Tests: `tests/test_join.py` (a failover with the choices changed on the primary), the contract case "S7 failover: a standby takes the primary's box-beacon choices" (both controllers), `protocol/vectors/join.json` `box_beacons` and `box_places`.

Tests: `tests/test_box_beacons.py`, the contract case "box beacons" (both controllers), the console's browser test.

## What only staff may read

Some of a game's data is a secret until a team earns it: the code a Hacking Terminal reveals, a Bomb's team codes, the Codes modifier's codes. The schema marks it (`gm_only` on an event's data fields in `protocol/schema/events.yaml`, `gm_only: true` on a mode's parameters in its `mode.yaml`), and the controller (`visibility.py`, decision M5-1) gives it to staff only: the GM token and the marshal and gm player tokens of the game. Players' connections, the read token (scoreboards, a read-only console) and MQTT get the events and the game without those fields, on the stream, `GET /games`, `/games/{id}`, `/games/{id}/log` and the read token's `/presets`. The radio, the controller's own log and the sync to the site server (where events and parameters are staff-only too) keep them whole.

## Android props on Wi-Fi

An Android phone running a prop that joined with a join payload links to the controller over the field's Wi-Fi ([protocol/prop-link.md](../protocol/prop-link.md)): `WS /api/v1/prop`, an HMAC proof of the game key, then its HELLO, STATE and events as JSON, which the controller encodes with the radio's codecs and hands to the same FieldController as a box's packets. TIME beacons and commands reach the linked props too; without a modem, commands reach the Wi-Fi props and are reported as sent. The join payload for a box carries the CA's fingerprint and the https addresses (keys 13 and 14) when HTTPS is on; boxes skip them.

## ATAK / Cursor on Target

Off by default. With `[atak] enabled = true` the controller in charge of the live game puts the field on ATAK maps as Cursor on Target events (`atak.py`; ADR-P4-7 as amended, decisions P4R18 and M9-1 to M9-10). What is sent:

- **every box placed on the field image** (the console's *Campo / Field* tab) as a coloured spot marker (`b-m-p-s-m`, as in the TAK examples): the box's name, its owner in the remarks (then `active` while Progressive Domination has made it the active box, decision PD-MODE-16), the owner team's colour (`<color>`) and, for a team named after one of ATAK's team colours, that team (`<__group>`), its battery and, on a level with a field grid, its cell (`grid C4`, PKE-2: the same for a map feature at its pin and an indoor player); a VIP / Payload game's extraction zone, with its radius as the circular error. Every `interval_s` (30 s) and **at once** when a box is captured or neutralised, moves on the image, or the game or the georeference changes; `stale` is twice the interval. When the game ends (or the georeference is removed) every marker is dropped (stale before start, CoT's "drop track"). On a multi-story field each box is placed by its level's georeference and its remarks end with the level's name (`Atalaia: Red (red), 1.º andar`; a player's only when the phone gave its level); the point's height stays unknown (decisions ML-6, ML-7);
- **the field's map features** (decisions MF-11 to MF-13), while a game is live and only where their plan has a map position: a pin as a spot marker in its type's or team's colour, a circle as ATAK's drawn circle (`u-d-c-c`, its radius in `<shape><ellipse>`), an area as a closed drawn shape (`u-d-f`, its corners as `<link point>`); the name as the callsign, the type, team, who sees it, the level and the note in the remarks. Only those for everyone go to multicast; the staff devices (`staff_endpoints`) get them all, a team's and the organisers' included, since the feed is not per team; the remote relay (below) gets the pins and circles for everyone, a circle as a spot marker with its radius as the circular error, never an area. A feature deleted, moved off the map or no longer for everyone is dropped where it was sent;
- **over UDP** to `multicast` (`239.2.3.1:6969`, ATAK's mesh default; TTL 1, so it stays on the field's network; a unicast `host:port` works too), one event per datagram (TAK Protocol version 0);
- **player positions are never multicast**: anyone on the field Wi-Fi can read a multicast group, and positions are filtered per role (phase 3 constraint 9). Only with `players = true` do they go, and only to the staff ATAK devices in `staff_endpoints` (TCP, `"host:port"`, 4242 when no port is given; at most 8), which see every player as the GM and marshals do: the latest GPS fix of each player (`a-f-G-U-C`, `m-g`), by pseudonymous player id and never by name, with the team as `<__group>`. Staff endpoints also get the boxes and the zone.

**ATAK away from the field (the remote relay; Phase 4 follow-up, decisions FU5-1 to FU5-20).** Off by default. With `[atak] remote = true` (it needs `[atak] enabled` and the sync on, and a site server whose relay is on), the controller also opens the sync's WebSocket to the site server (`/api/v1/sync/stream`, as the remote GM does: the controller opens the connection, the site server never connects to it) and says so in its `hello`; once the site server answers that its relay takes them, the emitter pushes the same boxes and zone there (`cot` messages, each event in the shared form `sync_format.cot_event` checks on both sides: the emitter's elements with only its attributes, in its forms, decision FU5-17), and everything again whenever the socket is new. The site server relays them over TLS to the field's enrolled ATAK devices, each with a client certificate its admin or gm issued (server/README.md, "Remote ATAK"). **Player positions** go there only with `remote_players = true` as well (default `false`), and the site server sends them only to a certificate whose holder has the field's `gm` or `marshal` role and that was issued with positions (P4R18); never to any other. Remote ATAK alone sends no live view and takes no remote GM command (`[sync] remote_gm` stays off). `GET /api/v1/atak` shows `remote`, `remote_players`, `remote_relay` (whether the site server takes them now) and `remote_events`; `sync.remote_gm.stream.atak` in `GET /api/v1/controller` the stream's side.

**Georeference.** Field Boxes have no GPS, so their places are fractions of the field image. In the *Campo / Field* tab, under the image, the GM gives two opposite corners of the image (top left and bottom right; the image must have north at the top) their latitude and longitude, pasted from a map app as `latitude, longitude` (`PUT /api/v1/field/georef`). The console shows the four corners back and a pin on the image per point. Through the API, 3-8 control points give a rotated or skewed image (a least-squares affine fit); points on one line, too close, mirrored or not fitting one flat image are refused. The points are kept in the store's settings (no schema change) and a new image clears them. On a multi-story field every level shares level 0's points (its plans drawn to the same scale and frame) unless the GM gives a level its own in that level's tab (`/api/v1/field/levels/{n}/georef`; decision ML-6).

```toml
[atak]
enabled = false
multicast = "239.2.3.1:6969"   # "" for no UDP
interval_s = 30.0
staff_endpoints = []           # ["10.42.0.5:4242"]; ATALAIA_ATAK_STAFF_ENDPOINTS separates them with commas
players = false
remote = false                 # the site server's relay for staff away from the field (needs [sync])
remote_players = false         # positions there too, for certificates allowed them only
```

The XML is built with ElementTree, so names from users are escaped; characters XML does not allow are dropped and texts are capped. The CoT rules the tests check (`protocol/vectors/cot.json`) are copied from the CoT base-event schema, MITRE's CoT types, the TAK detail schemas and examples and the TAK protocol description, each cited, and two TAK examples are rebuilt by the emitter as known answers. Tested in software (a loopback receiver for UDP, multicast and TCP; the remote relay through the real site server to a TLS client with a certificate from the site server's enrolment, `server/tests/test_atak_e2e.py`); **not yet with a real ATAK device** (HW3) or a real deployment.

## Scenarios

A GM writes a custom scenario as a YAML manifest (ADR-P4-6 as amended, decisions P4R7, P4R8 and M7-1 to M7-9); the compiler turns it into a scenario package, `mode.yaml` and `field.lua` (`kind: scenario`), that runs on the controller over the built-in objectives package (`org.club.foxhound+org.atalaia.objectives`, [modes/README.md](../modes/README.md#custom-scenarios-and-the-objectives-package-phase-4)). Nothing changes on the boxes.

The validator and the compiler are written once, in Lua inside the C core ([`core/scenario/`](../core/scenario/README.md), decision PE24-109), and the Pi and the phone both call it: the Pi through ctypes (`atalaia_controller/scenarios/`), the phone through `dart:ffi` (`app/lib/controller/scenarios/`). Each reads the manifest's text itself, the Pi with PyYAML, the phone with its PyYAML-compatible reader (YAML 1.1: `yes` is true, `0815` a text), and hands the core what it read as the manifest's data tree (every value typed, a YAML alias kept as one object). A rule is changed in one place; the shared vectors check both readers and the one compiler. Every call runs in a Lua state of its own with a memory and an instruction limit; a manifest past them is a problem (`too_complex`), not a crash.

On the field, the GM console's *Scenarios* tab is the editor (plan phase 8, decisions M8-1 to M8-9): the controller checks the manifest as it is typed (`POST /api/v1/scenarios/check`: every problem with its place, then the compiled `field.lua`'s load in the core) and installs it (`POST /api/v1/scenarios`), keeping the manifest next to the package so the GM can open it again (`GET /api/v1/scenarios/{id}`). A game of it is the scenario with the objectives package (*Game* tab: pick the scenario, tick *Objectives*). In the *Join* tab the GM gives each box one of the manifest's `nodes` names; the box's role is that node's, and the scenario's `field.nodes()` finds the box by that name (a box's own name otherwise). A standby controller needs the scenario too: with the site server's sync on, every controller of the field installs the field's scenario library from it (below, decision S20-1); without it, install the same manifest there before its join (it says which part it lacks; decision M8-3). A package compiled elsewhere can still be uploaded as files (`POST /api/v1/modes`). The tab also shows the manifest as blocks (phase 5 plan phase 7, decisions P5F-1 to P5F-12): the blocks write the same YAML, so everything above is unchanged.

Who sees which objective (P4R24, M8-4, SQ-1 to SQ-8): staff see everything (the GM, marshals and `gm` players; spectators and the read token see only `public` objectives); players see an objective by its `visibility` (`public`: everyone; `team`, `squad`: the assignee's; `hidden`: the assignee's, once revealed), on the stream, the log and the game, which carries the scenario's names and the objectives each player may know (M8-5); everyone else, MQTT and the read token's scoreboard included for a team's objective, learns that a team completed, failed or was shown an objective, not which one.

**Per-squad chains and who of a squad is told (SQ-1 to SQ-8).** An objective assigned to a squad (`assignee: { team, squad }`) reaches that squad alone, and with `reveal: active` only once it is active: nothing about a later one (its id, names, points, events) is sent to a player's phone, in the game, the log or the stream, until the one before it is completed; a completed one stays in the list, done. The scenario's `disclosure` (`members` or `leader`) says who of the squad is told; the GM overrides it for one game when creating it (`objective_disclosure` in `POST /api/v1/games`) or while it runs (`PUT /api/v1/games/{id}/objective-disclosure`, `{"disclosure": "members" | "leader" | null}`, null going back to the scenario's own; the apps get the game again at once). With `leader`, a squad leader (check-in role `squad_leader`) gets the objectives of their own squad and of their whole team; a member gets the `scenario.objective.revealed` event without the objective, with `leader_only: true`, and the app says "your squad leader has new orders"; a player in no squad has no leader to go through and gets the team's objectives whole. The objective's destination and codes are never in the payload (only in `field.lua`); what the leader tells the squad is the leader's to say. A leader who is absent (dead, off the network, not checked in) leaves the squad without the objective: the GM switches the game to `members` (decision SQ-6). Scenario objectives are not exported to ATAK (only the map features are, with their own visibility, MF-12), so ATAK shows nothing secret.

```sh
cd controller
python3 -m atalaia_controller.scenarios validate tests/scenarios/multi_objective.yaml  # the manifest's problems
python3 -m atalaia_controller.scenarios check tests/scenarios/multi_objective.yaml     # + compile, load the Lua in the core
python3 -m atalaia_controller.scenarios compile tests/scenarios/foxhound.yaml -o /tmp/foxhound  # write the package
python3 -m atalaia_controller scenario check tests/scenarios/foxhound.yaml             # the same, from the main entry point
```

Each problem says where and why (`objectives[2].depends_on[0]: error: 'nowhere' is not an objective id (unknown_reference)`); `--json` prints them for programs. Every command needs the core library (`ATALAIA_CORE_LIB`, or a build folder of the repository), which holds the validator and the compiler; `--no-core` only skips loading the generated `field.lua` in it. Exit status 0 (warnings are fine), 1 (errors), 2 (not a manifest, or no core). From Python: `load(text)`, `validate(manifest)`, `compile_scenario(manifest)` and `check_package(core, package)` (the first three take `core=`, else load the default core once). A controller without the core library reads a manifest but neither checks nor installs it (`checked_in_core` is false, as on the site server).

The manifest ([tests/scenarios/foxhound.yaml](tests/scenarios/foxhound.yaml) and [multi_objective.yaml](tests/scenarios/multi_objective.yaml) are examples):

| Key | What it is |
| --- | --- |
| `id`, `version`, `name`, `description`, `author` | The package's id (`org.club.name`, at most 40 bytes so the game's id fits a join; not `org.atalaia.`), its version, its texts in English |
| `i18n.pt`, `i18n.de`, `i18n.zh-tw` | `name`, `description` and `params` labels in Portuguese, German and Traditional Chinese (English is the text itself; SCL-1; a manifest with only `i18n.pt` is unchanged); a box whose `lang` is one of them shows each objective's name from there, else the English one |
| `lang` | The boxes' screens: `pt` (the default), `en`, `de` or `zh-tw` (PKB-9; an older manifest with `pt` or `en` is unchanged); each box shows the objective's name in that language |
| `teams`, `squads` | The game's team names the scenario uses (default `[red, blue]`) and its squads per team (numbers 1 to `squads`, 0: none) |
| `reveal`, `disclosure` | Per-squad chains (decisions SQ-1 to SQ-8). `reveal: all` (the default) shows an objective that depends on others from the start unless it is `hidden`; `reveal: active` makes every objective with `depends_on` and no `visibility` of its own `hidden`, so a squad knows only its active objective and the ones it has done, and the next is revealed when the one before it is completed. `disclosure: members` (the default) tells every member of the assignee squad or team; `leader` tells the squad leaders only, the other members hear that their leader has new orders |
| `params` | Whole-number parameters for the GM (`{ type: int, min, max, default, label }`), for points: `effect.points: { param: name }` |
| `nodes` | The names the GM gives the boxes (`box-a: { role: objective }`, `{ role: bomb_site }`; on a multi-story field optionally the box's level, `{ role: objective, level: 2 }`, 0-9, decision ML-8) and the players an objective is about (`vip: { player: true, role: vip }`, `role` being the player's check-in role) |
| `objectives` | A list; each has `id` (`[a-z][a-z0-9_]`, at most 24), `type`, `name` (one line; `description`, `i18n.pt`, `i18n.de`, `i18n.zh-tw`), `target`, `assignee` (`team`, `squad`), `params`, `visibility` (`public`, `team`, `squad`, `hidden`), `depends_on`, `time_window` (`start_min`, `end_min`), `effect` (`points`, `win`, `reveal`) |

| Type | Target | Params | Completed | Failed |
| --- | --- | --- | --- | --- |
| `capture_and_hold` | an `objective` box | `hold_ms` (to take it), `duration_s` (to keep it; 0, the default: at the capture) | the team (only the assignee's, if one) has held it for `duration_s` | -- |
| `defend` | an `objective` box | `duration_s` (required), `hold_ms`; an assignee team is required | the defenders still hold it `duration_s` after it opens (they start holding it) | another team captures it (`captured`) |
| `enter_code` | an `objective` box with a keypad | `code` (1-8 digits, in quotes) | the code is typed (credited to the assignee, else the last team to press) | -- |
| `scan_tags` | an `objective` box with NFC | `tag_count` (required), `any` (any cards, not only players' tags) | a team (the assignee, if one) scanned `tag_count` different tags | -- |
| `destroy` | a `bomb_site` box | `hold_ms`, `defuse_ms`, `fuse_s` | the bomb explodes | it is defused (`defused`) |
| `escort` | a player node (`player: true`) | `destination` (`{ lat, lon, radius_m }` or `{ points: [[lat, lon], ...] }`, 3-32 corners), `max_acc_m` | a GPS fix of a player with that role (of the assignee team) inside, no less precise than `max_acc_m` (default: the radius; 25 m for a polygon) | -- |
| `survive` | none | `minimum_lives` (required); an assignee team and `time_window.end_min` are required | the team still has `minimum_lives` of Respawn's lives at the window's end (compose the game with `org.atalaia.respawn`, per-team lives) | fewer lives left, or the team eliminated (`lives`) |

An objective opens when it is revealed (at the start, unless `hidden`; a hidden one when it could open, or when another's `effect.reveal` names it), its time window has started and everything in `depends_on` is completed; a box shows it inactive until then. One still open at `end_min` fails (`time`); a failed one fails what depends on it (`blocked`); an objective never revealed sends no event. Completing one scores its points for the team, reveals what `effect.reveal` lists and, with `effect.win`, ends the game won by that team. An objective of a team the game does not have is off. The validator checks unique ids, references and the dependency graph (a topological sort; every objective on a cycle is named), each type's target and parameters, teams and squads, time windows, destinations (a radius under 10 m is a warning; a polygon whose edges cross is an error), and sizes: every setup command fits a box's 127-byte command and every scenario event a LoRa packet. The rules are written as shared vectors, [`protocol/vectors/scenario.json`](../protocol/vectors/scenario.json).

The generated `field.lua` is a data table (`SCENARIO`) followed by the scenario runtime, [`core/scenario/runtime.lua`](../core/scenario/runtime.lua), the same code for every scenario (GPL-3.0-or-later, like the modes, since it is copied into every package; decision M7-2). No text from the manifest is ever Lua code: every value is written as a Lua literal, a quoted string with its quotes, backslashes and control characters escaped, so a name such as `"]] os.exit() --[[` is only ever a name. `mode.yaml` carries the names, teams, squads, nodes and each objective's id, type, names, assignee, visibility, dependencies and points (for the routing and the player view); a code and a destination are only in `field.lua`.

## GM console and scoreboard

The controller serves the GM console at `http://<controller>:8080/console/` (`/` redirects there) and a read-only scoreboard page at `/scoreboard#token=<read token>`: plain files from [`console/src/`](console/src/), no build step, with a strict Content-Security-Policy. The console asks for the GM or the read token; European Portuguese by default, English too. See [console/README.md](console/README.md). An example scoreboard that follows the game over MQTT is in [`examples/scoreboard/`](../examples/scoreboard/).

## MQTT

```
field/v1/{game}/events/{type}          every game event, JSON
field/v1/{game}/score                  totals per team (retained)
field/v1/{game}/nodes/{node}/state     owner, phase, game time, counters (retained)
field/v1/{game}/nodes/{node}/health    battery, RSSI, SNR, link, battery low, last seen (retained)
field/v1/{game}/cmd/{node}             {"cmd": "message", "params": {"text": "..."}} (GM only)
field/v1/{game}/cmd/all                the same, to every node
```

Who may publish commands is Mosquitto's job: [`deploy/mosquitto.conf`](deploy/mosquitto.conf) and [`deploy/atalaia.acl`](deploy/atalaia.acl) give the controller, a GM user and a read-only user. Retained topics are published again after the broker restarts; events published while the broker is down are not queued (they are in the log).
