Roadmap

Six phases, each closed by a real field test: its gate. The software is ahead of the hardware: phases 1 to 3 are done in software (real boards play whole games on the bench, and the iOS app has passed its checklist on an iPhone); phases 4 and 5 are built in software. The gates wait for built boxes, field tests, a real server and the project's registry key.

How the parts talk to each other: the architecture diagrams →

  1. Done

    0 · Foundations

    Shared core, Lua sandbox, Skirmesh-RF codec and browser simulator. Gate met.

    What is done

    • Shared core, the game logic every platform runs.
    • Lua sandbox, where the game modes' scripts run.
    • Skirmesh-RF codec, the radio messages' format.
    • Browser simulator, which runs Domination and Bomb.

    Gate: the simulator runs Domination and Bomb from Lua scripts. Met.

  2. Software done

    1 · Single box

    Field Box firmware and a build manual; a real board plays whole games on the bench. Waiting for the first built box.

    What is done

    • ESP32 firmware for the Field Box, with presets on the device, running in an emulator.
    • The box's small screen shows the hold bar, points and held time, in four languages.
    • A build manual with wiring diagrams.
    • The first board (Heltec V4.3, 20 October 2026) on the bench: it boots, powers the radio, reads its buttons and plays whole games, Bomb included (arming, defusing, the timer running out), on its own small screen.
    • The game-timer bar: while a timed game runs, a strip along the bottom of the small screen shows how much of it is left, and the OLED shows a clock. In software, not yet seen on a real panel.
    • The setup a scenario sends to the boxes is sent again until each box confirms it, and the box now sends that confirmation. In software and host tests only, not on a real board.
    • Change field in the box's admin menu moves an adopted box to another field, by its code. Host tests only, not on a real board.
    • The field's logo on the box's big screen. In software, not yet seen on a real panel.

    Next, and what it waits for

    • A built box that runs a 2-hour club game with no restarts.
    • Seeing the timer bar on a real panel.
    • Trying the setup re-send, Change field and the logo on a real board.

    Gate: one box runs a 2-hour club game with no restarts. Open until a built box does.

  3. Software done

    2 · Field network

    Skirmesh-RF over LoRa, field controller, API, GM console and a mode pack, tested in software; on the bench, real boards play whole games with the controller over the radio. Waiting for 5 built boxes on a field.

    What is done

    • The encrypted Skirmesh-RF radio protocol, and the USB radio modem.
    • The field controller with its API.
    • The organisers' console, with a scoreboard.
    • Joining a game with an NFC card or a QR code.
    • The boxes' firmware talking to the controller.
    • A mode pack: Hold-All Domination (score only while holding every box), Last Stand (a countdown to defeat while holding one of three), per-team arming codes on Bomb, and the Codes modifier (keypad codes that grant points, hints or unlocks, with the GM told who used them).
    • All of it tested in the simulator, the emulator and on a computer, whole games included; on the bench, real boards play whole games with the controller over the radio: invites, captures, pairing by code, updates over the air, a missing mode fetched.
    • Boxes listen before they talk: a box checks the channel is free before it sends, so fewer messages collide. In the simulator, a 20-box field hears 89 % of updates instead of 65 %.
    • The GM can set or free a box's owner in Domination too, as in the other modes.
    • The controller can send its own radio frames one at a time, spaced out. Built, and off until the field test decides.
    • The Pi controller fails a firmware update at once when the radio refuses the offer.
    • A box that was set up can go back into Wi-Fi setup, from a menu entry behind the admin PIN or a command on the USB console. The setup page is in English, Portuguese, German and Traditional Chinese, and phones open it by themselves.
    • The console's Game tab shows a QR code of the scoreboard for players.
    • Scenarios can be in German and Traditional Chinese; their objective names stay in Portuguese and English for now.

    Next, and what it waits for

    • The radio boards, and 5 built boxes for the field test.
    • A 20-box field test with listen-before-talk on and off.
    • Whether to turn the controller's pacing on, decided from the 20-box field test.

    Gate: 5 boxes on a CQB site and an outdoor field, zero lost captures. Open.

  4. Software done

    3 · Android and players

    Android props, the I/O pod, the player app and the modes that need phones: done in software, iOS included (checked on an iPhone). The field test waits for real phones and pods.

    What is done

    • The app for players, marshals and the GM, in Portuguese and English, on Android and iOS (the iOS version has passed its checklist on an iPhone).
    • An Android phone acts as a box, with any mode and the mode's own screens, and joins a game by QR code, NFC card or text.
    • The phone as the field controller, done in software and waiting for a real phone: it runs the game and the field's services on its own.
    • The I/O pod: firmware that lends a phone a Heltec board's buttons, keypad, lights, siren, NFC reader and LoRa radio.
    • Modes that use phones and tags: Kill Confirmed, Respawn and Lives, Player Check-in, the Medic Kit and Money Factory.
    Everything else that is done, by topic

    Modes and screens

    • Kill Confirmed, Respawn and Lives and Player Check-in read players' signed NFC tags.
    • The Medic Kit: a hit player scans their tag and holds a button to be healed, with a limited number of heals.
    • Money Factory: factories make money while a team holds them; players collect it with their tag and bank it at another box, and the controller keeps what each one carries.
    • Mode screens described in YAML, drawn alike by the Field Box and the app.

    Players and marshals

    • Players check in at the field by scanning a printed poster (no account, no internet), say which replicas they will use and see whether they have passed the chrono.
    • Chrono check-in: energy, limits per class, spot checks, readings signed by the marshal. Marshals work from a "replicas to chrono" list, and their signed readings mark each replica passed or refused; they also have the replica registry and players' tags.
    • Players can share their position during a game, and the controller decides who sees it.
    • A field or club that runs its own controller can show its logo, wallpaper and colour in the app, on the scoreboard and on the poster, and give its teams names and crests.
    • The GM console tells when the check-in poster changed after it was printed.
    • The marshal and chrono screens say what the app really does, and the limit lists are translated.
    • The app keeps more of its secrets sealed with the Android Keystore: the site key, players' secrets and the site login.
    • Players' NFC tags are signed by the field controller and written from the GM console, the phone controller or the marshal's app. Marshals no longer hold the field key for them.
    • Replica labels: the app shows, shares or prints each replica's QR sticker, and the GM console prints them for everyone checked in. The marshal's queue scans them.
    • Indoor positions: the GM places BLE beacons on the plan, and an Android phone that hears one reports its room instead of GPS. In software and fakes, not tried with real beacons. iOS stays on GPS.
    • The app follows a game from the scoreboard's QR code, also when the phone controller serves HTTPS with its own field CA. In software, not tried on a real phone.
    • A player says which floor they are on and sees the field plan with the positions they may see.
    • Game history in the app: the games a player took part in, newest first.
    • Login with Google, Microsoft, Apple or a passkey in the app, with an account screen. Android only; not tried on a real phone or against the real providers.
    • The player's field plan can show the field's grid and the player's own cell.
    • A marshal can bind an NFC sticker to a replica when registering it.

    Props and the I/O pod

    • An Android prop takes part in the controller's game over the field's Wi-Fi, or over its radio through an I/O pod.
    • The pod's firmware lends the phone a Heltec board's team buttons, keypad, lights, siren, NFC reader, enclosure switch and LoRa radio, over USB or Bluetooth.
    • The app reconnects to a lost I/O pod by itself. Not tried with a real pod.
    • Android props fetch signed mode packages from their controller, as boxes do. In software.

    The phone as the field controller

    • The game engine, with a mode's field.lua on the shared core, an MQTT broker and a position filter; the REST API, the live stream and the MQTT topics; games kept across a restart; join payloads.
    • Android props on its Wi-Fi, an I/O pod as its radio, field check-in with player tokens, the "replicas to chrono" list and players' positions. Checked by the same contract cases as the Pi controller, and run with the pod's and the Field Box's own code on a computer.
    • Its screen: the role on the app's home screen, kept running with the screen off, the GM console served from the app, and HTTPS with a field CA made on the phone.
    • The field plan (a plan per level, its map position, map features with the field boundary, the field loaded from a map, so the out-of-bounds warning works there too) and the radio channel, with a search for a quiet channel through the I/O pod.
    • The boxes over the radio: sealed invites into the next game; the end of a game told to its boxes even after the phone restarted without the game's key; new boxes adopted by the code they show or by a field card the phone writes by NFC; firmware updates between games, through the I/O pod or the Pi's USB radio modem, and the phone says why when its radio cannot carry them.
    • Presets, mode uploads and signed mode packages sent to the boxes that lack them, scenarios compiled on the phone, role packages in a game, team names and crests.
    • What the Pi controller does, too: failover (a phone and a Pi can each be the other's standby), the site server sync (games, logs and scores sent when the internet is there; rosters, branding and the scenario library from it), the remote GM and the ATAK feed.
    • The GM console fits a phone: its check-in and marshal tables stack, with no sideways scrolling.

    iOS

    • The project is in the repository, CI builds it on a Mac, and it has run on an iPhone.
    • On 2026-10-26 its on-device checklist passed on an iPhone: 12 automated checks and, by hand, QR scanning with the camera, check-in with the field's poster over HTTPS, position sharing while the app is on the screen, the out-of-bounds warning and its vibration, and atalaia:// links.

    Next, and what it waits for

    • The field test with real phones and pods (plan phase G) waits for the hardware. So far the app has run on Android emulators and on an iPhone against the bench's controller, and the pod firmware only as its own code on a computer.
    • The phone as the field controller waits for a real phone.
    • On iOS, NFC needs a paid Apple account; the prop and the phone as the field controller stay Android only.
    • Indoor beacons on iOS need a Swift plugin written on a Mac.
    • Trying the scoreboard QR code, the floor picker, the game history and the pod reconnect on a real phone and pod.
    • Trying the app's login on a real phone and against the real providers.

    Gate: one game mixes ESP32 and Android props without issues.

  5. Software done

    4 · Site server and advanced play

    Site server, game scheduling and registration, custom scenarios, advanced modes, ATAK. Every software step is built; a real server, a legal review and the hardware tests are next.

    What is done

    • Advanced modes: Master and Satellites, the Hacking Terminal, VIP / Payload, and the logic of Target Windows.
    • Custom scenarios: their runtime on the field controller, a compiler for YAML scenarios, an editor in the GM console and the objectives in the app.
    • The ATAK feed: boxes and zones on ATAK maps, on the field and, through the site server, for staff away from it.
    • The site server: accounts with two-factor codes, personal data rights, controller sync, the chrono registry, game history and the scenario library.
    • Game scheduling and registration, with public field pages, calendar feeds and club profiles.
    • Hosted mode: many fields on one server, each kept apart, with its deployment.
    Everything else that is done, by topic

    Modes

    • Master and Satellites: satellites held with the master raise its points; the master changing hands frees them.
    • The Hacking Terminal: a puzzle on the keypad that reveals a code or captures the terminal.
    • VIP / Payload: a team escorts its VIP, or a phone with GPS, to an extraction zone; checkpoint boxes score while held; positions stay on the field controller and the phone.
    • The rules of Target Windows: a hit while the target shows a team's colour scores for that team. The target addon is not built yet.
    • Geo utilities in the core: distances and zones for every script, identical on every platform.

    Custom scenarios

    • The runtime: a scenario runs on the field controller and tells the boxes of the built-in objectives package what to be (a point to capture, a code, tags or cards to scan, a bomb site); they report, the scenario scores.
    • The compiler: a YAML scenario of seven objective types, with dependencies, reveals and time windows, checked with every problem located and explained, and compiled from the command line.
    • In the GM console: an editor that lists every problem as the organiser types and installs the scenario; the boxes get the scenario's names when they join.
    • In the app: players see the objectives meant for them, with their names and how each stands, a hidden one only once it is revealed; each squad can have its own chain, one objective at a time, told to the whole squad or to the squad leader alone.

    ATAK and the field map

    • The ATAK feed: boxes and zones on ATAK maps over the field Wi-Fi, in their owners' colours, placed by giving two corners of the field image their map position.
    • The GM marks safe zones, each team's respawn and HQ, the car park, first aid and objectives on the field's plan, as a pin, a circle or an area, each shown to everyone, to one team or only to the organisers, in the console and on ATAK.
    • The field can be loaded from a map: the GM finds it from where they stand or by a place's name and traces its outline on OpenStreetMap, and the browser draws the field image from OpenStreetMap's data over the country's open aerial imagery (mainland Portugal, Spain, France with its overseas territories, the Netherlands, Belgium, Luxembourg, Switzerland, Liechtenstein, eleven German states, Poland and Czechia). The outline becomes the field boundary, the outside dimmed.
    • Players' phones warn them with a banner and a vibration when they leave the boundary, from their own GPS, sending nothing.
    • Player positions never go to everyone, only to staff devices when the field turns it on. Staff away from the field get the same through the site server, over an encrypted connection with a certificate per device that the field issues and can revoke at once, positions only to a GM or a marshal.
    • Multi-storey fields in the console: a floor plan per level and each box on its level.
    • Not yet tried with a real ATAK phone, nor at a real field.
    • A box that Progressive Domination has made the active one says so on ATAK.
    • The field map page works on the phone as the field controller too.
    • ATAK shows an indoor player at their beacon's place, with the room in the remarks.
    • The grid in ATAK, and a printable grid map.
    • The remote GM sees players' positions when they share them.

    Site server, accounts and data

    • Its skeleton: database, migrations and a health check, in its own container.
    • Accounts: passwords, two-factor codes required for organisers and marshals, sessions and roles per field.
    • Personal data rights: access, export, correction, erasure, consent records and a daily retention purge.
    • Controller sync: field controllers push their games, logs and scores, offline first and safe to replay. Not yet over a real 4G link.
    • The chrono registry: signed readings verified and kept as signed, public keys only, sharing between fields with consent. Not yet with a real chronograph.
    • reset-totp: the operator resets the two-factor code of an account that lost its authenticator.
    • Field controllers pull other fields' chrono records for the players on their roster, only with each player's consent. They keep them apart from their own readings and never judge them.
    • Controllers take the field's settings and branding from the site server, and a change reaches the Pi and the phone controller at once. In software.
    • Login with Google, Microsoft or Apple, and with passkeys. Passwords are optional; staff still need a second factor. Tested on a computer, not against the real login providers.
    • A staff account page where each person manages their own logins: passkeys, linked accounts, password and two-factor code.
    • Scenario, preset and schedule changes reach the controllers at once.

    Games, clubs and staff pages

    • Game scheduling, with a public page per field and open iCalendar and JSON feeds of its games (no personal data on them).
    • Registration for those games, with pre-declared replicas and a check-in ticket: the field controller pulls the list and reports who came. Registering from the app; importing a registration list (CSV or JSON) exported from another platform.
    • Club profiles: name, colour, logo and crest, members, a public page off by default with a report button and moderation. A field's branding and saved teams sync to its controllers, so a club's crest reaches every field that saved its team.
    • Game history: each game's score timeline and event log; players and spectators see a live game a minute behind, without secrets or player ids. A public scoreboard per field (off by default).
    • The field's scenario library with its game presets, checked as the field controller checks them and installed by every controller of the field, a standby included.
    • Web pages for the field's staff, in Portuguese and English and on a phone: login with the two-factor code, game history, the scenario library (every problem shown before saving, revisions and presets), device health, and the remote GM's live view and commands. Tested in a headless browser, not on a real server.
    • Controllers drop a scenario or preset the site archived or deleted, unless a game still uses it.
    • Staff pages for the schedule: list, create, edit, publish and cancel games, with times in the field's time zone.
    • Staff pages for registrations: who registered, changing a name, team or federation number, withdrawing a registration, and the CSV export and import.
    • A printable game-day roster page, with when a controller last pulled it.
    • Staff actions on a registration: paid or unpaid (the server takes no payment), no-show, move to another game, restore, edit the replicas. Tested in a headless browser, not on a real server.
    • Staff pages for roles, sync keys, branding, clubs, platform links, firmware and administration.
    • The remote GM page updates live, with no reload.
    • Association membership is checked at registration and at check-in: APDs for fields in Portugal, any association or federation elsewhere.
    • A staff page for the field's settings: the public page, the check-in rules, membership, chrono sharing and the country.
    • Chrono records show by how much a replica was over the limit, and flag repeat offenders.
    • A staff page for the field's data export and its use of the quotas.
    • Score timelines in game time.
    • A club's page lists the fields it plays at.
    • The controller imports a registration CSV on its own, with no site server needed.
    • The console warns when a name has letters the boxes cannot draw.

    Boxes and the field

    • Device health: each box's battery, link and firmware from what the controllers send; the field controller reports a box that goes silent or comes back and a low battery, which a box with a battery gauge also reports itself. Not yet on real boards.
    • A firmware catalogue that lists only releases signed with a trusted key, and over-the-air updates for the Field Box: the GM uploads a signed release to the field controller and updates the boxes between games, never during one; each box downloads it over the field Wi-Fi, checks the signature with keys built into its firmware, installs it in its spare slot and goes back to the old firmware if the new one does not start. In software, not yet on a real board.
    • Adopting boxes to the field with an NFC field card, the controller's USB cable or the 6-digit code the box shows, paired over the radio. In software, not yet on a real board.
    • Inviting boxes into the next game over the radio, with no card or QR code (the join travels encrypted under a key derived from the field join key), and a start that waits for every role to have a box, unless the GM chooses "Start anyway". Tested on two bench boards with the field controller.
    • Boxes heard in every new game (the radio's nonce counter is now per game, a fix found on the bench) and box screens that follow the game (Ready, Waiting, Neutral) in the field's language, English or Portuguese. Tested on two bench boards.
    • A controller restarted mid-game takes the game up again; one that lost the game's key still tells its boxes over the field radio that the game is over; wrong admin PINs wait longer and longer, counted across restarts, with no default PIN on a real box. In software, not yet on the bench boards.
    • The remote GM: an organiser with the GM role, logged in with a two-factor code, sees the live game and starts, pauses, resumes or ends it, or sends a message or a mode command, over a connection the field controller opens itself, only when the field turns it on, with every command logged on both sides.
    • The console's Controller tab lists the remote GM's state and every command it got.

    Deployment and hosted mode

    • The deployment: HTTPS through Caddy with an automatic certificate, a setup script that makes every secret, encrypted daily backups and a restore into a fresh database. Tested in Docker on a computer, not on a real server with a real domain.
    • Hosted mode: one server for many fields, each in a database schema of its own at its own address, with row-level security underneath so that no field ever sees another's data, and the operator's commands to export a field's data or delete it. Tested against PostgreSQL in Docker.
    • Its deployment: a setup script that makes the hub's database roles, each field at its own address with a certificate that only an active field's name can get, and encrypted backups restored with every field kept apart. Tested in Docker, not on a real hosted server with a real domain.
    • Hosted mode: a quota for each field, a data export a field's administrator can download, and a deleted field's open connections close at once.
    • Hosted mode: a storage quota, and custom domains per field.

    Next, and what it waits for

    • A real server with its domain.
    • A legal review of the templates before hosted mode goes live. It is not offered before.
    • The tests on hardware: real boards, a real ATAK phone, a real 4G link, a real chronograph.
    • The target addon, which the Target Windows rules wait for.
    • Testing the logins with the real Google, Microsoft and Apple.
    • jogarairsoft.pt: the maintainer wrote to them on 28 October 2026 proposing an integration (their events, teams and APDs to us; our games feed, field profiles, public clubs and results to them). Waiting for their answer; nothing is promised.

    Gate: a weekend milsim runs on Atalaia end to end.

  6. Software done

    5 · Community

    Visual mode editor, signed mode packages, the mode registry as a template, German and Traditional Chinese, build guides. Every software step is built.

    What is done

    • The visual mode editor: a page of the simulator where a mode is put together from blocks (what happens when a team holds the button, timers, points, screens and sounds, zones on the map, GM commands, several roles, the settings a GM can change and the field controller's logic across boxes). It writes the mode's Lua scripts and manifest as you go, in Portuguese and English, works offline, and a button tries the mode in the simulator at once. Its three examples pass the same tests as the hand-written modes.
    • Signed mode packages: one archive, signed like a firmware release. The editor makes the package itself and shows what the mode key will sign and the command that signs it; signing stays on the author's own computer, offline.
    • The field controller installs signed modes only with its own trusted keys, and shows who signed each one and whether the project reviewed it.
    • A battery of sandbox-escape attempts runs on every change; it closed two ways for a script to run past its time limit.
    • Send missing modes in the GM console: a box that lacks a game's mode fetches the signed package from the field controller over the field Wi-Fi, only between games, while the game waits for it; it checks the package with keys built into its firmware and keeps it. Tested on a computer, not on a real box.
    • Scenarios built from blocks in the GM console: the boxes, the objectives and who sees them, when they open, what completes them and what they give, by mouse, touch or keyboard, even on a phone. The field controller checks and installs them as if they were written by hand.
    • The mode registry, ready as a template: a pull request with a signed mode is checked automatically (its signature, that its source is what was signed, its licence, its tests in the simulator), and a mode the project has reviewed gets the verified badge, the project's own signature, which is what lets it reach the boxes. How to submit a mode, the review checklist, keys and moderation are written down.
    • German and Traditional Chinese (as written in Taiwan) on this page, the GM console, the mode editor, the app, the Field Box's screens, the built-in modes and the site server's pages: AI drafts, not yet reviewed by players who speak them.
    • The registry's repository exists (created 2026-10-26), and its page lists the modes, with no modes in it yet.
    • Build guides for the Satellite, the I/O pod and the target addon, as text. No box has been built from them yet.
    • User manuals for players, game masters, marshals and Field Box operators, in English and Portuguese.
    • Build manuals with a pin table for each board, a firmware guide (download a release or build it) and a controller setup guide, in English and Portuguese.
    • The simulator's web view has every input a mode uses: tags, keypad, hits and GM commands, with an event-log download.
    • The GM console's scenario blocks have a language list with all four languages.
    • The project's mode keys: an offline root key and a key the registry uses to sign the verified badge. Boxes, the app and the controllers trust both by default.

    Next, and what it waits for

    • The review of the German and the Chinese: if you play in German or in Chinese, help us review them. Translations into other languages start at docs/translations.
    • The hardware: the carrier PCB (a ready-made circuit board that makes builds easier) after the first built boxes, build photos, community content from a field.

    Ongoing after the first release.
