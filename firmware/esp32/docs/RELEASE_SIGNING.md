# Signing firmware releases

A Field Box installs a firmware update only if a **release key** built into its own firmware signed it (Ed25519 over the release's manifest: [protocol/firmware-update.md](../../../protocol/firmware-update.md)). Whoever holds a release key's private half can put firmware on every box that trusts it, so the key is kept like one: offline, encrypted, backed up, never in the repository, never on a field controller or a site server, and never on a CI runner, with one exception: the project's CI release key below. The tool is `tools/firmware_release.py` (it needs Python's `cryptography` package; the dev container has it).

Firmware up to v0.6.1 trusts only root and CI; v0.7.0 (the *transition release*, 2026-11-03) trusts root, CI and next CI; the firmware after it trusts root and next CI only. So a box on v0.7.0 takes the later releases over the air, and a box on v0.6.1 or older must install v0.7.0 first.

**What CI signs.** On a tag (release-please's, started by `.github/workflows/release-please.yml` with `gh workflow run release.yml --ref vX.Y.Z` because a tag made with the workflow token starts no workflow; or one pushed by hand), the workflow builds the Field Box, USB modem and I/O pod images (the project's keys as defaults, no bench options), and signs the **Field Box** image's manifest with the CI key `a4f6002b0122b131` (the variable `ATALAIA_RELEASE_SIGNING_KEY` may be unset or `next`, both meaning that key; any other value fails the release; `tools/firmware_release.py sign`, the key written to the runner's temporary folder only and deleted; the tool refuses a key inside the repository), checks the key's id before signing and the signature afterwards against the full list of trusted keys, which the build checked is the one in the image (a wrong secret fails the release), and publishes the files as a GitHub pre-release with `SHA256SUMS`: release-please's release is turned back into a draft before the build, the files go into the draft, and it is published only when all of them are attached (since v0.9.0 the phone app's release-signed APK and its checksum too: [The Android app's key](#the-android-apps-key)). The modem and the pod are not updated over the air and have no `.release.json`; their files are covered by `SHA256SUMS` alone. A dry run (the workflow started by hand) signs with a throw-away key and publishes nothing.

v0.6.1 (2026-11-02) was the first release made this way, through release-please with the signed firmware attached. v0.6.0 was tagged before it, but its firmware build failed (the I/O pod's boot-splash check, fixed by #26): its empty draft was deleted and only the tag remains.

This is a deliberate exception to "never on a CI runner" in the paragraph above, chosen by the maintainer (2026-10-28) so that releases can be signed without the root key leaving its offline media. Whoever can push a tag, change the workflow or read the repository's secrets can sign firmware that every box trusts; pull requests from forks never see the secrets.

**What guards the CI key (security review SC-1, SC-2).** The `Sign and publish` job of `release.yml` is bound to the GitHub environment `release` (`environment: release`), and it fails unless the tag's commit is an ancestor of `origin/main` (the `version` job checks the same, earlier). The workflow file runs from the tag, so a tag on a commit with an edited workflow could drop that check: the check is defence in depth, and the controls that matter are the environment's required reviewers (none for now: see "Current configuration" below) and the tag ruleset below, which only the maintainer can set (nothing in the repository can). A dry run (a branch) also waits for the environment's approval, when it has required reviewers. Third-party actions are pinned by commit SHA and the ESP-IDF image by digest, `cryptography` in the signing job by hash (`tools/release-requirements.txt`), and `.github/dependabot.yml` proposes updates weekly.

### Repository settings the release needs (the maintainer does these; no workflow can)

**Current configuration (2026-11-02).** The `release` environment exists and has **no required reviewers**, by the maintainer's choice while they are the only developer: the human gate is merging the release pull request, which only the maintainer does; the signing and the publishing then run by themselves. When other collaborators join, turn Required reviewers on (step 1). The steps below stay as the way to do it.

Until step 2 is done the workflow's `environment: release` is only a label: GitHub creates an unprotected `release` environment on first use, and **a repository-level secret still reaches the job, and so every run of any workflow that can name it**, whatever the environment says. Do them in this order:

1. **Settings > Environments > New environment** `release`. Turn on **Required reviewers** (the maintainer; a second person if there is one; leave "Prevent self-review" off while the maintainer is the only reviewer, or the release cannot be approved). Under **Deployment branches and tags** choose *Selected branches and tags* and add the tag pattern `v*` and the branch `main` (the branch is for dry runs).
2. **Keep the signing secrets in the environment only.** A secret cannot be read back, so the CI key's repository secrets are not moved: the [rotation](#rotating-the-ci-key-2026-11) puts the next CI key in the environment (`ATALAIA_RELEASE_CI_KEY_NEXT`, `ATALAIA_RELEASE_CI_KEY_NEXT_PASSPHRASE`) and, at its step 2, deletes `ATALAIA_RELEASE_CI_KEY` and `ATALAIA_RELEASE_CI_KEY_PASSPHRASE` from **Settings > Secrets and variables > Actions** (repository secrets). Run a dry run and a test tag afterwards: with required reviewers the job must show "Waiting for review", and the key-id and signature checks must pass.
3. **Settings > Rules > Rulesets > New tag ruleset** for the pattern `v*`: restrict creations, updates and deletions to the maintainer (bypass list: the repository admin role only), and block force pushes. A release tag then cannot be made, moved or deleted by anyone else, and a tag on an unreviewed branch is refused before any workflow starts. release-please (`release-please.yml`) creates the tag with the workflow token when its release pull request is merged: the ruleset's bypass list must include the GitHub Actions app for that, or the release-please job fails at the tag and the maintainer tags by hand (`git tag -a vX.Y.Z <merge commit>`, `git push origin vX.Y.Z`: `release.yml` then makes the release itself; release-please finds the tag on its next run). The bypass lets any workflow with `contents: write` make a `v*` tag, which is what the ruleset is there to stop; the environment's required reviewers, when it has them, still guard the signing either way. Choose one and say so in the maintainers' records.
4. **Reconsider Settings > Actions > General > "Allow GitHub Actions to create and approve pull requests"** (on since 2026-10-28; release-please needs it for its release pull request and `release-please.yml` for the "open the next dev version" one). With it on, any workflow with `pull-requests: write` can open a pull request and, with the setting's second half, approve one: together with a branch ruleset that counts the bot as a reviewer, a workflow change could merge unreviewed code into `main`, and the release signs what is on `main`. Keep it only if the `main` ruleset requires a review from a code owner (a human, `CODEOWNERS`) and not from the Actions bot; otherwise turn it off: release-please then cannot open its pull request with the workflow token, and needs a GitHub App token or a fine-grained token (contents, pull requests and issues: read and write, this repository only) as a secret passed to the action's `token` input instead ("Releases" in CONTRIBUTING.md). Such a token's pull requests and tags also start workflows (CI on the release pull request, `release.yml` on the tag), which the workflow token's do not.
5. Optional, Settings > Actions > General: **Workflow permissions** to *Read repository contents and packages permissions* (every workflow already declares its own `permissions:`), and *Require approval for all outside collaborators*.

The pins in the workflows are refreshed by Dependabot pull requests; check each one (the commit SHA must be the release the comment names) before merging. To re-resolve a pin by hand: `git ls-remote --tags https://github.com/actions/checkout "v7*"` for an action, `docker buildx imagetools inspect espressif/idf:v5.3.2` for the image's index digest.

**If the CI key leaks, or may have:**

1. Delete the two secrets (of whichever CI key signs: `ATALAIA_RELEASE_SIGNING_KEY`) and push no more tags. Remove the CI key from every controller's `[firmware] release_keys` (their lists withdraw every release it signed; the site server's `ATALAIA_FIRMWARE_KEYS` too, if you use it) and say so in a security notice.
2. Make a new CI key (the ceremony below), store it as two secrets of the `release` environment, and put its id in `release.yml` (`CI_KEY_NEXT_ID`, and its secrets' names in the signing step) and its hex in `RELEASE_KEYS_HEX` with the other places the CI key is listed ([Rotating the CI key](#rotating-the-ci-key-2026-11)).
3. Sign a release **with the root key**, by hand on the offline machine (steps below), whose firmware carries the root key and the new CI key in `CONFIG_ATALAIA_OTA_RELEASE_KEYS` and no longer the old one. A box accepts it because it still trusts the root key, and from then on refuses what the old key signs. Boxes on older firmware keep trusting the leaked key until they run it: software alone cannot protect them, so anyone with the leaked key and a box's controller could push an image, within the update rules (no game running, a higher version, the field's own controller sending the command). Treat every box that has not updated as exposed, and flash it by USB if in doubt.
4. If the **root** key is lost, the boxes need a firmware flashed by USB with new keys. The production hardening, ESP-IDF secure boot with flash encryption and the eFuse secure version (decision FU3-8), is not in use yet; [RELEASE_HARDENING.md](RELEASE_HARDENING.md) is the plan, and what it would add to this page (a second, RSA key for the hardware signature, and its compromise steps).

## The key ceremony (once per key)

1. On a machine you trust, ideally offline (a laptop with Wi-Fi off, a live USB system), make the key with a passphrase:

   ```sh
   python3 tools/firmware_release.py keygen --out ~/atalaia-release-keys/release-2026.pem
   ```

   The tool refuses a path inside the repository and never overwrites a key. It prints the key's id and its public halves: hex for the firmware, base64 for the controllers and the site server.
2. Back the `.pem` up to two offline places (encrypted USB sticks kept apart); write the passphrase down separately. Note the key id and the date in the maintainers' records.
3. Publish the public halves, which are not secret:
   - firmware: `CONFIG_ATALAIA_OTA_RELEASE_KEYS` in `sdkconfig.defaults` (a commit, reviewed like any other: it decides what every box will accept);
   - controllers: `[firmware] release_keys` in `controller.toml`;
   - site server: `ATALAIA_FIRMWARE_KEYS`.

Boxes already in the field learn a new key only from a firmware release that carries it, signed by a key they already trust.

## Signing a release

1. Build the release from a clean checkout of the tagged commit: `python3 tools/docker_fw.py build`, or `--fw-version=` for a release candidate. The release commit empties `ATALAIA_VERSION_PRERELEASE` in `core/include/atalaia/version.h` (`0.3.0-dev` becomes `0.3.0`) and is tagged `v0.3.0` (only with the maintainer's go-ahead); built there, clean, the image says exactly `0.3.0` (`docker_fw.py version` prints what a build would carry). Anywhere else a build carries its commit (`0.3.0-dev.412+g8560d54`, `0.3.0+3.gabcdef0` after the tag, `.dirty` with changes; decisions FV-1 to FV-4): sign those only with a bench key. The commit after the release sets the next version with `dev` again (`0.3.1`/`0.4.0`, `"dev"`), so that its builds sort above the release. Normally none of this is typed: release-please (`.github/workflows/release-please.yml`) keeps the release pull request open, with version.h's pre-release emptied by `tools/prepare_release.py release-pr`; merging it tags and starts `release.yml`, and a second pull request opens the next `dev` version ("Releases" in `CONTRIBUTING.md`).
2. Copy `firmware/esp32/build/atalaia_esp32.bin` to the signing machine and sign it:

   ```sh
   python3 tools/firmware_release.py sign atalaia_esp32.bin --key ~/atalaia-release-keys/release-2026.pem
   ```

   It refuses an image whose own descriptors are missing or say another version, and writes `atalaia_esp32.bin.release.json` (platform, version, size, SHA-256, signature, key id, variant, board).
3. Check it as a box would: `python3 tools/firmware_release.py verify atalaia_esp32.bin atalaia_esp32.bin.release.json --keys <public key>`.
4. Publish both files together. A GM uploads them in the console's *Boxes* tab; a server administrator may add the release to the site server's catalogue with the same fields.

## Rotating or withdrawing a key

- **Rotation:** make a new key (ceremony above); ship a release with both public keys in `CONFIG_ATALAIA_OTA_RELEASE_KEYS` (up to 4), signed with the old key; once the boxes run it, sign later releases with the new key and drop the old one in a later release. Add the new key to the controllers and the site server before the first release it signs. The CI key's rotation of November 2026 is below, step by step.
- **A key that leaked:** remove it from every controller and the site server at once (their lists withdraw every release it signed), and ship a release, signed with another trusted key, that no longer carries it. Until a box runs that release it still trusts the leaked key: a box with an older firmware cannot be protected by software alone. The production option is ESP-IDF secure boot with flash encryption and the eFuse secure version (decision FU3-8).

### Rotating the CI key (2026-11)

The CI key `32b3c815ac30ad43` lives only in repository secrets, which every workflow run could name and which cannot be read back to move them into the protected `release` environment. The maintainer chose (2026-11-03) to replace it over the air with the next CI key `a4f6002b0122b131`, whose private half lives only in the `release` environment. Boxes in the field learn a key only from a release signed by a key they already trust, hence three steps:

1. **Transition release (done: v0.7.0, 2026-11-03).** Every place that lists the project's release keys lists the next CI key third, after root and CI: `CONFIG_ATALAIA_OTA_RELEASE_KEYS` (Kconfig default), `tools/docker_fw.py` (`PROJECT_RELEASE_KEYS_HEX`), `release.yml` (`RELEASE_KEYS_HEX`, `CI_KEY_NEXT_ID`), the Pi's `PROJECT_RELEASE_KEYS` and `controller.example.toml`, the phone's `projectReleaseKeys`, and the docs. The next release is still signed with the **old** CI key (the variable `ATALAIA_RELEASE_SIGNING_KEY` unset), so boxes on v0.6.1 accept it over the air, and its firmware trusts all three keys. The maintainer adds the secrets `ATALAIA_RELEASE_CI_KEY_NEXT` and `ATALAIA_RELEASE_CI_KEY_NEXT_PASSPHRASE` to the `release` environment; they change nothing until the switch below says `next`. Their names differ from the old ones on purpose: an environment secret overrides a repository secret of the same name, so an environment `ATALAIA_RELEASE_CI_KEY` would silently replace the old key. Keep the names apart.
2. **Sign with the next key (after the transition release has shipped and the boxes run it; the variable was set to `next` on 2026-11-04, the old secrets are deleted once the first release it signs is checked).** Before anything is signed with the next key, every controller must trust it: a Pi that uses the default, and a phone that kept the earlier default (the app replaces exactly the old two-key default with the new list when it reads its settings), already does; a `controller.toml` that lists `release_keys` (the example did, so most do) needs `76eY5BoMQ4RHohhX/8iSUlIUA5o5Entfk7EFBUxpbSY=` added, and so does a site server's `ATALAIA_FIRMWARE_KEYS`. Then the maintainer:
   1. sets the variable **`ATALAIA_RELEASE_SIGNING_KEY` = `next`** (Settings > Environments > `release` > Environment variables; a repository variable of the same name works too, and the environment's wins);
   2. makes the next release as usual: the signing step takes the `_NEXT` secrets, checks the key's id is `a4f6002b0122b131` before signing and that the signature verifies against the trusted keys (three; two once step 3 is in, as for the first release it signs) as that key's (`signed by key a4f6002b0122b131` in the log); a dry run says which key a tag would use;
   3. once that release is published and checked (`firmware_release.py verify ... --keys <the three keys>` names `a4f6002b0122b131`), **deletes the repository secrets `ATALAIA_RELEASE_CI_KEY` and `ATALAIA_RELEASE_CI_KEY_PASSPHRASE`** (Settings > Secrets and variables > Actions), and notes the date in the maintainers' records.

   No code change is needed for step 2. If the variable says `next` and the `_NEXT` secret is missing, the release fails ("the secret ATALAIA_RELEASE_CI_KEY_NEXT is not set"); it never falls back to the old key. Any value other than unset, `current` or `next` fails the release too. To go back before the old secrets are deleted, delete the variable (or set it to `current`). Since step 3 the workflow no longer knows `current`: going back means reverting step 3's commit.
3. **Drop the old key (done in the change of 2026-11-04, for the first release after v0.7.0).** That commit removed `ac83bca20314dcb44b2ed9ede91cacf9445d2987e636fe66c6fb91250b17f53c` / `32b3c815ac30ad43` from every place listed in step 1, so the defaults are root and next CI, and added the three-key default to the phone's `earlierProjectReleaseKeys`: a phone that stored exactly that default takes the two-key one when it reads its settings, and an edited list is kept. The Pi stores no default (a `controller.toml` without `release_keys` takes the new one at its next start); a `controller.toml` or a site server's `ATALAIA_FIRMWARE_KEYS` that lists the old key by hand keeps it until its operator drops it, which the manuals and the CHANGELOG ask for. `release.yml` lost its `current` branch, `CI_KEY_ID` and the old secrets' names: it always signs with the `_NEXT` secrets and checks the key id `a4f6002b0122b131`; the variable `ATALAIA_RELEASE_SIGNING_KEY` unset or `next` both mean that key, any other value fails the release, and the signature is still verified against the full trusted list (now root and next CI). The `_NEXT` names stay for the rotation after this one. The first release that carries this commit is signed with the next key, which boxes on v0.7.0 trust; from then on the boxes that run it refuse what the old key signs. Releases the old key signed stay installable only by a box that still trusts it (firmware up to v0.7.0).

Room: a box carries at most 4 release keys (`FW_KEYS_MAX`). Since step 3 the project uses 2, so a bench build that adds the bench release key (below) uses 3, and one more key fits (for the next rotation's transition release, or a throw-away test key).

## The Android app's key

The phone app's APK attached to each release from v0.9.0 is signed with a separate key, an Android signing key (decisions APK-1 to APK-8). It is not an Ed25519 key and no box or controller trusts it; Android does: a phone installs an update over the app only when it is signed with the same key, and uninstalling (the only way round a different key) deletes the app's data, a phone controller's games, codes and join key included.

| What | Where |
| --- | --- |
| The keystore | PKCS12, alias `atalaia`, RSA 4096, valid 10000 days. Base64 in the `release` environment's secret `ATALAIA_ANDROID_KEYSTORE_B64` only, never a repository secret |
| Its password | the secret `ATALAIA_ANDROID_KEYSTORE_PASSWORD` of the same environment; the key's password is the same |
| Its certificate's SHA-256 | `9C:35:0D:17:37:D6:C5:35:CD:3E:D1:04:28:8E:65:AD:7D:B4:FA:CE:8E:4E:6F:27:75:3B:7B:7C:38:40:A1:99`, in `release.yml` (`ANDROID_CERT_SHA256`) and [docs/community/keys.md](../../../docs/community/keys.md#the-android-app) |
| The offline backup | **the maintainer's job**: the `.p12` file and its password on two offline media kept apart (as the root release key), noted in the maintainers' records. A secret cannot be read back from GitHub: the backup is the only copy outside the environment |

**What CI does.** The job **Android app (release-signed APK)** of `release.yml` runs in the environment `release`, in two steps that never share the key (decisions APS-1 to APS-6). **The build** has no secret: it runs `app/tool/check.sh apk-release` in the pinned Flutter image, which refuses any `ATALAIA_RELEASE_*` variable and builds an **unsigned** APK (`flutter build apk --release` with `-Patalaia.release.unsigned=true`, versionName the release's version and versionCode `X*1000000 + Y*1000 + Z`: 0.9.0 is 9000, always higher for a later release), with the debug APK's checks (the core for every ABI, the console assets, no Google Play services). This build downloads Gradle plugins, Maven artifacts and pub packages: pub is held to `pubspec.lock`'s hashes (`--enforce-lockfile`) and Gradle to the SHA-256 of every plugin and artifact in [`app/android/gradle/verification-metadata.xml`](../../../app/android/gradle/verification-metadata.xml) (dependency verification: a file with another checksum, or one not listed, stops the build). **The signing** comes after: on a tag it checks the tag is on `main`, decodes the keystore into a private folder under `RUNNER_TEMP` (umask 077), and runs [`app/tool/sign_apk.sh`](../../../app/tool/sign_apk.sh) in the same image with `docker run --network none` (the script also refuses to run where it sees any network interface but the loopback): `zipalign` (4 bytes, native libraries on 16 KB pages) if the APK is not aligned already, `apksigner sign`, then `apksigner verify --print-certs` must pass with exactly one signer whose certificate SHA-256 is `ANDROID_CERT_SHA256`, and the signed APK must still be aligned, or the release fails. The keystore is shredded when the step ends, however it ends, and a last step (`if: always()`) shreds anything left. The secrets reach only the signing step and only on a tag; they go into the container by name (`docker run -e NAME`), never as a value on a command line, and GitHub masks them in the log. The `Sign and publish` job then attaches `atalaia-app-<version>.apk` and `atalaia-app-<version>.apk.sha256`, both also in `SHA256SUMS`. A dry run signs with a throw-away keystore made on the runner (also with no network) and checks against its own fingerprint. Pull requests and CI build debug APKs (`check.sh apk`) and never see the secrets; a release build without a keystore still stops (APP-2) unless `-Patalaia.release.debugSigned=true` asks for the debug key or `-Patalaia.release.unsigned=true` for an unsigned APK. **After changing a Gradle plugin, an Android dependency, a pub package with Android code, or the Flutter SDK**, write the verification file again with `python tools/docker_app.py gradle-verification` and commit it (it also lists the macOS and Windows builds of `aapt2`, for native builds; see app/README.md).

**If the key is lost** (no secret and no backup): the next release must be signed with a new key, and every phone has to uninstall the app once more, losing its data, as at the v0.9.0 migration. Make the new key as in app/README.md, "Signing a release", put it in the two secrets, change `ANDROID_CERT_SHA256`, keys.md and every site server's `ATALAIA_APP_ANDROID_SHA256`, and say so in the release notes and the manuals.

**If it leaks, or may have:** delete the two secrets and push no tags until a new key is in place (as above: phones must uninstall once more). Say so in a security notice: an APK signed with the leaked key could be installed over the app and read its data. Android's key rotation (APK Signature Scheme v3 lineage) would avoid the uninstall but needs the old key; it is not set up (APK-8).

## Bench keys

For a test on the desk (`BRING_UP.md`, "Firmware update over the air") make a throw-away key with `keygen --unencrypted` outside the repository, build bench images with `--release-keys=<its hex>`, and delete it afterwards. Since 2026-11-02 the maintainer's bench also keeps one long-lived **bench release key** (key id `24a03cb8dc937d01`, its private half in a mode-600 file outside the repository): bench builds carry it beside the project's two keys (three in all, one under the most a box takes; four during the [CI key rotation](#rotating-the-ci-key-2026-11)'s transition), and the bench controller trusts them all and accepts the `box` and `box-bench` variants, so the bench's daily builds go over the air. A bench key must never sign anything meant for a Field Box; bench images (`box-bench`) do not install on Field Boxes anyway.
