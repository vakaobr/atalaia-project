# Plan: a hardened release image (flash encryption, NVS encryption, secure boot v2, anti-rollback)

**Status (2026-11-07): the hardened image is built and prepared; nothing is burned, and nothing will be until the maintainer decides otherwise.** The maintainer answered question 1 of section 5 on 2026-11-07: **not now**. No board, bench or field, gets the hardened image or any eFuse burn, so steps 3 to 5 of section 4 are on hold, and the steps that need no hardware go ahead. Step 2 (2026-11-06): `firmware/esp32/sdkconfig.release`, `tools/docker_fw.py release-hardened` and `tools/secure_boot_sign.py` build the hardened Field Box image and sign it for secure boot v2 with a throw-away key or a given one, and CI's `esp32-hardened-build` job builds it on every firmware change. The preparation of 2026-11-07 (section 7): the burn procedure as a script that only prints its plan unless it is given the port and the board's MAC (`tools/hardened_burn.py`), the digest revocation a leaked secure boot CI key needs (`main/sb_revoke.c`, compiled into the hardened build only, and `tools/firmware_release.py revoke-sb-digest`), and an emulator test (`tools/hardened_qemu.py`, section 8) that runs the burn and checks secure boot in Espressif's QEMU; the emulator cannot finish the first boot's flash encryption, so the app, the NVS encryption and the secure download mode stay for the hardware. No board has been flashed with the image, no serial port has been opened and no eFuse of a chip has been touched. The plan answers review finding FLD-2 and carries FLD-3 (the eFuse anti-rollback floor that decision FU3-8 left as a production option). Burning an eFuse cannot be undone, and a wrong step can leave a box that never boots again, so **every step that burns one is the maintainer's call** (decision SR-42 asks for it). The repository's `sdkconfig.defaults` stays as it is until then.

## 1. Where we are

The images the project builds and releases (Field Box, modem, I/O pod) have **none** of the four protections, and a box flashed from a release has all its eFuses unburnt:

| Protection | Today | Consequence |
| --- | --- | --- |
| NVS encryption | off (the box logs `NVS encryption is off` at boot) | the field join key, the game key, the admin PIN and the field Wi-Fi password sit in plain flash |
| Flash encryption | off | `esptool read_flash` returns the whole chip |
| Secure boot v2 | off | any image can be flashed over USB; a modified image can print the key |
| Anti-rollback | off | only the box's own version check (`fw_update.c`) stops an older image, and a USB flash skips it |

What is already in place: Ed25519-signed OTA images checked by the app (RELEASE_SIGNING.md, `protocol/firmware-update.md`), the app-level version floor, `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` (a new image that fails its self-test is rolled back), the admin PIN with counted waits, and decision AD-12's list of what a production Field Box needs (`protocol/adoption.md` section 2). SECURITY.md says what a lost box exposes today.

Decision S1 (2026-10-21) kept Ed25519 for modes and update packages and left hardware secure boot as "a separate, one-time eFuse decision". This is where that decision is prepared. On the ESP32-S3, ESP-IDF's secure boot v2 signs with **RSA-3072 (RSA-PSS)**; it cannot use Ed25519, so the hardware signature is a second signature beside the Ed25519 one (check the ESP-IDF version in use when the work starts: v5.3.2 today).

## 2. The target configuration

One overlay, `firmware/esp32/sdkconfig.release` (written 2026-11-06, step 2), used only by `tools/docker_fw.py release-hardened` (and CI's `esp32-hardened-build` job; the release workflow later), on top of `sdkconfig.defaults`:

- **Flash encryption, release mode** (`CONFIG_SECURE_FLASH_ENC_ENABLED`, `CONFIG_SECURE_FLASH_ENCRYPTION_MODE_RELEASE`): app, bootloader and the `storage` partition are encrypted on the chip with an AES-XTS key held in an eFuse block that software cannot read.
- **NVS encryption** (`CONFIG_NVS_ENCRYPTION`). Two schemes exist; the plan prefers the **flash-encryption scheme** over the HMAC scheme the repository documents today (BRING_UP.md step 0, decision AD-12), because with flash encryption on its key is unique per chip and needs no second eFuse key; the HMAC scheme with one fleet-wide key means one dumped box gives the NVS key of all of them (BRING_UP.md says "all boxes in the same fleet should use the same key"). The `nvs_keys` partition (already in `partitions.csv`) gets the `encrypted` flag. Either way a *running* image can read the NVS, so this protects a box that is dumped, not one that is attacked with code running on it.
- **Secure boot v2** (`CONFIG_SECURE_BOOT`, `CONFIG_SECURE_SIGNED_APPS_RSA_SCHEME`): the ROM verifies the bootloader, the bootloader verifies the partition table and the app. Up to three public-key digests can be burned; use **two, like the project's other keys** (`docs/community/keys.md`): a root key kept offline by the maintainer and a CI key (a repository secret) that signs the GitHub releases, and keep the third slot empty for a replacement. A digest can be revoked later, which is the way out of a leaked CI key.
- **Anti-rollback** (`CONFIG_BOOTLOADER_APP_ANTI_ROLLBACK` with `CONFIG_BOOTLOADER_APP_SECURE_VERSION`): the image carries a security version, the bootloader refuses lower ones, and a confirmed new image burns it into the eFuse. The S3 has **16 steps** (one eFuse bit each) for the whole life of the chip: raise it only for a security fix that old firmware must not be allowed to come back from, never with every release. The app-level version check stays.
- **Debug and download paths**: `DIS_USB_JTAG` (the JTAG half of the S3's USB port goes; the serial half stays, because `@adopt` over USB needs it), `SOFT_DIS_JTAG`/`HARD_DIS_JTAG`, the ROM's secure download mode (`CONFIG_SECURE_ENABLE_SECURE_ROM_DL_MODE`: no flash read-out over the ROM downloader), and no UART download re-enable. A `CONFIG_SECURE_DISABLE_ROM_DL_MODE` variant removes USB flashing altogether and is **not** recommended: it leaves no way to recover a box.

**Checked against ESP-IDF v5.3.2 (the pinned image) in step 2.** The Kconfig names above are right, with these findings from the IDF tree and the build:

- `DIS_USB_JTAG`, `SOFT_DIS_JTAG` and `HARD_DIS_JTAG` are eFuses, not options: the bootloader burns all three (and `DIS_DOWNLOAD_MANUAL_ENCRYPT`, `DIS_DIRECT_BOOT`, the download caches) when it enables secure boot or flash encryption, unless `CONFIG_SECURE_BOOT_ALLOW_JTAG` is set (it is not). `DIS_USB_SERIAL_JTAG` is not burned, so the USB serial port stays. "No UART download re-enable" is the default too.
- ESP-IDF 5.3.2 treats the `nvs_keys` partition as encrypted whenever flash encryption is on (`esp_partition`'s `partition.c`), so `partitions.csv` needs no `encrypted` flag and **the partition table does not change**. The `storage` partition (LittleFS: logos, mode files, no keys) is **not** encrypted by this overlay: that would need the `encrypted` flag on its row and a check that LittleFS's writes suit flash encryption's 16-byte blocks; left for a later decision, since the keys are in NVS.
- Secure boot v2 does not sign the partition table: the ROM checks the bootloader, the bootloader checks the app (the build lists only those two to sign). With flash encryption on, the table is encrypted.
- Keeping a digest slot empty (question 4) needs `CONFIG_SECURE_BOOT_ALLOW_UNUSED_DIGEST_SLOTS`, which ESP-IDF puts under "potentially insecure options" (`CONFIG_SECURE_BOOT_INSECURE`; no other option of that menu is set), **and** secure boot enabled from the host with `espefuse.py` before the first boot: when the bootloader enables secure boot itself it revokes every unused slot, whatever the option says. The more conservative alternative is to burn a third, spare root key's digest now (kept offline) and set neither option; step 3 decides between the two.
- The ROM downloader in secure download mode does not run `espefuse.py`: once a box is burned, its eFuses (a digest revocation, a new key in the spare slot) change only from code running on it, signed by a trusted key.
- `CONFIG_SECURE_FLASH_ENCRYPTION_AES128` (XTS-AES-128, one key block) is set; a key burned before the first boot decides the size anyway. With 2 + 1 digest slots and the flash key, 2 of the chip's 6 key blocks stay free.
- The bootloader does not fit with its log on (below, section 3): the overlay sets `CONFIG_BOOTLOADER_LOG_LEVEL_NONE`.

`tools/secure_boot_sign.py check-config` fails a build in which any option of the overlay is missing or has another value, so a later IDF that renames one cannot drop it in silence.

## 3. What it means for each way of putting software on a box

### USB re-flashing

- **Today**: `esptool write_flash`, the release's `-usb.zip` or the browser flasher with the `-merged.bin` at offset 0 work on any box, any time.
- **After the burn**: a plaintext image no longer boots. The bootloader and the app must be signed (secure boot) and **encrypted for the chip's flash key**. Whether that can be done over USB depends on **who made the flash-encryption key**:
  - *Key generated on the chip at first boot* (ESP-IDF's default): nobody knows it. A box can only be updated over the air from then on, and an OTA that fails in a way the rollback cannot catch (for example a bootloader or partition-table change) is a dead box. This is the strongest option and has no recovery.
  - *Key generated on the maintainer's computer and burned with `espefuse`*: `espsecure.py encrypt_flash_data` can encrypt an image for the chip and `esptool` writes it, so USB re-flashing and recovery stay possible, for whoever holds the key. A stolen key does not by itself open a box (reading is disabled), but it lets its holder write images; with secure boot also on, those still have to be signed. The key is as sensitive as the root release key: offline, encrypted, backed up.
  - **Recommended: the host-generated, fleet-wide flash key kept offline**, because losing the ability to recover boxes is the larger risk for a small project with no support staff. The maintainer chose this (2026-11-06, question 2).
- **The partition table can then never change over the air** (it never could: `main/fw_layout.c`) and now a table change also needs a signed table and a USB visit. The bootloader grows with secure boot and flash encryption; **check that it still fits below the partition table at 0x8000** (on the ESP32-S3 the bootloader starts at 0x0, so the area is 32 KB, its signature sector included). **Measured in step 2:** with secure boot v2 and flash encryption the bootloader is 0xb000 (45,056 bytes) at the default log level and 0x9000 (36,864) at Warning or Error, too big; with its log off (`CONFIG_BOOTLOADER_LOG_LEVEL_NONE`) it is 0x6000 (24,576), **0x7000 (28,672 bytes, 87.5 %) signed** with one, two or three keys (the signature blocks share one 4 KB sector), leaving 4 KB. The plain bootloader is 21,728 bytes. So the table does not move; the cost is a silent second-stage bootloader on a hardened box (the ROM's messages and the app's log stay). If it did not fit, the table would move (`CONFIG_PARTITION_TABLE_OFFSET`), which is a new layout (`FW_LAYOUT_VERSION` raised) and a first USB flash of every box. Decide this with the first test board, before any fleet burn: it is the one thing that can force a layout change.
- Boxes flashed before the burn are plain: **every existing box needs one USB visit** (new bootloader, the burn), there is no retrofit over the air. Today that is a handful of bench boards; once boxes are in customers' hands it would be a recall, which is a reason to decide before the first customer.

### The bench

- The bench build (`sdkconfig.bench`: `CONFIG_ATALAIA_SERIAL_KEYS`, no setup portal, radio logging, `@hold`, the listen-before-talk commands) and the Wokwi build are **never** signed with a release key and are never burned. Keep dedicated bench boards that stay un-burned, labelled so. A bench image flashed to a burned box will not boot, and a release image on a bench board is just a release image.
- Flash encryption can be tried in its *development* mode first: reversible a few times, so a test board can be flashed with a test key repeatedly. The sequence in section 4 uses a sacrificial board for it.
- Wokwi runs the plain build: unaffected. `tools/docker_fw.py build` for the Wokwi and bench variants stays as it is.
- The bench scripts and BRING_UP.md type `@joinkey` and `@update` without a PIN, which still works on a bench build (decision SR-40); a release build wants the PIN as the last word.
- A burned box cannot be bench-tested with ad-hoc images. The bench checklist for a hardened box is: boots, `NVS encryption is on` in the log, an unsigned image refused, an OTA of a signed image accepted, the old image refused after the security version is raised.

### Over-the-air updates

- The OTA path keeps its **Ed25519 manifest check** (decision S1) and the version floor. With secure boot on, the image **also** carries the RSA signature block and the bootloader verifies it before it boots the new slot; flash encryption encrypts the image as the box writes it (the OTA code needs no change).
- **The release pipeline gets one more step, before the Ed25519 manifest** (the manifest hashes the exact bytes of the image): build, sign with the RSA secure-boot key (`espsecure.py sign_data --version 2`), then `tools/firmware_release.py sign`. The CI key's RSA half goes into the release workflow as a second secret next to `ATALAIA_RELEASE_CI_KEY`; the root RSA key stays offline with the maintainer (RELEASE_SIGNING.md grows a section with the same compromise steps: revoke the digest). **Step 2:** `tools/secure_boot_sign.py sign` is that step and RELEASE_SIGNING.md has the section ("Secure boot signature"); the workflow is deliberately left unchanged and no secret has been added: an untested signing step in the release path, even an opt-in one, buys nothing before a board is burned, and wiring it in is a change for after step 4.
- The signature block adds a sector (4 KB) to the image, after padding to a 64 KB boundary. **Measured in step 2 (v0.9.0 + this change):** the hardened app is 2,228,224 bytes unsigned and **2,232,320 signed (0x221000), 53.22 % of the 4 MB slot** (the plain image: 2,194,160 bytes, 52.31 %); `tools/check_fw_ram.py` leaves **185,077 bytes** of internal RAM to the heap (plain: 185,805; the floor is 122,880). The build has no warnings.
- `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` stays; with anti-rollback on, a rolled-back image is one whose security version the eFuse still allows.
- A leaked CI RSA key: release signed with the root key, and revoke the CI key's digest on every box. `espefuse` over USB does not work on a burned box: its ROM downloader is in secure download mode (section 2), so the revocation comes from code on the box: **written 2026-11-07** (section 7.2), the hardened build's `main/sb_revoke.c`, which calls `esp_efuse_set_digest_revoke` when an instruction signed with the root release key (Ed25519) says so, built into the root-signed release or typed on the USB console. Until a box has done it, it is the same exposure RELEASE_SIGNING.md describes for the Ed25519 CI key, with a hardware floor under it.
- The modem and the I/O pod are USB-attached to a controller, not in the field's hands: their hardening is a separate, later decision (SR-42 asks only about the Field Box).

## 6. What does not change

## 7. Prepared without hardware (2026-11-07)

Question 1 is answered "not now", so nothing here has run against a board. Each piece is tested on the host or in the emulator (section 8).

### 7.1 The burn procedure: `tools/hardened_burn.py`

The sequence of steps 3 to 5, written as a script so that it is reviewed and tested before the day it is used. **By default it only prints the plan** (a dry run that opens no port): it checks the build (every option of `sdkconfig.release` through `secure_boot_sign.py check-config`, no bench option, the security version), that the bootloader is signed by both the root and the CI key and the app by one of them (`espsecure.py verify_signature` with the public keys), that the flash key is 32 bytes and every key file is outside the repository, then prints each `esptool`/`espefuse` command and the record line. **It does nothing to a device without both `--port` and `--i-understand-this-is-permanent=<the board's MAC>`**; with them it reads the chip's MAC and refuses unless it is the one typed, reads the eFuses and refuses unless the chip is blank (no secure boot, no flash encryption, no key in the blocks it uses, security version 0, no revocation, no secure download mode), and only then:

1. `esptool write_flash --no-stub`: one image from 0x0 to the end of `nvs_keys` (the signed bootloader, the partition table and otadata, with `nvs`, `phy_init` and `nvs_keys` blank, so no NVS of the board's plain life survives) and the signed app at 0x20000, plaintext. `ota_1` and `storage` are not rewritten (no key is ever there; a stale image fails secure boot); `--erase-first` adds `esptool erase_flash` before it, with the flasher stub (the ROM has no `erase_flash`).
2. `espefuse burn_key BLOCK_KEY0 <flash key> XTS_AES_128_KEY`: the host-made key (question 2), read- and write-protected by espefuse.
3. `espefuse burn_key BLOCK_KEY1 <root digest> SECURE_BOOT_DIGEST0 BLOCK_KEY2 <CI digest> SECURE_BOOT_DIGEST1`, and `BLOCK_KEY3 <spare digest> SECURE_BOOT_DIGEST2` with `--spare-pubkey` (the conservative choice of section 2). Without it the third slot stays empty (the maintainer's answer to question 4), which works because of the next two steps.
4. `espefuse burn_efuse SECURE_VERSION 0x1`: anti-rollback at security version 1 (question 5; the eFuse counts bits, so version *n* is *n* ones).
5. `espefuse burn_efuse SOFT_DIS_JTAG 7 SECURE_BOOT_EN 1`, last: **secure boot enabled from the host before the first boot**, so the bootloader skips its own enable and does not revoke the empty slot. That also skips the eFuses its secure boot enable would burn; all but the JTAG soft-disable are burned by its flash-encryption enable in release mode at the first boot (`DIS_DOWNLOAD_MANUAL_ENCRYPT`, `HARD_DIS_JTAG`, `DIS_USB_JTAG`, `DIS_DIRECT_BOOT`, the download caches, `WR_DIS_RD_DIS` and the secure download mode, `flash_encrypt.c` and `esp32s3/flash_encryption_secure_features.c` in ESP-IDF 5.3.2), so the script burns `SOFT_DIS_JTAG` itself.

NVS encryption takes no eFuse (question 3: the flash-encryption scheme; the app makes its keys in `nvs_keys` at its first start). Then the box is reset and must not lose power during its first boot, which encrypts the flash in place. The script appends one line per box to `--record` (default `~/atalaia-hardened-boxes.log`, refused inside the repository): the time, the MAC, the security version, the three digests (`empty` for an unused slot), the flash key's id (the first 16 hex digits of its SHA-256, never the key), the firmware version, the app's SHA-256 and `status=burned`, or `status=PARTIAL-<n>-burns` when a step failed after a burn, so a half-burned box is on record. `python3 tools/hardened_burn.py --selftest` (in `tools/check.sh` and CI's `esp32-hardened-build`) tests the planning, the argument checks and the guards with a fake device.

The emulator found one mistake in the first draft (section 8): it started with `esptool erase_flash` through the ROM loader, which has no such command.

### 7.2 Revoking a secure boot digest: `main/sb_revoke.c`

The way out of a leaked secure boot CI key (section 3), written ahead of the first burn because a box burned without it could only get it from an image signed with a key it still trusts.

- **Only in the hardened build.** `CONFIG_ATALAIA_SB_REVOKE` depends on `SECURE_BOOT_V2_ENABLED` (and not on a bench build's serial keys) and defaults to on there; `main/CMakeLists.txt` compiles `sb_revoke.c` and `sb_revoke_esp.c` only with it, and `secure_boot_sign.py check-config` fails a hardened build without it. Built before and after the change with the same `--fw-version`: the bench image is byte for byte the same; the plain image's 16 allocated ELF sections are identical, and its `.bin` differs only in the 32-byte ELF SHA-256 that `esp_app_desc_t` carries and the image's own 32-byte digest after it (the ELF's debug information moved); neither ELF has an `sb_revoke` symbol, the hardened one has them and `esp_efuse_set_digest_revoke`. The hardened app stays 2,232,320 bytes signed (the 64 KB padding), with 184,573 bytes of internal RAM left to the heap (504 fewer).
- **Triggered only by an instruction signed with the root release key** (Ed25519, the release signing's own code: `fw_signature_decode`, `fw_keys_parse` and Monocypher's `crypto_ed25519_check`). `CONFIG_ATALAIA_SB_REVOKE_KEYS` defaults to the root key `424d053af5cdbc35` alone: the CI release key, which a leak would concern, cannot revoke. The signed text is `atalaia-secure-boot-revoke-v1\nplatform=esp32s3\ndigest=<64 hex>\n`; the instruction is `<digest hex> <signature base64>`, made offline by `tools/firmware_release.py revoke-sb-digest` and checked by `verify-sb-revocation`. It names a digest, not a slot, so one instruction serves every box, and a replay changes nothing.
- **Two ways in:** built into a release (`CONFIG_ATALAIA_SB_REVOKE_BUILTIN`, carried out at boot once the image is confirmed, never while it is on trial after an update), or typed on the USB console with the admin PIN (`@sbrevoke <digest> <signature> <PIN>`, not during a game); `@sbdigests` lists the slots, their state and the keys the running image is signed with.
- **Refusals:** no secure boot; a digest no slot holds; a slot revoked already (reported, nothing burned); **the digest of a key the running image carries a signature block of** (the bootloader verified the image with one of them: revoking it would leave a box that never boots again), so the CI key is revoked from a root-signed release; **the last trusted digest**; eFuses or signature blocks that cannot be read. After the burn the revoke bit is read back.
- **Tests:** `firmware/esp32/test/test_sb_revoke.c` (in `python3 tools/docker_fw.py test`) runs the whole path with the eFuses faked and a burn counter: the form, a signature made by Python's `cryptography` with RFC 8032's public test key (also checked by `firmware_release.py --selftest`), every refusal with no burn, an eFuse that does not take the bit, and the built-in list.

What it does not do: write a new digest into the spare slot (a new CI key would need that, also from code on the box), or revoke the flash-encryption key (there is no such eFuse; a leaked flash key lets its holder write images that still have to pass secure boot).

## 8. The emulator test: `tools/hardened_qemu.py`

`python3 tools/docker_fw.py qemu-hardened` builds the hardened image and runs `tools/hardened_qemu.py` in the pinned ESP-IDF image, whose QEMU (`qemu-xtensa`, Espressif's `esp_develop_9.0.0_20240606`) has an `esp32s3` machine with the chip's real ROM, its eFuses in a file, the RSA and SHA peripherals and an XTS-AES flash encryption peripheral. Everything runs in a temporary folder deleted at the end: three throw-away RSA-3072 keys (root, CI, and one no eFuse knows), a throw-away flash key, a blank 16 MB flash file and the eFuse file. No serial port of the computer is opened; `esptool` and `espefuse` reach the emulated ROM over a TCP socket.

**What it checks, and passes** (10 of 10 checks on 2026-11-07, in 575 s, 416 of them the burn's flash write):

1. **The burn procedure, end to end.** `tools/hardened_burn.py` runs against the emulated chip exactly as it would against a board: the MAC and blank-chip checks, the flash write, the flash key, the root and CI digests with slot 2 empty, the security version and secure boot; it writes its record line, and a second run refuses the chip (`SECURE_BOOT_EN is True; SECURE_VERSION is 1; ...`).
2. **The ROM's secure boot.** With those eFuses, the bootloader signed by the root and the CI key passes (`Valid secure boot key blocks: 0 1`, `secure boot verification succeeded`: the empty spare slot is neither used nor revoked), while a bootloader signed by a key no eFuse knows and an unsigned one are refused (`secure boot verification failed`).
3. **The bootloader's secure boot.** With the right bootloader, an app signed by an unknown key and an unsigned app are refused: the flash stays as it was, because ESP-IDF's bootloader starts the first-boot encryption only for an image that passed its checks (`bootloader_utility.c`: `load_image` comes after `try_load_partition`). The CI-signed app is accepted and the encryption starts within seconds.

**What it cannot check: the rest of the first boot.** This QEMU's ESP32-S3 flash encryption does not behave like the chip, so the test stops where the emulator does, and says so:

- The bootloader encrypts the flash in place through the emulated XTS-AES peripheral, but the ciphertext matches what `espsecure.py encrypt_flash_data --aes_xts` makes with the same key (the chip's algorithm, which USB re-flashing of a burned box relies on, section 3) only in the **first 16 bytes of every 64**.
- The bootloader then never reaches its reset (watched for 25 minutes: no second ROM banner) and `SPI_BOOT_CRYPT_CNT` stays unburned; after a power cycle the ROM finds an encrypted bootloader it cannot read (`Invalid image block, can't verify`), the state ESP-IDF's own comment in `load_image` describes for a power cut between the encryption and the eFuse burn.
- So the app never runs, and the encrypted flash (with the app decrypting to the signed image), the NVS keys in `nvs_keys`, an NVS without plain text, the secure download mode and the anti-rollback at run time cannot be observed. Those stay on the hardware checklist of step 3 (section 3, "The bench"), on hold.

`CONFIG_EFUSE_VIRTUAL` / `CONFIG_EFUSE_VIRTUAL_KEEP_IN_FLASH` were not used: they keep ESP-IDF's own view of the eFuses in RAM or flash, a different image, while the ROM (which checks the bootloader's signature and decrypts the flash) still reads the chip's eFuses; the emulator's eFuse file is the chip's eFuses, and the image under test is the real one.

Findings about this QEMU, written into the script: the ESP32-S3's eFuse device is `nvram.esp32c3.efuse` (ESP-IDF 5.3's `idf.py qemu` passes `nvram.esp32s3.efuse`, which QEMU ignores with a warning, so its eFuses are not kept); download mode is the strap value `0x00` (`0x02` does not answer); `-monitor none` must come after `-serial`; in download mode the ROM never answers a start whose first byte reached UART0 at the wrong moment, about one start in two (the cause, found on 2026-11-10: the ROM's joint download mode polls UART0, UART1, the USB-OTG and the USB-Serial-JTAG in turn, and on UART0's turn `uart_buff_switch` enables UART0's receive interrupt before it records UART0 as the port its interrupt handler reads; bytes that arrived during another port's turn make that interrupt fire in between, the handler reads the previous port and never clears UART0's, and QEMU takes the interrupt again before the next instruction, for ever), so the script sends the first SYNC itself while the emulator is stopped in UART0's turn (QEMU's monitor: `stop`, read the ROM's `buff_uart_no` and UART0's interrupt enable, `cont`), after which the ROM stays in UART0's download loop and every `esptool` and `espefuse` session answers: the first start answers, where before up to five or six were needed; a flasher stub session leaves the ROM unreachable, so everything goes through the ROM loader (`--no-stub`), which writes about 58 kbit/s here (the whole 16 MB would take 40 minutes, one reason the burn writes only the boot region and the app, section 7.1). It found one mistake in the burn procedure's first draft: `esptool erase_flash` through the ROM loader, which has no such command.

**In CI, when it matters.** A run takes about 10 minutes on top of the hardened build, almost all of it the emulated flash write, for a result that changes only with the burn procedure, the overlay, the layout or ESP-IDF; so it is a step of CI's `esp32-hardened-build` job that runs when one of those changes (the job's `hardened` path filter: `sdkconfig.defaults`, `sdkconfig.release`, `partitions.csv`, `main/sb_revoke*`, `tools/hardened_*.py`, `tools/secure_boot_sign.py`) and on `main`, and the burn procedure's self-test runs on every firmware change (decision HPR-11). A later QEMU whose S3 flash encryption matches the chip would let the test go on to the app, the NVS and the secure download mode; until then the checks are written to fail rather than pass on what they cannot see.
